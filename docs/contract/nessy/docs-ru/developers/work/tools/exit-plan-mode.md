# Инструмент выхода из режима плана (`exit_plan_mode`)

Этот документ описывает инструмент `exit_plan_mode` для Nessy CLI.

## Описание

Используйте `exit_plan_mode`, когда вы находитесь в режиме плана и закончили представлять ваш план реализации. Этот инструмент запрашивает у пользователя одобрение или отклонение плана и переходит от режима планирования к режиму реализации.

Инструмент специально разработан для задач, требующих планирования шагов реализации перед написанием кода. Он НЕ должен использоваться для задач исследования или сбора информации.

### Аргументы

`exit_plan_mode` принимает один аргумент:

- `plan` (string, обязательно): План реализации, который вы хотите представить пользователю для одобрения. Это должен быть краткий, отформатированный в markdown план, описывающий шаги реализации.

## Как использовать `exit_plan_mode` с Nessy CLI

Инструмент Exit Plan Mode является частью рабочего процесса планирования Nessy CLI. Когда вы находитесь в режиме плана (обычно после исследования кодовой базы и проектирования подхода к реализации), вы используете этот инструмент для:

1. Представления вашего плана реализации пользователю
2. Запроса одобрения для продолжения реализации
3. Перехода от режима плана к режиму реализации на основе ответа пользователя

Инструмент запросит у пользователя ваш план и предоставит опции для:

- **Proceed Once**: Одобрить план только для этой сессии
- **Proceed Always**: Одобрить план и включить авто-одобрение для будущих операций редактирования
- **Cancel**: Отклонить план и остаться в режиме планирования

Использование:

```
exit_plan_mode(plan="Ваш детальный план реализации здесь...")
```

## Когда использовать этот инструмент

Используйте `exit_plan_mode` когда:

1. **Задачи реализации**: Вы планируете шаги реализации для задачи кодирования
2. **Завершение плана**: Вы закончили исследование и проектирование вашего подхода к реализации
3. **Нужно одобрение пользователя**: Вам нужно подтверждение пользователя перед продолжением изменений кода
4. **Задачи написания кода**: Задача включает написание, модификацию или рефакторинг кода

### Примеры подходящего использования:

- «Помогите мне реализовать аутентификацию пользователей» → Использовать после планирования реализации системы аутентификации
- «Добавить новый API эндпоинт для управления пользователями» → Использовать после проектирования структуры эндпоинта
- «Рефакторинг слоя базы данных для использования TypeORM» → Использовать после планирования подхода к рефакторингу

## Когда НЕ использовать этот инструмент

НЕ используйте `exit_plan_mode` для:

1. **Задач исследования**: Задачи, сфокусированные на понимании или исследовании существующего кода
2. **Сбора информации**: Когда вы ищете, читаете или анализируете без реализации
3. **Задач документации**: При создании документации без изменений кода
4. **Задач анализа**: При предоставлении объяснений или рецензий без реализации

### Примеры неподходящего использования:

- «Найти и понять реализацию режима vim в кодовой базе» → Не использовать (задача исследования)
- «Объяснить, как работает система аутентификации» → Не использовать (задача анализа)
- «Найти все TODO комментарии в проекте» → Не использовать (сбор информации)

## Примеры `exit_plan_mode`

### Пример планирования реализации

```
exit_plan_mode(plan="## План реализации для пользовательской панели

### 1. Создать компоненты панели
- Создать `UserDashboard.tsx` с основным макетом панели
- Добавить `DashboardStats.tsx` для отображения статистики пользователя
- Реализовать `ActivityFeed.tsx` для последних активностей пользователя

### 2. Добавить интеграцию API
- Создать `dashboardApi.ts` для получения данных панели
- Добавить эндпоинты для статистики пользователя и данных активности
- Реализовать обработку ошибок и состояния загрузки

### 3. Обновить маршрутизацию
- Добавить маршрут панели в `App.tsx`
- Обновить компонент навигации ссылкой на панель
- Добавить защиту маршрута для аутентифицированных пользователей

### 4. Тестирование и документация
- Написать модульные тесты для компонентов панели
- Добавить интеграционные тесты для вызовов API
- Обновить документацию пользователя с функциями панели

Эта реализация займёт приблизительно 4-6 часов и потребует изменений в 8-10 файлах.")
```

### Пример плана рефакторинга

```
exit_plan_mode(plan="## План рефакторинга слоя базы данных

### Фаза 1: Настройка и конфигурация
- Установить и настроить зависимости TypeORM
- Создать конфигурацию подключения к базе данных
- Настроить определения сущностей для существующих моделей

### Фаза 2: Миграция
- Создать скрипты миграции для существующих данных
- Реализовать новый паттерн репозитория используя TypeORM
- Заменить raw SQL запросы query builder TypeORM

### Фаза 3: Тестирование и валидация
- Обновить все тесты базы данных для использования TypeORM
- Проверить целостность данных после миграции
- Тестирование производительности для обеспечения отсутствия регрессий

Этот рефакторинг модернизирует наш слой базы данных, сохраняя обратную совместимость.")
```

## Обработка ответа пользователя

После вызова `exit_plan_mode` пользователь может ответить несколькими способами:

- **Proceed Once**: План одобрен для немедленной реализации с настройками подтверждения по умолчанию
- **Proceed Always**: План одобрен и авто-одобрение включено для последующих операций редактирования
- **Cancel**: План отклонён, и система остаётся в режиме плана для дальнейшего планирования

Инструмент автоматически регулирует режим одобрения на основе выбора пользователя, упрощая процесс реализации согласно предпочтениям пользователя.

## Важные заметки

- **Только режим плана**: Этот инструмент должен использоваться только когда вы сейчас находитесь в режиме плана
- **Фокус на реализации**: Используйте только для задач, которые включают написание или модификацию кода
- **Краткие планы**: Держите планы сфокусированными и краткими — стремитесь к ясности вместо исчерпывающей детализации
- **Поддержка markdown**: Планы поддерживают форматирование markdown для лучшей читаемости
- **Единое использование**: Инструмент должен использоваться один раз за сессию планирования, когда готовы продолжить
- **Контроль пользователя**: Финальное решение продолжить всегда остаётся за пользователем

## Интеграция с рабочим процессом планирования

Инструмент Exit Plan Mode является частью большего рабочего процесса планирования:

1. **Вход в режим плана**: Пользователь запрашивает или система определяет, что планирование нужно
2. **Фаза исследования**: Анализировать кодовую базу, понимать требования, исследовать опции
3. **Проектирование плана**: Создать стратегию реализации на основе исследования
4. **Представление плана**: Использовать `exit_plan_mode` для представления плана пользователю
5. **Фаза реализации**: После одобрения продолжить с запланированной реализацией

Этот рабочий процесс обеспечивает вдумчивые подходы к реализации и даёт пользователям контроль над значительными изменениями кода.
