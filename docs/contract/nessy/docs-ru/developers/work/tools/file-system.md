# Инструменты файловой системы Nessy CLI

Nessy CLI предоставляет комплексный набор инструментов для взаимодействия с локальной файловой системой. Эти инструменты позволяют модели читать из, записывать в, перечислять, искать и модифицировать файлы и каталоги, всё под вашим контролем и обычно с подтверждением для чувствительных операций.

**Примечание:** Все инструменты файловой системы работают в пределах `rootDirectory` (обычно текущий рабочий каталог, из которого вы запустили CLI) для безопасности. Пути, которые вы предоставляете этим инструментам, обычно должны быть абсолютными или разрешаются относительно этого корневого каталога.

## 1. `list_directory` (ListFiles)

`list_directory` перечисляет имена файлов и подкаталогов непосредственно в указанном каталоге. Он может опционально игнорировать записи, соответствующие предоставленным glob-паттернам.

- **Имя инструмента:** `list_directory`
- **Отображаемое имя:** ListFiles
- **Файл:** `ls.ts`
- **Параметры:**
  - `path` (string, обязательно): Абсолютный путь к каталогу для перечисления.
  - `ignore` (array of strings, опционально): Список glob-паттернов для исключения из перечисления (например, `["*.log", ".git"]`).
  - `respect_git_ignore` (boolean, опционально): Уважать ли паттерны `.gitignore` при перечислении файлов. По умолчанию `true`.
- **Поведение:**
  - Возвращает список имён файлов и каталогов.
  - Указывает, является ли каждая запись каталогом.
  - Сортирует записи: сначала каталоги, затем по алфавиту.
- **Вывод (`llmContent`):** Строка вида: `Directory listing for /path/to/your/folder:\n[DIR] subfolder1\nfile1.txt\nfile2.png`
- **Подтверждение:** Нет.

## 2. `read_file` (ReadFile)

`read_file` читает и возвращает содержимое указанного файла. Этот инструмент обрабатывает текстовые файлы и медиафайлы (изображения, PDF, аудио, видео), модальность которых поддерживается текущей моделью. Для текстовых файлов он может читать определённые диапазоны строк. Медиафайлы, модальность которых не поддерживается текущей моделью, отклоняются с полезным сообщением об ошибке. Другие бинарные типы файлов обычно пропускаются.

- **Имя инструмента:** `read_file`
- **Отображаемое имя:** ReadFile
- **Файл:** `read-file.ts`
- **Параметры:**
  - `path` (string, обязательно): Абсолютный путь к файлу для чтения.
  - `offset` (number, опционально): Для текстовых файлов, номер строки (0-based), с которой начать чтение. Требуется установка `limit`.
  - `limit` (number, опционально): Для текстовых файлов, максимальное количество строк для чтения. Если опущено, читает максимум по умолчанию (например, 2000 строк) или весь файл, если это возможно.
- **Поведение:**
  - Для текстовых файлов: Возвращает содержимое. Если используются `offset` и `limit`, возвращает только этот срез строк. Указывает, было ли содержимое усечено из-за лимитов строк или длины строки.
  - Для медиафайлов (изображения, PDF, аудио, видео): Если текущая модель поддерживает модальность файла, возвращает содержимое файла как base64-кодированный объект `inlineData`. Если модель не поддерживает модальность, возвращает сообщение об ошибке с рекомендациями (например, предлагая навыки или внешние инструменты).
  - Для других бинарных файлов: Пытается определить и пропустить их, возвращая сообщение, что это общий бинарный файл.
- **Вывод (`llmContent`):**
  - Для текстовых файлов: Содержимое файла, возможно с префиксом сообщения об усечении (например, `[File content truncated: showing lines 1-100 of 500 total lines...]\nActual file content...`).
  - Для поддерживаемых медиафайлов: Объект, содержащий `inlineData` с `mimeType` и base64 `data` (например, `{ inlineData: { mimeType: 'image/png', data: 'base64encodedstring' } }`).
  - Для неподдерживаемых медиафайлов: Сообщение об ошибке, объясняющее, что текущая модель не поддерживает эту модальность, с предложениями альтернатив.
  - Для других бинарных файлов: Сообщение вида `Cannot display content of binary file: /path/to/data.bin`.
- **Подтверждение:** Нет.

### Чтение Jupyter notebook

Для Jupyter notebook (`.ipynb`), `read_file` парсит JSON notebook и возвращает структурированное, читаемое для модели представление notebook вместо сырого JSON. Отрендеренный вывод включает язык notebook, упорядоченные ячейки, ID ячеек, исходный код и суммированные выводы.

Ячейки notebook могут затем быть отредактированы с помощью `notebook_edit`. Модель должна использовать ID ячеек, показанные `read_file`, при нацеливании на ячейку.

`offset` и `limit` не поддерживаются для файлов `.ipynb`. Чтение notebook трактуется как структурированное чтение полного файла; если отрендеренный вывод notebook внутренне усечён, потому что он слишком большой, `notebook_edit` отклонит редактирование на уровне ячеек и попросит уменьшить выводы или разделить notebook перед редактированием.

## 3. `notebook_edit` (NotebookEdit)

`notebook_edit` безопасно редактирует файлы Jupyter notebook (`.ipynb`) на уровне ячеек. Используйте его вместо `edit` или `write_file` при изменении ячеек notebook.

- **Имя инструмента:** `notebook_edit`
- **Отображаемое имя:** NotebookEdit
- **Файл:** `notebook-edit.ts`
- **Параметры:**
  - `notebook_path` (string, обязательно): Абсолютный путь к файлу `.ipynb`.
  - `cell_id` (string, опционально): Целевой ID ячейки, показанный `read_file`. Обязательно для `replace` и `delete`. Для `insert` новая ячейка вставляется после этой ячейки; если опущено, новая ячейка вставляется в начало.
  - `new_source` (string, опционально): Новый исходный код ячейки для `replace` и `insert`. Не требуется для `delete`.
  - `cell_type` (`code` или `markdown`, опционально): Тип ячейки для вставляемых ячеек, или целевой тип при замене ячейки.
  - `edit_mode` (`replace`, `insert` или `delete`, опционально): Операция редактирования. По умолчанию `replace`.
- **Поведение:**
  - Требуется, чтобы notebook был сначала прочитан с помощью `read_file` в текущей сессии.
  - Нацеливается на ячейки, используя ID, отрендеренные `read_file`, включая реальные ID ячеек notebook и отображаемые резервные ID `cell-N`.
  - Отклоняет неоднозначные отображаемые ID ячеек вместо угадывания.
  - Для ячеек кода очищает устаревшие выводы и сбрасывает `execution_count` при изменении исходного кода.
  - Сохраняет форматирование JSON notebook, окончания строк, кодировку и BOM, где возможно.
  - Аннулирует состояние предыдущего чтения после структурных редактирований, когда отображаемые резервные ID могут сместиться, поэтому следующее редактирование notebook требует свежего `read_file`.
- **Вывод (`llmContent`):** Сообщение об успехе, описывающее отредактированную ячейку notebook и, для операций кроме delete, обновлённый исходный код.
- **Подтверждение:** Да. Показывает JSON diff notebook и запрашивает одобрение пользователя перед записью, если текущий режим разрешений или правила не авто-одобряют инструменты редактирования.

### Примеры `notebook_edit`

Заменить ячейку кода:

```
notebook_edit(
  notebook_path="/path/to/analysis.ipynb",
  cell_id="load-data",
  new_source="result = 41 + 1\nprint(result)"
)
```

Вставить ячейку markdown после существующей ячейки:

```
notebook_edit(
  notebook_path="/path/to/analysis.ipynb",
  edit_mode="insert",
  cell_id="summary",
  cell_type="markdown",
  new_source="## Findings\n\nThe cleaned data is ready for modeling."
)
```

Удалить ячейку:

```
notebook_edit(
  notebook_path="/path/to/analysis.ipynb",
  edit_mode="delete",
  cell_id="old-experiment"
)
```

## 4. `write_file` (WriteFile)

`write_file` записывает содержимое в указанный файл. Если файл существует, он будет перезаписан. Если файл не существует, он (и любые необходимые родительские каталоги) будет создан.

- **Имя инструмента:** `write_file`
- **Отображаемое имя:** WriteFile
- **Файл:** `write-file.ts`
- **Параметры:**
  - `file_path` (string, обязательно): Абсолютный путь к файлу для записи.
  - `content` (string, обязательно): Содержимое для записи в файл.
- **Поведение:**
  - Записывает предоставленное `content` в `file_path`.
  - Не записывает сырой JSON Jupyter notebook. Используйте `notebook_edit` для редактирования ячеек `.ipynb`.
  - Создаёт родительские каталоги, если они не существуют.
- **Вывод (`llmContent`):** Сообщение об успехе, например, `Successfully overwrote file: /path/to/your/file.txt` или `Successfully created and wrote to new file: /path/to/new/file.txt`.
- **Подтверждение:** Да. Показывает diff изменений и запрашивает одобрение пользователя перед записью.

## 5. `glob` (Glob)

`glob` находит файлы, соответствующие специфичным glob-паттернам (например, `src/**/*.ts`, `*.md`), возвращая абсолютные пути, отсортированные по времени модификации (новейшие первые).

- **Имя инструмента:** `glob`
- **Отображаемое имя:** Glob
- **Файл:** `glob.ts`
- **Параметры:**
  - `pattern` (string, обязательно): Glob-паттерн для сопоставления (например, `"*.py"`, `"src/**/*.js"`).
  - `path` (string, опционально): Каталог для поиска. Если не указан, используется текущий рабочий каталог.
- **Поведение:**
  - Ищет файлы, соответствующие glob-паттерну в указанном каталоге.
  - Возвращает список абсолютных путей, отсортированный с новейшими первыми.
  - Уважает паттерны .gitignore, .nessyignore и настроенные пользовательские файлы игнорирования Nessy по умолчанию.
  - Ограничивает результаты 100 файлами для предотвращения переполнения контекста.
- **Вывод (`llmContent`):** Сообщение вида: `Found 5 file(s) matching "*.ts" within /path/to/search/dir, sorted by modification time (newest first):\n---\n/path/to/file1.ts\n/path/to/subdir/file2.ts\n---\n[95 files truncated] ...`
- **Подтверждение:** Нет.

## 6. `grep_search` (Grep)

`grep_search` ищет регулярное выражение в содержимом файлов в указанном каталоге. Может фильтровать файлы по glob-паттерну. Возвращает строки, содержащие совпадения, вместе с путями файлов и номерами строк.

- **Имя инструмента:** `grep_search`
- **Отображаемое имя:** Grep
- **Файл:** `grep.ts` (с `ripGrep.ts` как резерв)
- **Параметры:**
  - `pattern` (string, обязательно): Регулярное выражение для поиска в содержимом файлов (например, `"function\\s+myFunction"`, `"log.*Error"`).
  - `path` (string, опционально): Файл или каталог для поиска. По умолчанию текущий рабочий каталог.
  - `glob` (string, опционально): Glob-паттерн для фильтрации файлов (например, `"*.js"`, `"src/**/*.{ts,tsx}"`).
  - `limit` (integer, опционально): Ограничить вывод первыми N совпадающими строками. Должно быть положительным целым числом. Опционально - показывает все совпадения, если не указано.
- **Поведение:**
  - Использует ripgrep для быстрого поиска, когда доступно; иначе возвращается к реализации на JavaScript.
  - Возвращает совпадающие строки с путями файлов и номерами строк.
  - Без учёта регистра по умолчанию.
  - Уважает паттерны .gitignore, .nessyignore и настроенные пользовательские файлы игнорирования Nessy.
  - Ограничивает вывод для предотвращения переполнения контекста.
- **Вывод (`llmContent`):** Форматированная строка совпадений, например:

  ```
  Found 3 matches for pattern "myFunction" in path "." (filter: "*.ts"):
  ---
  src/utils.ts:15:export function myFunction() {
  src/utils.ts:22:  myFunction.call();
  src/index.ts:5:import { myFunction } from './utils';
  ---

  [0 lines truncated] ...
  ```

### Примеры `grep_search`

Поиск паттерна с ограничением результатов по умолчанию:

```
grep_search(pattern="function\\s+myFunction", path="src")
```

Поиск паттерна с пользовательским ограничением результатов:

```
grep_search(pattern="function", path="src", limit=50)
```

Поиск паттерна с фильтрацией файлов и пользовательским ограничением результатов:

```
grep_search(pattern="function", glob="*.js", limit=10)
```

## 7. `edit` (Edit)

`edit` заменяет текст внутри файла. По умолчанию требует, чтобы `old_string` соответствовал одному уникальному местоположению; установите `replace_all` в `true`, когда намеренно хотите изменить каждое вхождение. Этот инструмент предназначен для точных, целевых изменений и требует значительного контекста вокруг `old_string`, чтобы гарантировать модификацию правильного местоположения.

- **Имя инструмента:** `edit`
- **Отображаемое имя:** Edit
- **Файл:** `edit.ts`
- **Параметры:**
  - `file_path` (string, обязательно): Абсолютный путь к файлу для модификации.
  - `old_string` (string, обязательно): Точный буквальный текст для замены.

    **КРИТИЧНО:** Эта строка должна уникально идентифицировать единственный экземпляр для изменения. Она должна включать достаточный контекст вокруг целевого текста, точно соответствуя пробелам и отступам. Если `old_string` пуст, инструмент пытается создать новый файл в `file_path` с содержимым `new_string`.

  - `new_string` (string, обязательно): Точный буквальный текст для замены `old_string`.
  - `replace_all` (boolean, опционально): Заменить все вхождения `old_string`. По умолчанию `false`.

- **Поведение:**
  - Не редактирует сырой JSON Jupyter notebook. Используйте `notebook_edit` для редактирования ячеек `.ipynb`.
  - Если `old_string` пуст и `file_path` не существует, создаёт новый файл с `new_string` в качестве содержимого.
  - Если `old_string` предоставлен, читает `file_path` и пытается найти ровно одно вхождение, если `replace_all` не true.
  - Если совпадение уникально (или `replace_all` true), заменяет текст на `new_string`.
  - **Улучшенная надёжность (Многоэтапная коррекция редактирования):** Для значительного повышения успешности редактирований, особенно когда предоставленная моделью `old_string` может быть не совсем точной, инструмент включает механизм многоэтапной коррекции редактирования.
    - Если начальная `old_string` не найдена или совпадает с несколькими местоположениями, инструмент может использовать модель Nessy для итеративного уточнения `old_string` (и потенциально `new_string`).
    - Этот процесс самокоррекции пытается идентифицировать уникальный сегмент, который модель намеревалась модифицировать, делая операцию `edit` более устойчивой даже с немного неточным начальным контекстом.
- **Условия отказа:** Несмотря на механизм коррекции, инструмент завершится неудачей, если:
  - `file_path` не абсолютный или находится за пределами корневого каталога.
  - `old_string` не пуст, но `file_path` не существует.
  - `old_string` пуст, но `file_path` уже существует.
  - `old_string` не найден в файле после попыток коррекции.
  - `old_string` найдена несколько раз, `replace_all` равен false, и механизм самокоррекции не может разрешить её до одного однозначного совпадения.
- **Вывод (`llmContent`):**
  - При успехе: `Successfully modified file: /path/to/file.txt (1 replacements).` или `Created new file: /path/to/new_file.txt with provided content.`
  - При неудаче: Сообщение об ошибке, объясняющее причину (например, `Failed to edit, 0 occurrences found...`, `Failed to edit because the text matches multiple locations...`).
- **Подтверждение:** Да. Показывает diff предлагаемых изменений и запрашивает одобрение пользователя перед записью в файл.

## Кодировка файлов и поведение, специфичное для платформы

### Обнаружение и сохранение кодировки

При чтении файлов Nessy CLI обнаруживает кодировку файла, используя многошаговую стратегию:

1. **UTF-8** — пробуется первой (большинство современных инструментов выводят UTF-8)
2. **chardet** — статистическое обнаружение для содержимого не-UTF-8
3. **Системная кодировка** — fallback на кодовую страницу ОС (Windows `chcp` / Unix `LANG`)

И `write_file`, и `edit` сохраняют оригинальную кодировку и BOM (byte order mark) существующих файлов. Если файл был прочитан как GBK с UTF-8 BOM, он будет записан обратно так же.

### Настройка кодировки по умолчанию для новых файлов

Настройка `defaultFileEncoding` управляет кодировкой для **вновь созданных** файлов (не редактирований существующих файлов):

| Значение      | Поведение                                                                         |
| ------------- | --------------------------------------------------------------------------------- |
| _(не задано)_ | UTF-8 без BOM, с автоматическими платформенно-специфичными настройками (см. ниже) |
| `utf-8`       | UTF-8 без BOM, без автоматических настроек                                        |
| `utf-8-bom`   | UTF-8 с BOM для всех новых файлов                                                 |

Установите в `.nessy/settings.json` или `~/.nessy/settings.json`:

```json
{
  "general": {
    "defaultFileEncoding": "utf-8-bom"
  }
}
```

### Windows: CRLF для batch файлов

На Windows файлы `.bat` и `.cmd` автоматически записываются с окончаниями строк CRLF (`\r\n`). Это требуется, потому что `cmd.exe` использует CRLF как разделитель строк — окончания только LF могут сломать многострочные `if`/`else`, метки `goto` и циклы `for`. Это применяется независимо от настроек кодировки и только на Windows.

### Windows: UTF-8 BOM для скриптов PowerShell

На Windows с **не-UTF-8 системной кодовой страницей** (например, GBK/cp936, Big5/cp950, Shift_JIS/cp932), вновь созданные файлы `.ps1` автоматически записываются с UTF-8 BOM. Это необходимо, потому что Windows PowerShell 5.1 (версия, встроенная в Windows 10/11) читает скрипты без BOM, используя системную ANSI кодовую страницу. Без BOM не-ASCII символы в скрипте будут интерпретированы неправильно.

Этот автоматический BOM применяется только когда:

- Платформа — Windows
- Системная кодовая страница не UTF-8 (не кодовая страница 65001)
- Файл — новый файл `.ps1` (существующие файлы сохраняют оригинальную кодировку)
- Пользователь **не** явно установил `defaultFileEncoding` в настройках

PowerShell 7+ (pwsh) по умолчанию использует UTF-8 и обрабатывает BOM прозрачно, поэтому BOM безвреден там.

Если вы явно установите `defaultFileEncoding` в `"utf-8"`, автоматический BOM отключается — это преднамеренный выход для репозиториев или инструментов, которые отвергают BOMы.

### Итог

| Тип файла      | Платформа                           | Автоматическое поведение     |
| -------------- | ----------------------------------- | ---------------------------- |
| `.bat`, `.cmd` | Windows                             | Окончания строк CRLF         |
| `.ps1`         | Windows (не-UTF-8 кодовая страница) | UTF-8 BOM для новых файлов   |
| Все остальные  | Все                                 | UTF-8 без BOM (по умолчанию) |

Эти инструменты файловой системы предоставляют основу для Nessy CLI, чтобы понимать и взаимодействовать с контекстом вашего локального проекта.
