# Инструмент Monitor (`monitor`)

В этом документе описан инструмент `monitor` в Nessy CLI.

## Описание

Используйте `monitor`, чтобы запустить длительно выполняемую команду оболочки, которая передаёт строки stdout и stderr агенту в виде уведомлений фоновой задачи. Инструмент предназначен для команд наблюдения, у которых со временем появляется важный новый вывод: чтения журналов, отслеживания сборки, периодической проверки endpoint состояния или наблюдения за изменениями файлов.

Монитор работает в фоне, поэтому агент может продолжать работу по мере поступления событий. Каждая непустая строка вывода становится событием уведомления с учётом ограничения частоты.

### Аргументы

`monitor` принимает следующие аргументы:

- `command` (строка, обязательный): команда оболочки, которую нужно запустить и отслеживать.
- `description` (строка, необязательный): краткое описание наблюдаемого процесса. Отображаемый текст обрезается до 80 символов.
- `max_events` (число, необязательный): остановиться после указанного количества событий уведомления. Значение должно быть положительным целым числом. По умолчанию — `1000`, максимум — `10000` (значения вне диапазона отклоняются, а не ограничиваются автоматически).
- `idle_timeout_ms` (число, необязательный): остановиться, если команда не выводит данные указанное количество миллисекунд. Значение должно быть положительным целым числом. По умолчанию — `300000` (5 минут), максимум — `600000` (10 минут); значения вне диапазона отклоняются.
- `directory` (строка, необязательный): абсолютный путь к каталогу, в котором следует выполнить команду. После канонизации символических ссылок путь должен находиться внутри одного из зарегистрированных каталогов рабочего пространства и не должен находиться в каталоге пользовательских навыков. Если аргумент не указан, Nessy CLI использует корень проекта.

## Использование `monitor` в Nessy CLI

Модель выбирает инструмент `monitor`, когда ей нужно наблюдать за процессом во времени, а не получить единственный результат команды. Успешный вызов возвращает идентификатор монитора, команду, лимит событий и тайм-аут бездействия.

Пример:

```
monitor(command="tail -f logs/app.log", description="поток журнала приложения")
```

Вывод монитора отображается в диалоге как уведомления задачи. Запущенные и завершённые мониторы также можно посмотреть с помощью `/tasks` или интерактивного диалога фоновых задач.

Чтобы остановить запущенный монитор, вызовите инструмент `task_stop` с идентификатором монитора:

```
task_stop(task_id="mon_abc123def4567890")
```

## Примеры `monitor`

Наблюдение за журналом приложения:

```
monitor(
  command="tail -f logs/app.log",
  description="поток журнала приложения",
  max_events=200
)
```

Наблюдение за сервером разработки или сборкой:

```
monitor(
  command="npm run build -- --watch",
  description="вывод наблюдаемой сборки",
  idle_timeout_ms=600000
)
```

Периодическая проверка локального endpoint состояния:

```
monitor(
  command="while true; do curl -s http://localhost:8080/health; sleep 5; done",
  description="проверка локального состояния",
  max_events=120
)
```

Запуск из указанного каталога рабочего пространства:

```
monitor(
  command="npm run dev",
  description="сервер разработки frontend",
  directory="/absolute/path/to/workspace/packages/web"
)
```

## Monitor и фоновые команды оболочки

Используйте `monitor`, когда агент должен реагировать на потоковый вывод, пока команда продолжает работать. Для одноразового результата или полного вывода команды используйте `run_shell_command`.

| Задача                                                           | Инструмент                               |
| :--------------------------------------------------------------- | :--------------------------------------- |
| Наблюдение за журналами, сборкой или периодическими обновлениями | `monitor`                                |
| Одноразовая команда с чтением полного вывода                     | `run_shell_command(is_background=false)` |
| Запуск daemon без значимого вывода                               | `run_shell_command(is_background=true)`  |

Не добавляйте `&` в команды монитора. Завершающий `&`, например в `tail -f log &`, удаляется, поскольку `monitor` самостоятельно управляет фоновым выполнением. `&` не в конце команды, например в `cmd1 & cmd2`, приводит к отклонению вызова; перестройте такую команду без фонового запуска.

## Важные замечания

- **Автоматическая остановка:** мониторы автоматически останавливаются при достижении `max_events`, по истечении `idle_timeout_ms` без вывода или после самостоятельного завершения команды. Статус монитора отражает результат команды, а не ошибку инструмента: успешное завершение (`code 0`) получает статус `completed`, ненулевой код — статус `failed` с сообщением `Exit code N`, а завершение сигналом — статус `failed` с сообщением `Killed by signal SIG`. Команды не могут быть интерактивными, потому что stdin закрыт. При остановке монитора Nessy CLI отправляет `SIGTERM` группе процессов команды и примерно через 200 мс переходит к `SIGKILL`. В Windows используется `taskkill /f /t`. Если сам процесс Nessy CLI принудительно остановлен, аварийно завершился или исчерпал память, отсоединённая группа процессов автоматически не очищается. Чтобы восстановить состояние, перед выходом остановите монитор через `task_stop` либо завершите группу процессов вручную.
- **Ограничение параллелизма:** в одной сессии CLI допускается не более 16 одновременно работающих мониторов в общем пуле. Мониторы, запущенные субагентами, учитываются в том же лимите, что и мониторы основного агента. Если лимит достигнут, остановите существующий монитор перед запуском нового.
- **Обработка вывода:** stdout и stderr объединяются в единый поток уведомлений без префикса потока. Пустые строки игнорируются, управляющие последовательности и цвета ANSI удаляются, а отдельные строки длиннее 2000 символов обрезаются. Для большого объёма вывода действует ограничение частоты: начальный пакет из 5 событий, затем примерно 1 событие в секунду. Строки сверх лимита отбрасываются, а не буферизуются. Вывод монитора поступает в контекст агента как содержимое `<task-notification>`. Структурные теги уведомлений обезвреживаются, однако модель всё равно читает текст каждой строки, поэтому не отслеживайте потоки, доступные для записи внешним сторонам, если не уверены, что модель проигнорирует встроенные инструкции.
- **Разрешения:** у `monitor` собственная граница разрешений и собственные правила, например `Monitor(git status)`. Команды только для чтения разрешаются автоматически; команды, изменяющие состояние, требуют подтверждения пользователя. Команды с подстановкой (`$(...)`, обратные кавычки, `<(...)` или `>(...)`) отклоняются. Настройки `tools.core` и `tools.exclude` для `run_shell_command` не применяются к `monitor`.
- **Ограничение рабочего пространства:** необязательный `directory` должен быть абсолютным путём, который разрешается внутри зарегистрированного каталога рабочего пространства и вне каталога пользовательских навыков. Символические ссылки за пределы рабочего пространства отклоняются.
