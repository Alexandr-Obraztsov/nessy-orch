# Инструмент оболочки (`run_shell_command`)

Этот документ описывает инструмент `run_shell_command` для Nessy CLI.

## Описание

Используйте `run_shell_command` для взаимодействия с системой, запуска скриптов или выполнения операций командной строки. `run_shell_command` выполняет данную команду оболочки, включая интерактивные команды, требующие ввода пользователя (например, `vim`, `git rebase -i`), если настройка `tools.shell.enableInteractiveShell` установлена в `true`.

В Windows команды выполняются с `cmd.exe /c`. На других платформах они выполняются с `bash -c`.

### Аргументы

`run_shell_command` принимает следующие аргументы:

- `command` (string, обязательно): Точная команда оболочки для выполнения.
- `description` (string, опционально): Краткое описание цели команды, которое будет показано пользователю.
- `directory` (string, опционально): Каталог (относительно корневого каталога проекта), в котором выполнить команду. Если не предоставлен, команда выполняется в корневом каталоге проекта.
- `is_background` (boolean, обязательно): Запускать ли команду в фоне. Этот параметр обязателен для обеспечения принятия осознанных решений о режиме выполнения команды. Установите в true для долгоживущих процессов, таких как серверы разработки, наблюдатели или демоны, которые должны продолжать работать без блокировки дальнейших команд. Установите в false для одноразовых команд, которые должны завершиться перед продолжением.

## Как использовать `run_shell_command` с Nessy CLI

При использовании `run_shell_command` команда выполняется как подпроцесс. Вы можете контролировать, выполняются ли команды в фоне или переднем плане, используя параметр `is_background`, или явно добавив `&` к командам. Инструмент возвращает детальную информацию о выполнении, включая:

### Обязательный параметр is_background

Параметр `is_background` **обязателен** для всех выполнений команд. Этот дизайн гарантирует, что LLM (и пользователи) должны явно решить, должна ли каждая команда выполняться в фоне или переднем плане, способствуя преднамеренному и предсказуемому поведению выполнения команд. Делая этот параметр обязательным, мы избегаем непреднамеренного возврата к выполнению в переднем плане, что могло бы заблокировать последующие операции при работе с долго-running процессами.

### Выполнение в фоне и переднем плане

Инструмент интеллектуально обрабатывает выполнение в фоне и переднем плане на основе вашего явного выбора:

**Используйте выполнение в фоне (`is_background: true`) для:**

- Долго-running серверов разработки: `npm run start`, `npm run dev`, `yarn dev`
- Наблюдателей сборки: `npm run watch`, `webpack --watch`
- Серверов баз данных: `mongod`, `mysql`, `redis-server`
- Веб-серверов: `python -m http.server`, `php -S localhost:8000`
- Любых команд, которые, как ожидается, будут выполняться бесконечно до ручной остановки

**Используйте выполнение в переднем плане (`is_background: false`) для:**

- Одноразовых команд: `ls`, `cat`, `grep`
- Команд сборки: `npm run build`, `make`
- Команд установки: `npm install`, `pip install`
- Git операций: `git commit`, `git push`
- Запусков тестов: `npm test`, `pytest`

### Информация о выполнении

Инструмент возвращает детальную информацию о выполнении, включая:

- `Command`: Команда, которая была выполнена.
- `Directory`: Каталог, в котором была выполнена команда.
- `Stdout`: Вывод из стандартного выходного потока.
- `Stderr`: Вывод из стандартного потока ошибок.
- `Error`: Любое сообщение об ошибке, сообщённое подпроцессом.
- `Exit Code`: Код выхода команды.
- `Signal`: Номер сигнала, если команда была завершена сигналом.
- `Background PIDs`: Список PID для любых запущенных фоновых процессов.

Использование:

```bash
run_shell_command(command="Your commands.", description="Your description of the command.", directory="Your execution directory.", is_background=false)
```

**Примечание:** Параметр `is_background` обязателен и должен быть явно указан для каждого выполнения команды.

## Примеры `run_shell_command`

Перечислить файлы в текущем каталоге:

```bash
run_shell_command(command="ls -la", is_background=false)
```

Запустить скрипт в специфичном каталоге:

```bash
run_shell_command(command="./my_script.sh", directory="scripts", description="Run my custom script", is_background=false)
```

Запустить фоновый сервер разработки (рекомендуемый подход):

```bash
run_shell_command(command="npm run dev", description="Start development server in background", is_background=true)
```

Запустить фоновый сервер (альтернатива с явным &):

```bash
run_shell_command(command="npm run dev &", description="Start development server in background", is_background=false)
```

Запустить команду сборки в переднем плане:

```bash
run_shell_command(command="npm run build", description="Build the project", is_background=false)
```

Запустить несколько фоновых сервисов:

```bash
run_shell_command(command="docker-compose up", description="Start all services", is_background=true)
```

## Конфигурация

Вы можете конфигурировать поведение инструмента `run_shell_command`, модифицируя ваш файл `settings.json` или используя команду `/settings` в Nessy CLI.

### Включение интерактивных команд

Настройка `tools.shell.enableInteractiveShell` контролирует, выполняются ли команды оболочки через `node-pty` (интерактивный PTY) или через plain `child_process` бэкенд. Когда включена, интерактивные сессии, такие как `vim`, `git rebase -i` и TUI программы, работают корректно.

Эта настройка по умолчанию `true` на большинстве платформ. На Windows сборках **\<= 19041** (до Windows 10 версии 2004), она по умолчанию `false`, потому что старые реализации ConPTY имеют известные проблемы с надёжностью (отсутствующий вывод, зависания). Это соответствует тому же cutoff, используемому VS Code ([microsoft/vscode#123725](https://github.com/microsoft/vscode/issues/123725)). Если `node-pty` недоступен во время выполнения, инструмент возвращается к `child_process` независимо от этой настройки.

Для явного переопределения по умолчанию установите значение в `settings.json`:

**Пример `settings.json`:**

```json
{
  "tools": {
    "shell": {
      "enableInteractiveShell": true
    }
  }
}
```

### Отображение цвета в выводе

Чтобы показать цвет в выводе оболочки, нужно установить настройку `tools.shell.showColor` в `true`. **Примечание: Эта настройка применяется только когда `tools.shell.enableInteractiveShell` включена.**

**Пример `settings.json`:**

```json
{
  "tools": {
    "shell": {
      "showColor": true
    }
  }
}
```

### Установка pager

Вы можете установить собственный pager для вывода оболочки, установив настройку `tools.shell.pager`. Pager по умолчанию — `cat`. **Примечание: Эта настройка применяется только когда `tools.shell.enableInteractiveShell` включена.**

**Пример `settings.json`:**

```json
{
  "tools": {
    "shell": {
      "pager": "less"
    }
  }
}
```

## Интерактивные команды

Инструмент `run_shell_command` теперь поддерживает интерактивные команды, интегрируя псевдо-терминал (pty). Это позволяет вам запускать команды, требующие ввода пользователя в реальном времени, такие как текстовые редакторы (`vim`, `nano`), терминальные UI (`htop`), и интерактивные операции контроля версий (`git rebase -i`).

Когда интерактивная команда запущена, вы можете отправлять ввод в неё из Nessy CLI. Чтобы сфокусироваться на интерактивной оболочке, нажмите `ctrl+f`. Вывод терминала, включая сложные TUI, будет отображён корректно.

## Важные замечания

- **Безопасность:** Будьте осторожны при выполнении команд, особенно тех, которые сконструированы из пользовательского ввода, чтобы предотвратить уязвимости безопасности.
- **Обработка ошибок:** Проверяйте поля `Stderr`, `Error`, и `Exit Code`, чтобы определить, успешно ли выполнилась команда.
- **Фоновые процессы:** Когда `is_background=true` или когда команда содержит `&`, инструмент вернётся немедленно, и процесс продолжит выполняться в фоне. Поле `Background PIDs` будет содержать ID фонового процесса.
- **Выбор фонового выполнения:** Параметр `is_background` обязателен и предоставляет явный контроль над режимом выполнения. Вы также можете добавить `&` к команде для ручного фонового выполнения, но параметр `is_background` всё равно должен быть указан. Параметр предоставляет более явное намерение и автоматически обрабатывает настройку фонового выполнения.
- **Описания команд:** При использовании `is_background=true`, описание команды будет включать индикатор `[background]`, чтобы явно показать режим выполнения.

## Переменные окружения

Когда `run_shell_command` выполняет команду, она устанавливает переменную окружения `NESSY_CLI=1` в окружении подпроцесса. Это позволяет скриптам или инструментам определить, запускаются ли они изнутри CLI.

## Ограничения команд

Вы можете ограничить команды, которые могут быть выполнены инструментом `run_shell_command`, используя настройки `tools.core` и `tools.exclude` в вашем конфигурационном файле.

- `tools.core`: Чтобы ограничить `run_shell_command` специфичным набором команд, добавьте записи в список `core` под категорией `tools` в формате `run_shell_command(<command>)`. Например, `"tools": {"core": ["run_shell_command(git)"]}` позволит только команды `git`. Включение общего `run_shell_command` действует как wildcard, разрешая любую команду, не заблокированную явно.
- `tools.exclude`: Чтобы заблокировать специфичные команды, добавьте записи в список `exclude` под категорией `tools` в формате `run_shell_command(<command>)`. Например, `"tools": {"exclude": ["run_shell_command(rm)"]}` заблокирует команды `rm`.

Логика валидации разработана быть безопасной и гибкой:

1.  **Сцепление команд отключено**: Инструмент автоматически разделяет команды, сцепленные с `&&`, `||`, или `;`, и валидирует каждую часть отдельно. Если любая часть цепочки запрещена, вся команда блокируется.
2.  **Сопоставление префиксов**: Инструмент использует сопоставление по префиксу. Например, если вы разрешили `git`, вы можете запустить `git status` или `git log`.
3.  **Приоритет блоклиста**: Список `tools.exclude` всегда проверяется первым. Если команда совпадает с заблокированным префиксом, она будет отклонена, даже если она также совпадает с разрешённым префиксом в `tools.core`.

### Примеры ограничения команд

**Разрешить только специфичные префиксы команд**

Чтобы разрешить только команды `git` и `npm`, и заблокировать все остальные:

```json
{
  "tools": {
    "core": ["run_shell_command(git)", "run_shell_command(npm)"]
  }
}
```

- `git status`: Разрешено
- `npm install`: Разрешено
- `ls -l`: Заблокировано

**Заблокировать специфичные префиксы команд**

Чтобы заблокировать `rm` и разрешить все остальные команды:

```json
{
  "tools": {
    "core": ["run_shell_command"],
    "exclude": ["run_shell_command(rm)"]
  }
}
```

- `rm -rf /`: Заблокировано
- `git status`: Разрешено
- `npm install`: Разрешено

**Блоклист имеет приоритет**

Если префикс команды находится и в `tools.core`, и в `tools.exclude`, он будет заблокирован.

```json
{
  "tools": {
    "core": ["run_shell_command(git)"],
    "exclude": ["run_shell_command(git push)"]
  }
}
```

- `git push origin main`: Заблокировано
- `git status`: Разрешено

**Заблокировать все команды оболочки**

Чтобы заблокировать все команды оболочки, добавьте wildcard `run_shell_command` в `tools.exclude`:

```json
{
  "tools": {
    "exclude": ["run_shell_command"]
  }
}
```

- `ls -l`: Заблокировано
- `any other command`: Заблокировано

## Примечание по безопасности для `excludeTools`

Ограничения специфичных команд в `excludeTools` для `run_shell_command` основаны на простом сопоставлении строк и могут быть легко обойдены. Эта функция **не является механизмом безопасности** и не должна использоваться для безопасного выполнения ненадёжного кода. Рекомендуется использовать `coreTools` для явного выбора команд, которые могут быть выполнены.
