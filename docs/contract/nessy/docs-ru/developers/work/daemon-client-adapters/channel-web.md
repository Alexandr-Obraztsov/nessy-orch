# Адаптер канала и веб-бэкенда для демона (черновик)

## Цель

Позволить адаптерам каналов и веб-чат-бэкендам использовать `nessy serve` через
`DaemonSessionClient`, сохраняя при этом существующее поведение подпроцесса ACP канала
по умолчанию.

Этот черновик охватывает только серверные клиенты:

- Бэкенд канала (бот) -> `nessy serve`
- Веб-браузер -> веб-бэкенд / BFF -> `nessy serve`

Это явно не позволяет браузерному JavaScript вызывать демона напрямую.
Демон в настоящее время отклоняет запросы с браузерным `Origin` по замыслу.

## Предлагаемые точки входа

Бэкенд канала:

```bash
NESSY_CHANNEL_DAEMON_URL=http://127.0.0.1:4170 nessy channel start telegram
```

Веб-бэкенд:

```bash
NESSY_WEB_DAEMON_URL=http://127.0.0.1:4170 nessy web-chat-backend
```

Общие необязательные переменные:

```bash
NESSY_DAEMON_TOKEN=...
NESSY_DAEMON_WORKSPACE=/repo
```

## Минимальный поток канала

Этот PR добавляет `DaemonChannelBridge` — локально верифицируемый серверный мост
для адаптеров каналов и веб-бэкендов. Он сохраняет существующий ACP-мост по умолчанию
и владеет состоянием сессии демона внутри процесса бэкенда.

1. Разрешить отправителя канала/поток в ключ сессии канала.
2. Использовать `DaemonClient` + `DaemonSessionClient.createOrAttach()`.
3. Отправить входящий пользовательский текст через `session.prompt()`.
4. Подписаться на `session.events()` и собрать чанки текста ассистента.
5. Отправить финальный текст обратно через адаптер платформы.
6. Преобразовать голоса разрешений через `session.respondToPermission()`.
7. Отменить активную работу через `session.cancel()`.

## Минимальный поток веб-бэкенда

1. Браузер открывает websocket или HTTP-поток для веб-бэкенда.
2. Бэкенд владеет `DaemonSessionClient`.
3. Бэкенд транслирует сообщения браузера в запросы демона.
4. Бэкенд транслирует SSE-события демона в безопасные для приложений события браузера.
5. Бэкенд хранит `sessionId` демона и ID последнего просмотренного события на сервере.

Браузерные клиенты не должны получать токены-носители демона.

## Ограничение изоляции сессии

Текущее поведение демона Stage 1 фактически является `sessionScope: single` на уровне
настроек демона. Пока не появится `sessionScope` на каждый запрос, многопользовательские
развертывания каналов или веб-приложений должны выбрать одну из этих безопасных форм:

- один демон на каждый поток канала / веб-комнату
- один демон на рабочее пространство пользователя
- только однопользовательская демонстрация

Не следует неявно мультиплексировать несвязанные потоки каналов в одну сессию демона.

## Контракт сопоставления событий

| Событие демона                           | Обработка бэкендом канала/веба                 |
| ---------------------------------------- | ---------------------------------------------- |
| `session_update` / `agent_message_chunk` | Добавить текст ассистента                      |
| `session_update` / `agent_thought_chunk` | Необязательный скрытый/отладочный поток        |
| `session_update` / `tool_call`           | Создать карточку/сообщение статуса инструмента |
| `permission_request`                     | Взаимодействие с утверждением платформы        |
| `permission_resolved`                    | Закрыть/обновить взаимодействие с утверждением |
| `model_switched`                         | Обновить метаданные сессии бэкенда             |
| `session_died`                           | Уведомить пользователя и остановить поток      |

Неизвестные события демона должны игнорироваться или пересылаться как отладочные метаданные, а не вызывать фатальную ошибку.

Мост еще не подключен к `nessy channel start`. Существующие Telegram, Weixin, Dingtalk, плагин канала и поведение браузера остаются без изменений.

## Явные не-цели

- Нет прямого fetch или EventSource браузера к демону.
- Нет ослабления CORS в этом PR адаптера.
- Нет миграции по умолчанию Telegram, Weixin, Dingtalk или каналов плагинов.
- Нет CRUD файлов, CRUD памяти, перезапуска MCP или мутации провайдера.
- Нет эмуляции sessionScope в клиенте, когда поддержка на стороне демона отсутствует.

## Безопасность слияния

- По умолчанию отключено.
- Существующий мост канала ACP остается по умолчанию.
- Веб-бэкенд — это явный слой BFF, а не изменение безопасности демона.
- Ни один адаптер канала не должен импортировать токены демона в код фронтенда/браузера.

## План валидации

- Модульное тестирование привязки ключа сессии канала к сессии демона.
- Модульное тестирование сопоставления событий демона с сообщениями канала/веба.
- Модульное тестирование пересылки запросов, отмены, переключения модели и ответа на разрешения.
- Smoke-тест одного однопользовательского бэкенда канала против локального `nessy serve`.
- Smoke-тест браузера -> BFF -> демона без раскрытия токена демона.

## Блокеры перед миграцией по умолчанию

- `sessionScope` на каждый запрос.
- Метаданные сессии + жизненный цикл закрытия/удаления.
- Идентичность клиента с отметкой демона.
- Маршрут разрешений с областью сессии.
- Диагностика только для чтения для MCP, навыков, провайдеров и окружения.
