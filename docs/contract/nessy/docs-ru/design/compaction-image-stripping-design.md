# Удаление изображений при компрессии + Исправление оценки токенов

## Постановка проблемы

Когда `ChatCompressionService` срабатывает (автоматически или вручную), он отправляет `historyToCompress` модели суммаризации дословно. Две связанные проблемы ухудшают качество, точность и стоимость:

1. **Inline image / document bytes утекают в prompt суммаризации.** MCP инструменты, которые показывают вложения (скриншоты, макеты дизайна, PDF), помещают части `inlineData` напрямую в разговор. Конвейер компрессии не удаляет их, поэтому модель суммаризации получает сырой base64, который обычно не может интерпретировать, и payload side-query неоправданно раздувается.

2. **Оценка токенов `findCompressSplitPoint` неверна для бинарных частей.** Алгоритм точки разделения использует `JSON.stringify(content).length` для распределения символов по истории. Один 1 MB base64 image (~1.4M символов) делает одну запись похожей на ~350K токенов, затмевая фактический текст и смещая вырезание в неправильное место. Реальная стоимость токенов для qwen-vl image — максимум несколько тысяч токенов. Оценщик должен рассматривать бинарные части как небольшую константу.

claude-code решает (1) с помощью `stripImagesFromMessages`. nessy-cli не имеет ни этого удаления, ни соответствующего исправления подсчёта символов.

Это изменение добавляет оба, ограниченные **только входными данными side-query компрессии**. История разговора в реальном времени, персистентность (`.chats/<sessionId>.jsonl`), и prompt, отправленный основной модели на следующем ходу, не затрагиваются. Облегчение применяется только к payload side-query, построенному внутри `chatCompressionService`.

### Вне области (отложено или отклонено)

- **Вынос больших вставок во внешний кэш вставок.** Более ранний черновик этого дизайна предлагал хеширование текста сверх размера в `~/.nessy/paste-cache/<sha>.txt` и замену placeholder. Мы отклонили это после обзора релизов claude-code с 2026-03 по 2026-05: направление upstream — сохранять пользовательский ввод видимым для модели и амортизировать стоимость через кэширование prompt (1h TTL knobs, уменьшение размера изображений), а не выносить его вовне. Размещение дословного пользовательского ввода за hash placeholder рискует "intent drift" как только компрессия сколлапсировала оригинальный текст. Если вернёмся к этому позже, правильный паттерн — `read_paste(hash)` как реальный инструмент к которому модель может обратиться, не молчаливое переписывание.

## Предлагаемые изменения

### Слой 1: облегчение входных данных компрессии (`services/compactionInputSlimming.ts`)

Новый чистый модуль который принимает `Content[]` и возвращает slimmed `Content[]`. Одно преобразование: удаление inline-media. Обход каждого `Part`. Если часть имеет `inlineData` или `fileData`, заменить её на `text` часть вида `[image: image/png]` (или `[document: application/pdf]`).

nessy-cli прикрепляет media возвращённые инструментом на `functionResponse.parts` (расширение поверх стандартной схемы `@google/genai` `FunctionResponse`; см. `coreToolScheduler.createFunctionResponsePart`). Slimmer рекурсирует в этот вложенный массив так что base64 image возвращённый `read_file` или любым MCP attachment-emitting инструментом также заменяется.

Преобразование возвращает свежий массив `Content[]`; оригинал никогда не мутируется. Если преобразование не производит изменений, возвращается ссылка на оригинальный массив (identity-equal). Оркестратор вызывает `slimCompactionInput` как последний шаг перед `runSideQuery` в `chatCompressionService.ts`.

### Слой 2: исправление оценки токенов (`chatCompressionService.ts`)

`findCompressSplitPoint` в настоящее время использует `JSON.stringify(content).length` для распределения подсчёта символов. Заменить это на helper `estimateContentChars` который:

- Для частей `text`: `text.length`
- Для частей `inlineData` / `fileData`: `imageTokenEstimate * 4` (по умолчанию 1600 × 4 = 6400 символов).
- Для частей `functionCall` / `functionResponse`: `JSON.stringify(part).length` (неизменное поведение).

Это та же константа которую использует модуль slimming, поэтому бюджет который видит алгоритм точки разделения соответствует тому что фактически потребляет slimmed prompt downstream. Чтобы избежать дублирования обходов, `compress()` предварительно вычисляет `charCounts` один раз и передаёт их в `findCompressSplitPoint` (новый опциональный 4-й аргумент); тот же массив переиспользуется для guard `MIN_COMPRESSION_FRACTION`.

### Слой 3: очистка изображений microcompact (`microcompaction/microcompact.ts`)

`collectCompactablePartRefs` теперь возвращает три группы:

- `tool` — части `functionResponse` от compactable встроенных инструментов. Очищаются как единица: вывод response заменяется sentinel, `functionResponse.parts` удаляются вместе с ним.
- `media` — top-level части `inlineData` / `fileData` под сообщениями user-role (например изображения вставленные через `@reference`). Заменяются на `[Old inline media cleared: <mime>]`.
- `nested-media` — части `functionResponse` от **не-compactable** инструментов (например MCP screenshot инструменты чьи имена не в `COMPACTABLE_TOOLS`) которые несут изображения / документы на поле расширения `functionResponse.parts`. Только вложенные media удаляются; text вывод инструмента сохраняется.

Каждый вид имеет свой собственный бюджет `keepRecent`. Установка `toolResultsNumToKeep: 1` сохраняет самые последние каждой категории (1 tool + 1 media + 1 nested-media), не 1 запись всего на комбинированный список.

Значения mimeType surfaced от MCP tool серверов пропускаются через `sanitizeMimeForPlaceholder` перед встраиванием в любую placeholder строку. Slimmer и microcompact разделяют этот helper.

### Слой 4: конфигурация (`config/config.ts`)

Одно новое поле под настройками `chatCompression`:

```json
{
  "chatCompression": {
    "contextPercentageThreshold": 0.7,
    "imageTokenEstimate": 1600
  }
}
```

Плюс env override для ops/debug: `NESSY_IMAGE_TOKEN_ESTIMATE`.

## Ключевые решения дизайна

**Решение 1: `imageTokenEstimate = 1600`.**
Семейство qwen-vl максимум 1280 визуальных токенов на изображение без `vl_high_resolution_images`; с этим флагом до 16384. 1600 — консервативная средняя величина слегка завышенная — переоценка ведёт к более ранней компрессии (безопасно), недооценка ведёт к поздней компрессии (небезопасно). Для не-VL моделей (qwen3-Coder, default nessy-cli) константа важна только для корректности оценки токенов, поскольку изображения всё равно не достигают модели.

**Решение 2: Удалять slimmed копию, не live историю.**
`slimCompactionInput` возвращает свежий массив; история разговора хранимая в `GeminiChat` не тронута. Локальная персистентность (`.chats/<sessionId>.jsonl`) сохраняет полный разговор как пользователь его видел.
