# Структурированный вывод (`--json-schema`) — Дизайн

Этот документ описывает реализацию функции `--json-schema` для headless-режима. Информация для пользователя находится в [`docs/users/features/structured-output.md`](../users/work/features/structured-output.md).

## Цель

В headless-запусках (`nessy -p`, piped stdin или позиционный промпт) позволить вызывающей стороне ограничивать финальный ответ модели пользовательской JSON Schema и выводить валидированные данные в машиночитаемом формате для скриптов и downstream-инструментов. Планирование с побочным текстом допускается, но запуск должен завершаться данными, соответствующими схеме, а не свободным текстом.

## Подход: синтетический инструмент, чья схема параметров — это схема пользователя

При указании `--json-schema` в `Config.createToolRegistry` регистрируется синтетический инструмент `structured_output` (`syntheticOutput.ts`). Его `parametersJsonSchema` — это в точности схема пользователя; его `execute()` возвращает `llmContent` с сообщением об остановке. Инфраструктура вызова инструментов уже валидирует аргументы против `parametersJsonSchema` на стороне клиента (через Ajv в `BaseDeclarativeTool.build()`), поэтому «модель вернула ответ, соответствующий схеме» сводится к «модель успешно вызвала `structured_output`».

Три свойства вытекают бесплатно:

1. **Нет специального пути валидатора.** Валидация через Ajv уже выполняется в `BaseDeclarativeTool.build()` и отклоняет несоответствующие аргументы до вызова `execute()`.
2. **Стандартное поведение повторов.** Ошибка валидации передаётся модели как ошибка вызова инструмента, как и любая другая ошибка аргументов. Модель видит сообщение Ajv и может исправить в следующем ходе.
3. **Независимость от провайдера.** Gemini, OpenAI и Anthropic одинаково сериализуют схемы параметров инструментов (через абстракцию `DeclarativeTool`); синтетический инструмент работает со всеми тремя.

Инструмент регистрируется с `alwaysLoad: true`, чтобы инфраструктура загрузки инструментов по требованию (ToolSearch, #3589) никогда не скрывала его от модели. Без этого флага модель не узнает о терминальном контракте.

## Валидация на этапе парсинга

`resolveJsonSchemaArg(raw)` в `packages/cli/src/config/config.ts`) выполняет четыре проверки до передачи схемы в `Config.createToolRegistry`:

1. **Разрешение источника.** Принимается либо JSON-литерал, либо `@path/to/file`. Форма `@path` проверяет файл через `stat`, отклоняет не-обычные файлы (FIFO, устройства, директории), ограничивает размер 4 MiB и выводит общую ошибку при неудаче парсинга JSON.
2. **Форма JSON.** Результат должен быть не-массивным объектом — примитивы, булевы значения и массивы отклоняются.
3. **Корень принимает объекты** — `schemaRootAcceptsObject` `packages/cli/src/config/config.ts`. API вызова функций всегда передают объекты как аргументы инструментов; корневая схема вида `{type: "array"}` зарегистрировала бы непригодный инструмент. Обход обрабатывает `type`, `const`, `enum`, `anyOf`, `oneOf`, `allOf`, `not`, `if`/`then`/`else` и корневой `$ref`.
4. **Строгая компиляция Ajv** — `SchemaValidator.compileStrict` `packages/core/src/utils/schemaValidator.ts`. Специальный экземпляр Ajv с `strictSchema: true` выявляет опечатки вроде `propertees`, которые мягкий runtime-валидатор молча проглотил бы.

### Границы `schemaRootAcceptsObject`

Обход намеренно best-effort. Он отлавливает однозначные случаи «это никогда не примет объект», а всё, что требует анализа выполнимости по полной схеме, откладывает на Ajv во время выполнения.

**Решается на этапе парсинга:**

| Паттерн                                                | Исход                                                           |
| ------------------------------------------------------ | ----------------------------------------------------------------- |
| `type` присутствует, не включает `"object"`            | отклонить                                                       |
| `type: ["object", "null"]` и т.д.                      | принять                                                         |
| `const`: не-объектное значение                         | отклонить                                                       |
| `enum`: нет объектных членов (включая пустой)          | отклонить                                                       |
| `anyOf`/`oneOf`: пустой массив                         | отклонить                                                       |
| `anyOf`/`oneOf`: ни одна ветвь не принимает объект     | отклонить                                                       |
| `allOf`: любая ветвь `false` или отклоняет объект      | отклонить                                                       |
| Корневой `$ref` (с или без sibling `type`)             | отклонить                                                       |
| `not`: голый `{type: "object"}` (без сужающих ключей)  | отклонить                                                       |
| `not`: `{type: "object", required: […], …}` и т.д.     | принять (сужающие ключи оставляют некоторые объекты выполнимыми; откладывается) |
| `if: true` + `then` отклоняет объект                   | отклонить                                                       |
| `if: false` + `else` отклоняет объект                  | отклонить                                                       |

**Откладывается на Ajv во время выполнения:**

- `$ref` внутри ветвей `anyOf`/`oneOf`/`allOf` (непрозрачны — разрешение `$ref` потребует обнаружения циклов, JSON Pointer и обработки `$defs` vs `definitions`; затраты перевешивают выгоду).
- `if` со значением-объектом схемы (разрешимо только против кандидата).
- Отрицательные паттерны `anyOf`/`oneOf`/`const` сложнее, чем `not.type`.
- Произвольное воздействие ReDoS через `pattern` (пользовательский ввод; угроза узка, т.к. флаг — аргумент CLI, не сетевой ввод).

Путь выхода `maxSessionTurns` добавляет специфичную для `--json-schema` подсказку, указывающую на частый симптом зависания (модель не вызвала `structured_output`) и две вероятные причины (инструмент запрещён через permissions / схема невыполнима).

## Runtime: диспетчеризация ходов

`packages/cli/src/nonInteractiveCli.ts` обрабатывает runtime-диспетчеризацию. Специфика structured output:

### Пре-скан и подавление соседей

Когда модель генерирует `structured_output` вместе с другими инструментами в одном ходе ассистента, синтетический вызов — терминальный контракт. Пре-скан в `processToolCallBatch` фильтрует `requestsToExecute` до **только** вызовов `structured_output`, поэтому побочные инструменты (`write_file`, `run_shell_command`, `edit`, …) никогда не выполняются.

Примеры пакетов (когда активен `--json-schema`):

| Модель генерирует                                      | Поведение                                                                                                                                                                                                                                                                                                         |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `[write_file(…), structured_output(…)]`                  | `write_file` пропускается. `structured_output` валидируется, запуск завершается.                                                                                                                                                                                                                                                |
| `[structured_output(bad-args), structured_output(good)]` | Первый падает на валидации Ajv; второй успешен. Запуск завершается с аргументами второго вызова.                                                                                                                                                                                                                               |
| `[structured_output(bad-args), write_file(…)]`           | `structured_output(bad)` падает. `write_file` также пропускается (подавлен заранее). Модель видит оба: сообщение Ajv для структурированного вызова и синтезированное `"Skipped: …"` tool_result для side-effect вызова. Следующий ход: модель может переиздать оба или исправить только структурированный вызов. |
| `[other_tool_a, other_tool_b]` (без `structured_output`)  | Пре-скан инертен. Оба инструмента работают нормально; запуск НЕ завершается.                                                                                                                                                                                                                                          |

Синтезированное тело "Skipped:" имеет два варианта:

- **Путь успеха** (структурированный вызов захватил контракт в этом ходе): `"Skipped: this turn's structured_output contract took precedence as the terminal output."` — коротко, т.к. сессия завершается немедленно.
- **Путь повтора** (нет структурированного вызова, модель получает ещё ход): добавляется `"Re-issue this call in a separate turn if needed."` — это единственный случай, где модель может действовать.

### Паритет основного/дренирующего хода

`processToolCallBatch(batchRequests, setModelOverride)` определён внутри `runNonInteractive` и вызывается из:

- Цикла основного хода (верх функции).
- `drainOneItem` (цикл ответа на cron-промпт / уведомления фоновых задач).

Дренирующий ход важен, т.к. `structured_output` зарегистрирован на всю сессию, поэтому cron-задача или ответ на уведомление МОГУТ вызвать инструмент. Хендлер обрабатывает оба сайта идентично; разница только в том, какая переменная `modelOverride` записывается.

**Пост-хендлер терминации** различается: путь основного хода напрямую вызывает `return emitStructuredSuccess()`, путь дренирующего требует двухшаговой терминации (`processToolCallBatch` захватывает результат в `structuredSubmission`; `drainLocalQueue` проверяет его для остановки цикла, затем holdback-цикл проверяет его для выхода и вызова `emitStructuredSuccess`). Оба сходятся на одном терминальном блоке.

### Терминальный блок структурированного успеха

`emitStructuredSuccess()` (также внутри `runNonInteractive`) — общий путь «получили валидный вызов, завершаемся»:

1. `registry.abortAll()` прерывает фоновые агенты — контракт structured output однократный и не должен гоняться с `task_notification`.
2. Ограниченный holdback (`STRUCTURED_SHUTDOWN_HOLDBACK_MS = 500` мс), чтобы естественные обработчики отмены прерванных агентов успели выдать терминальный `task_notification`. Цикл: `Date.now() < deadline && registry.hasUnfinalizedTasks()`. 500 мс — best-effort; осиротевшие `task_started` возможны под нагрузкой.
3. `flushQueuedNotificationsToSdk(localQueue)` дренирует всё ещё заqueued.
4. `finalizeOneShotMonitors()` (идемпотентен).
5. `adapter.emitResult({ structuredResult: …, isError: false, … })`.

### Пути неудачи

| Причина                                                           | Код выхода | Поверхность                                                                                                                                                                                                                                                                            |
| ----------------------------------------------------------------- | ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Модель выдаёт только текст                                        | 1          | Ошибка с количеством ходов + `Output preview`.                                                                                                                                                                                                                                |
| Модель не вызывает `structured_output` за `maxSessionTurns` ходов | 53         | `Reached max session turns` + подсказка `--json-schema` о симптоме и причинах.                                                                                                                                                                                                     |
| Валидация многократно падает                                      | (53 через max-turns) | Каждая неудача передаётся модели с сообщением Ajv.                                                                                                                                                                                                          |
| Abort / SIGINT                                                    | 130        | Путь отмены. Результат обычно не выдаётся, но holdback-цикл `emitStructuredSuccess()` не опрашивает сигнал отмены — SIGINT во время capture/emit может всё ещё выдать результат. Код выхода — надёжный сигнал. |

## Конверт вывода

Пайплайн адаптера в `BaseJsonOutputAdapter.buildResultMessage` `packages/cli/src/nonInteractive/io/BaseJsonOutputAdapter.ts` при наличии `structuredResult`:

- `result` форсируется в `JSON.stringify(payload)` — перезаписывая свободный текст.
- Поле верхнего уровня `structured_result` содержит сырой объект для потребителей, не желающих парсить строку.
- `undefined` нормализуется в `null`, чтобы поле не исчезало молча.

TEXT mode пишет только `result` + newline в stdout (побочный текст отбрасывается). JSON mode выдаёт полный лог событий как JSON-массив; `structured_result` на финальном элементе `type: "result"`. Stream-json mode выдаёт каждое сообщение как JSONL; завершающая `result` строка несёт `structured_result`.

## Приватность: кросс-поверхностное редактирование

Аргументы `structured_output` — это и есть структурированная нагрузка. На пути успеха они уже в stdout; при повторах валидации могут никогда не достичь stdout. В любом случае сохранение их на долговременных поверхностях (или экспорт через телеметрию) — дублирование, утечка в более долговременное хранилище. Правило редактирования: «никогда не сохранять аргументы этого синтетического инструмента, независимо от исхода».

Две поверхности должны редактироваться, обе используют константу `STRUCTURED_OUTPUT_REDACTED_ARGS` `packages/core/src/tools/syntheticOutput.ts`:

- `ToolCallEvent.function_args` (телеметрия) — покрывает OTLP, NessyLogger, ui-telemetry, chat-recording UI.
- `redactStructuredOutputArgsForRecording` (в `recordAssistantTurn` в `geminiChat.ts`) — покрывает on-disk chat-recording JSONL.

Общая константа предотвращает дрейф между поверхностями. Метрики вызовов (длительность, успех, решение) сохраняются.

Hooks (`PreToolUse`, `PostToolUse`, `PostToolUseFailure`) намеренно **не** редактируются — они получают сырой `tool_input`, т.к. контракт хуков «видеть то, что видит инструмент». Это документировано в разделе Privacy пользовательской документации как «Hooks видят сырые аргументы».

Редактирование намеренно ограничено **on-device** поверхностями (экспорт телеметрии + chat-recording JSONL). Сама схема всё ещё передаётся провайдеру в блоке `parameters` декларации функции `structured_output` — редактирование на стороне провайдера невозможно. Раздел Privacy предупреждает пользователей держать `enum`/`const`/`default`/`examples`/`description` без секретов.

## Управление разрешениями

`structured_output` намеренно исключён из `PermissionManager.CORE_TOOLS` (набор инструментов, подпадающих под `--core-tools` allowlist) — наряду с другими синтетическими (`agent`, `exit_plan_mode`, `ask_user_question`, `task_stop`, `send_message`). Динамически обнаруживаемые инструменты (skill, MCP) — отдельная категория исключения.

Явные правила `permissions.deny` и настройки `--exclude-tools` всё ещё применяются через `PermissionManager.evaluate` → `isToolEnabled`. Оба используют один механизм запрета и предотвращают регистрацию — декларация инструмента удаляется из реестра, модель никогда не видит инструмент. Типичный исход: модель отвечает текстом (выход 1). Если модель зацикливается на других инструментах без текста, eventually hitting `maxSessionTurns` (выход 53) и подсказка `--json-schema` в `handleMaxTurnsExceededError` говорит пользователю, куда смотреть.

**Взаимодействие с `--bare`.** Bare mode коротко замыкает мост settings → CLI config: `packages/cli/src/config/config.ts` строит `mergedDeny` как `[...(bareMode ? [] : settings.permissions.deny), ...]`, поэтому settings-level denies (и `tools.exclude`) отбрасываются при `--bare`. Argv-level `--exclude-tools` безусловно добавляется в `mergedDeny`, поэтому всё ещё применяется. Синтетический инструмент регистрируется независимо (управляется `jsonSchema`, не deny list), поэтому settings-only deny `structured_output` молча становится no-op при `--bare`, пока инструмент остаётся вызываемым.

## Контексты subagent

`Config.createToolRegistry` принимает опцию `forSubAgent: true`, которая подавляет синтетическую регистрацию. Subagent overrides переиспользуют родительский Config через делегацию прототипа (`createApprovalModeOverride` / `buildSubagentContextOverride` → `Object.create(base)`), и `this.jsonSchema` передаётся по цепочке прототипов. Без флага синтетический инструмент зарегистрировался бы в реестре subagent тоже, и subagent, вызывающий его, получил бы «сессия завершается сейчас» llmContent — но только циклы main/drain `runNonInteractive` детектируют это как терминал, поэтому subagent продолжил бы работать и сжигал токены.

> **Заметка мейнтейнера.** Эта супрессия держится на единственном пути вызова через `createToolRegistry(forSubAgent: true)`. Любой будущий механизм spawn subagent, обходящий этот путь, утечит синтетический инструмент в реестр subagent и вернёт режим burn-tokens-forever. Fail-safe дополнением был бы runtime guard внутри `syntheticOutput.execute()`, возвращающий `fatalError` (или no-op) при вызове из контекста subagent.

## Guard теневого инструмента MCP

`tool-registry.ts:registerTool` проверяет карту ленивых `factories` на коллизии имён, не только карту eager `tools`. Если MCP server обнаруживает инструмент буквально с именем `structured_output`, путь авто-квалификации для коллизий eager-инструментов срабатывает для коллизий factories тоже: MCP инструмент переименовывается в `mcp__<server>__structured_output`, и синтетическая фабрика сохраняет голое имя. Без этого guard MCP server мог бы молча перехватить контракт structured output.

## Поверхность совместимости

| Комбинация                                               | Статус                 | Обоснование                                                                                                                                 |
| -------------------------------------------------------- | ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `--json-schema` + `-p` (или stdin, или позиционный)      | Поддерживается         | Основной headless путь.                                                                                                                    |
| `--json-schema` + `--output-format text` (по умолчанию)  | Поддерживается         | `JSON.stringify(payload)` + newline.                                                                                                      |
| `--json-schema` + `--output-format json` / `stream-json` | Поддерживается         | Поле `structured_result` содержит сырой объект.                                                                                         |
| `--json-schema` + `--bare`                               | Поддерживается         | `--bare` ограничивает реестр до `read_file`, `edit`, `run_shell_command`; синтетический инструмент регистрируется рядом с этим минимальным набором. |
| `--json-schema` + `-i`                                   | Отклонено на парсинге  | TUI не имеет терминального контракта для синтетического инструмента.                                                                                      |
| `--json-schema` + `--input-format stream-json`           | Отклонено на парсинге  | Однократный контракт vs. long-lived протокол.                                                                                             |
| `--json-schema` + `--acp` / `--experimental-acp`         | Отклонено на парсинге  | ACP loop независим.                                                                                                                  |
| `--json-schema` + `--prompt-interactive`                 | Отклонено на парсинге  | То же, что `-i`.                                                                                                                             |
| `--json-schema` + нет промпта + нет piped stdin          | Отклонено на парсинге  | Headless требует промпт.                                                                                                               |

## Альтернативы

**Промпт с осведомлённостью о схеме (без синтетического инструмента).** Просить модель «ответить JSON по этой схеме» через системный промпт и парсить финальное сообщение ассистента. Отклонено, т.к. у модели нет синтаксических гарантий — вывод может быть с префиксом, chatter, или галлюцинировать поля. Валидация вызова инструмента обеспечивается слоем function-calling до `execute()`, что даёт жёсткую гарантию.

**Выделенный конечный инструмент вывода.** Создать специальный инструмент, который модель вызывает только в конце. Отклонено, т.к. дублирует инфраструктуру и требует от модели изучать дополнительный инструмент. Синтетический `structured_output` уже служит этой цели.

**Пост-процессинг stdout.** Запустить модель без ограничений, затем распарсить stdout на предмет JSON. Отклонено, т.к. ненадёжно: модель может добавить префикс/суффикс, несколько блоков JSON, или ответить текстом при неудаче. Валидация tool-call гарантирует, что модель явно выбрала структурированный вывод.
