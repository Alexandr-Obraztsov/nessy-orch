# Session Recap Design (Дизайн резюме сессии)

> Краткое (1-2 предложения) резюме "где я остановился", отображаемое, когда пользователь возвращается к бездействующей сессии, по запросу (`/recap`) или после того, как терминал был не в фокусе 5+ минут.

## Обзор

Когда пользователь `/resume`ит старую сессию через несколько дней, прокрутка назад через страницы истории, чтобы вспомнить, **что они делали и что делать дальше**, является реальной точкой трения. Простая перезагрузка сообщений не решает эту UX-проблему.

Цель — проактивно отображать краткое резюме из 1-2 предложений, когда пользователь возвращается:

- **Высокоуровневая задача** (что они делают) → **следующий шаг** (что делать дальше).
- Визуально отличается от реальных ответов ассистента, чтобы никогда не ошибочно приниматься за новый вывод модели.
- **Best-effort**: отказы должны быть тихими и никогда не ломать основной поток.

## Триггеры

| Триггер    | Условия                                                                                    | Реализация                                                                           |
| ---------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| **Ручной** | Пользователь запускает `/recap`                                                            | `recapCommand.ts` вызывает ту же службу                                              |
| **Авто**   | Терминал не в фокусе (протокол фокуса DECSET 1004) ≥ 5 мин + возврат фокуса + поток `Idle` | `useAwaySummary.ts` — 5-минутный таймер неактивности + обработчик события `useFocus` |

Оба пути ведут к одной функции — `generateSessionRecap()` — для гарантии идентичного поведения. Авто-триггер контролируется `general.showSessionRecap` (по умолчанию: выкл — явное согласие, поэтому фоновые вызовы LLM никогда молча не добавляются к счёту пользователя); ручная команда игнорирует эту настройку.

## Дизайн промпта

### Системный промпт

`generationConfig.systemInstruction` заменяет системный промпт главного агента для этого единственного вызова, поэтому модель ведёт себя только как генератор резюме, а не как ассистент по кодированию.

Заметьте, что `GeminiClient.generateContent()` внутренне пропускает промпт через `getCustomSystemPrompt()`, который добавляет память пользователя (NESSY.md / управляемая авто-память) как суффикс. Итоговый системный промпт — это therefore `промпт резюме + память пользователя` — полезный контекст проекта для резюме, не утечка.

Пункты ниже соответствуют 1:1 с `RECAP_SYSTEM_PROMPT`:

- Менее 40 слов, 1-2 простых предложения (без markdown / списков / заголовков). Для китайского считайте бюджет примерно 80 символов всего.
- Первое предложение: высокоуровневая задача. Затем: конкретный следующий шаг.
- Явно запретить: перечисление сделанного, цитирование вызовов инструментов, отчёты о статусе.
- Соответствовать доминирующему языку разговора (английский или китайский).
- Обернуть вывод в `<recap>...</recap>`; ничего вне тегов.

### Структурированный вывод + извлечение

Модель инструктируется оборачивать ответ в `<recap>...</recap>`:

```
<recap>Рефакторинг loopDetectionService.ts для устранения OOM длинной сессии. Следующий шаг — реализовать вариант B.</recap>
```

Зачем: некоторые модели (семейство GLM, модели рассуждения) пишут параграф "размышления" перед финальным ответом. Возврат сырого текста утечёт это размышление в UI.

`extractRecap()` имеет три уровня отката:

1. Оба тега присутствуют: взять то, что между `<recap>...</recap>` (предпочтительно).
2. Только открывающий тег (например, `maxOutputTokens` обрезал закрывающий тег): взять всё после открывающего тега.
3. Тег полностью отсутствует: вернуть пустую строку → служба возвращает `null` → UI ничего не отображает.

Третий уровень — "пропустить, а не показать неправильное" — отображение преамбулы размышлений модели хуже, чем показ отсутствия резюме вообще.

| Параметр            | Значение                       | Причина                                                                  |

## Фильтрация истории

`geminiClient.getChat().getHistory()` возвращает `Content[]`, который включает:

- Текстовые сообщения `user` / `model`
- Части `functionCall` модели
- Части `functionResponse` пользователя (которые могут содержать полные содержимые файлов)
- Части размышлений модели (`part.thought` / `part.thoughtSignature`, скрытые размышления модели)

`filterToDialog()` сохраняет только части `user` / `model`, которые имеют **непустой текст и не являются размышлениями**. Две причины:

- **Вызовы инструментов / ответы**: один `functionResponse` может быть 10K+ токенов. 30 таких сообщений утопят LLM резюме в нерелевантных деталях, тратя токены и смещая резюме к шуму реализации вроде "вызвал инструмент X для чтения файла Y".
- **Части размышлений**: содержат внутренние размышления модели. Их включение рискует трактовать скрытую цепочку размышлений как диалог и отображать её в тексте резюме.

После отбрасывания пустых сообщений, `takeRecentDialog` обрезает до последних 30 сообщений и отказывается начинать срез с висящего ответа модели/инструмента.

## Параллелизм и граничные случаи

### Машина состояний хука авто-триггера

`useAwaySummary` хранит три ref:

| Ref               | Значение                                                |
| ----------------- | ------------------------------------------------------- |
| `blurredAtRef`    | Время начала размытия (не очищается до возврата фокуса) |
| `recapPendingRef` | Вызов LLM в полёте                                      |
| `inFlightRef`     | Текущий `AbortController` в полёте                      |

Зависимости `useEffect`: `[enabled, config, isFocused, isIdle, addItem, thresholdMs]`.

| Событие                                                             | Действие                                                                                                                                               |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `!enabled \|\| !config`                                             | Прервать вызов в полёте + очистить `inFlightRef` + очистить `blurredAtRef`                                                                             |
| `!isFocused` и `blurredAtRef === null`                              | Установить `blurredAtRef = Date.now()`                                                                                                                 |
| `isFocused` и `blurredAtRef === null`                               | Вернуться рано (нет цикла размытия для обработки — первый рендер или сразу после сброса краткого размытия)                                             |
| `isFocused` и длительность размытия < 5 мин                         | Очистить `blurredAtRef`, ждать следующего цикла размытия                                                                                               |
| `isFocused` и размытие ≥ 5 мин и `recapPendingRef`                  | Вернуться (дедупликация)                                                                                                                               |
| `isFocused` и размытие ≥ 5 min и `!isIdle`                          | **Сохранить** `blurredAtRef` и ждать завершения хода (`isIdle` в зависимостях, поэтому эффект срабатывает снова, когда потоковая передача завершается) |
| `isFocused` и размытие ≥ 5 min и `shouldFireRecap` возвращает false | Очистить `blurredAtRef` и вернуться — разговор не сдвинулся достаточно с последнего резюме (требуется ≥ 2 хода пользователя, зеркалирует Claude Code)  |
| `isFocused` и все условия выполнены                                 | Очистить `blurredAtRef`, установить `recapPendingRef = true`, создать `AbortController`, отправить запрос LLM                                          |

`.then` обратный вызов **перепроверяет** `isIdleRef.current`: если пользователь начал новый ход, пока LLM работал, поздно пришедшее резюме отбрасывается, чтобы избежать вставки в середине хода.

`.finally` очищает `recapPendingRef` и очищает `inFlightRef` только если `inFlightRef.current === controller` (чтобы не перезаписать newer controller).

Второй `useEffect` прерывает in-flight controller при размонтировании.

### Блокировка `/recap`

`CommandContext.ui.isIdleRef` предоставляет текущее состояние потока (зеркалирует существующий паттерн `btwAbortControllerRef`). В интерактивном режиме, `recapCommand` отказывает, когда `!isIdleRef.current` **или** `pendingItem !== null`. Одного `pendingItem` недостаточно, потому что нормальный ответ модели запускается с `streamingState === Responding` и null `pendingItem`.

## Конфигурация и выбор модели

### Пользовательские регуляторы

| Настройка                                  | По умолчанию | Примечания                                                                                   |
| ------------------------------------------ | ------------ | -------------------------------------------------------------------------------------------- |
| `general.showSessionRecap`                 | `false`      | Только авто-триггер. Ручной `/recap` игнорирует это.                                         |
| `general.sessionRecapAwayThresholdMinutes` | `5`          | Минут не в фокусе перед авто-резюме на возврате фокуса. Соответствует умолчанию Claude Code. |
| `fastModel`                                | unset        | Рекомендуется (например, `qwen3-coder-flash`) для быстрых и дешёвых резюме.                  |

### Откат модели

`config.getFastModel() ?? config.getModel()`:

- У пользователя установлен `fastModel`, и он валиден для текущего типа аутентификации → использовать `fastModel`.
- Иначе → откат к основной модели сессии (работает, просто дороже и медленнее).

## Наблюдаемость

`createDebugLogger('SESSION_RECAP')` испускает:

- пойманные исключения из пути резюме (`debugLogger.warn`).

Все отказы **полностью прозрачны** для пользователя — резюме вспомогательная функция и никогда не бросает в UI. Разработчики могут grep'ать тег `[SESSION_RECAP]` в файле отладочного лога: по умолчанию записывается в `~/.nessy/debug/<sessionId>.txt` (`latest.txt` симлинкуется на текущую сессию); отключается через `NESSY_DEBUG_LOG_FILE=0`.

## Вне области

| Пункт                                            | Почему нет                                                                                                                                         |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Progress UI для `/recap` (спиннер / pendingItem) | 3-5 секундное ожидание терпимо; добавляет сложность.                                                                                               |
| Автоматизированные тесты                         | Служба мала (~150 строк), вручную протестирована end-to-end сначала; юнит-тесты могут приземлиться в отдельном PR.                                 |
| Локализованные промпты                           | Системный промпт для модели; английский — наиболее надёжная подложка. Модель выбирает язык вывода из разговора.                                    |
| `NESSY_CLI_ENABLE_AWAY_SUMMARY` env var          | Claude Code использует его для сохранения функции включённой, когда телеметрия отключена; текущая модель телеметрии Nessy CLI не нуждается в этом. |
| Авто-резюме на завершении `/resume`              | Естественное продолжение, но нуждается в точке зацепления в `useResumeCommand`; вне области для этого PR.                                          |
