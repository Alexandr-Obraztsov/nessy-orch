# Slash Command Refactoring Roadmap (Дорожная карта рефакторинга slash команд)

## Общая цель

Использовать внутренний архитектурный стиль Nessy для доставки платформы команд, которая на 95% выравнивается с внешним опытом Claude Code, одновременно исправляя три основные проблемы: разделение трёх режимов, единственность источников команд, невозможность вызова модели prompt command.

---

## Основные принципы дизайна

1. **Каждый Phase может быть независимо отправлен**: после завершения поведение самосогласовано, не зависит от будущих Phase для запуска
2. **Phase 1 — чистая инфраструктура**: кроме исправления ошибочного перехвата MCP_PROMPT, не изменяет никакие существующие наборы доступных команд
3. **Изменения поведения и архитектурные изменения разделены**: Phase 1 делает архитектуру, Phase 2 делает расширение возможностей
4. **Не копировать внутреннюю архитектуру Claude Code**: но выровнять воспринимаемые пользователем возможности

---

## Phase 1: Перестройка инфраструктуры (чистая архитектура, нулевые изменения поведения)

### Цели

Создать единую модель метаданных команд и механизм управления между режимами, предоставляющий нижележащую поддержку для всех последующих Phase.

### Функциональные точки

#### 1.1 Расширение модели метаданных `SlashCommand`

Добавить следующие поля к существующему интерфейсу `SlashCommand`:

**Поля источника**

- `source: CommandSource`: перечисление источников команд (`builtin-command` / `bundled-skill` / `skill-dir-command` / `plugin-command` / `mcp-prompt` и т.д.)
- `sourceLabel?: string`: метка источника для отображения (например, `"Built-in"` / `"MCP: github-server"`)

**Поля возможностей режима**

- `supportedModes: ExecutionMode[]`: объявление, в каких режимах выполнения доступно (`interactive` / `non_interactive` / `acp`)

**Поля типа выполнения**

- `commandType: CommandType`: объявление типа выполнения (`prompt` / `local` / `local-jsx`)

**Поля видимости**

- `userInvocable: boolean`: может ли пользователь вызывать через slash command (по умолчанию `true`)
- `modelInvocable: boolean`: может ли модель вызывать через tool call (по умолчанию `false`)

**Вспомогательные метаданные** (зарезервировано для Phase 3, Phase 1 только определяет, не использует)

- `argumentHint?: string`: подсказка параметров, например `"<model-id>"` / `"show|list|set"`
- `whenToUse?: string`: описание, когда вызывать команду (для модели)
- `examples?: string[]`: примеры использования

#### 1.2 Заполнение полей source/commandType каждым Loader

Каждый Loader при построении `SlashCommand` должен заполнить `source` и `commandType`:

| Loader                                    | source              | commandType                                         |
| ----------------------------------------- | ------------------- | --------------------------------------------------- |
| `BuiltinCommandLoader`                    | `builtin-command`   | объявляется каждой командой (`local` / `local-jsx`) |
| `BundledSkillLoader`                      | `bundled-skill`     | `prompt`                                            |
| `FileCommandLoader` (пользователь/проект) | `skill-dir-command` | `prompt`                                            |
| `FileCommandLoader` (плагин)              | `plugin-command`    | `prompt`                                            |
| `McpPromptLoader`                         | `mcp-prompt`        | `prompt`                                            |

#### 1.3 Объявление built-in командами supportedModes и commandType

Для всех built-in команд явно объявить:

- `commandType`: `local` (без зависимости от UI) или `local-jsx` (зависит от dialog/React)
- `supportedModes`: команды `local` объявляют `['interactive', 'non_interactive', 'acp']`; команды `local-jsx` объявляют `['interactive']`

#### 1.4 Замена жёстко закодированного белого списка на фильтрацию на основе capabilities

- Удалить константу `ALLOWED_BUILTIN_COMMANDS_NON_INTERACTIVE`
- Удалить функцию `filterCommandsForNonInteractive`
- Добавить функцию `filterCommandsForMode(commands, mode)`, фильтрация на основе поля `supportedModes`
- Добавить инструментальную функцию `getEffectiveSupportedModes(cmd)` (учитывает стратегию по умолчанию CommandKind)
- Изменить сигнатуры функций `handleSlashCommand` / `getAvailableCommands`, удалить параметр `allowedBuiltinCommandNames`

#### 1.5 Обновление CommandService до единого Registry

- Добавить метод `getCommandsForMode(mode: ExecutionMode)`
- Добавить метод `getModelInvocableCommands()` (используется в Phase 2/3, Phase 1 предоставляет интерфейс)
- Существующий `getCommands()` остаётся без изменений (для interactive)

### Критерии приёмки

- [ ] Интерфейс `SlashCommand` содержит все новые поля, компиляция TypeScript проходит
- [ ] Все Loader заполняют поля `source` и `commandType`
- [ ] Все built-in команды объявляют `commandType` и `supportedModes`
- [ ] `ALLOWED_BUILTIN_COMMANDS_NON_INTERACTIVE` удалён, заменён capability filter
- [ ] **Набор доступных команд в non-interactive полностью согласован с до рефакторинга** (существующие тесты не ломаются)
- [ ] Команды MCP prompt могут нормально выполняться в non-interactive/acp (исправление оригинального ошибочного ограничения)
- [ ] `CommandService.getCommandsForMode('non_interactive')` возвращает правильный набор команд
- [ ] Все существующие тесты проходят

## Phase 2: Расширение возможностей (упорядочивание команд и вызов модели prompt command)

### Цели

На основе метаданных Phase 1 расширить доступность команд в трёх режимах и Реализовать путь вызова модели prompt command.

### Функциональные точки

#### 2.1 Расширение набора доступных команд non-interactive / acp

**Принципы дизайна семантики ACP**

Перед расширением команд в режимы ACP/non-interactive следует соблюдать следующие принципы дизайна:

1. **Разные получатели**: в режиме ACP получатель сообщений — IDE (плагин Zed/VS Code), а не пользователь терминала. Содержимое сообщений должно быть в формате чистого текста или Markdown, не должно содержать ANSI-стилей, специфичных для терминала.
2. **Стратегия реализации — добавление ветвления режима, а не замена**: правильный подход — добавить определение режима внутри `action` команды — путь interactive сохраняет существующую логику рендеринга UI без изменений, путь non_interactive/acp возвращает `message` или `submit_prompt`, подходящие для потребления машиной. Два пути сосуществуют в одной функции `action`.
3. **Операции с состоянием требуют объяснения семантики**: в одноразовом неинтерактивном вызове (например, параметр CLI `-p`) изменения команд с состоянием, таких как `/model set`, `/language set`, действительны только в пределах текущей сессии, следует отметить в тексте ответа команды.
4. **Только чтение vs с побочными эффектами**: команды только для чтения (например, `/about`, `/stats`) напрямую возвращают текст текущего состояния; команды с побочными эффектами (например, `/model set`, `/language set`) должны подтверждать результат операции в ответе.
5. **Избегать зависимых от окружения побочных эффектов**: операции, зависящие от графического окружения, такие как открытие браузера (`/docs`, `/insight`), операции буфера обмена (`/copy`), в пути non_interactive/acp следует пропускать, вместо этого возвращая соответствующий URL или само содержимое в тексте ответа.

**Обзор команд для расширения**

> Заметка: `btw`, `bug`, `compress`, `context`, `init`, `summary` уже расширены до всех режимов в Phase 1, не в списке этого этапа.

Следующие 13 команд будут расширены в режимы `non_interactive` и `acp` в Phase 2:

**Класс A: action уже возвращает `message` или `submit_prompt`, нужно только расширить `supportedModes` и разработать содержимое сообщений ACP**

| Команда       | Тип возврата    | Особенности обработки ACP/non-interactive                                                   |
| ------------- | --------------- | ------------------------------------------------------------------------------------------- |
| `/copy`       | `message`       | В ACP нет буфера обмена, вместо этого вернуть само содержимое или подсказку в тексте ответа |
| `/export`     | `message`       | Вернуть полный путь экспортированного файла                                                 |
| `/plan`       | `submit_prompt` | Без изменений, напрямую расширить режим                                                     |
| `/restore`    | `message`       | Вернуть описание результата операции восстановления                                         |
| `/language`   | `message`       | Вернуть текст текущей настройки языка или подтверждения изменения                           |
| `/statusline` | `submit_prompt` | Без изменений, напрямую расширить режим                                                     |

**Класс A': с аргументами нормально выполняется, без аргументов запускает dialog (нужно добавить путь non-interactive для случая без аргументов)**

| Команда          | Поведение без аргументов interactive | Поведение без аргументов non_interactive/acp         |
| ---------------- | ------------------------------------ | ---------------------------------------------------- |
| `/model`         | Открыть dialog выбора модели         | Вернуть текущее имя модели и поясняющий текст        |
| `/approval-mode` | Открыть dialog режима утверждения    | Вернуть текущий режим утверждения и поясняющий текст |

**Класс B: action внутренне использует `context.ui.addItem()` для рендеринга React-компонентов, нужно добавить ветвление режима для возврата чистого текста**

| Команда    | Поведение interactive                              | Возврат non_interactive/acp                                                                                                           |
| ---------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `/about`   | Рендеринг React-компонента версии/конфигурации     | Текстовое резюме номера версии, текущей модели, ключевых конфигураций                                                                 |
| `/stats`   | Рендеринг компонента статистики токенов/расходов   | Текстовый формат статистики session                                                                                                   |
| `/insight` | Рендеринг компонента анализа + открытие браузера   | `non_interactive` синхронно генерирует и возвращает путь файла message; `acp` через `stream_messages` отправляет прогресс и результат |
| `/docs`    | Рендеринг входа в документацию + открытие браузера | Вернуть URL документации, не открывать браузер                                                                                        |

**Класс C: специальная обработка**

| Команда  | Поведение interactive                                        | Поведение non_interactive/acp                                                                                             |
| -------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| `/clear` | Вызов `context.ui.clear()` для очистки отображения терминала | Вернуть message с маркером границы контекста, содержимое `"Context cleared. Previous messages are no longer in context."` |

#### 2.2 Реализация вызова модели prompt command

- Реализовать `getModelInvocableCommands()` в `CommandService` (или `CommandRegistry`), вернуть все команды с `modelInvocable: true`
- Пометить команды, загруженные `BundledSkillLoader`, `FileCommandLoader` (пользователь/проект), как `modelInvocable: true`
- **MCP prompt не помечать как `modelInvocable`**: MCP prompt вызываются моделью через независимый механизм MCP tool call, не нуждаются в посредничестве `SkillTool`
- Преобразовать `SkillTool`: с потребления только `SkillManager.listSkills()` на одновременное потребление `CommandService.getModelInvocableCommands()`
- Построить единое описание вызываемых моделью команд, внедрить в description `SkillTool`

#### 2.3 Обнаружение mid-input slash command (базовая версия)

- В `InputPrompt` обнаружение slash token рядом с курсором (не только в начале строки)
- После обнаружения slash token через inline ghost text подсказать наилучшее совпадение имени команды (Tab принять)
- **Не** включать dropdown меню автозаполнения, argument hints, source badge и т.д. (Phase 3 делает)
- Набор кандидатов ghost text только команды с `modelInvocable: true` (skill / file command)

### Критерии приёмки

**2.1 Расширение команд**

- [ ] Класс A: `/copy`, `/export`, `/plan`, `/restore`, `/language`, `/statusline` могут нормально выполняться в режимах non-interactive и acp и возвращать осмысленный текстовый вывод
- [ ] Класс A': `/model`, `/approval-mode` без аргументов в non-interactive/acp возвращают текст текущего состояния (не запускают dialog); с аргументами выполняют изменение и возвращают текст подтверждения
- [ ] Класс B: `/about`, `/stats`, `/docs` в non-interactive/acp возвращают чистый текст, `/docs` не открывает браузер; `/insight` в `non_interactive` синхронно генерирует и возвращает message с путём файла, в `acp` через `stream_messages` отправляет прогресс
- [ ] Класс C: `/clear` в non-interactive/acp возвращает message с маркером границы контекста, не вызывает `context.ui.clear()`
- [ ] Все расширенные команды в режиме interactive ведут себя полностью согласованно с до рефакторинга (нет регрессии)

**2.2 Вызов модели**

- [ ] Модель может вызывать bundled skill, file command (пользователь/проект) через `SkillTool`
- [ ] MCP prompt не проходят через `SkillTool`, вызываются моделью нативно через механизм MCP tool call
- [ ] Модель не может вызывать built-in commands (`userInvocable: true`, `modelInvocable: false`)
- [ ] description `SkillTool` содержит описание всех команд `modelInvocable`

**2.3 mid-input slash**

- [ ] mid-input slash: после ввода `/` в теле текста inline ghost text подсказывает наилучшее совпадение команды (Tab принять)

## Phase 3: Выравнивание опыта (улучшение автозаполнения + дополнение команд Claude Code)

### Цели

На основе метаданных и возможностей команд Phase 1/2 дополнить опыт автозаполнения и дополнить команды, существующие в Claude Code и отсутствующие в Nessy CLI.

### Функциональные точки

#### 3.1 Улучшение опыта автозаполнения

**source badge**

- Отображать метку источника команды в меню автозаполнения (`[MCP]` уже есть, расширить до `[Skill]`, `[Custom]` и т.д.)
- Использовать поля `source` / `sourceLabel` для рендеринга

**argument hint**

- Отображать `argumentHint` после имени команды в меню автозаполнения (например, `set <model-id>`)
- Поле `argumentHint` предоставляется метаданными Phase 1

**сортировка recently used**

- Записывать недавно использованные команды пользователем (уровень session, без персистентности)
- Взвешивать недавно использованные команды в сортировке автозаполнения

**подсветка совпадения alias**

- При совпадении автозаполнения `altNames`, а не основного имени, указать в отображении (например, `help (alias: ?)`)

**выравнивание стратегии конфликтов**

- Явно определить приоритет: built-in > bundled/skill-dir > plugin > mcp
- При конфликте переименовать команду с низким приоритетом (например, `pluginName.commandName`)

#### 3.2 Полная версия mid-input slash command

- Добавить argument hints и отображение source badge к базовой версии Phase 2
- Подсказка ghost text (при вводе `/he` отображать бледную подсказку `/help`)
- Подсветка действительных токенов команд (завершённое совпадение slash command отображается другим цветом)

#### 3.3 Рефакторинг каталога Help

Преобразовать `/help` из плоского списка в группированный каталог:

- **Built-in Commands** (local + local-jsx, отметить режим)
- **Bundled Skills**
- **Custom Commands** (пользователь/проект file commands)
- **Plugin Commands**
- **MCP Commands**

Каждая команда отображает: имя, argumentHint, description, source, метку supportedModes

#### 3.4 Усиление метаданных ACP available commands

В `sendAvailableCommandsUpdate()` Предоставить больше метаданных клиенту ACP:

- `argumentHint`
- `source`
- `supportedModes`
- `subcommands` (список имён)
- `modelInvocable`

#### 3.5 Дополнение отсутствующих команд Claude Code

Дополнить команды, отсутствующие в текущем Nessy CLI, но существующие в Claude Code и часто используемые:

| Команда          | Тип     | Описание                                                                                  |
| ---------------- | ------- | ----------------------------------------------------------------------------------------- |
| `/doctor`        | `local` | Самопроверка окружения, вывод диагностики конфигурации/подключения/состояния инструментов |
| `/release-notes` | `local` | Показать changelog текущей версии                                                         |
| `/cost`          | `local` | Показать потребление токенов и оценку расходов текущей session                            |

> Заметка: команды типа `/review`, `/commit` предоставляются в виде bundled skill, не в этом списке.

### Критерии приёмки

- [ ] Меню автозаполнения отображает source badge (`[MCP]`, `[Skill]`, `[Custom]`)
- [ ] Меню автозаполнения отображает argumentHint (например, `set <model-id>`)
- [ ] Недавно использованные команды приоритетно появляются в списке автозаполнения
- [ ] При совпадении alias указать оригинальное имя в элементе автозаполнения
- [ ] mid-input slash: подсказка ghost text правильно рендерится
- [ ] Вывод `/help` сгруппирован по источнику, каждая команда отображает метку поддерживаемых режимов
- [ ] ACP available commands содержит поля `argumentHint`, `source`, `subcommands`
- [ ] Команды `/doctor`, `/release-notes`, `/cost` доступны
- [ ] `/doctor` может выполняться в режиме non-interactive (возвращает `message`)

## Зависимости между Phase

```
Phase 1 (метаданные + единая фильтрация)
    │
    ├──► Phase 2 (расширение возможностей)
    │        │
    │        ├──► Разбиение подкоманд slash command
    │        └──► Вызов модели prompt command (требует getModelInvocableCommands())
    │
    └──► Phase 3 (выравнивание опыта)
             │
             ├──► source badge (требует поля source Phase 1)
             ├──► argument hint (требует поля argumentHint Phase 1)
             └──► Группировка Help (требует поля source Phase 1)
```

Phase 2 и Phase 3 не зависят друг от друга, могут продвигаться параллельно (или менять порядок некоторых подпунктов в зависимости от приоритета).
