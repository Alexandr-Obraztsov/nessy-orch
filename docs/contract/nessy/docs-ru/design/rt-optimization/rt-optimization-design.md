# Техническое решение по оптимизации RT агентского цикла Nessy CLI

## 1. Предпосылки и определение проблемы

### 1.1 Текущее состояние

Агентский цикл Nessy CLI представляет собой строго последовательную модель:

```
User Prompt → [LLM решение] → Выполнение инструмента → [LLM решение] → Выполнение инструмента → ... → [LLM ответ] → Idle
               ~3-4s          ~Xms-Ns          ~3-4s          ~Xms-Ns            ~3-4s
```

Каждый вызов LLM (включая сетевой RTT + логический вывод модели) занимает около 3-4 секунд и является основным компонентом задержки end-to-end.

### 1.2 Измеренные данные

Сценарий тестирования: "Какие у меня есть рабочие пространства" (3 цикла агентского цикла, 2 вызова инструментов, одна выборка)

| Этап                              | Время    | Доля |
| --------------------------------- | -------- |------|
| LLM цикл 1 (решение вызвать skill) | 3.8s     | 28%  |
| Выполнение skill                  | 1ms      | \<1% |
| LLM цикл 2 (решение вызвать shell) | 3.0s     | 22%  |
| Выполнение shell                  | 2.5s     | 19%  |
| LLM цикл 3 (текстовое резюме)     | 3.8s     | 28%  |
| Накладные расходы фреймворка (синхронизация состояния, рендеринг) | 0.3s     | 3%   |
| **Итого**                         | **13.4s** | 100% |

**Вывод**: Вызовы LLM занимают 78%, выполнение инструментов 19%, фреймворк 3%. Ключевая оптимизация — **сокращение количества вызовов LLM** и **снижение задержки одного вызова LLM**.

> Примечание: однократная выборка, единственный сценарий. 19% выполнения инструментов определяются медленным вызовом shell; в сценариях с преобладанием чтения доля инструментов может снижаться до \<5%. Перед внедрением решения необходимо дополнить базовые метрики ≥3 категориями сценариев (операции записи, логический вывод с участием нескольких инструментов, восстановление после ошибок).

### 1.3 Ключевые ограничения текущей архитектуры

| Ограничение                     | Расположение в коде                                                                                   | Описание                                                                             |
| ------------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Отсутствие пост-обработки результатов инструмента | `tools.ts` интерфейс `ToolResult` (L422)                                                        | Только `llmContent`/`returnDisplay`/`error`, невозможно выразить "пропустить LLM"                    |
| Безусловная передача результатов в LLM | `useGeminiStream.ts` `handleCompletedTools` (L2038) → `submitQuery(ToolResult, …)` (L2355) | Все результаты инструментов, инициированных gemini, передаются обратно                                             |
| Планирование только после завершения потока | `useGeminiStream.ts` `processGeminiStreamEvents` (L1365)                                   | После завершения цикла потока выполняется `scheduleToolCalls`, инкрементальное планирование отсутствует                              |
| Отсутствие уровня стратегии выбора модели | `client.ts` `modelOverride ?? getModel()` (L1305, Л1598)                                   | Инфраструктура доведена до `turn.run(model, …)` (L1707), но вызывающая сторона использует явное указание модели только в skill |

### 1.4 Готовая инфраструктура (широко используется в данном решении)

| Возможность                                          | Расположение                                                   | Текущее состояние                                                                   |
| ---------------------------------------------------- | ------------------------------------------------------ | ---------------------------------------------------------------------- |

**Ключевой пробел**: **Отсутствует продакшен-код**, использующий fast-модель для потоковой обработки в основном чате. Данное решение (D2) станет первым случаем, требуется предварительная валидация (см. §3.2 Предварительные условия).

## 2. Принципы проектирования

1. **Универсальность**: решение не привязано к конкретному инструменту/skill
2. **Обратная совместимость**: существующие инструменты продолжают работать без модификаций
3. **Прогрессивность + явные сигналы**: стратегия по умолчанию консервативна, оптимизация включается явно через поля от авторов инструментов
4. **Возможность отката**: все оптимизации управляются feature flag; пользователь может принудительно отключить
5. **Честный компромисс**: явно обозначены риски качества, риски стоимости и границы применимости

## 3. Решение по оптимизации

### 3.1 Направление 1: Директивы пост-выполнения инструмента (ToolResult Post-Execution Directive)

#### Проблема

Текущий `ToolResult` не содержит информации о том, "что делать дальше". Независимо от того, является ли результат инструмента самодостаточным, всегда запускается следующий цикл LLM.

#### Проектирование

Расширение интерфейса `ToolResult` (`packages/core/src/tools/tools.ts` L422):

```typescript
export interface ToolResult {
  llmContent: PartListUnion;
  returnDisplay: ToolResultDisplay;
  error?: { message: string; type?: ToolErrorType };

  // Новое: директивы пост-выполнения
  postExecution?: {
    /**
     * Результат инструмента не передаётся в LLM, отображается как финальный ответ пользователю.
     * Применимо для сценариев, где результат полностью самодостаточен и не требует интерпретации моделью.
     * Является локальным свойством ToolResult.
     */
    skipLlmRound?: boolean;

    /**
     * Результат инструмента "самодостаточен и готов к показу пользователю" — то есть `returnDisplay` уже находится в
     * форме, которую пользователь ожидает увидеть, без дополнительной обработки моделью.
     * Является локальным свойством ToolResult, **не** предсказывает "будет ли следующий цикл summary".
     * Связано с направлением 3 (разделение отображения): true → переход в состояние Summarizing разрешает ввод пользователя.
     */
    resultIsTerminal?: boolean;
  };
}
```

> **Исправление дизайна**: Ранние версии использовали единое поле `selfExplanatory`, выполнявшее одновременно обязанности "атрибут продукта инструмента" и "сигнал прогноза потока диалога", но эти обязанности не совпадают (пример: пользовательский промпт "прочитай X затем исправь Y", результат read_file самодостаточен, но следующий цикл очевидно не summary). **Сигнал прогноза — глобальное свойство потока диалога**, не должно выражаться через поле инструмента — D2 полностью заменён на эвристику потока диалога (см. §3.2).

#### Изменение поведения

В `handleCompletedTools` добавляется проверка:

```
Завершена партия инструментов
  → Проверить postExecution.skipLlmRound у всех инструментов в партии
  → Все равны true?
    → YES: markToolsAsSubmitted, не вызывать submitQuery, перейти в idle
    → NO: сохранить текущее поведение (submitQuery)
```

**Важное ограничение**: `skipLlmRound` действует только когда **все инструменты в текущей партии объявили skip**. Смешанные партии по-прежнему передаются в LLM.

#### Историческая инвариантность

После пропуска LLM история имеет вид: `user → function_call → function_response → <нет assistant>`.

- Проверить `repairOrphanedToolUseTurnsInHistory` (вызывается при загрузке сессии) на толерантность к этой форме
- Проверить поведение auto-compaction при отсутствии assistant-текста
- PR #4176 только что закрыл инвариант tool_use↔tool_result, перед внедрением требуется добавить модульные тесты для "пользовательского сообщения после пропуска skip"
- API Nessy / OpenAI толерантны; Anthropic требует строгого чередования — при будущей прямой поддержке Anthropic потребуется заглушка (вставка пустого assistant-текста в историю)

> **Единая точка исправления**: Здесь и в §3.3 (D3 прерывание Summarizing на полпути) нарушается **одна и та же историческая инвариантность**. Решение выбирается одно из двух (вставка пустого assistant / принятие толерантности Nessy), оба направления должны использовать одинаковый выбор.

#### Экосистема сигналов (работа Phase 2)

| Инструмент                          | `skipLlmRound`       | `resultIsTerminal` | Примечания                                                            |
| ----------------------------------- | -------------------- | ------------------ | --------------------------------------------------------------------- |
| `read_file`                           | в сочетании со сценарием только-чтение | true               | Содержимое файла уже является ответом                                                  |
| `cat` (через shell)                    | зависит от сценария               | true               | Аналогично read_file                                                    |
| `grep` / `glob` / `ls`                | false                | **false (по умолчанию)**  | Результаты часто требуют отбора/сортировки/суммаризации моделью; skill-слой явно устанавливает true для сценариев "чистый запрос" |
| `git status` / `git log` (через shell) | false                | true               | Вывод уже отформатирован                                                    |
| Инструменты Skill                            | на усмотрение каждого skill        | на усмотрение каждого skill      | Skill-ы для запросов склоняются к true                                          |
| Инструменты MCP                              | по умолчанию false           | по умолчанию false         | Явное включение через allowlist                                      |

Сторонние/MCP инструменты не доверяются, по умолчанию не маркируются; явное включение через `config.toolPostExecAllowlist`.

> `grep/glob/ls` по умолчанию false — строгий выбор: избегаем ошибочного срабатывания D2/D3 в сценариях, требующих суммаризации/сортировки моделью.

#### Применимость

- **Применимо**: финальные запросы (тип read/cat/print), самодостаточные результаты (skill уже отформатировал вывод)
- **Не применимо**: промежуточные шаги многошаговых задач, подтверждение операций записи, сложные логи требующие интерпретации

#### Риски и снижение

| Риск                                       | Серьёзность | Снижение                                       |
| ------------------------------------------ | ------ | ------------------------------------------ |
| Ошибочная установка skipLlmRound инструментом приводит к прерыванию многошаговой задачи | Средняя     | Семантика уровня партии + llmContent остаётся в истории для восстановления |
| Злоупотребление сторонними инструментами                             | Средняя     | MCP по умолчанию отключён, явное включение через allowlist           |
| Нарушение исторической инвариантности                             | Средняя     | Добавить модульные тесты перед внедрением; покрытие повторного воспроизведения session-load        |
| Несоответствие ожиданиям пользователя (ожидается суммаризация, но её нет)           | Низкая     | Настройка `alwaysSummarize: true` может переопределить     |

#### Выгода

Экономия 3-4 секунды в сценариях финального запроса (пропуск последнего цикла LLM).

### 3.2 Направление 2: Стратегия маршрутизации fast-model для цикла summary

#### Позиционирование

**Данное направление не вводит новых каналов, но требует расширения интерфейса GeminiChat для поддержки переключения модели во время выполнения**.

Инфраструктура из §1.4 предоставляет конфигурацию fast-модели и сквозную интеграцию modelOverride, но **отсутствует прецедент использования fastModel + streaming в основном чате**, требуется:

- Функция принятия решений: когда передавать `config.getFastModel()` как override
- Безопасный откат: новый интерфейс `GeminiChat.retryStreamWithModel` (обрабатывает внутреннее состояние чата)
- Экспериментальная проверка: переключение основного чата fast/primary не нарушает compaction / history-recording

#### Область применения

D2 действует только для:

- **useGeminiStream** (основной путь TUI) — вызов sendMessageStream L1841
- **ACP Session** (путь интеграции IDE) — `acp-integration/session/Session.ts:1182`, синхронное изменение в Phase 3

D2 **не действует** для следующих путей, чтобы избежать дополнительных режимов отказа в неинтерактивных или изолированных контекстах:

- **Subagent runtime** (`agents/runtime/agent-core.ts:614`): дочерний агент уже имеет собственную конфигурацию модели
- **Cron trigger turn** (`SendMessageType.Cron`, client.ts:127): неинтерактивный, без срочности по RT
- **Notification turn** (`SendMessageType.Notification`, client.ts:129): аналогично

#### Ключевые сложности

Во время вызова `submitQuery` **мы не знаем**, решит ли модель после просмотра результатов вызвать новый инструмент или сразу выдать текст. Если использовать fast-модель, а модель фактически потребует ещё инструменты — последствием будет **молчаливая ошибка**: fast может вызвать неправильный инструмент или с неверными параметрами, ошибка не получит явных сигналов.

**Любые поля уровня инструментов не могут надёжно предсказать** "будет ли следующий цикл summary", поскольку это зависит от потока диалога (пользовательский промпт + накопленный контекст), а не от локальных свойств продукта инструмента. Пример:

```
Пользователь: "прочитай utils.ts затем замени все console.log на logger.info"
  → Инструмент 1: read_file → результат самодостаточен
  → Но следующий цикл очевидно не summary
```

Поэтому D2 полностью использует **эвристику потока диалога** для прогнозирования, не полагаясь на поля инструментов.

#### Функция принятия решений: эвристика потока диалога + вето

```typescript
import { Kind, MUTATOR_KINDS } from '../tools/tools.js';

function selectContinuationTier(
  turn: Turn,
  userPrompt: string,
  batch: ToolCall[],
): 'fast' | 'primary' {
  // ===== Переключатель уровня пользователя (наивысший приоритет) =====
  const userPref = config.getSummaryTierStrategy();
  if (userPref === 'always_primary') return 'primary';
  if (userPref === 'always_fast') return 'fast'; // всё ещё подчиняется страховке времени выполнения

  // ===== Вето намерения пользователя =====
  // 1. Пользовательский промпт содержит глаголы действия → следующий цикл вероятно потребует ещё инструменты
  if (requestImpliesFurtherAction(userPrompt)) return 'primary';

  // 2. В текущей партии есть инструменты-мутаторы → высокая вероятность последующей проверки/чтения
  if (batch.some((c) => MUTATOR_KINDS.includes(c.tool.kind))) return 'primary';

  // 3. В текущей партии или истории есть нерешённая ошибка → модели требуется primary для диагностики
  if (hasUnresolvedError(turn.toolResults, batch)) return 'primary';

  // ===== Вето сложности вывода =====
  // 4. Пользовательский промпт требует глубокого анализа (объяснить/сравнить/почему)
  if (needsDeepReasoning(userPrompt)) return 'primary';

  // 5. Вызовов инструментов ≥3 различных инструментов → повествование по результатам требует primary
  if (needsCrossResultReasoning(turn)) return 'primary';

  // 6. Слишком длинный вывод инструментов → суммаризация длинного контента требует primary
  if (estimateTotalToolOutputTokens(turn) > 4000) return 'primary';

  // ===== Вето осуществимости модели =====
  // 7. Окно контекста fast-модели недостаточно → переключение на fast вызовет compression
  //    (compression сам требует вызова LLM, замедляя и увеличивая стоимость)
  if (wouldTriggerCompression(turn.history, config.getFastModel()))
    return 'primary';

  // ===== Многоязычная страховка =====
  if (!isPromptLanguageSupported(userPrompt)) return 'primary';

  // ===== Страховка состояния сессии =====
  if (turn.justCompacted || turn.justCleared) return 'primary';

  return 'fast';
}
```

Восемь пунктов вето означают:

- **`requestImpliesFurtherAction`**: глаголы действия (`изменить | удалить | добавить | заменить | исправить | реализовать | создать | create|fix|change|add|remove|implement|write|update`) → многошаговая задача
- **Попадание в `MUTATOR_KINDS`**: в текущей партии уже были записи → высокая вероятность последующего чтения/проверки.**Использовать существующий `tools.ts:806` `MUTATOR_KINDS = [Edit, Delete, Move, Execute]`** (свойство `kind: Kind` каждого экземпляра Tool — авторитетная классификация, не изобретать заново `isWriteTool`)
- **`hasUnresolvedError(turnResults, currentBatch)`**: двухэтапное определение —
  - **Любая ошибка в текущей партии → всегда нерешена** (не предполагаем, что параллельные партии могут самокорректироваться)
  - **История дедуплицируется по `(toolName, args fingerprint)`, последняя остающаяся ошибка считается нерешённой** (только по toolName при одинаковом имени но разных параметрах будет ошибочное определение)
  - shell и т.д. должны корректно заполнять `ToolResult.error` (зависимость от качества предварительных данных)
- **`needsDeepReasoning`**: содержит ключевые слова "анализ/объяснить/почему/сравнить/диагностика"
- **`needsCrossResultReasoning`**: различных вызовов инструментов ≥3 (одинаковый инструмент с одинаковыми параметрами считается одним вызовом)
- **Вывод tokens > 4000**: эмпирический порог, **подлежит корректировке после фактических измерений fast-модели**
- **`wouldTriggerCompression`**: окно контекста fast-модели обычно меньше primary, одинаковая history на fast раньше вызовет `tryCompress` (geminiChat.ts:1418) — compression сам требует вызова LLM, может **обратно ухудшить RT и стоимость**. Оценка бюджета: `estimateHistoryTokens(history) > fastModelContextWindow × COMPACTION_THRESHOLD` считается триггером
- **Неподдерживаемый язык**: обнаруживаются только китайские и английские ключевые слова, другие языки (японский, корейский и т.д.) по умолчанию primary
- **Мутация состояния сессии**: первый continuation после `/compact` или `/clear` → primary для восстановления mental model

Направление вето **смещено в сторону primary** (лучше лишние 2с чем ухудшение качества).

#### Ключевая реализация: `GeminiChat.retryStreamWithModel`

**Проблема**: прямой abort + вызов `client.sendMessageStream` нарушает состояние чата:

1. `geminiChat.ts:1428` при запуске stream push'ит `userContent` в историю; перезапуск приведёт к **повторному push** и появлению дубликатов `function_response` в истории
2. Блокировка `sendPromise` (`geminiChat.ts:1392, 1398`) — после abort необходимо убедиться, что `streamDoneResolver` вызван
3. Маркер инвариантности PR #4176 `pendingPartialState` требует правильной очистки
4. Атрибут model telemetry span требует обновления

**Новый интерфейс** (`packages/core/src/core/geminiChat.ts`):

```typescript
/**
 * Повторить потоковую отправку, находящуюся в полёте или только что прерванную, с другой моделью.
 * НЕ делает повторный push userContent (сохранён из оригинальной отправки).
 * Сбрасывает pendingPartialState; освобождает stale sendPromise; повторно открывает span.
 */
async retryStreamWithModel(
  model: string,
  signal: AbortSignal,
): Promise<AsyncGenerator<StreamEvent>>;
```

Контракт вызова:

- Вызывать только после abort оригинальной отправки (не параллельно)
- prompt_id переиспользуется (одно и то же намерение пользователя)
- Уже push'нутый в историю userContent не push'ится повторно

Объём реализации около 1.5 дней с модульными тестами.

#### Страховка времени выполнения

`selectContinuationTier` возвращает `'fast'` но в stream появляется событие `ServerGeminiEventType.ToolCallRequest` → **немедленно abort текущего потока, вызвать `retryStreamWithModel(primaryModel)`**.

Это покрывает единственный сценарий молчаливой ошибки "прогноз как summary фактически требует инструментов". Цена: wastage tokens одного вызова fast (отнесение стоимости см. §5.3).

#### Развязка с skill `modelOverride`

`useGeminiStream.modelOverrideRef` (L376, L2225) в настоящее время несёт **явно выбранную модель skill**, относится к "бизнес-семантике". Маршрутизация fast данного направления относится к "оптимизационной семантике", они **должны быть разделены**:

```typescript
// Новый независимый ref
const summaryTierRef = useRef<'fast' | 'primary' | undefined>(undefined);

// Объединение в точке вызова (не повторно используя modelOverrideRef)
const stream = geminiClient.sendMessageStream(
  finalQueryToSend,
  abortSignal,
  prompt_id!,
  {
    type: submitType,
    notificationDisplayText: metadata?.notificationDisplayText,
    modelOverride:
      modelOverrideRef.current ?? // явный выбор skill приоритетен
      (summaryTierRef.current === 'fast' ? config.getFastModel() : undefined),
  },
);
```

Жизненный цикл:

| Момент                                       | `modelOverrideRef` (skill) | `summaryTierRef` (маршрутизация fast)            |
| ------------------------------------------ | --------------------------- | ---------------------------------------- |
| Новый user turn (`!Retry && !ToolResult`)     | Очистка                        | Очистка                                     |
| Skill инструмент возвращает поле `modelOverride`        | Запись                        | Без изменений                                     |
| Завершение партии инструментов → `selectContinuationTier` | Без изменений                        | Запись                                     |
| Runtime fallback (увидел ToolCallRequest)   | Без изменений                        | Повышение до `'primary'`                       |
| Retry (пользователь вручную Ctrl+Y)                   | Сохранение                        | Повышение до `'primary'` (fast неудачен больше не fast) |

Явный выбор skill **всегда выигрывает** — явное намерение пользователя приоритетно стратегии оптимизации.

#### Исправление Telemetry

`client.ts:1303` interaction span записывает свойство `model` при запуске turn. При срабатывании fallback модель фактически меняется, данные span искажаются. Требуется:

```typescript
// при срабатывании fallback
span.setAttribute('llm.model.requested', fastModel);
span.setAttribute('llm.model.actual', primaryModel);
span.setAttribute('llm.fallback.reason', 'tool_call_seen');
```

и в `addUserPromptAttributes` различать модели `requested` / `actual`, избегая путаницы биллинга/аудита.

#### Принудительный переключатель уровня пользователя

Добавить настройку (`packages/cli/src/config/settingsSchema.ts`):

```typescript
summaryTierStrategy: 'auto' | 'always_primary' | 'always_fast';
// по умолчанию: 'auto'
```

- `'auto'`: использовать `selectContinuationTier` (рекомендуется)
- `'always_primary'`: полностью отключить оптимизацию D2 (чувствительные продакшен-сценарии)
- `'always_fast'`: пропустить вето, **всё ещё подчиняется страховке времени выполнения** (продвинутые пользователи)

Обоснование: D2 — качество в обмен на скорость, некоторым пользователям/сценариям требуется явное право выхода.

### 3.3 Направление три: Развязка представления результатов и взаимодействия (Presentation Decoupling)

#### Проблема

Пользователь от завершения инструмента до возможности повторного ввода должен ждать завершения цикла резюме LLM:

```
Завершение инструмента → [Рендеринг результатов] → [submitQuery] → [Ожидание потокового ответа LLM 3-4s] → Idle → Можно вводить
                                         ~~~~~~~~~~~~~~~~~~~~~~~~
                                         Пользователь уже видит результат, но не может оперировать
```

#### Дизайн

Добавить новое состояние `StreamingState.Summarizing`:

```typescript
export enum StreamingState {
  Idle = 'idle',
  Responding = 'responding',
  WaitingForConfirmation = 'waiting_for_confirmation',
  Summarizing = 'summarizing', // Новое
}
```

#### Изменения конечного автомата

```
Завершение инструмента и результаты уже показаны
  → Если batch все postExecution.resultIsTerminal === true:
    → Перейти в Summarizing (пользователь может вводить)
    → submitQuery асинхронно выполняется
    → Резюме LLM добавляется в history (или отменяется новым сообщением пользователя)
  → Иначе:
    → Оставаться в Responding (пользователь не может вводить)
```

#### Обработка нового сообщения пользователя

- В состоянии `Summarizing` пользователь отправляет новое сообщение → abort текущего резюме → обработка нового сообщения
- Сгенерированный **частичный текст резюме отбрасывается** (не попадает в history), избегать загрязнения контекста наполовину assistant
- `function_response` остается в history (модель знает, что инструмент выполнен)
- followup suggestion срабатывает после завершения Summarizing или отмены

#### Чеклист очистки partial text при Abort

partial text распределен в нескольких местах, требуется **одновременная** очистка, отсутствие одного приведет к несогласованности состояния:

| Позиция                                                           | Действие очистки                                                                                  |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `pendingHistoryItemRef.current` (useGeminiStream React state) | Установить `null`, не вызывать `addItem`                                                                 |
| `GeminiChat.history` внутреннее накопление                                  | abort перед если уже push часть assistant content, требуется новый интерфейс `discardPendingAssistant()` откат |
| `ChatRecordingService` buffered turn                           | Пометить как cancelled, не записывать в JSONL                                                            |
| `dualOutput.emitText` (если включено)                                | Отправить abort sentinel, sidecar самостоятельно отбрасывает                                                     |
| `loopDetectorRef` накопление token                                   | Сбросить счетчик текущего turn                                                                        |

Порядок выполнения: срабатывание abort signal → собрать все пять очисток → только затем разрешать новому user message войти в `submitQuery`. Race тест покрытие: срабатывание abort в момент получения последнего chunk.

#### Условия применения

batch все `postExecution.resultIsTerminal === true`.

#### Инварианты history (общие с §3.1)

Прерывание Summarizing на полпути создаст:

```
[user_1, function_call, function_response, user_2]
                                          ↑ нет assistant turn
```

**Это с §3.1 пропуск LLM цикла разрушает тот же инвариант**, требуется использовать ту же стратегию исправления D1 (инъекция пустого assistant / принятие терпимости Nessy).

- Повторное использование D1 инвариант unit test покрытие
- session-load воспроизведение (содержащий `repairOrphanedToolUseTurnsInHistory`) должен покрывать эту форму
- Anthropic alternation: прямое подключение одновременно с D1 добавить страховку

#### Риски и смягчения

| Риск                                | Серьезность | Смягчение                                                           |
| ----------------------------------- | ------ | -------------------------------------------------------------- |
| Abort при полфразы assistant попадает в history   | **Средняя** | Явно отбрасывать partial text; только сохранять function_response; unit test покрытие race |
| Нарушение инвариантов history (нет assistant продолжения) | **Средняя** | Общая с D1 проблема, унифицированное исправление (см. §3.1 инварианты history)                 |
| Сложность состояния UI увеличивается                   | Средняя     | Summarizing = Idle + фоновая задача; путь ввода повторное использование Idle               |
| Выгода восприятия пользователя зависит от паттерна поведения            | Низкая     | Пользователь если 3s не вводит, summary завершен → нет выгоды восприятия; но**не деградирует**  |

#### Выгода

- **Теоретический предел**: 3-4s восприятие RT (пользователь завершение инструмента сразу ввод)
- **Фактический медианный**: зависит от интервала ввода пользователя — читающий результаты 2-5s затем вводящий пользователь не почувствует разницу, но**никогда не будет медленнее**

### 3.4 Направление четыре: Потоковое предварительное планирование (Stream-Ahead Scheduling)

#### Проблема

`processGeminiStreamEvents` после полного завершения stream пакетно планирует инструменты. `ToolCallRequest` событие может уже yield в середине stream.

#### Дизайн

В обработке событий stream для `ToolCallRequest` немедленно начинать **предварительную валидацию** (не выполнение):

```typescript
case ServerGeminiEventType.ToolCallRequest:
  toolCallRequests.push(event.value);
  scheduler.prevalidate(event.value, signal);  // Новое
  break;
```

`CoreToolScheduler.prevalidate(request)`:

1. Поиск регистрации инструмента
2. Построение invocation
3. Выполнение `shouldConfirmExecute` (кэширование результата)
4. `schedule()` напрямую использовать кэшированный результат

#### Контракт чистоты и Allowlist

`prevalidate` требует `shouldConfirmExecute` быть side-effect-free **и** результат в промежутке между prevalidate→schedule не будет внешне модифицирован так, чтобы стать недействителен.

**Напрямую повторное использование `tools.ts:818` `CONCURRENCY_SAFE_KINDS`**:

```typescript
export const CONCURRENCY_SAFE_KINDS: ReadonlySet<Kind> = new Set([
  Kind.Read,
  Kind.Search,
  Kind.Fetch,
]);
```

Это проект уже имеет "без побочных эффектов + можно параллельно" классификацию, точно соответствует prevalidate требованию.

| Инструмент Kind                     | В allowlist        | Обоснование                                                    |
| ----------------------------- | ----------------------- | ------------------------------------------------------- |
| `Read` (read_file и т.д.)        | ✅                      | Чистое чтение                                                    |
| `Search` (grep / glob)       | ✅                      | Чистое чтение                                                    |
| `Fetch` (web_fetch и т.д.)       | ✅                      | Удаленное чтение, без записи побочных эффектов                                      |
| `Edit`                        | **❌** (см. TOCTOU ниже) | shouldConfirmExecute чисто только чтение, но diff в промежутке планирования может стать недействителен |
| `Delete` / `Move` / `Execute` | ❌                      | MUTATOR_KINDS                                           |
| `Think`                       | ❌                      | Содержит save_memory / todo_write и т.д. неявная запись                    |
| MCP инструменты                      | ❌                      | Ненадежный                                                  |

**TOCTOU: почему Edit не входит в allowlist**

Теоретически Edit `shouldConfirmExecute` чисто только чтение (чтение файла, расчет diff). Но между prevalidate и schedule существует временное окно:

```
T=0      stream получает Edit(file=a.ts, ...) → prevalidate
T=10ms   shouldConfirmExecute читает a.ts, кэширует diff_v0
T=300ms  stream завершен, scheduler.schedule()
T=305ms  В промежутке другие инструменты/IDE/внешний процесс модифицирует a.ts
T=310ms  scheduler использует diff_v0 показывает пользователю
T=320ms  Пользователь на основе v0 подтверждает
T=330ms  Edit применяет старые params к v1 файлу → содержание повреждено / merge неудача
```

Это TOCTOU. Направление исправления:

- **A (рекомендуется)**: Edit не входит в allowlist, prevalidate покрывает только `CONCURRENCY_SAFE_KINDS` три категории. Цена: выгода от "50-200ms (Edit доминирует)" падает до "50-100ms (только чтение категории)"
- **B (опциональное усиление)**: Edit входит в allowlist но кэш прикрепляет `(mtime, size, content_hash)`; schedule() проверка не изменилась затем использовать кэш, иначе пересчет

Документ временно выбирает A.

#### Взаимодействие с существующим параллельным планированием

`coreToolScheduler.attemptExecutionOfScheduledCalls` (L2436+) использует `partitionToolCalls` делит инструменты на "параллельно безопасный batch" и "последовательный batch", параллельный batch через `runConcurrently` (L2473) выполняется.

prevalidate должен выравниваться с этой моделью пакетирования:

- Кэш по индексу `callId` (не `(toolName, args)`, избегать параллельного вызова с тем же именем конфликта)
- prevalidate неудачный call → не влияет на другой call, когда этот call идет по оригинальному `shouldConfirmExecute` пути
- stream отмена по `signal` каскадно abort все in-flight prevalidate

#### Риски

| Риск                                       | Серьезность | Смягчение                                                                   |
| ------------------------------------------ | ------ | ---------------------------------------------------------------------- |
| Кэш diff и подтверждение фактический файл несовпадает (TOCTOU) | Высокая     | План A: Edit не входит в allowlist; План B: кэш прикрепляет `(mtime, size, hash)` проверка |
| prevalidate неудача влияет на планирование                   | Низкая     | Неудача/тайм-аут возвращается к оригинальному `shouldConfirmExecute` пути, кэш отсутствует ≡ не включено         |
| Параллельный prevalidate shared fd / ресурсная борьба        | Низкая     | `NESSY_CLI_MAX_TOOL_CONCURRENCY` уже ограничен параллельный верхний предел (по умолчанию 10)               |

#### Выгода

50-100ms/цикл (только `CONCURRENCY_SAFE_KINDS` диапазон). Если выбрать план B с Edit, теоретическая выгода 100-200ms.

### 5.4 Schema журнала решений

Ключевые решения `selectContinuationTier` и `handleCompletedTools` записываются в структурный журнал:

```
{
  turn_id, prompt_id,
  decision: 'skip' | 'fast' | 'primary',
  tier_requested: 'fast' | 'primary',          // решение (до fallback)
  tier_actual:    'fast' | 'primary',          // фактически запущено (после fallback)
  signal_skipLlmRound: bool,
  signal_resultIsTerminal: bool,
  user_strategy: 'auto' | 'always_primary' | 'always_fast',
  veto_reason: 'further_action' | 'write_tool' | 'unresolved_error' |
               'deep_reasoning' | 'cross_result' | 'output_tokens' |
               'lang_unsupported' | 'compact_or_clear' | null,
  tool_count, distinct_tool_count,
  has_write_tool: bool,
  has_error: bool, has_cancel: bool,
  output_tokens_est: int,
  user_prompt_classification: 'query' | 'action' | 'analysis',
  fast_ttft_ms, primary_ttft_ms,                // двойной при fallback
  fast_tokens_consumed: int,                    // wasted tokens fallback (атрибуция стоимости)
  total_rt_ms,
  fallback_triggered: bool,
  fallback_reason: 'tool_call_seen' | 'timeout' | 'error' | null,
}
```

Наблюдаемые метрики:

- Частота срабатывания fast (ожидаемая 30-50%)
- Частота fallback_triggered (ожидаемая \<10%; >20% указывает на необходимость отключения default flag в следующем release)
- Доля каждого veto (идентификация слишком строгий/слабый)
- fast_tokens_consumed × fallback_rate (риск обратной стоимости)
- Частота пользовательского follow-up "подробнее" (сигнал регрессии качества fast)

**Измерение `fast_tokens_consumed`**:

Прерванный abort stream **скорее всего не получит `finishReason` / `usageMetadata`** — последние заполняются только при полном завершении stream. Реализация должна оценить:

- Приоритет: попытаться `stream.return()` перед abort чтобы генератор прошел finally путь, возможно получится partial usage
- Fallback: накопленная длина текста уже полученных chunk × 4 оценка output tokens; input tokens оценка по history
- Метка: поле журнала с `tokens_source: 'usage' | 'estimated'`, последующий анализ требует разделения

### 5.5 Метод валидации и стратегия выпуска

#### Валидация

- Повторное использование фреймворка тайминга `/tmp/tool-timing.log`
- Добавление `T_userIdle` (момент когда пользователь может снова вводить)
- Добавление `T_firstToken` (момент первого token потока)
- A/B тестирование сравнение распределения RT и cost до/после каждого Phase

#### Стратегия выпуска (адаптировано для локального CLI)

Nessy CLI — локальный CLI, **нет возможности runtime развертывания** — традиционное"5% / 25% / 100% gradual rollout"не применимо. Используется**поэтапное продвижение release**:

| Этап                  | Узел Release           | Значение feature flag по умолчанию | Условие срабатывания                                                                    |
| --------------------- | ---------------------- | ------------------- |-----------------------------------------------------------------------------------------|
| Phase 3a: dogfood     | Release N              | `false`             | Внутренние пользователи самостоятельно включают через `summaryTierStrategy=always_fast` |
| Phase 3b: opt-in по умолчанию | Release N+1 (≥2 недели спустя) | `false` (без изменений)     | decision журнал dogfood этапа соответствует: fallback \<10%, чистая выгода RT/cost >0   |
| Phase 3c: включено по умолчанию    | Release N+2 (≥4 недели спустя) | `true`              | Phase 3b пользователи не сообщают о регрессии качества                                  |
| Откат                  | Release N+3 (если требуется)    | `true → false`      | Массовый fallback >20% или деградация метрик качества                                   |

**Механизм отката**:

- Нет runtime развертывания, **откат = выпуск нового release с выключенным default flag**
- Пользовательский уровень `summaryTierStrategy=always_primary` всегда предоставляет"мне нужно немедленно выйти"канал, не зависит от нового release
- `fallback_rate` / `cost_regression` журнала решений оценивается в каждом цикле Release, определяет следующий шаг

### 5.6 Известные ограничения

1. **Базовые данные единичны**: однократная выборка не может покрыть все режимы задач, перед внедрением требуется дополнить сценарии
2. **Предпосылка fast модели**: не существует значительно более быстрой модели того же семейства с соответствующим tool-calling → D2 не включается
3. **`skipLlmRound` — качество в обмен на скорость**: пропуск LLM = отказ от понимания и исправления моделью, применимо только для сценариев с высокой определенностью
4. **D2 — качество+стоимость в обмен на скорость**: качество fast model ниже primary; fallback путь наоборот дороже — необходимо измерять чистую выгоду через decision журнал
5. **`tryCompress` может обратно ухудшить**: fast model context меньше, compression сам требует вызова LLM — `wouldTriggerCompression` gate является обязательной защитой
6. **Развязка отображения изменяет интерактивную модель**: новый режим требует адаптации пользователя; фактическая выгода восприятия определяется поведением пользователя
7. **Сетевая задержка неконтролируема**: это решение уменьшает количество вызовов, не оптимизирует единичный вызов
8. **Anthropic прямое подключение не покрыто**: текущая tolerancy alternation зависит от Nessy / OpenAI стиль API
9. **Основной чат на fastModel-streaming — первое внедрение**: нет production прецедента, требуется независимый эксперимент валидации
10. **Локальный CLI без runtime развертывания**: стратегия выпуска может только поэтапно продвигаться, не поддерживает быстрое gradual регулирование
11. **D2 действует только на интерактивный путь**: Subagent / Cron / Notification не получают выгоду, намеренно так
12. **Долгосрочное влияние смешанной модели history неизвестно**: после включения D2 turn в сессии переключаются между fast/primary, длительные сессии resume и согласованность контекста требуют наблюдения
13. **Выгода D4 сокращается**: после выхода Edit из allowlist, prevalidate покрывает только инструменты чтения (50-100ms выгода); 200ms выгода с Edit требует сценарий B механизма проверки mtime/hash

### 6.2 Находка 1: Эвристика `hasUnresolvedError` имеет 32% слепую зону инструментов (влияет на D2)

**Факт**: Из 22 инструментов с путями обработки ошибок **15 (68%) штатно заполняют поле `ToolResult.error`** (shell, read-file, write-file, edit, grep, glob, ls, web-fetch, mcp-tool, cron-\* и другие ключевые I/O инструменты в наличии), **7 (32%) помещают ошибку только в строку `llmContent`**: `askUserQuestion`, `monitor`, `skill`, `lsp`, `exitPlanMode`, `todoWrite` и т.д.

**Не существует** единого helper'а `createErrorResult`, каждый инструмент реализует конструирование ошибки независимо.

**Влияние на дизайн**:

- Если §3.2 вето пункт `hasUnresolvedError` проверяет только поле `ToolResult.error`, то **ошибки этих 7 инструментов никогда не запустят "переключение на primary"** — следующий цикл всё равно будет маршрутизирован на fast model
- **Ошибки инструмента `skill` ошибочно суммируются fast model** — это риск-сценарий с высоким приоритетом (затрагивает множество workflow, управляемых skill в этом репозитории)
- Перечисленное в §3.2 "shell и другие инструменты должны корректно заполнять `ToolResult.error` (предзависимость качества данных)" **слишком узко** — shell на самом деле уже стандартизирован, реально пропускаются skill / lsp / todoWrite и другие

**Рекомендуемая правка**: Внести **"преобразование 7 инструментов, передающих ошибку только через `llmContent`, в стандартное заполнение поля `error`"** в жёсткую предзависимость D2 (§3.2 Предусловия), оценка ~2 дня; не принимать грязный путь "заглушка через `llmContent.match(/^Error:/i)`" (высокий риск ложных срабатываний).

### 6.3 Находка 2: Стоимость реализации метрики `fast_tokens_consumed` недооценена (влияет на D2 / §5.3)

**Факт**:

- Путь abort в `turn.ts` (L289-291) напрямую делает `return`, **нет блока finally, нет вызова `stream.return()`** — подразумеваемый в §5.4 дизайн-документом путь "перед abort `stream.return()` заставляет генератор пройти finally" в текущем коде не существует
- Цикл `for await` в `geminiChat.ts:processStreamResponse` записывает turn только при полном обходе (L1286), прерывание abort означает, что финальный chunk только с usage (обычно несущий полные metadata) **прямо отбрасывается**
- Основной путь чата **не имеет никакой подушки накопления token на уровне chunk**; только subagent-слой (`agent.ts:731-744`) имеет накопление, невозможно переиспользовать
- Вывод: при abort `usageMetadata` **не получается вообще**, можно полагаться только на оценку `chars/4` (погрешность ±20%)

**Влияние на дизайн**:

- Путь "приоритет" в конце §5.4 схемы "приоритет / подушка / пометка" **недостижим в текущем коде** — сначала нужно изменить структуру генератора `sendMessageStream`, добавив finally, объём работ около 1 дня, дизайн-документ не учитывает эту стоимость
- §5.3 ставит "стоимость на тысячу сессий token \<70%" как цель Phase 3, но если сама метрика имеет погрешность ±20%, то **"70%" и "82%" попадают в шум измерения**

**Рекомендуемая правка**:

- §5.3 переписать как **тренд-метрику**, не использовать как gate релиза; вместо этого использовать "комбинированную оценку по двум метрикам: частота `fallback_triggered` в журнале решений + однонаправленный тренд `fast_tokens_consumed`"
- §5.4 дополнить: реализация `fast_tokens_consumed` требует сначала переделать путь abort в turn.ts, добавив finally + `stream.return()`, как дополнение к объёму работ §3.2 (+1 день)

### 6.4 Находка 3: Закладка `user_prompt_classification` и "уточняющий вопрос пользователя" требует создания (влияет на D2 / §5.2)

- §5.2 "частота пользовательских уточнений 'подробнее'" сигнал мониторинга аналогичен, **ближайшая существующая точка привязки `followupState.onOutcome` не переиспользуется**

**Рекомендуемая правка**:

- В предусловия §3.2 добавить "минимальная реализация классификатора пользовательского ввода" (сопоставление по шаблону китайский/английский, ~3 дня), иначе §5.4 журнала решений поля `user_prompt_classification` и `requestImpliesFurtherAction` оба не имеют данных
- Либо **принять**, что на этапе Phase 3a dogfood эти два сигнала отсутствуют, полагаться только на частоту `fallback_triggered` для мониторинга регрессии качества — низкая стоимость, но высокий риск

### 6.5 Находка 4: Внутреннее противоречие дизайна D4 — allowlist и атрибуция выгоды не выровнены (влияет на D4 / §3.4)

**Факт**:

- Три категории инструментов `Kind.Read` (read_file), `Kind.Search` (glob / grep), `Kind.Fetch` (web_fetch) в `shouldConfirmExecute` / `getConfirmationDetails`, **большинство наследуют реализацию по умолчанию от `BaseToolInvocation`, делают ноль IO** (read_file / glob / grep вообще не переопределяют, web_fetch делает только 5-10 строк парсинга URL hostname)
- Реально IO есть у `Edit` / `WriteFile` (`calculateEdit` + `readTextFile` + `Diff.createPatch`, типично ~20ms), но §3.4 сценарий A исключает их из allowlist для избежания TOCTOU
- **Результат**: три категории инструментов, оставшиеся в allowlist, prevalidate и без prevalidate имеют практически одинаковый объём работы — allowlist на самом деле перехватывает "единственный Edit с возможной экономией IO", оставляя "инструменты, которые и так нулевой стоимости"

**Влияние на дизайн**:

- Нарратив §3.4 "предварительная верификация IO" **не состоятелен**: истинный источник выгоды 50-100ms — **"ожидание планирования устраняется, когда stream полностью завершается → затем пакетно schedule"**, почти не связано с IO на стороне инструментов
- Ошибочная атрибуция выгоды ведёт к двум проблемам:
  1. **allowlist может быть шире** — подходят все инструменты с идемпотентной prevalidate, не обязательно привязываться к `CONCURRENCY_SAFE_KINDS`
  2. **затраты 5-7 дней трудно обосновать** — если реальная выгода только ~50ms от изменения модели планирования, а Edit не в allowlist, то ROI этих затрат ниже, чем подразумевает дизайн-документ

**Рекомендуемая правка**: §3.4 переписать атрибуцию выгоды —

- Разделить на две части: (a) изменение модели планирования экономит ожидание stream ~50ms, (b) объём работы, который можно сэкономить на prevalidate инструментов ~0ms (внутри allowlist) / ~20ms (если Edit входит в allowlist)
- В таблице комплексной оценки §4.1 изменить выгоду RT D4 с "50-200ms" на "30-80ms (сценарий A, в основном от изменения модели планирования) / 100-200ms (сценарий B, с Edit)"
- В дорожной карте §4.2 дополнительно понизить приоритет D4 — чистое преобразование модели планирования можно делать независимо, не обязательно жёстко привязывать к концепции prevalidate

   - **раунд summary как раз является раундом с самым длинным хитом префикса**

2. **system prompt уже находится в стабильном состоянии** (результаты аудита `prompts.ts`)

### 7.2 Как эти два факта меняют оценку ROI из D2

В §3.2 документ предполагал "fast model примерно на ~2с быстрее primary", базовым случаем было **primary uncached против fast uncached**.

Но в реальном запуске primary — **cached** (раунд summary как раз попадает в самый сильный кэш), поэтому правильным сравнением будет:

> primary cached против fast uncached

| Маршрутизация                          | Оценка задержки  | Примечание                     |
| -------------------------------------- | ---------------- | ------------------------------ |
| primary с 80% попаданием в prefix cache | ~1.8-2.2с        | текущее поведение в раунде summary |
| fast без cache (между моделями не共享)  | ~1.5-2с          | реальное поведение после переключения D2 |

**Чистая разница: несколько сотен миллисекунд, возможно fast даже медленнее**. С учётом инженерных затрат 14-16 дней + риски качества + потери на fallback, **чистая выгода D2 близка к 0 или отрицательна**.

В предусловия §3.2 **должно быть добавлено**: базовое измерение должно сравнивать primary **cached** против fast **uncached**, и D2 не должен включаться, когда `T_primary_cached < T_fast_uncached × 1.5`.

### 7.4 Три новых открытия, заслуживающие развёрнутого рассмотрения

#### Находка A: реальный механизм `tool_choice='none'`

В OpenAI / DashScope API `tool_choice='none'` — это не просто "запретить вызов инструментов" — на этапе sampling модель **полностью пропускает распределение вероятностей специальных токенов `<tool_call>`**, decoder напрямую идёт по пути генерации естественного языка. Выгода не в "экономии одной-двух retry", а в том, что сам sampling быстрее.

#### Находка B: `scope: 'global'` уже имеет прецедент Anthropic в репозитории

В `packages/core/src/core/anthropicContentGenerator/converter.test.ts:85, 1543` уже есть использование `cache_control: { type: 'ephemeral', scope: 'global' }`. Но `provider/dashscope.ts:288` при маркировке cache_control **не передаёт scope**:

```typescript
cache_control: { type: 'ephemeral' },   // нет scope
```

Если DashScope сервер распознаёт `scope: 'global'`:

- system + tools переводятся в global cache (TTL намного больше 5мин ephemeral)
- **попадание между session**, задержка запуска также снижается
- выгода только от этого одного пункта может превысить всю предполагаемую выгоду D2

##### Результаты исследования (2026-05-26, вывод: (c) неfeasible, закрыть эту линию)

Фактологический список из официальной документации Alibaba Cloud Bailian `help.aliyun.com/zh/model-studio/context-cache`:

| Вопрос                   | Вывод                                                                                                                                                                                               | Доказательство                                               |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| Поддержка поля `scope`   | **не поддерживается**. Распознаётся только `type: 'ephemeral'`, любой `scope`/`persistent`/`global` будет silently dropped                                                                                                   | оригинальный текст официальной документации: "поддерживает только установку `type` в `ephemeral`" |
| Фактический TTL ephemeral | **5 минут скользящее окно** (сброс после попадания)                                                                                                                                                                   | явно указано в документации Bailian                                   |
| Долгий TTL / глобальный механизм      | **никакого механизма публичного облачного API**. Нет значения type `persistent`, нет отдельного API предзагрузки, нет `prompt_cache_key`; единственный "глобальный персистентный" продукт — PAI глобальный кэш контекста (саморазвёртывание + vLLM + Lingjun +共享 Redis), не относится к DashScope API | документация PAI                                           |
| Общий доступ между session | один аккаунт + одна модель + совпадение содержимого → уже попадает (это то, что `ephemeral` уже делает); разные аккаунты абсолютно не共享                                                                                                         | документация Bailian                                           |
| Ценообразование                   | запись cache 125%, явное чтение cache 10%, **неявное чтение cache 20%** (скидка 20% без маркировки `cache_control` также доступна)                                                                                     | документация по ценам Bailian                                       |
| Минимальный кэшируемый prompt      | **1024 токена**                                                                                                                                                                                    | документация Bailian                                           |
| Поддержка моделей (явный cache) | qwen3.7-max / qwen3.6-plus / qwen3.5-plus / qwen3-coder-plus / qwen3-vl-plus / deepseek-v3.2 / kimi-k2.5 / glm-5.1 явно перечислены. **qwen3.6-plus и qwen3.7-max также получают 90% скидку явного cache**        | список моделей Bailian (перепроверено 2026-05-26)                    |

**Несколько связанных значений побочных находок**:

1. **Скользящее окно TTL** — хорошая новость для agent loop — интервал между последовательными вызовами внутри loop обычно < 30с, **cache всегда свежий, не истекает за 5мин**
2. **Неявная скидка cache 20%** — бесплатное преимущество — даже без маркировки `cache_control` можно получить; но тонкий контроль требует явного
3. ~~`qwen3.6-plus` не в списке явного cache~~ — **исправление (2026-05-26)**: после перепроверки, qwen3.6-plus **действительно в списке явного cache**, получает 90% скидку. Предыдущий отчёт здесь ошибался, исправлено в первой таблице этого раздела
4. **Текущий подход `dashscope.ts:288` уже является пределом возможностей публичного облачного API DashScope** — нет пространства для дальнейшего выжимания

**Сопутствующее усиление оценки D2 из §7.2**:

Скользящее окно TTL означает, что в agent loop раунд summary **почти 100% попадает** в cache primary (предыдущие раунды только что попадали, в пределах 5мин). Переключение D2 на fast model не только разобьёт цепочку записи cache, накопленную ранее, **но и заставит раунд summary деградировать с "почти 100% попадания" до "полного miss"** — оценка чистой выгоды более определённо отрицательна, чем предполагалось в §7.2.

#### Находка C: уровень UI рендеринга — игнорируемая слепая зона

В §1.2 базовой линии "накладные расходы фреймворка" оценены в 0.3с (3%), но это грубая оценка. Ink 7 + React 19.2 при каждом chunk вызывает setState → re-render, длинное summary накопленная может составлять 200-500мс. Нужно проверить, как `useGeminiStream` обрабатывает поток токенов, есть ли `requestAnimationFrame` / `useDeferredValue` для объединения chunk.

### 7.8 Аудит динамического содержимого `prompts.ts` (2026-05-27)

В §7.1 при выводе заключения "system prompt уже стабилен" был сделан только приблизительный grep. Этот раздел — систематический аудит `packages/core/src/core/prompts.ts` (1169 строк), перечисление в виде списка для последующего анализа hit rate cache и решений по низко висящим фруктам.

**Метод аудита**: перечислить все выражения интерполяции `${...}`, IIFE, вызовы `process.*` / `new Date` / `Date.now` / `Math.random` / `fs.*`, для каждого определить "изменится ли в пределах одной session".

#### Полностью отсутствуют (часто подозреваемые критические проблемы)

| Кандидат                               | Факты кода                                                                            |
| -------------------------------------- | ----------------------------------------------------------------------------------- |
| `Date.now()` / `new Date()`            | во всём файле **ноль появлений** (`rg` нет совпадений)                                                  |
| `Math.random()`                        | **ноль появлений**                                                                        |
| Значение `process.cwd()` записывается в prompt      | только L366 `if (isGitRepository(process.cwd())) { ... }`, **значение не записывается в строку**, только как переключатель |
| Вызовы подпроцессов git status / git branch | **ноль раз**, секция git — статический инструктирующий текст                                                      |
| Инъекция текущего списка файлов / структуры проекта        | **ноль раз**                                                                            |
| Состояние LSP / количество ошибок                  | **ноль раз**                                                                            |
| История пользовательского ввода                       | **ноль раз** (history идёт через messages, не в system)                                        |

#### Один раз при запуске, неизменно в пределах session

| Позиция     | Содержимое                                                                                             | Когда может измениться                |
| ----------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------- |
| L190     | `process.env['NESSY_SYSTEM_MD']` определяет источник basePrompt (по умолчанию vs пользовательский system.md)                   | неизменно в пределах процесса                |
| L342-343 | `process.env['SANDBOX']` определяет, какая версия секции sandbox выбирается (Seatbelt / Sandbox / Outside)                 | неизменно в пределах процесса                |
| L366     | `isGitRepository(process.cwd())` определяет, вставляется ли секция git                                             | cwd обычно неизменен в пределах session |
| L871     | `process.env['NESSY_CLI_TOOL_CALL_STYLE']` определяет стиль вызова инструментов (qwen-coder / qwen-vl / general) | неизменно в пределах процесса                |

#### Срабатывание по событию (низкая частота)

| Параметр                                              | Условие срабатывания                                          | Оценка частоты           |
| ----------------------------------------------------- | ------------------------------------------------------------- | ------------------------ |
| `userMemory` (1-й параметр `getCoreSystemPrompt`)     | инструмент `save_memory` / `/memory refresh` / загрузка расширения | 0-3 раза/session     |
| Имя `model` (влияет на выбор ветки `getToolCallExamples`) | переключение `/model`                                     | редко               |
| `appendInstruction`                               | элемент конфигурации, в пределах session почти неизменен                        | почти никогда           |
| `deferredTools` (`buildDeferredToolsSection`)    | динамическая загрузка инструментов MCP                                  | в основном период запуска session |

#### Одна скрытая небольшая яма

L207-209: если установлен env `NESSY_SYSTEM_MD`, **каждый раз** `getCoreSystemPrompt` выполняет `fs.readFileSync(systemMdPath)`:

```typescript
const basePrompt = systemMdEnabled
  ? fs.readFileSync(systemMdPath, 'utf8')
  : `...`;
```

- содержимое стабильно при неизменном файле → попадание в cache не затронуто
- но каждый вызов LLM имеет один синхронный IO (по умолчанию `.nessy/system.md`, для файлов на сетевом монтировании будет медленнее)
- не влияет на вывод этого раздела о "дружелюбности cache", только как известная небольшая яма производительности

#### Сопутствующие выводы

1. **system prompt в стабильной session каждый раз выдаёт byte-for-byte идентичный** → ключ кэша DashScope ephemeral (на основе hash содержимого) вся секция стабильна → **hit rate секции system почти 100%**
2. Единственное событие, бьющее cache — `save_memory`— ключевая функция, нельзя уступать ради cache
3. **Анализ цены низко висящих фруктов #1 (инструкция краткого ответа)**: добавление инструкции в секцию Final Reminder (L389-390) → содержимое system prompt изменяется один раз → **первый запрос cache miss (единовременная стоимость прогрева), затем все запросы продолжают попадать**
4. **Вывод об отбрасывании "стабилизации system prompt" из §7 получает официальную доказательную поддержку** — не только нет необходимости делать, даже "теоретически сделанное могло бы дополнительно снизить процент miss cache" недействительно, потому что изначально уже ≈ 0
5. Этот аудит может служить базой для ссылок для последующих обсуждений по этой теме, избегая повторного grep; при больших изменениях prompts.ts этот раздел должен синхронно обновляться
