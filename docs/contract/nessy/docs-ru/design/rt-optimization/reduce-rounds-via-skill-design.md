# Сокращение раундов Agent Loop: через проектирование навыков

> Находится в той же директории, что и `rt-optimization-design.md`, взаимодополняющий: тот документ обсуждает сокращение раундов на уровне **механизмов фреймворка** (D1 пропуск итогового раунда, D2 быстрая маршрутизация, D4 prevalidate), этот документ утверждает, что **настоящий рычаг сокращения раундов — на уровне проектирования skill/tool**, и предлагает реализуемый путь, не зависящий от модификации фреймворка или данных cache hit rate.

---

## 0. Спецификация приёмки (gate перед разработкой)

> Этот раздел — **gate перед разработкой** — перечисляет, какие спецификации должны быть подтверждены перед началом coding, а какие должны подождать данных. Спецификации фиксируются заранее, а не "посмотрим на метрики после реализации", чтобы избежать: (a) обнаружения после реализации, что метрики неизмеримы, (b) дрейфа порогов вместе с результатами, что приводит к искажению выводов, (c) отсутствия стоп-линий, из-за чего схема погружается в "кажется, что работаем, но выгоды нет".
>
> **Границы применимости этой spec-схемы**: эта схема предполагает, что правильность направления можно оценить после замера базовой линии P1.5. Это предположение верно для сценария "сокращение раундов", потому что у него есть чёткие измеримые сигналы (количество раундов, followup_rate, batch_size). **Сценарии за пределами этого предположения** (например, в будущем использование той же схемы для "оптимизации качества" и других трудно квантифицируемых направлений), предварительная спецификация может скорее препятствовать быстрому обучению; при столкновении с такими сценариями возвращайтесь к процессу управления §0.5 для повторной оценки, не применяйте эту схему механически.

**Спецификация делится на 4 уровня — разные сроки**:

| Уровень | Тип                                     | Срок фиксации                  |
| ------- | --------------------------------------- | ------------------------------ |
| §0.1    | Инженерная спецификация (корректность конвейера данных, изменений кода) | **До начала**, можно зафиксировать немедленно |
| §0.2    | Статистическая спецификация (метрики "успеха проекта") | **До начала**, пороги фиксируются после базовой линии P1.5 |
| §0.3    | Стоп-линии (жёсткие условия "если произошло, то отказаться") | **До начала**, нельзя перемещать |
| §0.4    | Спецификация на skill (что конкретно меняем, какая цель) | **После**, данные-driven Layer 1 |

### 0.1 Инженерная спецификация (обязательно до начала · можно зафиксировать немедленно)

Спецификация корректности конвейера данных и изменений кода — не зависит от каких-либо бизнес-решений или базовых данных, должна быть зафиксирована до начала разработки:

- **Беспрепятственный канал nessy-logger** (§4.1.1b): события skill_launch должны попадать одновременно в оба канала — OTLP и nessy-logger
- **Связывание через `prompt_id`**: `skill_launch` + последующие `tool_call`, вызванные одним user prompt, должны иметь возможность вычленить полный trail по одному `prompt_id`
- **`batch_size` не undefined** (направление A §4.3.2): для одиночного инструмента в batch явно установить `batch_size = 1` / `batch_position = 0`
- **SQL исполняется** (§4.1.2): офлайн-SQL в реальном telemetry backend выдаёт непустой результат и может различать skill с высоким/низким followup_rate
- **Дисперсия базовой линии < P50 × 20%** (P1.5): стабильность измерения базовой линии (иначе последующее A/B-сравнение недостоверно) — примечание: этот пункт, хотя и указан в §0.1 инженерного уровня, но **фиксация зависит от данных базовой линии P1.5**, является единственным пост-условием в §0.1; если P1.5 не пройден, то пороги §0.2 невозможно достоверно зафиксировать
- **Бюджет объёма Skill** (модификация Layer 2): после встраивания followup количество токенов в описании skill не должно превышать 2× от исходного, и абсолютное значение ≤ 500 токенов (берётся меньшее). При превышении — разделить skill по §4.2, а не объединять. Этот пункт согласован со §7 пункт 2, §4.2 существующими ограничениями, поднимается на уровень спецификации
- **`npm run preflight` полностью пройден**: жёсткий порог для каждого PR

### 0.2 Статистическая спецификация (обязательно до начала · пороги фиксируются после P1.5)

Метрики, по которым проект считается "успешным в статистическом смысле" — **направление** фиксируется заранее, **пороги** фиксируются после получения данных базовой линии (чтобы избежать произвольного заполнения цифр):

| Метрика                               | Направление | Срок фиксации  | Текущий порог-заглушка (требует калибровки) |
| ------------------------------------- | ----------- | ------------- | ------------------------------------------- |
| Взвешенный `followup_rate` top-3 skill | ↓           | Конец P1.5    | ≥ 30%                                       |
| E2E RT P50 сессий с skill             | ↓           | Конец P1.5    | ≥ 2s                                        |
| Доля `tool_call` с `batch_size > 1`   | ↑           | До P3         | ≥ 30%                                       |
| Статистическая значимость A/B сценариев запуска skill | p < 0.05 | До завершения P2 | n TBD            |

> **Ключевое ограничение**: порог-заглушка — это не обещание. Если базовая линия P1.5 покажет "взвешенный followup_rate top-5 skill < 30%" (срабатывает стоп-линия §0.3 #1), проект закрывается; **нельзя снижать спецификацию, чтобы пороги "достигались"**.
>
> **Как измерять**: методы измерения каждой метрики, SQL-шаблоны, дизайн A/B см. в §5.1-§5.2; расчёт выборки для статистической значимости (p < 0.05) см. в §5.1.

### 0.3 Стоп-линии (обязательно до начала · регулируются после фиксации P-1)

Перечислены в §5.3. Это жёсткие условия "если произошло, то отказаться" — **ни при каких обстоятельствах нельзя ослаблять стоп-линии ради достижения §0.2 статистической спецификации**.

- **Метрики результата** (3 пункта): взвешенный `followup_rate < 30%` для top-5 / после изменения 2 skill RT P50 ↓ < 1s / после Layer 3 `batch_size P50` остаётся = 1
- **Метрики процесса** (3 пункта): hit rate skill ↓ ≥ 5pp / частота неудач встроенного followup ≥ 5% / уровень отмены пользователем ↑ ≥ 2pp

См. §5.3.

**Правило регулируемости** (избегать жёсткой дисциплины без данных):

| Этап                         | Можно ли регулировать              | Направление регулировки                                                                 |
| ---------------------------- | ---------------------------------- | --------------------------------------------------------------------------------------- |
| Фиксация P-1                 | ✅ Любая регулировка (на основе исторической telemetry или консенсуса) | Любое                                                                                   |
| После фиксации P-1 → Конец P1.5 | ❌ Нельзя регулировать          | —                                                                                       |
| Конец P1.5 (после базовой линии) | ✅ Только **однократное ослабление** | Ослабление (например, 30% → 25%) требует приложения доказательств данных + ревью 2 лицами; **нельзя ужесточать** (избегать постфактум добавления стоп-линий) |
| После P1.5                   | ❌ Нельзя регулировать          | —                                                                                       |

> Текущие пороги-заглушки (30% / 1s / 5pp и т. д.) **не подкреплены историческими данными**: это инженерная оценка перед ревью P-1. Если к ревью P-1 удастся получить данные telemetry за последние четыре недели, стоп-линии следует откалибровать по ним; иначе нужно сохранить пороги-заглушки и в конце P1.5 применить описанное выше правило «однократного ослабления».

### 0.4 per-skill спецификация (обязательно после · данные-driven)

Какой конкретно skill изменять, до какого значения менять `followup_rate` — **не фиксируется до получения данных Layer 1**.

Причина нефиксации: априорный дизайн и апостериорные данные могут сильно отличаться. Принудительная предфиксация повторит путь `rt-optimization-design.md` §7 D2 — априорное предположение "fast модель быстрее на 2-3s" было опровергнуто постфактум реализацией cache, что привело к чистому выигрышу схемы близкому к 0 или даже отрицательному.

**Место публикации**: per-skill спецификация формируется на основе данных в конце P1.5 и отдельно декларируется в описании каждого PR Layer 2. В design-документ она не входит, чтобы не менять его при каждом изменении skill.

**Шаблон структуры per-skill спецификации** (согласован с обязательными пунктами описания PR §4.2 — эти два списка одно и то же, §4.2 это view процесса, этот раздел это view спецификации):

| Поле            | Содержание                                                                                                   | Источник данных                               |
| --------------- | ------------------------------------------------------------------------------------------------------ | -------------------------------------- |
| 1. Текущие данные     | invocation_count, followup_rate, top followup tools                                                    | Layer 1 telemetry                      |
| 2. Цель         | followup_rate с X% до Y%                                                                            | На основе направления улучшения §0.2, абсолютное значение определяется внутри PR |
| 3. Область изменения     | Какие followup встраиваются (read/grep/shell read-only), а какие явно **не** встраиваются (write-операции / переходы между skill / глубокое рассуждение) | §4.2 таблица паттернов изменения                         |
| 4. Обновление контракта вывода | Предварительные объявления, добавляемые в описание skill ("Returns: ...")                                                               | §3.2 пример изменения                          |
| 5. A/B план     | После изменения 2 недели наблюдения followup_rate / RT P50 / метрики процесса, сверка с приёмочной линией §5.1                                    | §5.1                                   |
| 6. Доказательство объёма     | Количество токенов описания skill до/после изменения (оценка через tiktoken), не должно превышать §0.1"Бюджет объёма Skill"                          | §0.1 пункт 6                           |

### 0.5 Управление спецификациями

- **Изменение спецификаций §0.1 / §0.3** требует обновления design документа + ревью PR; §0.3 регулируется только согласно "правилу регулируемости" §0.3 в окне конца P1.5
- **Изменение порогов §0.2 (после фиксации P1.5)** требует приложения как минимум одного из следующих доказательств данных:
  - (a) анализ отклонения результатов измерения базовой линии P1.5 от уже зафиксированных порогов (со ссылкой на исходные записи измерений)
  - (b) публичные benchmark данные аналогичных проектов (со ссылками на источники)
  - (c) подписанное как минимум 2 лицами объяснение отклонения от внутренней рецензии

  Если указанные доказательства отсутствуют при ревью PR, рецензент **обязан** заблокировать PR — не принимается "интуитивная регулировка инженера"

- **per-skill спецификация §0.4** после формирования на основе данных записывается в описание PR (по шаблону из шести пунктов §0.4), но не включается в design-документ

## 1. Контекст и позиционирование

### 1.1 Проблема

Базовая линия, приведённая в `rt-optimization-design.md` §1.2: 3 раунда agent loop, 13.4s от начала до конца, из которых вызов LLM занимает 78%. Каждый раунд длится ~3–4s.

```
Round 1 (3.8s, 28%): LLM решение вызвать skill
Round 2 (3.0s, 22%): LLM решение вызвать shell
Round 3 (3.8s, 28%): LLM суммаризация
```

После двух раундов ревью в `rt-optimization-design.md` §6/§7 варианты D2/D4 были отклонены, а D1/D3 отложены до завершения более простых оптимизаций. Но **весь исходный документ сосредоточен на последнем Round 3 (раунде суммаризации) или микрооптимизациях внутри одного раунда (D4) и прямо не рассматривает, почему появляется «промежуточный раунд» Round 1 → Round 2 и можно ли его устранить**.

Факт: Round 2 существует **в большинстве случаев потому, что skill, вызванный в Round 1, не вернул полный ответ**, и модель добавляет shell-запрос для получения недостающих данных. Если skill спроектирован так, чтобы вернуть полный ответ за один вызов, 3 раунда превращаются в 2, а экономия составляет ~3s на Round 2. Эта выгода совершенно не пересекается с D1.

### 1.2 Связь с rt-optimization-design

| Направление сокращения раундов | Затронутые раунды                      | Расположение рычага           | Позиционирование этого документа                   |
| ------------------------------ | ------------------------------------- | ---------------------------- | -------------------------------------------------- |
| D1 `skipLlmRound`              | Итоговый раунд суммаризации           | Механизм фреймворка + per-tool opt-in   | Подстраховка, **после Layer 2**  |
| D2 быстрая маршрутизация       | Задержка одного раунда                | Механизм фреймворка                     | Отложено, **не в scope этого документа** |
| D3 состояние Summarizing       | Итоговый раунд суммаризации (уровень восприятия)            | UI state machine                    | Опционально, ортогонально этой схеме   |
| D4 prevalidate                 | Задержка одного раунда                | Механизм фреймворка                     | Отложено, **не в scope этого документа** |
| **Эта схема Layer 1-3** | **Промежуточный раунд принятия решений + раунды, не запущенные параллелизмом** | **Проектирование skill + prompt engineering** | **Новое направление**                 |

### 1.3 Ключевой тезис

Настоящий рычаг сокращения раундов — на уровне проектирования skill/tool, а не agent фреймворка. Три причины:

1. **Базовая линия §1.2 сама выявляет проблему в skill** — переход Round 1 → Round 2 происходит потому, что skill вернул неполный ответ: фреймворк отработал правильно, а skill — нет
2. **Сокращение на уровне фреймворка в конечном счёте тоже требует per-tool opt-in** — D1 `skipLlmRound` должен явно помечать каждый инструмент, обходя возвращается к skill engineering, плюс ещё набор затрат на восстановление invariant + gating решений
3. **ROI можно измерять локально и внедрять постепенно** — изменение одного skill экономит один раунд × частоту запуска этого skill и не зависит ни от данных cache hit rate, ни от межсистемных изменений

> **Перед реализацией обязательно предварительное ревью §0 Acceptance Spec (этап P-1, 0.5d)** — инженерная спецификация §0.1 и стоп-линии §0.3 должны быть зафиксированы до начала работ; направление статистических порогов §0.2 также нужно подтвердить заранее (конкретные значения фиксируются после измерения базовой линии P1.5). Пропуск §0 и немедленный переход к P0 означает использование антипаттерна «сначала код, потом метрики», который этот документ не поддерживает.

## 2. Принципы проектирования

1. **Не менять agent-фреймворк** — не затрагивать основной путь `useGeminiStream` / `coreToolScheduler` / `geminiChat`
2. **Data-driven приоритизация** — сначала построить telemetry, пусть данные подскажут, какой skill изменять, не полагаться на догадки
3. **Per-skill измеримость и grayscale** — каждое изменение skill независимо A/B, неудача локально откатывается
4. **Приоритет накопительного эффекта** — выгода = экономия на одном раунде × частота запуска, поэтому приоритет получают часто используемые skill
5. **Не привязываться к D1** — успех этой схемы не зависит от того, будет ли D1 реализован

## 3. Трёхуровневая схема

### 3.1 Layer 1: Telemetry для сокращения раундов (поиск золотой жилы)

**Цель**: использовать данные для определения skill, которые выгоднее всего изменить, то есть выяснить вероятность дополнительного вызова инструмента моделью после использования конкретного skill.

**Ключевые поля** (per-turn, per-skill-invocation):

```typescript
interface SkillFollowupRecord {
  skill_name: string;
  prompt_id: string; // 关联同一 user prompt 内的所有 events
  turn_index: number; // 该 skill 在 loop 里是第几轮
  followup_tool_names: string[]; // 同一 prompt_id 下，skill 之后还调了哪些工具
  followup_count: number; // followup_tool_names.length
  followup_kinds: Kind[]; // Read/Edit/Execute/...
  next_turn_is_terminal: boolean; // skill 之后下一轮就出文字（不再调工具）
  user_followup_within_30s: boolean; // 用户在结果显示后 30s 内追加新 prompt（质量回归信号）
}
```

**Ключевые метрики**:

- `skill_followup_rate = sum(followup_count > 0) / total_invocations`
- `terminal_after_skill_rate = sum(next_turn_is_terminal) / total_invocations`
- Агрегация по `(skill_name, top followup tool)` — смотреть, какой инструмент чаще всего дополнительно вызывается после каждого skill

**Определение золотой жилы**:

```
(invocation_count_weekly × skill_followup_rate) ≥ threshold
↓
Этот skill — золотая жила сокращения раундов, приоритетная модификация Layer 2
```

Рекомендуемый порог: top-3 skill по формуле выше, сначала изменить первые 2.

### 3.2 Layer 2: Полнота вывода skill

**Цель**: обеспечить, чтобы skill, признанные наиболее перспективными, возвращали полный ответ за один вызов и устраняли переход Round 1 → Round 2.

**Паттерны модификации (классификация по типу followup)**:

| Паттерн Followup               | Типичный сценарий                   | Направление модификации                           |
| --------------------------- | -------------------------- | ---------------------------------- |
| skill → `read_file`         | skill даёт путь, модель затем читает     | Читать файл внутри skill и возвращать содержимое         |
| skill → `grep/glob`         | skill даёт каталог, модель затем ищет     | Выполнять поиск внутри skill и возвращать совпадения      |
| skill → `shell` (read-only) | skill даёт команду, модель затем выполняет   | Выполнять команду внутри skill и возвращать вывод         |
| skill → `shell` (write)     | skill даёт решение, модель затем выполняет запись | **Сохранить отдельно**: запись требует подтверждения и не должна объединяться |
| skill → another skill       | Цепочка вызовов                   | **Не объединять**, чтобы сохранить композиционность       |

**Чек-лист модификации (шаблон per-skill PR)**:

1. В описании skill **предварительно объявить контракт вывода**: явно написать "Returns: full file content / matched lines / command output", чтобы модель знала, что дополнительный запрос не нужен
2. Внутри skill **выполнить все read-only followup**: встроить в skill те операции read/search, для которых telemetry показывает частоту дополнительных вызовов >50%
3. **Не встраивать write операции**: write операции требуют подтверждения пользователя, должны быть отдельным раундом
4. **Не встраивать followup глубокого рассуждения**: если followup это "дальнейший анализ на основе этого", это дело модели, не skill
5. **Приложить A/B telemetry**: после изменения 2 недели сравнения, упал ли `followup_rate` до \<20%

**Типичный пример модификации (схематично)**:

До модификации:

```
skill "list-workspaces" returns: ["ws_a", "ws_b"]
→ Round 2: model calls shell to get details for each workspace
```

После модификации:

```
skill "list-workspaces" returns:
  - ws_a (owner: foo, last_active: 2026-05-20, status: active)
  - ws_b (owner: bar, last_active: 2026-05-01, status: archived)
description updated: "Returns workspaces with owner, last_active, status"
→ Round 2 disappears for ~80% of queries
```

### 3.3 Layer 3: Prompt-обучение модели параллелизму

**Цель**: для независимых инструментов (чтение нескольких файлов, поиск по нескольким каталогам) заставить модель инициировать tool_calls в одном раунде параллельно, сжимая N раундов в 1.

**Предпосылка**: инфраструктура готова — `tools/tools.ts:818` `CONCURRENCY_SAFE_KINDS` + `coreToolScheduler` `partitionToolCalls` уже могут выполнять инструменты одного batch параллельно.**Не хватает только готовности модели инициировать параллельные tool_calls**, qwen-coder по умолчанию склонен к последовательному выполнению.

**Место изменения**: `packages/core/src/core/prompts.ts` (уже проверено: добавление возле `# Final Reminder` L396 повлияет только на попадание в cache и создаст лишь однократные затраты на прогрев).

**Текст руководства (схематично, требует A/B tuning)**:

```
When you need to call multiple independent read-only tools (read_file,
grep, glob, web_fetch), emit them in a SINGLE tool_calls batch — do NOT
call them sequentially across rounds. They will execute concurrently.

Examples:
- Reading 3 files for comparison: emit 3 read_file calls in one batch
- Searching for 2 patterns: emit 2 grep calls in one batch

Do NOT batch when the second call depends on the first call's result.
```

**Оценка эффективности**: новое telemetry поле `batch_size` (количество tool_calls в одном turn) — сравнение распределения до/после изменения prompt.

#### 3.3.1 Расширение `CONCURRENCY_SAFE_KINDS` (подпункт Layer 3)

Prompt-обучение модели параллелизму — это только supply side (модель готова отправлять несколько tool_calls за раз), но `tools/tools.ts:818` `CONCURRENCY_SAFE_KINDS = { Read, Search, Fetch }` определяет,**какие инструменты фактически могут выполняться параллельно**: `partitionToolCalls` (`coreToolScheduler.ts:775`) упакует "последовательные безопасные инструменты" в concurrent batch, остальные выполняются последовательно.

Если модель согласно руководству отправила 3 tool_calls за раз, но 1 из них относится к `Kind.Execute` и не входит в безопасное множество, весь batch будет разобран и выполнен последовательно — выгода изменения Layer 3 prompt будет компенсирована runtime планировщиком.

**Кандидаты на расширение** (по возрастанию риска):

- `Kind.Think` (содержит save_memory / todo_write) — **не добавлять**, есть implicit write
- Только для чтения shell (`isShellCommandReadOnly()` возвращает true для Execute) — `partitionToolCalls` уже имеет special case (комментарий `coreToolScheduler.ts` `partitionToolCalls` упоминает "Execute (shell) is safe only when isShellCommandReadOnly() returns true"), поэтому текущая реализация это покрывает и менять `CONCURRENCY_SAFE_KINDS` не нужно
- MCP инструменты классифицируются по `Kind` — разные MCP server ведут себя по-разному, требуется явный opt-in при регистрации инструмента для безопасности

**Вывод**: текущее множество разумно, **Layer 3 не зависит от расширения `CONCURRENCY_SAFE_KINDS`**. Смысл существования этого раздела: после получения данных telemetry `batch_size`, **если обнаружится "P50 параллельного batch < ожидаемого", сначала проверить, не был ли разрезан `partitionToolCalls`, а не модель не параллелит**. Это диагностический путь при неудачном A/B Layer 3, не обязательный пункт.

> Credit: codex review предложил считать расширение `CONCURRENCY_SAFE_KINDS` упущенным рычагом. Проверка показала, что текущая реализация уже имеет special case `isShellCommandReadOnly`, покрывающий основную массу случаев; расширение множества само по себе даёт малую выгоду при высоком риске, поэтому его следует сохранить лишь как диагностический путь.

#### 4.1.1b Предварительное восстановление канала nessy-logger

Перед добавлением `prompt_id` нужно решить **существующую точку разрыва канала**: `packages/core/src/telemetry/nessy-logger/nessy-logger.ts:908` определяет метод `logSkillLaunchEvent(event)`, но**во всём репозитории нет вызывающих сторон** — `loggers.ts:958` `logSkillLaunch` напрямую идёт по пути `logs.getLogger(SERVICE_NAME).emit()` OTLP, обходя nessy-logger.

Последствия:

- Путь OTLP может доставлять события skill_launch в OTLP collector (уже работает), но канал специализированной телескопии nessy-logger сейчас мёртв
- Если telemetry backend потребляет из nessy-logger (а не OTLP), события skill_launch **полностью не отправляются**
- Офлайн-SQL §4.1.2 для вывода `SkillFollowupRecord` зависит от попадания событий skill_launch в хранилище — **сначала нужно проверить, видны ли сейчас skill_launch в backend**

Направление исправления (выбрать одно):

- **A** (рекомендуется): в `loggers.ts:958` `logSkillLaunch` добавить строку `NessyLogger.getInstance(config)?.logSkillLaunchEvent(event)`, выравнивая по записи `logToolCall` в `loggers.ts:230`
- **B**: подтвердить, что backend потребляет только из OTLP, пометить `logSkillLaunchEvent` в nessy-logger как `@deprecated` или удалить

**Почему только один путь NessyLogger, а не все 4 пути как `logToolCall`**:

`logToolCall` (`loggers.ts:220-247`) фактически имеет 4 выхода:

1. `uiTelemetryService.addEvent(...)` — UI отображение
2. `config.getChatRecordingService()?.recordUiTelemetryEvent(...)` — история чата
3. `NessyLogger.getInstance(config)?.logToolCallEvent(...)` — телескопия backend nessy-logger
4. OTLP `logger.emit(...)` — OpenTelemetry

skill_launch — это **чисто backend telemetry событие**, не требует отображения в UI (пользователь уже видит returnDisplay SkillTool), не нужно входить в историю turn ChatRecording (вызовы инструментов внутри skill уже записаны через recordUiTelemetryEvent). Поэтому дополняется только пункт 3 (NessyLogger), сохраняется пункт 4 (OTLP), пропуск 1/2 — намеренный, не упущение.

**Детали передачи поля**: `loggers.ts:961-966` использует spread `{ ...event }` для автоматической передачи новых полей (после добавления `prompt_id` в `SkillLaunchEvent` этот путь автоматически работает), но если `logSkillLaunchEvent` внутри `nessy-logger.ts:908` явно деструктуризирует `event.skill_name` / `event.success`, новые поля не будут автоматически включены, требуется ручная синхронизация.

Объём работ: путь A около 0.5d (включая подтверждение backend); путь B около 0.2d (удаление кода + документация).

#### 4.1.2 Вывод `SkillFollowupRecord` (офлайн-агрегация)

Не требуется новый тип события — `ToolCallEvent` и `SkillLaunchEvent` уже содержат `prompt_id`, офлайн-SQL может вывести:

```sql
-- 伪 SQL，按实际 telemetry backend 调整
WITH skill_events AS (
  SELECT prompt_id, skill_name, timestamp FROM events
  WHERE event_name = 'skill_launch' AND success = true
),
tool_events AS (
  SELECT prompt_id, function_name, timestamp FROM events
  WHERE event_name = 'tool_call'
),
followups AS (
  SELECT s.skill_name, s.prompt_id,
         COUNT(t.function_name) AS followup_count,
         ARRAY_AGG(t.function_name) AS followup_tool_names
  FROM skill_events s
  LEFT JOIN tool_events t
    ON s.prompt_id = t.prompt_id AND t.timestamp > s.timestamp
  GROUP BY s.skill_name, s.prompt_id
)
SELECT skill_name,
       COUNT(*) AS invocations,
       AVG(followup_count) AS avg_followup,
       SUM(CASE WHEN followup_count > 0 THEN 1 ELSE 0 END)::FLOAT / COUNT(*) AS followup_rate
FROM followups
GROUP BY skill_name
ORDER BY invocations * followup_rate DESC;
```

#### 4.1.3 Сбор данных telemetry 1 неделя

- Не изменяет user-facing поведение
- Не требуется никаких конфигурационных переключателей — telemetry уже имеет opt-in фреймворк (настройка `telemetry.target`)
- Через 1 неделю подготовить отчёт с рейтингом skill

### 4.2 Layer 2: Модификация skill (per-skill 0.5-1d)

Модификация сверху вниз по данным Layer 1. Каждый skill — отдельный PR, описание PR должно содержать:

1. **Данные**: текущий invocation_count, followup_rate, top followup tools
2. **Область модификации**: какие followup встроены (явно указать, что не встроено)
3. **Обновление контракта вывода**: какие предварительные объявления добавлены в описание skill
4. **A/B план**: через 2 недели после модификации снова наблюдать followup_rate

**Замечания**:

- Skill встроенный read операция не должен повторно обрабатывать все boundary cases `read_file` (кодировка, бинарное обнаружение и т.д.) — вызывать сам инструмент `read_file`, не переписывать
- Skill встроенный grep/glob аналогично
- Skill встроенная shell команда должна проходить стандартный путь `executeToolCall` (сохранять telemetry)
- **Не допускать взрыва объёма skill**: когда описание skill после встраивания followup > 500 токенов, разделить skill, а не объединять

### 4.3 Layer 3: Prompt-обучение (0.5d изменение + фактическая настройка)

#### 4.3.1 Добавление руководства по параллелизму

**Место**: `packages/core/src/core/prompts.ts` раздел `# Final Reminder` (L396)

Добавить текст руководства из раздела 3.3. Конкретная формулировка требует A/B — сначала использовать простейшую версию, затем уточнять по мере роста уровня параллелизма.

#### 4.3.2 Добавление telemetry `batch_size`

**Место**: `ToolCallEvent` в `packages/core/src/telemetry/types.ts` или новый облегчённый `ToolBatchEvent`

```typescript
// Вариант A: добавление поля в ToolCallEvent (малое вторжение)
export class ToolCallEvent {
  ...
  batch_size?: number;        // количество tool_call в одном batch
  batch_position?: number;    // позиция в batch (0-indexed)
}

// Вариант B: новый ToolBatchEvent (семантически яснее, требует полного процесса нового типа события)
```

**Рекомендуется вариант A** — малое изменение, удобно для агрегации при запросе.

**Путь передачи состояния** (ключевой — эта стоимость была недооценена в ранних версиях):

`coreToolScheduler.ts:2456` `partitionToolCalls(callsToExecute)` возвращает `batches`, **но информация о batch сразу теряется в пути планирования**:

```
executeToolCalls
  └─ batches = partitionToolCalls(...)           // знает batch.calls.length
     └─ for batch of batches:
        └─ this.runConcurrently(batch.calls, ...) // знает batch.calls.length
           └─ executeSingleToolCall(call, ...)   // ❌ уже не знает batch
              └─ ...
                 └─ finalizeToolCalls
                    └─ logToolCall(config, new ToolCallEvent(call)) // ❌ нет batch context
```

Конструктор `ToolCallEvent` (`types.ts:189`) принимает только одиночный `CompletedToolCall`, нет поля batch.

Направление исправления:

- **Направление A** (рекомендуется): добавить в `ScheduledToolCall` поля `batchSize?: number` + `batchPosition?: number`. Две ветви заполняют соответственно:
  - Ветка параллелизма (`coreToolScheduler.ts:2459-2460`, `batch.calls.length > 1`): перед входом в цикл `runConcurrently(batch.calls, ...)` для каждого `call` записать `batchSize = batch.calls.length`, `batchPosition = i`
  - Ветка последовательного выполнения (`L2462-2464` `for (const call of batch.calls)`): для single tool batch явно установить `batchSize = 1`, `batchPosition = 0` (**не оставлять undefined по умолчанию**, иначе downstream telemetry ошибочно интерпретирует раунды, где параллелизм не сработал, как отсутствующие данные)

  `new ToolCallEvent(call)` в конструкторе читает эти два поля из `call`

- **Направление B**: изменить сигнатуру конструктора `ToolCallEvent` `new ToolCallEvent(call, batchInfo?)`, синхронно изменить все точки вызова (4 точки вызова logToolCall + тесты). Площадь изменения больше, чем A

Объём работ: направление A около 0.5d включая unit test; направление B около 1d (больше вызывающих сторон).

**Синхронное измерение "готовности модели к параллелизму"** — до/после изменения Layer 3 prompts.ts сравнение распределения `доля tool_call с batch_size > 1`. Это ключевой показатель эффективности Layer 3, без этих данных A/B Layer 3 не может завершиться.

#### 4.3.3 Оценка влияния на cache

Изменение `prompts.ts` приведёт к однократному сбою DashScope ephemeral cache (первый запрос cache miss, затем восстановление). Это известная однократная стоимость, см. аудит steady state prompt в `rt-optimization-design.md` §7.8.

| Метрика                                      | Приёмочная линия                   | Примечание                       |

### 5.2 Общие RT метрики

| Метрика                               | Базовая линия                                  | Цель после модификации top-3 skill Layer 2  |
| ---------------------------------- | ------------------------------------- | -------------------------------- |
| E2E RT P50 (сессии с skill)   | 13.4s (однократная выборка) / требуется дополнить ≥3 сценария базовой линии | Снижение 2-3s                        |

### 5.3 Сигналы неудачи — когда отказаться от этого направления

**Стоп-линии метрик результата**:

- После получения данных Layer 1, **взвешенный followup_rate top-5 skill < 30%** → мало пространства для сокращения раундов, не стоит продолжать Layer 2
- После модификации 2 skill, **снижение E2E RT P50 < 1s** → выбрано неправильное направление (возможно, followup — write-операции, которые не следует объединять); остановиться и провести разбор
- После 2 недель изменения prompt Layer 3 **batch_size P50 всё ещё = 1** → модель не принимает руководство по параллелизму, отказаться от Layer 3, сохранить только Layer 1+2

**Стоп-линии метрик процесса (превентивное предупреждение, избегать схемы "кажется, что работаем, но выгоды нет")**:

- **Снижение hit rate skill (intended skill vs selected skill) ≥ 5pp** → описание skill изменено так, что модель выбирает неправильный skill. Типичный сценарий: до модификации запрос X всегда попадал в skill_a, а после неё иногда маршрутизируется в skill_b без генерации error (модель использует неправильный skill, но всё же формирует ответ); метрики результата выглядят нормально, однако followup_rate растёт. **Метод измерения**: добавить в telemetry `skill_invocation_pattern` — кластеризовать user prompt по первым N ключевым словам, определить основной skill каждого кластера и сравнить смещение top-1 до и после модификации
- **Частота неудач встроенного followup skill ≥ 5%** → модификация skill внесла режимы неудач, которых раньше не было (например, встроенный `read_file` обрабатывает большие файлы, взрывается память). Измерение: сравнение `SkillLaunchEvent.success` до/после модификации
- **Уровень отмены пользователем (Ctrl+C) на skill ≥ 2pp** → вывод skill стал медленнее или длиннее, пользователь теряет терпение. Измерение: доля `ToolCallEvent.status === 'cancelled'`

## 6. Связь с D1/D3

### 6.1 Связь с D1

После модификации top skill в Layer 2 **оставшиеся skill с большим числом followup становятся настоящими сценариями применения D1 `skipLlmRound`**: они уже имеют полный вывод (Round 2 не нужен) и действительно представляют собой конечные запросы (суммаризация Round 3 также избыточна).

Порядок выполнения:

1. Запуск telemetry Layer 1 → 1 неделя данных
2. Модификация Layer 2 top 2-3 skill → A/B 2 недели
3. Prompt параллелизм Layer 3 → фактическое тестирование 1 неделя
4. **В этот момент** оценить D1: сколько из оставшихся часто используемых skill имеют форму «полный вывод + конечный запрос» → стоит ли модификация фреймворка длительностью 2–3d

### 6.2 Связь с D3

D3 (`StreamingState.Summarizing`) — оптимизация уровня восприятия, полностью ортогональна этой схеме. Layer 1-3 уменьшает **фактическое количество раундов**, D3 уменьшает **воспринимаемое время ожидания пользователем**. Если Layer 2 уже снизил RT до приемлемого для пользователя диапазона, ценность D3 снижается; наоборот, D3 можно наложить сверху.

## 7. Ограничения и известные риски

1. **Покрытие ограничено областью модификации** — модификация 10 skill покрывает только их сценарии. Однако выгода точно измерима и накапливается
2. **Встроенный followup может утяжелить отдельный skill** — раздуть описание, замедлить загрузку и снизить возможность повторного использования. От этого защищает пункт 5 чек-листа Layer 2
3. **Layer 3 модель может не слушать руководство по параллелизму** — данные обучения qwen-coder склонны к последовательному выполнению; данные A/B могут показать, что изменение prompt неэффективно, как известный режим неудачи
4. **Границы приватности telemetry** — `SkillFollowupRecord` не должен записывать параметры инструментов (они уже по умолчанию берутся из `ToolCallEvent.function_args`, но нужно проверить, не раскрывает ли skill_name намерения пользователя)
5. **Не применимо к subagent / cron / notification** — эти пути не проходят через систему skill, поэтому схема их не покрывает
6. **Слабые базовые данные** — используется однократная выборка `rt-optimization-design.md` §1.2, перед реализацией Layer 2 нужно дополнить ≥3 сценария базовой линии
7. **Расширение полей `logSkillLaunch` нарушит существующие telemetry consumer** — 4 точки вызова + downstream logger требуют синхронной модификации
8. **`nessy-logger.ts:908` `logSkillLaunchEvent` сейчас мёртвый код** — в репозитории нет вызывающих сторон, §4.1.1b уже перечислил предварительное исправление

### 7.1 Границы с существующими механизмами фреймворка (не в scope этой схемы)

В репозитории уже есть несколько механизмов фреймворка, косвенно связанных с сокращением раундов; **эта схема не изобретает их заново и не заменяет**:

## 8. Временная линия реализации

> **Предпосылка: эта временная шкала начинается с P-1, который нельзя пропускать**. P-1 — предварительное ревью §0 Acceptance Spec объёмом 0.5d, но оно **обязательно**: без его прохождения нельзя переходить к P0. Ограничение предотвращает антипаттерн «сначала код, потом spec»: поздняя фиксация spec откладывает определение успеха до получения результатов и создаёт риск подгонки spec под красивые метрики (см. путь D2 в `rt-optimization-design.md` §7).

| Phase    | Содержание                                                                   | Затраты               | Результат                      | Действия по фиксации spec                           |
| -------- | ---------------------------------------------------------------------- | --------------------- | ------------------------------ | --------------------------------------- |
| **P-1**  | Предварительное ревью spec                                                       | 0.5d                  | Фиксация §0.1 / §0.3               | **Фиксация инженерной спецификации §0.1 + стоп-линий §0.3** |
| **P0**   | Восстановление канала nessy-logger (§4.1.1b предварительное)                                   | 0.5d                  | Подтверждение видимости событий skill_launch    | Проверка §0.1 пункт 1                       |
| **P1**   | Telemetry Layer 1: добавление поля `prompt_id` + офлайн SQL                      | 1-2d                  | Отчёт с рейтингом skill             | Проверка §0.1 пункты 2/3/4                   |
| **P1.5** | 1 неделя сбора данных + измерение базовой линии (≥3 сценария × ≥10 раз)                          | 1 неделя                    | Решение, какие 2-3 skill изменять          | **Фиксация порогов §0.2 + проверка §0.1 пункт 5**  |
| **P2**   | Модификация Layer 2 top-1 skill (PR + A/B)                                   | 0.5-1d модификация + 2 недели наблюдение | Подтверждение снижения followup_rate ↓, RT P50 ↓ | **Декларация per-skill spec §0.4 внутри PR**       |
| **P3**   | Prompt параллелизм Layer 3 + telemetry `batch_size` (включая передачу состояния §4.3.2) | 1-1.5d изменение + 1 неделя тестирование | Распределение batch_size                | Проверка §0.2 пункт 3                       |
| **P4**   | Продолжение модификации Layer 2 top-2 / top-3 skill (параллельно P3)                          | 0.5-1d × N            | Суммарное снижение RT P50                  | Декларация §0.4 в каждом PR                       |
| **P5**   | Оценка, сохраняет ли D1 ценность                                                  | Решение на встрече                | Обновление дорожной карты            | —                                       |

**Ключевые точки принятия решений (сверка со стоп-линиями §0.3)**:

- **Конец P-1**: по любому пункту §0.1 / §0.3 невозможно достичь консенсуса → не переходить к P0
- **Конец P1.5**: срабатывает стоп-линия §0.3 результат #1 (взвешенный followup_rate top-5 < 30%) → прекратить направление; иначе зафиксировать пороги §0.2
- **Конец P2**: срабатывает стоп-линия §0.3 для результата #2 (после модификации top-1 RT P50 ↓ < 1s) или любая процессная метрика → остановиться и провести разбор
- **Конец P3**: срабатывает стоп-линия §0.3 результат #3 (batch_size P50 всё ещё = 1) → отказаться от Layer 3
- **P5**: по форме оставшихся skill решить D1 ROI
