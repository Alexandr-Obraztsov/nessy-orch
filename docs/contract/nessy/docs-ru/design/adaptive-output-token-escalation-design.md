# Проектирование адаптивного увеличения выходных токенов

> Уменьшает избыточное резервирование GPU-слотов примерно в 4 раза за счёт стратегии «низкий лимит по умолчанию + увеличение при усечении» для выходных токенов с многоходовым восстановлением для ответов, превышающих даже увеличенный лимит.

## Проблема

Каждый API-запрос резервирует фиксированный GPU-слот, пропорциональный `max_tokens`. Предыдущее значение по умолчанию 32K токенов означает, что каждый запрос резервирует 32K выходной слот, но 99% ответов занимают менее 5K токенов. Это избыточно резервирует GPU-ёмкость в 4-6 раз, ограничивая параллелизм сервера и увеличивая стоимость.

## Решение

Использовать ограниченное значение по умолчанию **8K** выходных токенов. Когда ответ усечён (модель достигает `max_tokens`):

1. **Увеличить** до полного выходного лимита модели (с 64K в качестве нижнего предела для неизвестных моделей)
2. Если всё ещё усечено, **восстановить** путём сохранения частичного ответа в истории и вставки сообщения продолжения, до 3 раз
3. Если восстановление исчерпано, вернуться к рекомендациям по усечению планировщика инструментов

Поскольку фактически усечено менее 1% запросов, это значительно уменьшает среднее резервирование слотов, сохраняя при этом качество вывода для длинных ответов.

## Определение лимитов токенов

Эффективный `max_tokens` определяется в следующем порядке приоритета:

| Приоритет     | Источник                                           | Значение (известная модель)    | Значение (неизвестная модель) | Поведение при увеличении            |
| ------------- | -------------------------------------------------- | ------------------------------ | ----------------------------- | ----------------------------------- |
| 1 (высший)    | Конфигурация пользователя (`samplingParams.max_tokens`) | `min(userValue, modelLimit)`   | `userValue`                   | Без увеличения                        |
| 2             | Переменная окружения (`NESSY_CLI_MAX_OUTPUT_TOKENS`) | `min(envValue, modelLimit)`    | `envValue`                    | Без увеличения                        |
| 3 (низший)    | Ограниченное значение по умолчанию                 | `min(modelLimit, 8K)`          | `min(32K, 8K)` = 8K           | Увеличение до лимита модели (пол 64K) + восстановление |

«Известная модель» — модель с явной записью в `OUTPUT_PATTERNS` (проверяется через `hasExplicitOutputLimit()`). Для известных моделей эффективное значение всегда ограничено declared выходным лимитом модели во избежание ошибок API. Неизвестные модели (кастомные развёртывания, self-hosted endpoints) передают значение пользователя напрямую, поскольку бэкенд может поддерживать большие лимиты.

Эта логика реализована в трёх генераторах контента:

- `DefaultOpenAICompatibleProvider.applyOutputTokenLimit()` — OpenAI-совместимые провайдеры
- `DashScopeProvider` — наследует `applyOutputTokenLimit()` от провайдера по умолчанию
- `AnthropicContentGenerator.buildSamplingParameters()` — Anthropic провайдер

## Механизм увеличения

Логика увеличения находится в `geminiChat.ts`, размещена **вне** основного цикла повторных попыток. Это намеренно:

1. Цикл повторных попыток обрабатывает временные ошибки (ограничения скорости, невалидные стримы, валидация контента)
2. Усечение — не ошибка, а успешный ответ, который был обрезан
3. Ошибки из увеличенного стрима должны передаваться напрямую вызывающему коду, а не перехватываться логикой повторных попыток

### Шаги увеличения (geminiChat.ts)

```
1. Стрим завершён успешно (lastError === null)
2. Последний чанк имеет finishReason === MAX_TOKENS
3. Проверки guard проходят:
   - maxTokensEscalated === false (предотвращение бесконечного увеличения)
   - hasUserMaxTokensOverride === false (уважение намерений пользователя)
4. Вычислить увеличенный лимит: max(ESCALATED_MAX_TOKENS, tokenLimit(model, 'output'))
5. Извлечь частичный ответ модели из истории чата
6. Вернуть событие RETRY (isContinuation: false) → UI отбрасывает частичный вывод и сбрасывает буферы
7. Повторно отправить тот же запрос с maxOutputTokens: escalatedLimit
```

### Шаги восстановления (geminiChat.ts)

Если увеличенный ответ также усечён (finishReason === MAX_TOKENS), цикл восстановления выполняется до `MAX_OUTPUT_RECOVERY_ATTEMPTS` (3) раз:

```
1. Частичный ответ модели уже в истории (добавлен через processStreamResponse)
2. Вставить сообщение восстановления пользователя: OUTPUT_RECOVERY_MESSAGE
3. Вернуть событие RETRY (isContinuation: true) → UI сохраняет текстовый буфер для продолжения
4. Повторно отправить с обновлённой историей (модель видит свой частичный вывод + инструкцию восстановления)
5. Если всё ещё усечено и попытки остались, вернуться к шагу 1
6. Если попытка восстановления выбрасывает ошибку (пустой ответ, сетевая ошибка):
   - Извлечь зависшее сообщение восстановления из истории
   - Выйти из цикла восстановления
```

### Очистка состояния при RETRY (turn.ts)

Когда класс `Turn` получает событие RETRY, он очищает накопленное состояние для предотвращения несоответствий:

- `pendingToolCalls` — очищается во избежание дублирования вызовов инструментов, если первый усечённый ответ содержал завершённые вызовы, которые повторяются в увеличенном ответе
- `pendingCitations` — очищается во избежание дублирования цитат
- `finishReason` — сбрасывается в `undefined`, чтобы использовалась причина завершения нового ответа

Флаг `isContinuation` передаётся в UI, чтобы он мог решить, сбрасывать ли текстовые буферы (увеличение) или сохранять их (восстановление).

## Константы

Определены в `geminiChat.ts` и `tokenLimits.ts`:

| Константа                        | Значение | Назначение                                                  |
| -------------------------------- | -------- | ----------------------------------------------------------- |
| `CAPPED_DEFAULT_MAX_TOKENS`      | 8,000    | Лимит выходных токенов по умолчанию без переопределения пользователя |
| `ESCALATED_MAX_TOKENS`           | 64,000   | Нижний предел увеличения (используется при неизвестном лимите модели) |
| `MAX_OUTPUT_RECOVERY_ATTEMPTS`   | 3        | Максимум попыток многоходового восстановления после увеличения |

Эффективный увеличенный лимит: `max(ESCALATED_MAX_TOKENS, tokenLimit(model, 'output'))`:

| Модель           | Увеличенный лимит |
| ---------------- | ----------------- |
| Claude Opus 4.6  | 131,072 (128K)    |
| GPT-5 / o-series | 131,072 (128K)    |
| qwen3.x          | 65,536 (64K)      |
| Неизвестные модели | 64,000 (пол)      |

## Проектные решения

### Почему 8K по умолчанию?

- 99% ответов занимают менее 5K токенов
- 8K обеспечивает разумный запас для немного более длинных ответов без запуска ненужных повторных попыток
- Уменьшает среднее резервирование слотов с 32K до 8K (улучшение в 4 раза)

### Почему увеличение до лимита модели вместо фиксированных 64K?

- Модели с более высокими выходными лимитами (Claude Opus 128K, GPT-5 128K) были необоснованно ограничены 64K
- Использование фактического лимита модели охватывает подавляющее большинство длинных выводов без второго повторного запроса
- `ESCALATED_MAX_TOKENS` (64K) служит нижним пределом для неизвестных моделей, где `tokenLimit()` возвращает значение по умолчанию 32K

### Почему многоходовое восстановление вместо прогрессивного увеличения?

- Прогрессивное увеличение (8K → 16K → 32K → 64K) требует перегенерации полного ответа каждый раз
- Многоходовое восстановление сохраняет частичный ответ и позволяет модели продолжить, экономя токены и задержку
- Сообщения восстановления дёшевы (~40 токенов каждое) по сравнению с перегенерацией больших ответов
- Лимит в 3 попытки предотвращает бесконечные циклы, охватывая большинство практических случаев

### Почему увеличение вне цикла повторных попыток?

- Усечение — случай успеха, а не ошибка
- Ошибки из увеличенного стрима (ограничения скорости, сетевые сбои) должны передаваться напрямую, а не молча повторяться с некорректными параметрами
- Держит цикл повторных попыток сфокусированным на его исходной цели (восстановление после временных ошибок)
- Ошибки восстановления перехватываются отдельно во избежание прерывания всего разговора
