# Публикация расширений

Существует четыре основных способа публикации расширений для пользователей:

- [Git-репозиторий](#публикация-через-git-репозиторий)
- [GitHub Releases](#публикация-через-github-releases)
- [GitLab Releases](#публикация-через-gitlab-releases)
- [npm Registry](#публикация-через-npm-registry)

Публикация через Git-репозиторий — самый простой и гибкий вариант, в то время как Releases (GitHub/GitLab) могут быть более эффективными при первоначальной установке, поскольку поставляются как единые архивы вместо клонирования репозитория, загружающего каждый файл по отдельности. Releases могут также содержать архивы для конкретных платформ, если вам нужно поставлять бинарные файлы для конкретных платформ. Публикация через npm-реестр идеальна для команд, которые уже используют npm для распространения пакетов, особенно с приватными реестрами.

## Публикация через Git-репозиторий

Это самый гибкий и простой вариант. Всё, что вам нужно сделать, — создать публично доступный Git-репозиторий (например, публичный репозиторий GitHub), и затем пользователи смогут установить ваше расширение с помощью `nessy extensions install <your-repo-uri>`, или для репозитория GitHub они могут использовать упрощённый формат `nessy extensions install <org>/<repo>`. Они могут опционально зависеть от определённой ссылки (ветка/тег/коммит) с помощью аргумента `--ref=<some-ref>`, по умолчанию используется ветка по умолчанию.

Когда коммиты пушатся в ссылку, от которой зависит пользователь, им будет предложено обновить расширение. Обратите внимание, что это также позволяет лёгкие откаты — HEAD-коммит всегда рассматривается как последняя версия независимо от фактической версии в файле `nessy-extension.json`.

### Управление каналами выпуска с помощью Git-репозитория

Пользователи могут зависеть от любой ссылки из вашего Git-репозитория, такой как ветка или тег, что позволяет вам управлять несколькими каналами выпуска.

Например, вы можете поддерживать ветку `stable`, которую пользователи могут установить так: `nessy extensions install <your-repo-uri> --ref=stable`. Или вы можете сделать это по умолчанию, рассматривая вашу ветку по умолчанию как ветку стабильного выпуска и ведя разработку в другой ветке (например, называемой `dev`). Вы можете поддерживать столько веток или тегов, сколько хотите, обеспечивая максимальную гибкость для вас и ваших пользователей.

Обратите внимание, что эти аргументы `ref` могут быть тегами, ветками или даже конкретными коммитами, что позволяет пользователям зависеть от определённой версии вашего расширения. Вам решать, как вы хотите управлять вашими тегами и ветками.

### Пример потока выпуска через Git-репозиторий

Хотя есть много вариантов того, как вы хотите управлять выпусками через Git-поток, мы рекомендуем рассматривать вашу ветку по умолчанию как ветку «стабильного» выпуска. Это означает, что поведение по умолчанию для `nessy extensions install <your-repo-uri>` — быть на ветке стабильного выпуска.

Скажем, вы хотите поддерживать три стандартных канала выпуска: `stable`, `preview` и `dev`. Вы бы вели всю стандартную разработку в ветке `dev`. Когда вы готовы сделать предварительный выпуск, вы сливаете эту ветку в вашу ветку `preview`. Когда вы готовы продвинуть вашу ветку preview до стабильной, вы сливаете `preview` в вашу стабильную ветку (которая может быть вашей веткой по умолчанию или другой веткой).

Вы также можете выбирать изменения из одной ветки в другую с помощью `git cherry-pick`, но обратите внимание, что это приведёт к тому, что ваши ветки будут иметь немного расходящуюся историю друг от друга, если вы не форсируете пуш изменений в ваши ветки при каждом выпуске, чтобы восстановить историю до чистого состояния (что может быть невозможно для ветки по умолчанию в зависимости от настроек вашего репозитория). Если вы планируете делать cherry-picks, вы можете избежать того, чтобы ваша ветка по умолчанию была стабильной веткой, чтобы избежать форсирования пуша в ветку по умолчанию, чего обычно следует избегать.

## Публикация через GitHub Releases

Расширения Nessy CLI могут распространяться через [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases). Это обеспечивает более быстрый и надёжный опыт первоначальной установки для пользователей, поскольку избегает необходимости клонировать репозиторий.

Каждый выпуск включает по крайней мере один файл архива, который содержит полное содержимое репозитория на теге, к которому он был привязан. Выпуски могут также включать [предварительно собранные архивы](#пользовательские-предварительно-собранные-архивы), если ваше расширение требует шага сборки или имеет привязанные бинарные файлы для конкретных платформ.

При проверке обновлений Nessy CLI просто ищет последний выпуск на GitHub (вы должны отметить его как таковой при создании выпуска), если пользователь не установил конкретный выпуск, передав `--ref=<some-release-tag>`. В настоящее время мы не поддерживаем opting in к pre-release выпускам или semver.

### Пользовательские предварительно собранные архивы

Пользовательские архивы должны быть прикреплены непосредственно к выпуску GitHub как ассеты и должны быть полностью самодостаточными. Это означает, что они должны включать всё расширение, см. [структура архива](#структура-архива).

Если ваше расширение не зависит от платформы, вы можете предоставить один универсальный ассет. В этом случае к выпуску должен быть прикреплён только один ассет.

Пользовательские архивы также могут быть использованы, если вы хотите разрабатывать ваше расширение в большем репозитории — вы можете собрать архив, который имеет другую структуру, чем сам репозиторий (например, это может быть просто архив подкаталога, содержащего расширение).

#### Архивы для конкретных платформ

Чтобы обеспечить автоматическое нахождение Nessy CLI правильного ассета выпуска для каждой платформы, вы должны следовать этому соглашению об именах. CLI будет искать ассеты в следующем порядке:

1.  **Для конкретной платформы и архитектуры:** `{platform}.{arch}.{name}.{extension}`
2.  **Для конкретной платформы:** `{platform}.{name}.{extension}`
3.  **Универсальный:** Если предоставлен только один ассет, он будет использоваться как универсальный запасной вариант.

- `{name}`: Имя вашего расширения.
- `{platform}`: Операционная система. Поддерживаемые значения:
  - `darwin` (macOS)
  - `linux`
  - `win32` (Windows)
- `{arch}`: Архитектура. Поддерживаемые значения:
  - `x64`
  - `arm64`
- `{extension}`: Расширение файла архива (например, `.tar.gz` или `.zip`).

**Примеры:**

- `darwin.arm64.my-tool.tar.gz` (специфично для Mac на Apple Silicon)
- `darwin.my-tool.tar.gz` (для всех Mac)
- `linux.x64.my-tool.tar.gz`
- `win32.my-tool.zip`

#### Структура архива

Архивы должны быть полностью содержащими расширения и иметь все стандартные требования — в частности, файл `nessy-extension.json` должен находиться в корне архива.

Остальная структура должна выглядеть точно так же, как типичное расширение, см. [introduction.md](introduction.md).

#### Пример рабочего процесса GitHub Actions

Вот пример рабочего процесса GitHub Actions, который собирает и выпускает расширение Nessy CLI для нескольких платформ:

```yaml
name: Release Extension

on:
  push:
    tags:
      - 'v*'

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3

      - name: Set up Node.js
        uses: actions/setup-node@v3
        with:
          node-version: '22'

      - name: Install dependencies
        run: npm ci

      - name: Build extension
        run: npm run build

      - name: Create release assets
        run: |
          npm run package -- --platform=darwin --arch=arm64
          npm run package -- --platform=linux --arch=x64
          npm run package -- --platform=win32 --arch=x64

      - name: Create GitHub Release
        uses: softprops/action-gh-release@v1
        with:
          files: |
            release/darwin.arm64.my-tool.tar.gz
            release/linux.arm64.my-tool.tar.gz
            release/win32.arm64.my-tool.zip
```

#### Пример рабочего процесса GitLab CI

Вот пример рабочего процесса GitLab CI, который собирает и выпускает расширение Nessy CLI для нескольких платформ:

```yaml
stages:
  - build
  - release

build:
  stage: build
  image: node:20
  script:
    - npm ci
    - npm run build
  artifacts:
    paths:
      - dist/

release:
  stage: release
  image: registry.gitlab.com/gitlab-org/release-cli:latest
  needs:
    - build
  script:
    - echo "Creating release for $CI_COMMIT_TAG"
  release:
    tag_name: $CI_COMMIT_TAG
    assets:
      links:
        - name: darwin.arm64.my-extension.tar.gz
          url: ${CI_PROJECT_URL}/-/jobs/${CI_JOB_ID}/artifacts/dist/darwin.arm64.my-extension.tar.gz
        - name: linux.x64.my-extension.tar.gz
          url: ${CI_PROJECT_URL}/-/jobs/${CI_JOB_ID}/artifacts/dist/linux.x64.my-extension.tar.gz
        - name: win32.my-extension.zip
          url: ${CI_PROJECT_URL}/-/jobs/${CI_JOB_ID}/artifacts/dist/win32.my-extension.zip
  rules:
    - if: $CI_COMMIT_TAG
```

### Пример: Внутреннее расширение T-Bank

Для внутренних расширений, публикуемых в GitLab T-Bank:

```bash
# Установка из выпусков GitLab
nessy extensions install https://gitlab.tcsbank.ru/nestor/nessy-cli-extensions

# Установка конкретного выпуска
nessy extensions install https://gitlab.tcsbank.ru/nestor/nessy-cli-extensions --ref=v1.0.0
```

Конвейер GitLab CI обрабатывает сборку и создание выпусков автоматически при пуше тегов. Конвейер:

1. Проверяет соответствие версии между тегом и `package.json`
2. Собирает расширение в каталог `dist/`
3. Создаёт выпуск GitLab с прикреплёнными архивами
4. Автоматически увеличивает версию и создает MR для следующего выпуска

Для получения дополнительной информации о конфигурации CI/CD см. файл `.gitlab-ci.yml` проекта.

## Публикация через npm-реестр

Вы можете публиковать расширения Nessy CLI как скоупированные npm-пакеты (например, `@your-org/my-extension`). Это хорошо подходит, когда:

- Ваша команда уже использует npm для распространения пакетов
- Вам нужна поддержка приватного реестра с существующей инфраструктурой аутентификации
- Вы хотите, чтобы разрешение версий и контроль доступа обрабатывались npm

### Требования к пакету

Ваш npm-пакет должен включать файл `nessy-extension.json` в корне пакета. Это тот же конфигурационный файл, который используется всеми расширениями Nessy CLI — npm-тарболл — это просто другой механизм доставки.

Минимальная структура пакета выглядит так:

```
my-extension/
├── package.json
├── nessy-extension.json
├── NESSY.md              # опциональный файл контекста
├── commands/             # опциональные пользовательские команды
├── skills/               # опциональные пользовательские навыки
└── agents/               # опциональные пользовательские субагенты
```

Убедитесь, что `nessy-extension.json` включён в ваш опубликованный пакет (т.е. не исключён `.npmignore` или полем `files` в `package.json`).

### Публикация

Используйте стандартные инструменты публикации npm:

```bash
# Публикация в реестр по умолчанию
npm publish

# Публикация в приватный/кастомный реестр
npm publish --registry https://your-registry.com
```

### Установка

Пользователи устанавливают ваше расширение, используя скоупированное имя пакета:

```bash
# Установить последнюю версию
nessy extensions install @your-org/my-extension

# Установить конкретную версию
nessy extensions install @your-org/my-extension@1.2.0

# Установить из кастомного реестра
nessy extensions install @your-org/my-extension --registry https://your-registry.com
```

### Поведение обновления

- Расширения, установленные без привязки к версии (например, `@scope/pkg`), отслеживают dist-тег `latest`.
- Расширения, установленные с dist-тегом (например, `@scope/pkg@beta`), отслеживают этот конкретный тег.
- Расширения, привязанные к точной версии (например, `@scope/pkg@1.2.0`), всегда считаются обновлёнными и не будут предлагать обновления.

### Аутентификация для приватных реестров

Nessy CLI автоматически считывает учётные данные npm:

1.  **Переменная окружения `NPM_TOKEN`** — наивысший приоритет
2.  **Файл `.npmrc`** — поддерживает как записи `_authToken` на уровне хоста, так и с областью пути (например, `//your-registry.com/:_authToken=TOKEN` или `//pkgs.dev.azure.com/org/_packaging/feed/npm/registry/:_authToken=TOKEN`)

Файлы `.npmrc` считываются из текущего каталога и домашнего каталога пользователя.

### Управление каналами выпуска

Вы можете использовать npm dist-теги для управления каналами выпуска:

```bash
# Публикация beta-выпуска
npm publish --tag beta

# Пользователи устанавливают beta-канал
nessy extensions install @your-org/my-extension@beta
```

Это работает аналогично каналам выпуска на основе Git-веток, но использует собственный механизм dist-тегов npm.

### Пример: Внутреннее расширение T-Bank

Для внутренних расширений, публикуемых в реестр artifactory T-Bank:

```bash
# Установка из внутреннего реестра (npm-all включает все реестры)
nessy extensions install @nestor/nessy-cli-extensions --registry=https://artifactory.tcsbank.ru/artifactory/api/npm/npm-all/

# Установка beta-версии из внутреннего реестра
nessy extensions install @nestor/nessy-cli-extensions@beta --registry=https://artifactory.tcsbank.ru/artifactory/api/npm/npm-all/
```

Конвейер GitLab CI обрабатывает публикацию автоматически при пуше тегов выпуска. Конвейер:

1. Проверяет соответствие версии между тегом и `package.json`
2. Собирает расширение в каталог `dist/`
3. Публикует в размещенный npm artifactory с соответствующим dist-тегом (`beta` или `latest`)
4. Автоматически увеличивает версию и создает MR для следующего выпуска

Пользователи устанавливают из `npm-all` (агрегирующий реестр).

Для получения дополнительной информации о конфигурации CI/CD см. файл `.gitlab-ci.yml` проекта.
