# Subagents (Субагенты)

Subagents — это специализированные AI-ассистенты, которые выполняют определённые типы задач в рамках Nessy CLI. Они позволяют вам делегировать сфокусированную работу AI-агентам, настроенным с специфичными для задачи подсказками, инструментами и поведением.

## Что такое Subagents?

Subagents — это независимые AI-ассистенты, которые:

- **Специализируются на конкретных задачах** — каждый Subagent настроен с сфокусированным системным промптом для определённых типов работы
- **Имеют отдельный контекст** — они поддерживают свою собственную историю разговора, отдельную от основного чата
- **Используют контролируемые инструменты** — вы можете настроить, к каким инструментам имеет доступ каждый Subagent
- **Работают автономно** — получив задачу, они работают независимо до завершения или отказа
- **Предоставляют детальную обратную связь** — вы можете видеть их прогресс, использование инструментов и статистику выполнения в реальном времени

## Fork Subagent (Неявный Fork)

В дополнение к именным субагентам, Nessy CLI поддерживает **неявное форкирование** — когда AI опускает параметр `subagent_type`, это запускает fork, который наследует полный контекст разговора родителя.

### Как Fork отличается от именованных субагентов

|                       | Именованный субагент                                   | Fork субагент                                                 |
| --------------------- | ------------------------------------------------------ | ------------------------------------------------------------- |
| Контекст              | Начинает с нуля, без истории родителя                  | Наследует полную историю разговора родителя                   |
| Системный промпт      | Использует свой настроенный промпт                     | Использует точный системный промпт родителя (для кэширования) |
| Выполнение            | Блокирует родителя до завершения                       | Работает в фоне, родитель продолжает немедленно               |
| Вариант использования | Специализированные задачи (тестирование, документация) | Параллельные задачи, нуждающиеся в текущем контексте          |

### Когда используется Fork

AI автоматически использует fork, когда ему нужно:

- Запустить несколько исследовательских задач параллельно (например, "исследовать модуль A, B и C")
- Выполнить фоновую работу, продолжая основной разговор
- Делегировать задачи, требующие понимания текущего контекста разговора

### Кэширование промптов

Все forks разделяют точный префикс API-запроса родителя (системный промпт, инструменты, история разговора), обеспечивая попадания кэша DashScope. Когда 3 forks выполняются параллельно, общий префикс кэшируется один раз и переиспользуется — экономия 80%+ стоимости токенов по сравнению с независимыми субагентами.

### Предотвращение рекурсивного Fork

Fork-дети не могут создавать дальнейшие forks. Это обеспечивается на runtime — если fork пытается породить другой fork, он получает ошибку с инструкцией выполнять задачи напрямую.

### Текущие ограничения

- **Нет обратной связи с результатом**: Результаты Fork отображаются в UI прогресса, но не автоматически возвращаются в основной разговор. Родительский AI видит сообщение-заполнитель и не может действовать на вывод fork.
- **Нет изоляции worktree**: Forks разделяют рабочую директорию родителя. Одновременные изменения файлов от нескольких forks могут конфликтовать.

## Ключевые преимущества

- **Специализация задач**: Создание агентов, оптимизированных для конкретных рабочих процессов (тестирование, документация, рефакторинг и т.д.)
- **Изоляция контекста**: Разделение специализированной работы от основного разговора
- **Наследование контекста**: Fork субагенты наследуют полный разговор для контекстно-тяжёлых параллельных задач
- **Разделение кэша промптов**: Fork субагенты разделяют префикс кэша родителя, снижая стоимость токенов
- **Повторное использование**: Сохранение и повторное использование конфигураций агентов между проектами и сессиями
- **Контролируемый доступ**: Ограничение инструментов, к которым каждый агент имеет доступ, для безопасности и фокуса
- **Видимость прогресса**: Мониторинг выполнения агента с обновлением прогресса в реальном времени

## Как работают Subagents

1. **Конфигурация**: Вы создаёте конфигурации Subagents, которые определяют их поведение, инструменты и системные промпты
2. **Делегирование**: Основной AI может автоматически делегировать задачи соответствующим Subagents — или неявно форкать, когда не нужен специфический тип субагента
3. **Выполнение**: Subagents работают независимо, используя свои настроенные инструменты для выполнения задач
4. **Результаты**: Они возвращают результаты и сводки выполнения обратно в основной разговор

## Начало работы

### Быстрый старт

1. **Создайте ваш первый Subagent**:

   `/agents create`

   Следуйте пошаговому мастеру для создания специализированного агента.

2. **Управляйте существующими агентами**:

   `/agents manage`

   Просмотр и управление настроенными Subagents.

3. **Используйте Subagents автоматически**: Просто попросите основной AI выполнить задачи, соответствующие специализациям ваших Subagents. AI будет автоматически делегировать соответствующую работу.

### Пример использования

```
Пользователь: "Пожалуйста, напишите комплексные тесты для модуля аутентификации"
AI: Я делегирую это вашему специализированному субагенту по тестированию.
[Делегирует субагенту "testing-expert"]
[Показывает прогресс создания тестов в реальном времени]
[Возвращается с готовыми тестовыми файлами и сводкой выполнения]
```

## Управление

### CLI команды

Subagents управляются через slash-команду `/agents` и её подкоманды:

**Использование:** `/agents create` — создаёт новый Subagent через пошаговый мастер.

**Использование:** `/agents manage` — открывает интерактивный диалог управления для просмотра и управления существующими Subagents.

### Места хранения

Subagents хранятся как Markdown-файлы в нескольких местах:

- **Уровень проекта**: `.nessy/agents/` (наивысший приоритет)
- **Уровень пользователя**: `~/.nessy/agents/` (резервный)
- **Уровень расширений**: Предоставляются установленными расширениями

Это позволяет иметь агентов для конкретного проекта, личных агентов, работающих во всех проектах, и агентов от расширений, добавляющих специализированные возможности.

### Subagents расширений

Расширения могут предоставлять пользовательские субагенты, которые становятся доступными при включении расширения. Эти агенты хранятся в директории `agents/` расширения и следуют тому же формату, что и личные агенты и агенты проекта.

Subagents расширений:

- Автоматически обнаруживаются при включении расширения
- Появляются в диалоге `/agents manage` в секции "Extension Agents"
- Не могут быть отредактированы напрямую (редактируйте исходник расширения)
- Следуют тому же формату конфигурации, что и определённые пользователем агенты

Чтобы увидеть, какие расширения предоставляют субагенты, проверьте файл `nessy-extension.json` расширения на поле `agents`.

### Формат файла

Subagents настраиваются с помощью Markdown-файлов с YAML frontmatter. Этот формат читаем человеком и легко редактируется любым текстовым редактором.

#### Базовая структура

```yaml
---
name: agent-name
description: Краткое описание, когда и как использовать этого агента
model: inherit # Опционально: inherit или model-id
approvalMode: auto-edit # Опционально: default, plan, auto-edit
tools: # Опционально: разрешённые инструменты
  - tool1
  - tool2
disallowedTools: # Опционально: заблокированные инструменты
  - tool3
---
Содержимое системного промпта идёт здесь.
Несколько параграфов поддерживаются.
```

#### Выбор модели

Используйте опциональное поле frontmatter `model` для контроля, какую модель использует субагент:

- `inherit`: Использовать ту же модель, что и основной разговор
- Опустить поле: То же, что `inherit`
- `glm-5`: Использовать этот ID модели с типом аутентификации основного разговора
- `openai:gpt-4o`: Использовать другого провайдера (учётные данные из env var)

#### Режим разрешений

Используйте опциональное поле frontmatter `approvalMode` для контроля, как утверждаются вызовы инструментов субагента. Валидные значения:

- `default`: Инструменты требуют интерактивного утверждения (то же, что default сессии)
- `plan`: Режим только анализа — агент планирует, но не выполняет изменения
- `auto-edit`: Инструменты автоматически утверждаются без запроса (рекомендуется для большинства агентов)

Если вы опускаете это поле, режим разрешений субагента определяется автоматически:

- Если родительская сессия в режиме **plan**, субагент остаётся в режиме plan. Сессия только анализа не может изменять файлы через делегированного агента.
- Если родительская сессия в режиме **default** (в доверенной папке), субагент получает **auto-edit**, чтобы работать автономно.

Когда вы устанавливаете `approvalMode`, пермиссивные режимы родителя всё ещё имеют приоритет. Например, если родитель в режиме auto-edit, субагент с `approvalMode: plan` всё ещё будет работать в режиме auto-edit.

```yaml
---
name: cautious-reviewer
description: Рецензирует код без внесения изменений
approvalMode: plan
tools:
  - read_file
  - grep_search
  - glob
---
Вы — рецензент кода. Анализируйте код и сообщайте о находках.
Не изменяйте никакие файлы.
```

#### Конфигурация инструментов

#### Поля совместимости с Claude Code

При импорте определений Claude Code поддерживаются совместимые поля описания,
модели, разрешений и инструментов; неизвестные поля игнорируются.

Используйте `tools` и `disallowedTools` для контроля, к каким инструментам имеет доступ субагент.

**`tools` (allowlist)**: При указании субагент может использовать только перечисленные инструменты. При опускании субагент наследует все доступные инструменты от родительской сессии.

```yaml
---
name: reader
description: Агент только для чтения для исследования кода
tools:
  - read_file
  - grep_search
  - glob
  - list_directory
---
```

**`disallowedTools` (blocklist)**: При указании перечисленные инструменты удаляются из пула инструментов субагента. Это полезно, когда вы хотите "всё кроме X" без перечисления каждого разрешённого инструмента.

```yaml
---
name: safe-worker
description: Агент, который не может изменять файлы
disallowedTools:
  - write_file
  - edit
  - run_shell_command
---
```

Если установлены и `tools`, и `disallowedTools`, allowlist применяется первым, затем blocklist удаляет из этого набора.

**Инструменты MCP** следуют тем же правилам. Если у субагента нет списка `tools`, он наследует все инструменты MCP от родительской сессии. Если у субагента есть явный список `tools`, он получает только инструменты MCP, явно названные в этом списке.

Поле `disallowedTools` поддерживает паттерны уровня MCP-сервера:

- `mcp__server__tool_name` — блокирует конкретный инструмент MCP
- `mcp__server` — блокирует все инструменты от этого MCP-сервера

```yaml
---
name: no-slack
description: Агент без доступа к Slack
disallowedTools:
  - mcp__slack
---
```

#### Пример использования

```yaml
---
name: project-documenter
description: Создаёт документацию проекта и README-файлы
---
Вы — специалист по документации.
```

## Эффективное использование Subagents

### Автоматическое делегирование

Nessy CLI проактивно делегирует задачи на основе:

- Описания задачи в вашем запросе
- Поля description в конфигурациях Subagents
- Текущего контекста и доступных инструментов

Чтобы поощрить более проактивное использование Subagents, включите фразы вроде "use PROACTIVELY" или "MUST BE USED" в вашем поле description.

### Явный вызов

Запросите конкретного Subagent, упомянув его в вашей команде:

```
Пусть testing-expert Subagent создаст юнит-тесты для модуля оплаты
Пусть documentation-writer Subagent обновит справочник API
Пусть react-specialist Subagent оптимизирует производительность этого компонента
```

## Примеры

### Агенты рабочего процесса разработки

#### Специалист по тестированию

Идеально для комплексного создания тестов и test-driven разработки.

```yaml
---
name: testing-expert
description: Пишет комплексные юнит-тесты, интеграционные тесты и обрабатывает автоматизацию тестирования с лучшими практиками
tools:
  - read_file
  - write_file
  - read_many_files
  - run_shell_command
---

Вы — специалист по тестированию, сфокусированный на создании высококачественных, поддерживаемых тестов.

Ваша экспертиза включает:

- Юнит-тестирование с соответствующим мокированием и изоляцией
- Интеграционное тестирование для взаимодействий компонентов
- Практики test-driven разработки
- Идентификация граничных случаев и комплексное покрытие
- Производительность и нагрузочное тестирование, когда уместно

Для каждой задачи тестирования:

1. Анализируйте структуру кода и зависимости
2. Идентифицируйте ключевую функциональность, граничные случаи и условия ошибок
3. Создавайте комплексные тестовые наборы с описательными именами
4. Включайте правильную setup/teardown и осмысленные утверждения
5. Добавляйте комментарии, объясняющие сложные сценарии тестов
6. Убеждайтесь, что тесты поддерживаемы и следуют принципам DRY

Всегда следуйте лучшим практикам тестирования для обнаруженного языка и фреймворка.
Фокусируйтесь как на позитивных, так и на негативных тестовых случаях.
```

**Варианты использования:**

- "Напишите юнит-тесты для сервиса аутентификации"
- "Создайте интеграционные тесты для рабочего процесса обработки платежей"
- "Добавьте тестовое покрытие для граничных случаев в модуле валидации данных"

#### Писатель документации

Специализирован на создании ясной, комплексной документации.

```yaml
---
name: documentation-writer
description: Создаёт комплексную документацию, README-файлы, API-документацию и руководства пользователя
tools:
  - read_file
  - write_file
  - read_many_files
---

Вы — специалист по технической документации.

Ваша роль — создавать ясную, комплексную документацию, которая служит как разработчикам, так и конечным пользователям. Фокусируйтесь на:

**Для API-документации:**

- Ясные описания endpoints с примерами
- Детали параметров с типами и ограничениями
- Документирование формата ответов
- Объяснения кодов ошибок
- Требования аутентификации

**Для пользовательской документации:**

- Пошаговые инструкции со скриншотами, когда полезно
- Руководства по установке и настройке
- Опции конфигурации и примеры
- Секции устранения неполадок для распространённых вопросов
- Секции FAQ на основе распространённых пользовательских вопросов

**Для документации разработчика:**

- Обзоры архитектуры и решения дизайна
- Рабочие примеры кода
- Руководства по контрибьюции
- Настройка среды разработки

Всегда проверяйте примеры кода и убеждайтесь, что документация остаётся актуальной с фактической реализацией. Используйте ясные заголовки, маркированные списки и примеры.
```

**Варианты использования:**

- "Создайте API-документацию для endpoints управления пользователями"
- "Напишите комплексный README для этого проекта"
- "Задокументируйте процесс развёртывания с шагами устранения неполадок"

```yaml

  - read_file
  - read_many_files
---

Вы — опытный рецензент кода, сфокусированный на качестве, безопасности и поддерживаемости.

Критерии ревью:

- **Структура кода**: Организация, модульность и разделение ответственности
- **Производительность**: Алгоритмическая эффективность и использование ресурсов
- **Безопасность**: Оценка уязвимостей и практики безопасного кодирования
- **Лучшие практики**: Специфичные для языка/фреймворка конвенции
- **Обработка ошибок**: Правильная обработка исключений и покрытие граничных случаев
- **Читаемость**: Ясные имена, комментарии и организация кода
- **Тестирование**: Покрытие тестами и соображения тестируемости

Предоставляйте конструктивную обратную связь с:

1. **Критические проблемы**: Уязвимости безопасности, крупные баги
2. **Важные улучшения**: Проблемы производительности, проблемы дизайна
3. **Минорные предложения**: Улучшения стиля, возможности рефакторинга
4. **Позитивная обратная связь**: Хорошо реализованные паттерны и хорошие практики

Фокусируйтесь на действенной обратной связи с конкретными примерами и предлагаемыми решениями.
Приоритизируйте проблемы по влиянию и предоставляйте обоснование для рекомендаций.
```

### Принципы дизайна

#### Принцип единственной ответственности

Каждый Subagent должен иметь ясную, сфокусированную цель.

**✅ Хорошо:**

```yaml
---
name: testing-expert
description: Пишет комплексные юнит-тесты и интеграционные тесты
---
```

**❌ Избегайте:**

```yaml
---
name: general-helper
description: Помогает с тестированием, документацией, ревью кода и развёртыванием
---
```

**Почему:** Сфокусированные агенты дают лучшие результаты и их легче поддерживать.

#### Ясная специализация

Определите специфичные области экспертизы, а не широкие возможности.

**✅ Хорошо:**

```yaml
---
name: react-performance-optimizer
description: Оптимизирует React-приложения для производительности, используя профилирование и лучшие практики
---
```

**❌ Избегайте:**

```yaml
---
name: frontend-developer
description: Работает над задачами фронтенд-разработки
---
```

**Почему:** Специфичная экспертиза ведёт к более целевой и эффективной помощи.

#### Действенные описания

Пишите описания, которые ясно указывают, когда использовать агента.

**✅ Хорошо:**

```yaml
description: Рецензирует код на уязвимости безопасности, проблемы производительности и проблемы поддерживаемости
```

**❌ Избегайте:**

```yaml
description: Полезный рецензент кода
```

**Почему:** Ясные описания помогают основному AI выбрать правильного агента для каждой задачи.

### Лучшие практики конфигурации

#### Руководства по системному промпту

**Будьте специфичны об экспертизе:**

```
Вы — специалист по тестированию Python с экспертизой в:

- Фреймворк pytest и fixtures
- Mock-объекты и внедрение зависимостей
- Практики test-driven разработки
- Тестирование производительности с pytest-benchmark
```

**Включайте пошаговые подходы:**

```
Для каждой задачи тестирования:

1. Анализируйте структуру кода и зависимости
2. Идентифицируйте ключевую функциональность и граничные случаи
3. Создавайте комплексные тестовые наборы с ясным именованием
4. Включайте setup/teardown и правильные утверждения
5. Добавляйте комментарии, объясняющие сложные сценарии тестов
```

**Указывайте стандарты вывода:**

```
Всегда следуйте этим стандартам:

- Используйте описательные имена тестов, объясняющие сценарий
- Включайте как позитивные, так и негативные тестовые случаи
- Добавляйте docstrings для сложных тестовых функций
- Убеждайтесь, что тесты независимы и могут запускаться в любом порядке
```

## Соображения безопасности

- **Ограничения инструментов**: Используйте `tools` для ограничения инструментов, к которым имеет доступ субагент, или `disallowedTools` для блокировки специфичных инструментов, наследуя всё остальное
- **Режим разрешений**: Субагенты наследуют режим разрешений родителя по умолчанию. Сессии в режиме plan не могут эскалировать до auto-edit через делегированных агентов. Привилегированные режимы (auto-edit) блокируются в недоверенных папках.
- **Песочница**: Всё выполнение инструментов следует той же модели безопасности, что и прямое использование инструментов
- **Аудит-трейл**: Все действия Subagents логируются и видны в реальном времени
- **Контроль доступа**: Разделение на уровне проекта и пользователя обеспечивает соответствующие границы
- **Чувствительная информация**: Избегайте включения секретов или учётных данных в конфигурации агентов
- **Продакшен-окружения**: Рассмотрите отдельные агенты для продакшена и разработки

## Лимиты

Следующие мягкие предупреждения применяются к конфигурациям Subagent (жёсткие лимиты не применяются):

- **Поле description**: Предупреждение показывается для описаний, превышающих 1000 символов
- **Системный промпт**: Предупреждение показывается для системных промптов, превышающих 10 000 символов
