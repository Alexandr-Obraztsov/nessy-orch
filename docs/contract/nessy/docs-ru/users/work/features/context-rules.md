# Контекстные правила (.nessy/rules/)

Контекстные правила позволяют определять инструкции для проекта или глобально, которые автоматически добавляются в системный промпт модели. Правила живут в директориях `.nessy/rules/` и поддерживают условную загрузку на основе паттернов путей к файлам.

Эта функция полезна для закрепления командных соглашений, архитектурных решений, стандартов кодинга и предметных знаний, которым модель должна следовать при работе с вашей кодовой базой.

## Обзор

Контекстные правила предоставляют структурированный способ сохранения и автоматического применения знаний между сессиями. В отличие от NESSY.md, который является единственным файлом, правила могут быть:

- **Организованы иерархически** — разбиты на несколько файлов по темам, командам или компонентам
- **Загружены условно** — добавляются только при обращении к соответствующим файлам
- **Глобальными или для проекта** — делитесь правилами между проектами или храните их только для конкретного проекта

## Структура директорий

Правила обнаруживаются в двух местах:

| Расположение           | Путь                          | Когда загружается           |
| ---------------------- | ----------------------------- | --------------------------- |
| **Глобальные правила** | `~/.nessy/rules/`             | Всегда (для всех проектов)  |
| **Правила проекта**    | `<projectRoot>/.nessy/rules/` | Только для доверенных папок |

**Важно:** Правила проекта требуют доверия к папке. Если корень проекта совпадает с глобальной директорией правил, дубликаты пропускаются.

### Организация файлов

Правила — это Markdown-файлы (`.md`), которые могут быть организованы в поддиректории:

```
.nessy/rules/
├── general.md              # Базовые правила (всегда загружаются)
├── security.md             # Базовые правила (всегда загружаются)
├── frontend/
│   ├── react.md            # Условные (src/**/*.tsx)
│   └── styling.md          # Условные (src/**/*.css)
└── backend/
    ├── api.md              # Условные (src/api/**/*.ts)
    └── database.md         # Условные (prisma/**/*.prisma)
```

## Формат файла правил

Каждый файл правила — это Markdown-документ с опциональным YAML frontmatter.

### Базовые правила (всегда загружаются)

Правила без `paths:` во frontmatter добавляются в начале сессии:

```markdown
---
description: Общие стандарты кодинга
---

Всегда пишите юнит-тесты для нового функционала.
Используйте описательные имена переменных и функций.
Добавляйте JSDoc комментарии для публичных API.
```

### Условные правила (ленивая загрузка)

Правила с `paths:` добавляются только когда модель обращается к соответствующему файлу:

```markdown
---
description: Гайдлайны для React компонентов
paths:
  - 'src/**/*.tsx'
  - 'src/**/*.ts'
---

Используйте функциональные React компоненты с хуками.
Избегайте классовых компонентов и устаревших методов жизненного цикла.
Размещайте стили компонентов рядом с кодом компонента.
```

### Поля Frontmatter

| Поле          | Тип      | Обязательно | Описание                                                      |
| ------------- | -------- | ----------- | ------------------------------------------------------------- |
| `description` | string   | Нет         | Человекочитаемая метка правила (используется в логах/отладке) |
| `paths`       | string[] | Нет         | Glob-паттерны, определяющие когда применяется правило         |

### Содержимое тела

- Пишите естественным языком (английский или предпочтительный язык команды)
- Используйте четкие императивные утверждения («Всегда...», «Никогда...», «Предпочитайте...»)
- HTML-комментарии (`<!-- ... -->`) вырезаются для экономии токенов
- Пустые файлы или файлы только с комментариями игнорируются

## Паттерны путей

Поле `paths:` использует glob-паттерны, обрабатываемые [picomatch](https://github.com/micromatch/picomatch):

| Паттерн            | Соответствует                           |
| ------------------ | --------------------------------------- |
| `src/**/*.ts`      | Все `.ts` файлы под `src/` (рекурсивно) |
| `*.test.ts`        | Тест-файлы в корне проекта              |
| `**/*.test.ts`     | Тест-файлы в любой директории           |
| `**/*.prisma`      | Все файлы схемы Prisma                  |
| `packages/core/**` | Всё под `packages/core/`                |

**Важно:**

- Паттерны сопоставляются с путями относительно корня проекта
- Если указано несколько паттернов, правило применяется при совпадении хотя бы с одним из них
- Отрицательные паттерны (`!pattern`) не исключают файлы из результатов других паттернов; используйте отдельные правила с более точными позитивными паттернами
- Используйте прямые слеши (`/`) для кроссплатформенной консистентности
- Паттерны чувствительны к регистру

## Конфигурация

### Доверие к папке

Правила проекта (`.nessy/rules/` внутри проекта) загружаются только когда папка помечена как доверенная. Глобальные правила (`~/.nessy/rules/`) загружаются всегда.

Чтобы добавить папку в доверенные:

```bash
/directory add /path/to/your/project
```

## Как загружаются правила

### При старте сессии

1. **Глобальные правила** загружаются из `~/.nessy/rules/` (все `.md` файлы, рекурсивно)
2. **Правила проекта** загружаются из `<project>/.nessy/rules/` (если папка доверена)
3. Правила разделяются на:
   - **Базовые правила** (без `paths:`) → добавляются в системный промпт немедленно
   - **Условные правила** (с `paths:`) → сохраняются для ленивой загрузки
4. Файлы сортируются по алфавиту для детерминированного порядка

### Ленивая загрузка на уровне ходов

Когда модель читает или редактирует файл:

1. Реестр условных правил проверяет, соответствует ли путь к файлу каким-либо паттернам `paths:`
2. Соответствующие правила, которые еще не были добавлены, форматируются и добавляются в контекст разговора
3. Каждое правило добавляется **только один раз за сессию**

Этот подход:

- Уменьшает начальное использование токенов
- Держит системный промпт сфокусированным на релевантных правилах
- Масштабируется на большие наборы правил без перегрузки модели

## Примеры

### Пример 1: Стандарты кодинга команды

```markdown
---
description: Соглашения для Backend API
paths:
  - 'src/api/**/*.ts'
---

Все API эндпоинты должны:

1. Использовать async/await для асинхронных операций
2. Валидировать входные данные с помощью Zod схем
3. Возвращать консистентный формат ошибок через класс AppError
4. Логировать запросы с correlation ID

Запросы к базе данных должны использовать паттерн repository — никаких прямых вызовов Prisma в контроллерах.
```

### Пример 2: Гайдлайны по безопасности

```markdown
---
description: Правила безопасности для работы с чувствительными данными
---

Никогда не логируйте чувствительную информацию:

- API ключи, токены или учетные данные
- Пароли пользователей или PII
- Строки подключения к базе данных

Используйте переменные окружения для секретов (process.env.XYZ).
Никогда не коммитьте .env файлы и не хардкодьте учетные данные.

Все пользовательские данные должны быть санированы перед запросами к базе данных.
```

### Пример 3: Правила для конкретных компонентов

```markdown
---
description: Правила для обработки платежей
paths:
  - 'src/payments/**/*.ts'
  - 'src/checkout/**/*.tsx'
---

Код для платежей должен:

1. Использовать ключи идемпотентности для всех операций списания
2. Проверять подписи вебхуков перед обработкой
3. Все суммы обрабатывать в центах (целые числа), не в десятичных
4. PCI-DSS compliance: никогда не логируйте полные номера карт

Используйте абстракцию PaymentService — прямые вызовы Stripe SDK запрещены.
```

### Пример 4: Архитектурные решения

```markdown
---
description: Архитектура управления состоянием
paths:
  - 'src/**/*.tsx'
---

Иерархия управления состоянием:

1. Состояние сервера → React Query (кеширование, фоновый рефетч)
2. Клиентское состояние → Zustand (глобальное UI состояние)
3. Локальное состояние → useState/useReducer (состояние компонента)

Избегайте prop drilling — используйте контекст или Zustand для общего состояния.
Никогда не храните чувствительные данные в localStorage.
```

## Лучшие практики

### Организация по областям

Разбивайте правила на сфокусированные файлы вместо одного большого:

```
✅ Хорошо:
.nessy/rules/
  ├── testing.md
  ├── security.md
  ├── api-conventions.md
  └── frontend/
      ├── react.md
      └── css.md

❌ Избегайте:
.nessy/rules/
  └── everything.md  (500+ строк)
```

### Используйте условную загрузку разумно

Добавляйте `paths:` только когда правила действительно контекстно-специфичны:

```markdown
✅ Хорошо: paths для правил конкретных компонентов
paths:

- "src/components/\*_/_.tsx"

❌ Избыточно: paths для общепроектных стандартов
paths:

- "\*_/_" (просто опустите paths: и сделайте правило базовым)
```

### Пишите исполнимые правила

Делайте правила конкретными и проверяемыми:

```markdown
✅ Хорошо:
Всегда включайте error boundaries в компоненты страниц.
Используйте формат ISO 8601 для всех строковых дат (YYYY-MM-DDTHH:mm:ssZ).

❌ Размыто:
Пишите хороший код.
Следуйте лучшим практикам.
```

### Держите правила краткими

- Каждый файл правил должен быть сканируемым (цельтесь в \<200 строк)
- Используйте маркированные и нумерованные списки
- Избегайте длинных объяснений — ссылайтесь на внешнюю документацию при необходимости

### Версионирование

Коммитьте `.nessy/rules/` в репозиторий, чтобы команда использовала один контекст:

```bash
git add .nessy/rules/
git commit -m "Добавить контекстные правила для API соглашений и безопасности"
```

Исключите глобальные правила из версионирования (они живут в `~/.nessy/rules/` у каждого пользователя).

## Отладка проблем

### Правила не загружаются

**Проверьте доверие к папке:**

```bash
# Проверить список доверенных папок
/directory list
```

**Проверьте расположение файлов:**

- Глобальные: `~/.nessy/rules/*.md`
- Проект: `<project>/.nessy/rules/*.md`

**Проверьте расширение файлов:** Загружаются только `.md` файлы.

**Посмотрите логи:**

```bash
# Искать вывод отладки RULES_DISCOVERY
DEBUG=RULES_DISCOVERY npx nessy
```

### Правила загружаются, но не применяются

**Условные правила могут не соответствовать:**

- Проверьте, что glob-паттерны соответствуют путям к файлам
- Помните, что паттерны относительны относительно корня проекта
- Используйте прямые слеши для кроссплатформенной консистентности

**Протестируйте сопоставление паттернов:**

```typescript
import picomatch from 'picomatch';
const isMatch = picomatch('src/**/*.tsx');
console.log(isMatch('src/components/Button.tsx')); // true
```

### Слишком много токенов

**Уменьшите базовые правила:**

- Переместите контекстно-специфичные правила в условную загрузку с `paths:`
- Разбейте большие файлы правил на меньшие, сфокусированные файлы

**Удалите лишнее содержимое:**

- Удалите подробные объяснения
- Используйте HTML-комментарии для заметок только для команды (они вырезаются): `<!-- internal note -->`

### Конфликтующие правила

Когда несколько правил применяются к одному файлу, все соответствующие правила добавляются. Разрешите конфликты:

1. Консолидируйте перекрывающиеся правила в один файл
2. Используйте более специфичные `paths:` паттерны
3. Удалите или заархивируйте устаревшие правила

## Сравнение с другими функциями

| Функция                | Назначение                                | Когда использовать                                             |
| ---------------------- | ----------------------------------------- | -------------------------------------------------------------- |
| **`.nessy/rules/`**    | Постоянные инструкции в системном промпте | Командные соглашения, архитектурные решения, стандарты кодинга |
| **`NESSY.md`**         | Единый файл обзора проекта                | Быстрый онбординг проекта, высокоуровневый контекст            |

| **Skills**             | Комплексные многошаговые возможности      | Когда нужна оркестрация инструментов и условная логика         |

## Технические детали

### Процесс обнаружения

1. Рекурсивный скан директорий `.nessy/rules/`
2. Парсинг YAML frontmatter (если есть)
3. Удаление HTML-комментариев из тела
4. Разделение на базовые и условные правила
5. Сортировка файлов по алфавиту для детерминированного порядка
6. Компиляция glob-паттернов с picomatch

### Оптимизация токенов

- HTML-комментарии удаляются перед добавлением
- Условные правила загружаются лениво (не все сразу)
- Каждое условное правило добавляется только один раз за сессию
- Пустые файлы или файлы только с комментариями игнорируются

### Точки интеграции

- **Системный промпт:** Базовые правила добавляются при старте сессии
- **Вызовы инструментов:** Условные правила добавляются после `read_file`, `edit`, `write_file`
- **Worktrees:** Правила обнаруживаются для каждого worktree

## FAQ

**В: Можно ли использовать правила в недоверенных папках?**
О: Правила проекта требуют доверия к папке. Глобальные правила (`~/.nessy/rules/`) загружаются всегда независимо от доверия.

**В: Как отладить какие правила загружены?**
О: Включите отладочное логирование: `DEBUG=RULES_DISCOVERY npx nessy`. Логи показывают найденные файлы, разделение базовых/условных и события добавления.

**В: Могут ли правила ссылаться на внешнюю документацию?**
О: Да — включайте ссылки на вашу вики, Notion или другую документацию. Правила — это обычный Markdown, поэтому стандартные Markdown-ссылки работают.

**В: Поддерживают ли правила переменные или шаблонизацию?**
О: Нет — правила это статический текст. Для динамического контента используйте Skills или Commands с параметрами.

**В: Как временно отключить правило?**
О: Удалите файл, переместите его за пределы `.nessy/rules/` или закомментируйте содержимое HTML-комментариями (которые вырезаются).

**В: Можно ли иметь правила в поддиректориях?**
О: Да — `.nessy/rules/` поддерживает произвольную вложенность. Поддиректории помогают организовать большие наборы правил.

**В: Что происходит если я редактирую файл правила во время сессии?**
О: Изменения вступят в силу в следующей сессии. Чтобы применить их, перезапустите сессию.
