# Двойной вывод (Dual Output)

Dual Output — это sidecar-режим для интерактивного TUI: пока Nessy CLI продолжает нормально рендерить вывод в `stdout`, он одновременно испускает структурированный JSON-поток событий в отдельный канал, чтобы внешняя программа — расширение IDE, веб-фронтенд, CI-пайплайн, скрипт автоматизации — могла наблюдать за сессией и управлять ею.

Он также предоставляет обратный канал: внешняя программа может записывать JSONL-команды в файл, который отслеживается TUI, позволяя отправлять подсказки и отвечать на запросы разрешения инструментов так, как если бы человек работал за клавиатурой.

Dual Output полностью опционален. Когда флаги ниже отсутствуют, TUI ведёт себя точно так же, как раньше, без дополнительного ввода/вывода и изменений поведения.

## Варианты использования

Dual Output — это низкоуровневый сантехнический примитив. Вот конкретные интеграции, которые он открывает:

### Синхронизация реального времени Terminal + Chat

Флагманский вариант использования. Веб или десктопный ChatUI размещает TUI внутри PTY и рендерит параллельное представление разговора, управляемое структурированным потоком событий:

- Пользователь может печатать в любой поверхности — TUI (для терминальных power-пользователей) или веб-UI (для более богатого UX, общих ссылок, мобильных устройств). Оба представления остаются синхронизированными, потому что каждое сообщение проходит через одни и те же JSON-события.
- Подсказки подтверждения инструментов появляются в обоих местах; кто первый одобрит, тот и побеждает.
- История сессии захватывается дословно из `--json-file`, поэтому серверная сторона имеет каноническую машиночитаемую расшифровку без парсинга ANSI.

### Расширения IDE (VS Code / JetBrains / Cursor / Neovim)

Встраивание Nessy CLI внутри IDE. TUI работает в интегрированной терминальной панели редактора для пользователей, которые этого хотят, в то время как расширение потребляет события `--json-fd` / `--json-file` для управления:

- Встроенными diff-оверлеями, когда агент касается файлов.
- Боковой панелью webview с отформатированным markdown, подсветкой синтаксиса для вызовов инструментов и кликабельными цитатами.
- Индикаторами статус-бара (думает / отвечает / ожидает подтверждения).
- Программной записью `confirmation_response`, когда пользователь нажимает родную кнопку подтверждения IDE.

### Браузерные Chat-фронтенды

Node/Bun сервер запускает TUI в PTY для его семантики рендеринга, но предоставляет WebSocket-канал браузеру. События из `--json-file` пересылаются клиенту; пользовательские сообщения, введённые в браузере, инжектируются через `--input-file`. Никакого парсинга ANSI ни с одной стороны.

### Наблюдатели CI / автоматизации

CI-задача запускает Nessy CLI с подсказкой задачи. Человек видит TUI в логе задачи; CI-система tail'ит `--json-file` для:

- Провала задачи, если событие `result` сообщает об ошибке.
- Отправки подсчётов `token usage` / `duration_ms` / `tool_use` в метрики.
- Архивации полной расшифровки как артефакта сборки.

### Оркестрация нескольких агентов

Агент-супервизор запускает несколько TUI-воркеров, каждый со своей парой файлов событий/ввода. Он отслеживает прогресс, инжектирует последующие подсказки и обеспечивает глобальные политики бюджета / безопасности, одобряя или отклоняя вызовы инструментов во всех воркерах.

### Запись сессии, аудит и воспроизведение

Запись каждой TUI-сессии в обычный файл с `--json-file`. Позже:

- Аудиты соответствия могут реконструировать, что именно было выполнено.
- Автоматизированные регрессионные тесты могут сравнивать запуски по версиям моделей.
- Инструмент воспроизведения может повторно испускать события через тот же протокол для питания панелей визуализации.

### Панели наблюдаемости

Поток `--json-file` в Loki / OTEL / любой пайплайн, принимающий JSONL. Извлечение `usage.input_tokens`, `tool_use.name`, `result.duration_api_ms` как первоклассных метрик в Grafana. Никакой необходимости в regex для парсинга логов.

### Тестирование и QA

Интеграционные тесты запускают Nessy CLI безголово, управляют им с помощью скриптов `--input-file` и утверждают события `--json-file`. В отличие от парсинга stdout ANSI, утверждения стабильны при рефакторинге UI.

## Флаги

| Флаг                  | Тип             | Назначение                                                                                                                                                             |
| --------------------- | --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--json-fd <n>`       | число, `n >= 3` | Запись структурированных JSON-событий в файловый дескриптор `n`. Вызывающий должен предоставить этот fd через конфигурацию `stdio` spawn или перенаправление оболочки. |
| `--json-file <path>`  | путь            | Запись структурированных JSON-событий в файл. Путь может быть обычным файлом, FIFO (именованный канал) или `/dev/fd/N`.                                                |
| `--input-file <path>` | путь            | Наблюдение за этим файлом для JSONL-команд, записанных внешней программой.                                                                                             |

`--json-fd` и `--json-file` взаимно исключают друг друга. fds 0, 1 и 2 отклоняются, чтобы предотвратить повреждение собственного вывода TUI.

## Почему два флага вывода? (`--json-fd` против `--json-file`)

На первый взгляд `--json-fd` выглядит достаточным — вызывающий запускает Nessy CLI с дополнительным файловым дескриптором, TUI записывает события в него, готово. На практике передача fd ломается в самом важном сценарии встраивания: запуск TUI внутри псевдотерминала (PTY). Именно поэтому эта функция также предоставляет альтернативу на основе путей.

### Когда работает `--json-fd`

Чистый `child_process.spawn` с массивом `stdio`:

```ts
const child = spawn('nessy', ['--json-fd', '3'], {
  stdio: ['inherit', 'inherit', 'inherit', eventsFd],
});
```

Node's spawn поддерживает произвольные записи `stdio`; fd 3 наследуется дочерним процессом, который может писать в него напрямую. Zero-copy, zero-buffer, zero filesystem — самый быстрый путь.

### Почему `--json-fd` **не работает** под PTY

Обёртки PTY, такие как [`node-pty`](https://github.com/microsoft/node-pty) и [`bun-pty`](https://github.com/oven-sh/bun) — это то, как любой серьёзный встраивающий (расширения IDE, веб-терминалы, tmux-подобные мультиплексоры) размещает интерактивный TUI. Они не могут пересылать дополнительные fd дочернему процессу по трём взаимно усиливающим причинам:

1. **Поверхность API.** `node-pty.spawn(file, args, options)` принимает `cwd`, `env`, `cols`, `rows`, `encoding` и т.д. — но **никакого массива `stdio`**. В API просто нет места, чтобы сказать «также прикрепи этот fd как fd 3 в дочернем процессе». `bun-pty` предоставляет ту же форму.
2. **Семантика `forkpty(3)`.** Под капотом обёртки PTY вызывают `forkpty(3)` (или эквивалентный танец `posix_openpt` + `login_tty`). Этот системный вызов выделяет пару master/slave псевдотерминалов и перенаправляет fds 0/1/2 дочернего процесса на slave-сторону, чтобы дочерний процесс думал, что он подключён к реальному терминалу. Любые fd выше 2 в родителе закрываются `login_tty`, который вызывает `close(fd)` для `fd >= 3` перед `exec`. Дополнительные fd активно стираются, не наследуются.
3. **Побочный эффект управляющего терминала.** Даже если вы взломаете дополнительный fd через, он не будет терминалом, поэтому рендерер TUI дочернего процесса (который записывает escape-последовательности, предполагая TTY на fd 1) всё равно будет нуждаться в slave для своего вывода. Вы всё равно получите два независимых транспорта.

Короче говоря: в момент, когда встраивающему нужен настоящий TTY для рендеринга TUI — а это каждое расширение IDE, каждый веб-терминал, каждое десктопное chat-приложение — наследование fd исключается.

### `--json-file` заполняет пробел

Путь к файлу передаётся как обычный аргумент CLI, поэтому он выживает в любой модели spawn:

```ts
import { spawn } from 'node-pty';

const pty = spawn(
  'nessy',
  [
    '--json-file',
    '/tmp/nessy-events.jsonl',
    '--input-file',
    '/tmp/nessy-input.jsonl',
  ],
  { cols: 120, rows: 40 },
);
```

Дочерний процесс открывает файл сам и записывает события туда; встраивающий tail'ит тот же путь с `fs.watch` + инкрементальным чтением. Три вещи, которые нужно отметить:

- **Обычный файл**, FIFO (именованный канал) или `/dev/fd/N` — всё работает. FIFO — вариант с наименьшей задержкой, когда обе стороны на одном хосте.
- Мост открывает FIFO с `O_NONBLOCK` и возвращается в блокирующий режим при `ENXIO` (пока нет читателя), поэтому запуск PTY никогда не блокируется в ожидании потребителя.
- Для изоляции нескольких сессий используйте пути для каждой сессии под `$XDG_RUNTIME_DIR` или директорией `mkdtemp` с режимом `0700`.

### Какой флаг использовать?

| Стиль встраивания                                        | Использовать         |
| -------------------------------------------------------- | -------------------- |
| `child_process.spawn` с простым stdio                    | `--json-fd`          |
| `node-pty` / `bun-pty` / любой хост PTY                  | `--json-file`        |
| Перенаправление оболочки / ручное тестирование пайплайна | любой                |
| Сбор логов CI (обычный файл, чтение после выхода)        | `--json-file`        |
| Наименьшая возможная задержка на одном хосте             | `--json-file` + FIFO |

Общее правило: **если вам нужно, чтобы TUI рендерился правильно, вам нужен PTY, а это значит, что вам нужен `--json-file`.** `--json-fd` — для более простых встраивающих, которым не важна точность TUI — обычно программные обёртки, которые всё равно выбрасывают stdout.

## Быстрый старт

Запустите Nessy CLI со всеми тремя включёнными каналами:

```bash
mkfifo /tmp/nessy-events.jsonl /tmp/nessy-input.jsonl
nessy \
  --json-file /tmp/nessy-events.jsonl \
  --input-file /tmp/nessy-input.jsonl
```

Во втором терминале tail'те поток событий:

```bash
cat /tmp/nessy-events.jsonl
```

В третьем терминале отправьте подсказку в работающий TUI:

```bash
echo '{"type":"submit","text":"Explain this repo"}' >> /tmp/nessy-input.jsonl
```

Подсказка появляется в TUI точно так, как если бы пользователь ввёл её, а потоковый ответ отображается в `/tmp/nessy-events.jsonl`.

## Схема выходных событий

События испускаются как JSON Lines (один объект на строку). Схема та же, что используется в неинтерактивном режиме `--output-format=stream-json`, с всегда включённым `includePartialMessages`.

Первое событие на канале всегда `system` / `session_start`, испускаемое при создании моста. Используйте его для корреляции канала с session id до прибытия любого другого события.

```jsonc
// Жизненный цикл сессии
{
  "type": "system",
  "subtype": "session_start",
  "uuid": "...",
  "session_id": "...",
  "data": { "session_id": "...", "cwd": "/path/to/cwd" }
}

// Потоковые события для идущего хода ассистента
{ "type": "stream_event", "event": { "type": "message_start", "message": { ... } }, ... }
{ "type": "stream_event", "event": { "type": "content_block_start", "index": 0, "content_block": { "type": "text" } }, ... }
{ "type": "stream_event", "event": { "type": "content_block_delta", "index": 0, "delta": { "type": "text_delta", "text": "Hello" } }, ... }
{ "type": "stream_event", "event": { "type": "content_block_stop", "index": 0 }, ... }
{ "type": "stream_event", "event": { "type": "message_stop" }, ... }

// Завершённые сообщения
{ "type": "user", "message": { "role": "user", "content": [...] }, ... }
{ "type": "assistant", "message": { "role": "assistant", "content": [...], "usage": { ... } }, ... }
{ "type": "user", "message": { "role": "user", "content": [{ "type": "tool_result", ... }] } }

// Плоскость управления разрешениями (только когда инструмент требует подтверждения)
{
  "type": "control_request",
  "request_id": "...",
  "request": {
    "subtype": "can_use_tool",
    "tool_name": "run_shell_command",
    "tool_use_id": "...",
    "input": { "command": "rm -rf /tmp/x" },
    "permission_suggestions": null,
    "blocked_path": null
  }
}
{
  "type": "control_response",
  "response": {
    "subtype": "success",
    "request_id": "...",
    "response": { "allowed": true }
  }
}
```

`control_response` испускается независимо от того, было ли решение принято в TUI (родной UI подтверждения) или внешним `confirmation_response` (см. ниже). В любом случае все наблюдатели видят окончательный результат.

## Схема входных команд

Две формы команд принимаются на `--input-file`:

```jsonc
// Отправка пользовательского сообщения в очередь подсказок
{ "type": "submit", "text": "What does this function do?" }

// Ответ на ожидающий control_request
{ "type": "confirmation_response", "request_id": "...", "allowed": true }
```

Поведение:

- Команды `submit` ставятся в очередь. Если TUI занят ответом, они автоматически повторяются в следующий раз, когда TUI возвращается в состояние idle.
- Команды `confirmation_response` отправляются немедленно и никогда не ставятся в очередь, потому что вызов инструмента блокирующий и ответ должен достичь базового обработчика `onConfirm` без ожидания любой более ранней `submit`.
- Какая бы сторона ни одобрила инструмент первой, та и побеждает; запоздалый ответ другой стороны безвредно отбрасывается.
- Строки, которые не удаётся распарсить как JSON, логируются и пропускаются — они не останавливают наблюдатель.

## Заметки о задержках

Входной файл наблюдается с `fs.watchFile` с интервалом опроса 500 мс, поэтому наихудшая задержка кругового пути для удалённой `submit` составляет около полусекунды. Это намеренно: опрос переносим между платформами и файловыми системами (включая macOS / сетевые монтирования) и соответствует типичному темпу human-in-the-loop, на который нацелена функция. Выходной канал не имеет опроса — события записываются синхронно, когда TUI испускает их.

## Режимы отказа

- **Плохой fd.** Если fd, переданный в `--json-fd`, не открыт или является одним из 0/1/2, TUI печатает предупреждение в `stderr` и продолжает без включённого dual output.
- **Плохой путь.** Если файл, переданный в `--json-file`, не может быть открыт, TUI печатает предупреждение и продолжает без dual output.
- **Отключение потребителя.** Если читатель на другой стороне канала уходит (`EPIPE`), мост молча отключается, и TUI продолжает работать. Никаких повторных попыток.
- **Исключение адаптера.** Любое исключение, брошенное при испускании события, перехватывается, логируется и отключает мост. TUI никогда не падает из-за сбоя dual-output.

## Пример spawn

Типичный встраивающий родительский процесс запускает Nessy CLI с обоими каналами:

```ts
import { spawn } from 'node:child_process';
import { openSync } from 'node:fs';

const eventsFd = openSync('/tmp/nessy-events.jsonl', 'w');
const child = spawn(
  'nessy',
  ['--json-fd', '3', '--input-file', '/tmp/nessy-input.jsonl'],
  { stdio: ['inherit', 'inherit', 'inherit', eventsFd] },
);
```

TUI всё ещё владеет терминалом пользователя на stdio 0/1/2, в то время как встраивающий читает структурированные события из файла, поддерживающего fd 3, и отправляет команды, добавляя строки JSONL в `/tmp/nessy-input.jsonl`.

## Конфигурация на основе настроек

Для долгоживущих встраивающих часто неудобно протаскивать флаги CLI через каждый запуск. Те же каналы могут быть настроены в `settings.json` под ключом верхнего уровня `dualOutput`:

```jsonc
// ~/.nessy/settings.json  (уровень пользователя)
// или <workspace>/.nessy/settings.json  (уровень workspace)
{
  "dualOutput": {
    "jsonFile": "/tmp/nessy-events.jsonl",
    "inputFile": "/tmp/nessy-input.jsonl",
  },
}
```

Правила приоритета:

- Флаг CLI **побеждает** настройки. Передача `--json-file /foo` в командной строке переопределяет `dualOutput.jsonFile` в настройках.
- `--json-fd` не имеет эквивалента в настройках — передача fd является заботой времени spawn, которая не может быть статически объявлена.
- Если ни флаг, ни настройка не присутствуют, dual output остаётся отключённым (идентично сегодняшнему default).

Флаг `requiresRestart: true` означает, что изменения вступают в силу только при следующем запуске Nessy CLI, поскольку мост создаётся один раз во время запуска.

## Рабочие демо

Каждый скрипт ниже готов к копированию и вставке. Начните с POC&nbsp;1, чтобы проверить, что сборка имеет dual output; POC&nbsp;4 — ближайший аналог реальной интеграции с расширением IDE.

### POC 1 — наблюдение за потоком событий

Наблюдайте каждое структурированное событие, которое TUI испускает, пока человек использует его нормально:

```bash
# Терминал A
mkfifo /tmp/nessy-events.jsonl
cat /tmp/nessy-events.jsonl | jq -c 'select(.type != "stream_event") | {type, subtype}'

# Терминал B
nessy --json-file /tmp/nessy-events.jsonl
# ...затем общайтесь нормально; терминал A показывает session_start,
# user/assistant/result/control_request lifecycle в реальном времени.
```

Ожидаемая первая строка в терминале A:

```json
{ "type": "system", "subtype": "session_start" }
```

### POC 2 — инжекция подсказок извне

Управляйте TUI из второго терминала, не касаясь клавиатуры первого:

```bash
# Терминал A
touch /tmp/nessy-in.jsonl
nessy --input-file /tmp/nessy-in.jsonl

# Терминал B — TUI отвечает, как если бы вы ввели это
echo '{"type":"submit","text":"list files in the current directory"}' \
  >> /tmp/nessy-in.jsonl
```

### POC 3 — мост удалённого разрешения инструментов

Одобряйте или отклоняйте вызовы инструментов из отдельного процесса:

```bash
# Терминал A — наблюдение за control_requests
mkfifo /tmp/nessy-out.jsonl
touch /tmp/nessy-in.jsonl
(cat /tmp/nessy-out.jsonl \
  | jq -c 'select(.type == "control_request")') &

# Терминал B
nessy --json-file /tmp/nessy-out.jsonl --input-file /tmp/nessy-in.jsonl
# Попросите Nessy сделать что-то, что требует подтверждения, например
# "run `ls -la /tmp`". В терминале A появится control_request.
```

### POC 4 — Node встраивающий (подобный IDE)

Наиболее реалистичная форма: родительский процесс запускает Nessy CLI, tail'ит события и инжектирует подсказки по собственному расписанию.

```ts
// demo-embedder.ts
import { spawn } from 'node:child_process';
import { appendFileSync, createReadStream, writeFileSync } from 'node:fs';
import { createInterface } from 'node:readline';
import { tmpdir } from 'node:os';
import { join } from 'node:path';

const events = join(tmpdir(), `nessy-events-${process.pid}.jsonl`);
const input = join(tmpdir(), `nessy-input-${process.pid}.jsonl`);
writeFileSync(events, '');
writeFileSync(input, '');

const child = spawn('nessy', ['--json-file', events, '--input-file', input], {
  stdio: 'inherit',
});

// Tail выходного канала. В продакшене вы бы использовали правильный
// tail со смещением байтов; этот для краткости перепоточивает с 0.
const rl = createInterface({
  input: createReadStream(events, { encoding: 'utf8' }),
});
rl.on('line', (line) => {
  if (!line.trim()) return;
  const ev = JSON.parse(line);
  if (ev.type === 'system' && ev.subtype === 'session_start') {
    console.log('[embedder] handshake:', {
      protocol_version: ev.data.protocol_version,
      version: ev.data.version,
      supported_events: ev.data.supported_events,
    });
    // Feature-detect перед использованием возможности
    if (ev.data.supported_events.includes('control_request')) {
      console.log('[embedder] permission control-plane available');
    }
  }
  if (ev.type === 'assistant') {
    console.log(
      '[embedder] ход ассистента завершён, токенов =',
      ev.message.usage?.output_tokens,
    );
  }
  if (ev.type === 'system' && ev.subtype === 'session_end') {
    console.log('[embedder] сессия чисто завершена');
  }
});

// Через 2с инжектировать подсказку, как если бы пользователь ввёл её
setTimeout(() => {
  appendFileSync(
    input,
    JSON.stringify({ type: 'submit', text: 'hello from embedder' }) + '\n',
  );
}, 2000);

child.on('exit', () => process.exit(0));
```

Запустить с:

```bash
npx tsx demo-embedder.ts
# TUI Nessy CLI открывается в текущем терминале; встраивающий логирует
# события handshake + turn-end + session_end в stdout родителя.
```

### POC 5 — feature detection рукопожатия возможностей

Более старые версии Nessy CLI не испускают `protocol_version`. Относитесь к полю как к опциональному и делайте feature-detect:

```ts
rl.on('line', (line) => {
  const ev = JSON.parse(line);
  if (ev.type === 'system' && ev.subtype === 'session_start') {
    const v = ev.data?.protocol_version ?? 0;
    if (v < 1) {
      console.error(
        'nessy-cli dual output присутствует, но protocol < 1; ' +
          'возврат к best-effort поведению',
      );
    } else {
      console.log('nessy-cli dual output протокол v' + v);
    }
  }
});
```

### POC 6 — session_end как сигнал чистого завершения

```ts
rl.on('line', (line) => {
  const ev = JSON.parse(line);
  if (ev.type === 'system' && ev.subtype === 'session_end') {
    console.log('[embedder] чистое завершение, сессия', ev.data.session_id);
    // Сброс метрик, закрытие WebSockets и т.д.
  }
});
```

Если TUI падает до `session_end`, выходной поток закрывается (`EPIPE` при следующей записи); встраивающие должны обрабатывать оба пути.

## Связь с Claude Code

Claude Code предоставляет похожий формат событий stream-json в `--print --output-format stream-json`, но только в неинтерактивном режиме — у него нет эквивалента запуска TUI и структурированного sidecar-канала одновременно. Dual Output заполняет этот пробел.
