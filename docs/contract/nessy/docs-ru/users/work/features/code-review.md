# Code Review

:::tip
Ревью изменений кода на корректность, безопасность, производительность и качество кода с помощью `/review`.
:::

## Быстрый старт

```bash
# Ревью локальных незакоммиченных изменений
/review

# Ревью merge request (по номеру или URL)
/review 123
/review https://gitlab.tcsbank.ru/org/repo/-/merge_requests/123

# Ревью и публикация inline-комментариев на MR
/review 123 --comment

# Ревью конкретного файла
/review src/utils/auth.ts
```

Если нет незакоммиченных изменений, `/review` сообщит вам об этом и остановится — никакие агенты не запускаются.

## Как это работает

Команда `/review` запускает многоэтапный пайплайн:

```
Шаг 1:  Определение области (локальный diff / MR worktree / файл)
Шаг 2:  Загрузка правил ревью проекта
Шаг 3:  Запуск детерминированного анализа (линтер, typecheck)    [ноль LLM стоимости]
Шаг 4:  9 параллельных агентов ревью                              [9 LLM вызовов]
           |-- Агент 1: Корректность
           |-- Агент 2: Безопасность
           |-- Агент 3: Качество кода
           |-- Агент 4: Производительность и эффективность
           |-- Агент 5: Покрытие тестами
           |-- Агент 6: Ненаправленный аудит (3 персоны: 6a/6b/6c)
           '-- Агент 7: Сборка и тесты (запускает shell-команды)
Шаг 5:  Дедупликация --> Пакетная верификация --> Агрегация      [1 LLM вызов]
Шаг 6:  Итеративный обратный аудит (1-3 раунда, поиск пробелов)  [1-3 LLM вызовов]
Шаг 7:  Представление находок + вердикт
Шаг 8:  Автофикс (подтверждается пользователем, опционально)
Шаг 9:  Публикация inline-комментариев MR (если запрошено)
Шаг 10: Сохранение отчёта + инкрементальный кэш
Шаг 11: Очистка (удаление worktree + временных файлов)
```

### Агенты ревью

| Агент                                       | Фокус                                                                                         |
| ------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Агент 1: Корректность                       | Логические ошибки, пограничные случаи, обработка null, состояния гонки, типобезопасность      |
| Агент 2: Безопасность                       | Инъекции, XSS, SSRF, обход аутентификации, утечка чувствительных данных                       |
| Агент 3: Качество кода                      | Стилевая согласованность, именование, дублирование, мёртвый код                               |
| Агент 4: Производительность и эффективность | N+1 запросы, утечки памяти, ненужные ререндеры, размер бандла                                 |
| Агент 5: Покрытие тестами                   | Непокрытые пути кода в diff, отсутствующее покрытие ветвей, слабые утверждения                |
| Агент 6: Ненаправленный аудит               | 3 параллельные персоны (атакующий / 3am-oncall / мейнтейнер) — ловят кросс-размерные проблемы |
| Агент 7: Сборка и тесты                     | Запускает команды сборки и тестов, сообщает об ошибках                                        |

Все агенты выполняются параллельно (Агент 6 запускает 3 варианта персон одновременно, всего 9 параллельных задач для ревью одного репозитория). Находки от агентов 1-6 верифицируются за **один проход пакетной верификации** (один агент просматривает все находки сразу, сохраняя стоимость верификации фиксированной независимо от количества находок). После верификации **итеративный обратный аудит** запускает 1-3 раунда поиска пробелов — каждый раунд получает кумулятивный список находок от предыдущих раундов, поэтому последующие раунды фокусируются на том, что осталось необнаруженным. Цикл останавливается, как только раунд возвращает «Проблем не найдено», или после 3 раундов (жёсткий лимит). Находки обратного аудита пропускают верификацию (агент уже имеет полный контекст) и включаются как высокоточные результаты.

## Детерминированный анализ

Перед запуском LLM-агентов `/review` автоматически запускает существующие линтеры и чекеры типов вашего проекта:

| Язык                  | Инструменты обнаружены                               |
| --------------------- | ---------------------------------------------------- |
| TypeScript/JavaScript | `tsc --noEmit`, `npm run lint`, `eslint`             |
| Python                | `ruff`, `mypy`, `flake8`                             |
| Rust                  | `cargo clippy`                                       |
| Go                    | `go vet`, `golangci-lint`                            |
| Java                  | `mvn compile`, `checkstyle`, `spotbugs`, `pmd`       |
| C/C++                 | `clang-tidy` (если доступен `compile_commands.json`) |

Для проектов, которые не соответствуют стандартным паттернам (например, OpenJDK), `/review` читает конфигурационные файлы CI, чтобы обнаружить, какие команды линтинга/проверки использует проект. Никакой пользовательской конфигурации не требуется.

Детерминированным находкам присваиваются теги `[linter]` или `[typecheck]`, и они пропускают LLM-верификацию — это истина в последней инстанции.

- **Ошибки** → Критическая серьёзность
- **Предупреждения** → Приятно иметь (только терминал, не публикуется как комментарии MR)

Если инструмент не установлен или истекает таймаут, он пропускается с информационной заметкой.

## Уровни серьёзности

| Серьёзность      | Значение                                                                                | Публикуется как комментарий MR? |
| ---------------- | --------------------------------------------------------------------------------------- | ------------------------------- |
| **Critical**     | Должно быть исправлено перед мержем (баги, безопасность, потеря данных, падения сборки) | Да (только высокая уверенность) |
| **Suggestion**   | Рекомендуемое улучшение                                                                 | Да (только высокая уверенность) |
| **Nice to have** | Опциональная оптимизация                                                                | Нет (только терминал)           |

Находки с низкой уверенностью появляются в отдельной секции "Нужно человеческое ревью" в терминале и никогда не публикуются как комментарии MR.

## Autofix

После представления находок `/review` предлагает автоматически применить исправления для находок Critical и Suggestion, которые имеют ясные решения:

```
Найдено 3 проблемы с авто-исправляемыми предложениями. Применить авто-исправления? (y/n)
```

- Исправления применяются с помощью инструмента `edit` (целевые замены, не полные перезаписи файлов)
- После исправлений запускаются проверки линтера для каждого файла, чтобы убедиться, что они не вводят новые проблемы
- Для MR-ревью исправления коммитятся и пушатся из worktree автоматически — ваше локальное дерево остаётся чистым
- Nice to have и низкоточные находки никогда не авто-исправляются
- Отправка MR-ревью всегда использует **вердикт до исправления** (например, "Request changes"), поскольку удалённый MR не был обновлён, пока автофикс не завершит пуш

## Изоляция worktree

При ревью MR `/review` создаёт временный git worktree (`.nessy/tmp/review-mr-<номер>`) вместо переключения вашей текущей ветки. Это означает:

- Ваше рабочее дерево, staged изменения и текущая ветка **никогда не затрагиваются**
- Зависимости устанавливаются в worktree (`npm ci` и т.д.), поэтому линтинг и сборка/тесты работают
- Команды сборки и тестов выполняются в изоляции без загрязнения вашего локального кэша сборки
- Если что-то идёт не так, ваше окружение не затронуто — просто удалите worktree
- Worktree автоматически очищается после завершения ревью
- Если ревью прерывается (Ctrl+C, крах), следующее `/review` того же MR автоматически очищает устаревший worktree перед новым запуском
- Отчёты о ревью и кэш сохраняются в основную директорию проекта (не в worktree)

## Ревью MR из другого репозитория

Вы можете ревьюить MR из других репозиториев, передав полный URL:

```bash
/review https://gitlab.tcsbank.ru/other-org/other-repo/-/merge_requests/456
```

Это запускается в **облегчённом режиме** — без worktree, без линтера, без сборки/тестов, без автофикса. Ревью основывается только на тексте diff (полученном через GitLab API). Комментарии MR всё ещё могут быть опубликованы, если у вас есть права на запись.

| Возможность                                                       | Один репозиторий | Другой репозитория              |
| ----------------------------------------------------------------- | ---------------- | ------------------------------- |
| LLM-ревью (Агенты 1-6 + верификация + итеративный обратный аудит) | ✅               | ✅                              |
| Агент 7: Сборка и тесты                                           | ✅               | ❌ (нет локальной кодовой базы) |
| Детерминированный анализ (линтер/typecheck)                       | ✅               | ❌                              |
| Анализ влияния на несколько файлов                                | ✅               | ❌                              |
| Autofix                                                           | ✅               | ❌                              |
| Inline-комментарии MR                                             | ✅               | ✅ (если есть права на запись)  |
| Кэш инкрементального ревью                                        | ✅               | ❌                              |

## Inline-комментарии MR

Используйте `--comment` для публикации находок напрямую на MR:

```bash
/review 123 --comment
```

Или после запуска `/review 123` введите `post comments` для публикации находок без повторного запуска ревью.

**Что публикуется:**

- Высокоточные находки Critical и Suggestion как inline-комментарии на конкретных строках
- Для вердиктов Approve/Request changes: сводка ревью с вердиктом
- Для вердикта Comment со всеми опубликованными inline-комментариями: без отдельной сводки (inline-комментарии достаточны)
- Подпись атрибуции модели на каждом комментарии (например, _— qwen3-coder через Nessy CLI /review_)

**Что остаётся только в терминале:**

- Nice to have находки (включая предупреждения линтера)
- Низкоточные находки

**Self-authored MR:** GitHub не позволяет отправлять ревью `APPROVE` или `REQUEST_CHANGES` на собственный pull request — оба завершаются HTTP 422. Когда `/review` обнаруживает, что автор MR совпадает с текущим аутентифицированным пользователем, он автоматически понижает событие API до `COMMENT` независимо от вердикта, поэтому отправка всё равно succeeds. Терминал всё ещё показывает честный вердикт («Approve» / «Request changes» / «Comment») — только событие ревью на стороне GitHub нейтрализуется. Фактические находки всё ещё появляются как inline-комментарии на конкретных строках, поэтому содержательная обратная связь неизменна.

**Повторное ревью MR с предыдущими комментариями Nessy CLI:** когда `/review` запускается на MR, который уже имеет предыдущие комментарии ревью Nessy CLI, он классифицирует их перед публикацией новых. Только **перекрытие на той же строке** (существующий комментарий на той же `(path, line)`, что и новая находка) предлагает вам подтвердить — это случай, когда вы увидите визуальный дубликат на той же строке кода. Комментарии из старых коммитов, комментарии с ответами (считаются разрешёнными) и комментарии, которые просто не пересекаются ни с одной новой находкой, молча пропускаются, с строкой журнала терминала, чтобы вы знали, что было отфильтровано.

**Проверка статуса CI/сборки перед APPROVE:** если вердикт «Approve», `/review` запрашивает check-runs PR и статусы коммитов перед отправкой. Если какая-либо проверка не удалась (или все проверки всё ещё ожидаются), событие API автоматически понижается с `APPROVE` до `COMMENT`, с телом ревью, объясняющим почему. Обоснование: LLM-ревью читает код статически и не может видеть падения runtime-тестов; утверждение, пока CI красный, было бы вводящим в заблуждение. Inline-находки всё ещё публикуются неизменными. Если вы хотите утвердить всё равно (например, известный-flaky сбой CI), отправьте утверждение GitHub вручную после проверки.

## Follow-up действия

После ревью появляются контекстно-зависимые подсказки как ghost-текст. Нажмите Tab для принятия:

| Состояние после ревью                       | Подсказка          | Что происходит                                         |
| ------------------------------------------- | ------------------ | ------------------------------------------------------ |
| Локальное ревью с неисправленными находками | `fix these issues` | LLM интерактивно исправляет каждую находку             |
| MR-ревью с находками                        | `post comments`    | Публикует inline-комментарии MR (без повторного ревью) |
| MR-ревью, ноль находок                      | `post comments`    | Утверждает MR на GitLab (LGTM)                         |
| Локальное ревью, всё чисто                  | `commit`           | Коммитит ваши изменения                                |

Заметка: `fix these issues` доступно только для локальных ревью. Для MR-ревью используйте Autofix (Шаг 8) — worktree очищается после ревью, поэтому пост-ревью интерактивное исправление невозможно.

## Правила ревью проекта

Вы можете настроить критерии ревью для каждого проекта. `/review` читает правила из этих файлов (по порядку):

1. `.nessy/review-rules.md` (родной Nessy CLI)
2. `.gitlab/merge_request_template.md` (предпочтительно) или `MR_TEMPLATE.md` (резервный — загружается только один, не оба)
3. `AGENTS.md` — секция `## Code Review`
4. `NESSY.md` — секция `## Code Review`

Правила инжектируются в LLM-агенты ревью (1-6) как дополнительные критерии. Для MR-ревью правила читаются из **базовой ветки**, чтобы предотвратить злонамеренное внедрение правил обхода MR.

Пример `.nessy/review-rules.md`:

```markdown
# Правила ревью

- Все API endpoints должны валидировать аутентификацию
- Запросы БД должны использовать параметризованные утверждения
- React-компоненты не должны использовать inline-стили
- Сообщения об ошибках не должны раскрывать внутренние пути
```

## Инкрементальное ревью

При ревью MR, которое ранее ревьюилось, `/review` исследует только изменения с последнего ревью:

```bash
# Первое ревью — полное ревью, кэш создан
/review 123

# MR обновлён новыми коммитами — ревьюятся только новые изменения
/review 123
```

### Ревью между моделями

Если вы переключаете модели (через `/model`) и повторно ревьюите тот же MR, `/review` обнаруживает изменение модели и запускает полное ревью вместо пропуска:

```bash
# Ревью с моделью A
/review 123

# Переключить модель
/model

# Ревью снова — полное ревью с моделью B (не пропущено)
/review 123
# → "Предыдущее ревью использовало qwen3-coder. Запуск полного ревью с gpt-4o для второго мнения."
```

Кэш сохраняется в `.nessy/review-cache/` и отслеживает как SHA коммита, так и ID модели. Убедитесь, что эта директория находится в вашем `.gitignore` (более широкое правило вроде `.nessy/*` также работает). Если закэшированный коммит был ребейзен, возвращается к полному ревью.

## Отчёты о ревью

Для ревью одного репозитория результаты сохраняются как Markdown-файл в директории `.nessy/reviews/` вашего проекта (лёгкие ревью другого репозитория пропускают сохранение отчёта):

```
.nessy/reviews/2026-04-06-143022-mr-123.md
.nessy/reviews/2026-04-06-150510-local.md
```

Отчёты включают: временную метку, статистику diff, результаты детерминированного анализа, все находки со статусом верификации и вердикт.

## Анализ влияния на несколько файлов

Когда изменения кода изменяют экспортируемые функции, классы или интерфейсы, агенты ревью автоматически ищут все вызовы и проверяют совместимость:

- Изменения количества/типа параметров
- Изменения типа возврата
- Удалённые или переименованные публичные методы
- Критические изменения API

Для больших diff (>10 изменённых символов) анализ приоритизирует функции с изменениями сигнатур.

## Эффективность токенов

Пайплайн ревью использует ограниченное количество LLM-вызовов независимо от того, сколько находок произведено:

| Этап                               | LLM-вызовы        | Заметки                                                                    |
| ---------------------------------- | ----------------- | -------------------------------------------------------------------------- |
| Детерминированный анализ (Шаг 3)   | 0                 | Только shell-команды                                                       |
| Агенты ревью (Шаг 4)               | 9 (или 8)         | Выполняются параллельно; Агент 7 пропускается в режиме другого репозитория |
| Пакетная верификация (Шаг 5)       | 1                 | Один агент верифицирует все находки сразу                                  |
| Итеративный обратный аудит (Шаг 6) | 1-3               | Цикл до «Проблем не найдено» или лимит 3 раунда                            |
| **Всего**                          | **11-13 (10-12)** | Один репозиторий: 11-13; другой репозиторий: 10-12 (без Агента 7)          |

Большинство MR сходятся к нижней границе диапазона (1 раунд обратного аудита); лимит предотвращает runaway-стоимость на патологических случаях.

## Что НЕ отмечается

Ревью намеренно исключает:

- Существующие проблемы в неизменённом коде (фокус только на diff)
- Стиль/форматирование/именование, соответствующее конвенциям вашей кодовой базы
- Проблемы, которые поймал бы линтер или type checker (обрабатываются детерминированным анализом)
- Субъективные предложения "рассмотрите делать X" без реальной проблемы
- Незначительный рефакторинг, который не исправляет баг или риск
- Отсутствующая документация, если логика не действительно запутанная
- Проблемы, уже обсуждённые в существующих комментариях MR (избегает дублирования человеческой обратной связи)

## Философия дизайна

> **Молчание лучше шума.** Каждый комментарий должен стоить времени читателя.

- Если не уверены, является ли что-то проблемой → не сообщайте об этом
- Проблемы линтера/typecheck обрабатываются инструментами, не LLM-догадками
- Одинаковый паттерн в N файлах → агрегируется в одну находку
- Комментарии MR только высокоточные
- Проблемы стиля/форматирования, соответствующие конвенциям кодовой базы, исключены
