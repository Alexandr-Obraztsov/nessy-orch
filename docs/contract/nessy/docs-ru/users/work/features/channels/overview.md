# Каналы

Каналы позволяют взаимодействовать с агентом Nessy CLI из платформ обмена сообщениями, таких как Time вместо терминала. Вы отправляете сообщения со своего телефона или десктопного чат-приложения, и агент отвечает так же, как в CLI.

## Как это работает

Когда вы запускаете `nessy channel start`, Nessy CLI:

1. Читает конфигурации каналов из вашего `settings.json`
2. Создаёт один агентский процесс, используя [Agent Client Protocol (ACP)](../../../../developers/architecture.md)
3. Подключается к каждой платформе обмена сообщениями и начинает слушать сообщения
4. Маршрутизирует входящие сообщения агенту и отправляет ответы обратно в правильный чат

Все каналы используют один агентский процесс с изолированными сессиями на пользователя. Каждый канал может иметь свой working directory, модель и инструкции.

## Быстрый старт

1. Настройте бота на вашей платформе обмена сообщениями (см. гайды по каналам: [Channel Time](./channel-time.md))
2. Добавьте конфигурацию канала в `~/.nessy/settings.json`
3. Выполните `nessy channel start` для запуска всех каналов или `nessy channel start <name>` для одного канала

Хотите подключить платформу, которая не встроена? См. [Плагины](./plugins.md) для добавления кастомного адаптера как расширения.

## Конфигурация

Каналы настраиваются под ключом `channels` в `settings.json`. Каждый канал имеет имя и набор опций:

```json
{
  "channels": {
    "my-channel": {
      "type": "time",
      "token": "$MY_CT_TOKEN",
      "serverUrl": "$CT_SERVER_URL",
      "senderPolicy": "allowlist",
      "allowedUsers": ["123456789"],
      "sessionScope": "user",
      "cwd": "/path/to/working/directory",
      "instructions": "Опциональные системные инструкции для агента.",
      "groupPolicy": "disabled",
      "groups": {
        "*": { "requireMention": true }
      }
    }
  }
}
```

### Опции

| Опция                    | Требуется | Описание                                                                                                                                                              |
| ------------------------ | --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `type`                   | Да        | Тип канала: `time` или кастомный тип из расширения (см. [Плагины](./plugins.md))                                                                                      |
| `token`                  | Time      | Токен бота или персональный токен доступа. Поддерживает синтаксис `$ENV_VAR` для чтения из переменных окружения. Не нужно для WeChat или DingTalk                     |
| `serverUrl`              | Time      | URL сервера Time (например, `https://time.tbank.ru`). Поддерживает синтаксис `$ENV_VAR`                                                                               |
| `model`                  | Нет       | Модель для использования этим каналом (например, `qwen3.5-plus`). Переопределяет модель по умолчанию. Полезно для multimodal моделей, поддерживающих ввод изображений |
| `senderPolicy`           | Нет       | Кто может говорить с ботом: `allowlist` (по умолчанию), `open` или `pairing`                                                                                          |
| `allowedUsers`           | Нет       | Список ID пользователей, разрешённых для использования бота (используется политиками `allowlist` и `pairing`)                                                         |
| `sessionScope`           | Нет       | Как сессии имеют область: `user` (по умолчанию), `thread` или `single`                                                                                                |
| `cwd`                    | Нет       | Working directory для агента. По умолчанию — текущая директория                                                                                                       |
| `instructions`           | Нет       | Кастомные инструкции, добавляемые в начало первого сообщения каждой сессии                                                                                            |
| `groupPolicy`            | Нет       | Доступ к групповым чатам: `disabled` (по умолчанию), `allowlist` или `open`. См. [Групповые чаты](#group-chats)                                                       |
| `groups`                 | Нет       | Настройки на группу. Ключи — ID групповых чатов или `"*"` для default. См. [Групповые чаты](#group-chats)                                                             |
| `dispatchMode`           | Нет       | Что происходит, когда вы отправляете сообщение, пока бот занят: `steer` (по умолчанию), `collect` или `followup`. См. [Dispatch Modes](#dispatch-modes)               |
| `blockStreaming`         | Нет       | Прогрессивная доставка ответов: `on` или `off` (по умолчанию). См. [Block Streaming](#block-streaming)                                                                |
| `blockStreamingChunk`    | Нет       | Границы размера chunk: `{ "minChars": 400, "maxChars": 1000 }`. См. [Block Streaming](#block-streaming)                                                               |
| `blockStreamingCoalesce` | Нет       | Idle flush: `{ "idleMs": 1500 }`. См. [Block Streaming](#block-streaming)                                                                                             |

### Sender Policy

Контролирует, кто может взаимодействовать с ботом:

- **`allowlist`** (по умолчанию) — Только пользователи, перечисленные в `allowedUsers`, могут отправлять сообщения. Остальные молча игнорируются.
- **`pairing`** — Неизвестные отправители получают pairing code. Оператор бота утверждает их через CLI, и они добавляются в персистентный allowlist. Пользователи в `allowedUsers` пропускают pairing полностью. См. [DM Pairing](#dm-pairing) ниже.
- **`open`** — Любой может отправлять сообщения. Используйте с осторожностью.

### Session Scope

Контролирует, как управляются сессии конверсации:

- **`user`** (по умолчанию) — Одна сессия на пользователя. Все сообщения от одного пользователя используют одну конверсацию.
- **`thread`** — Одна сессия на тред/топик. Полезно для групповых чатов с тредами.
- **`single`** — Одна общая сессия для всех пользователей. Все делят одну конверсацию.

### Безопасность токенов

Токены ботов не должны храниться напрямую в `settings.json`. Вместо этого используйте ссылки на переменные окружения:

```json
{
  "token": "$CT_TOKEN"
}
```

Установите фактический токен в вашем shell окружении или в `.env` файле, который загружается перед запуском канала.

## DM Pairing

Когда `senderPolicy` установлен в `"pairing"`, неизвестные отправители проходят flow утверждения:

1. Неизвестный пользователь отправляет сообщение боту
2. Бот отвечает 8-символьным pairing code (например, `VEQDDWXJ`)
3. Пользователь делится кодом с вами (оператором бота)
4. Вы утверждаете его через CLI:

```bash
nessy channel pairing approve my-channel VEQDDWXJ
```

После утверждения ID пользователя сохраняется в `~/.nessy/channels/<name>-allowlist.json`, и все будущие сообщения проходят нормально.

### Pairing CLI команды

```bash
# Вывести ожидающие запросы pairing
nessy channel pairing list my-channel

# Утвердить запрос по коду
nessy channel pairing approve my-channel <CODE>
```

### Pairing правила

- Коды — 8 символов, uppercase, используя неоднозначный алфавит (нет `0`/`O`/`1`/`I`)
- Коды истекают через 1 час
- Максимум 3 ожидающих запроса на канал одновременно — дополнительные запросы игнорируются, пока один не истечёт или не будет утверждён
- Пользователи, перечисленные в `allowedUsers` в `settings.json`, всегда пропускают pairing
- Утверждённые пользователи хранятся в `~/.nessy/channels/<name>-allowlist.json` — относитесь к этому файлу как к чувствительному

## Групповые чаты

По умолчанию бот работает только в direct messages. Для включения поддержки групповых чатов установите `groupPolicy` в `"allowlist"` или `"open"`.

### Group Policy

Контролирует, участвует ли бот в групповых чатах вообще:

- **`disabled`** (по умолчанию) — Бот игнорирует все групповые сообщения. Самый безопасный вариант.
- **`allowlist`** — Бот отвечает только в группах, явно перечисленных в `groups` по chat ID. Ключ `"*"` предоставляет default настройки, но **не** действует как wildcard allow.
- **`open`** — Бот отвечает во всех группах, куда он добавлен. Используйте с осторожностью.

### Mention Gating

В группах бот требует `@mention` или ответа на одно из его сообщений по умолчанию. Это предотвращает ответы бота на каждое сообщение в групповом чате.

Настройте на группу с настройкой `groups`:

```json
{
  "groups": {
    "*": { "requireMention": true },
    "-100123456": { "requireMention": false }
  }
}
```

- **`"*"`** — Default настройки для всех групп. Только устанавливает config default, не allowlist entry.
- **Group chat ID** — Override настройки для конкретной группы. Переопределяет `"*"` default.
- **`requireMention`** (по умолчанию: `true`) — Когда `true`, бот отвечает только на сообщения, которые @mention его или отвечают на одно из его сообщений. Когда `false`, бот отвечает на все сообщения (полезно для dedicated task групп).

### Как оцениваются групповые сообщения

```
1. groupPolicy — разрешена ли эта группа?           (no → игнорировать)
2. requireMention — был ли бот упомянут/ответ?     (no → игнорировать)
3. senderPolicy — утверждён ли отправитель?         (no → pairing flow)
4. Маршрутизация в сессию
```

## Поддержка медиа

Каналы поддерживают отправку изображений и файлов агенту, не только текст.

### Изображения

Отправьте фото боту, и агент увидит его — полезно для обмена скриншотами, сообщениями об ошибках или диаграммами. Изображение отправляется напрямую модели как vision ввод.

Для использования поддержки изображений настройте multimodal модель для канала:

```json
{
  "channels": {
    "my-channel": {
      "type": "time",
      "model": "qwen3.5-plus",
      ...
    }
  }
}
```

### Файлы

Отправьте документ (PDF, файл кода, текстовый файл и т.д.) боту. Файл загружается и сохраняется во временную директорию, и агенту сообщается путь к файлу, чтобы он мог прочитать содержимое, используя свои инструменты чтения файлов.

Файлы работают с любой моделью — поддержка multimodal не требуется.

## Dispatch Modes

Контролирует, что происходит, когда вы отправляете новое сообщение, пока бот ещё обрабатывает предыдущее.

- **`steer`** (по умолчанию) — Бот отменяет текущий запрос и начинает работать над новым сообщением. Лучше для обычного чата, где follow-up обычно означает, что вы хотите скорректировать или перенаправить бота.
- **`collect`** — Ваши новые сообщения буферизуются. Когда текущий запрос завершается, все буферизованные сообщения объединяются в один follow-up промпт. Хорошо для async workflow, где хотите queued thoughts.
- **`followup`** — Каждое сообщение queued и обрабатывается как свой собственный отдельный turn, по порядку. Полезно для batch workflow, где каждое сообщение независимо.

```json
{
  "channels": {
    "my-channel": {
      "type": "time",
      "dispatchMode": "steer",
      ...
    }
  }
}
```

Вы также можете установить dispatch mode на группу, переопределяя default канала:

```json
{
  "groups": {
    "*": { "requireMention": true, "dispatchMode": "steer" },
    "-100123456": { "dispatchMode": "collect" }
  }
}
```

## Block Streaming

По умолчанию агент работает некоторое время и затем отправляет один большой ответ. С включённым block streaming ответ приходит как несколько более коротких сообщений, пока агент ещё работает — похоже на то, как ChatGPT или Claude показывают прогрессивный вывод.

```json
{
  "channels": {
    "my-channel": {
      "type": "time",
      "blockStreaming": "on",
      "blockStreamingChunk": { "minChars": 400, "maxChars": 1000 },
      "blockStreamingCoalesce": { "idleMs": 1500 },
      ...
    }
  }
}
```

### Как это работает

- Ответ агента разбивается на блоки на границах параграфов и отправляется как отдельные сообщения
- `minChars` (по умолчанию 400) — не отправлять блок, пока он не станет хотя бы такой длины, чтобы избежать спама крошечными сообщениями
- `maxChars` (по умолчанию 1000) — если блок становится такой длины без естественного разрыва, отправить всё равно
- `idleMs` (по умолчанию 1500) — если агент паузирует (например, запуская инструмент), отправить буферизованное на данный момент
- Когда агент завершается, любой оставшийся текст отправляется немедленно

Только `blockStreaming` требуется. Chunk и coalesce настройки опциональны и имеют sensible default.

## Slash команды

Каналы поддерживают slash команды. Они обрабатываются локально (без agent round-trip):

- `/help` — Вывести доступные команды
- `/clear` — Очистить вашу сессию и начать заново (алиасы: `/reset`, `/new`)
- `/status` — Показать информацию о сессии и access policy

Все остальные slash команды (например, `/compress`, `/summary`) пересылаются агенту.

Эти команды работают на всех типах каналов (Time).

## Запуск

```bash
# Запустить все настроенные каналы (shared агентский процесс)
nessy channel start

# Запустить один канал
nessy channel start my-channel

# Проверить, запущен ли сервис
nessy channel status

# Остановить работающий сервис
nessy channel stop
```

Бот работает в foreground. Нажмите `Ctrl+C` для остановки или используйте `nessy channel stop` из другого терминала.

### Multi-Channel Mode

Когда вы запускаете `nessy channel start` без имени, все каналы, определённые в `settings.json`, запускаются вместе, используя один агентский процесс. Каждый канал поддерживает свои собственные сессии — Time пользователь получают отдельные конверсации, хотя используют одного агента.

Каждый канал использует свой собственный `cwd` из своей конфигурации, поэтому разные каналы могут работать на разных проектах одновременно.

### Service Management

Сервис каналов использует PID файл (`~/.nessy/channels/service.pid`) для отслеживания работающего экземпляра:

- **Предотвращение дубликатов**: Запуск `nessy channel start`, пока сервис уже запущен, покажет ошибку вместо запуска второго экземпляра
- **`nessy channel stop`**: Плавно останавливает работающий сервис из другого терминала
- **`nessy channel status`**: Показывает, запущен ли сервис, его uptime и количество сессий на канал

### Crash Recovery

Если агентский процесс неожиданно падает, сервис каналов автоматически перезапускает его и пытается восстановить все активные сессии. Пользователи могут продолжать свои конверсации без начала заново.

- Сессии персистентны в `~/.nessy/channels/sessions.json`, пока сервис запущен
- При crash: агент перезапускается в течение 3 секунд и перезагружает сохранённые сессии
- После 3 последовательных crash сервис выходит с ошибкой
- При чистом shutdown (Ctrl+C или `nessy channel stop`): session data очищается — следующий запуск всегда свежий
