# Режим демона (`nessy serve`)

Запускайте Nessy CLI как локальный HTTP-демон, чтобы несколько клиентов (плагины IDE, веб-интерфейсы, CI-скрипты, пользовательские CLI) использовали одну сессию агента через HTTP и Server-Sent Events вместо того, чтобы каждый запускал свой собственный подпроцесс.

:::note
**Статус:** Stage 1 (экспериментальный). Stage 1.5 (флаг `nessy --serve` — TUI совместно размещает тот же HTTP-сервер) и Stage 2 (рефакторинг внутри процесса + полировка mDNS/OpenAPI/WebSocket/Prometheus) находятся непосредственно в разработке.

**Честность о масштабе:** Stage 1 рассчитан на **разработчиков, создающих прототипы клиентов на основе поверхности протокола**, и на **локальное сотрудничество одного пользователя / небольшой команды**. Продакшн-нагрузки с несколькими клиентами / длительной работой / нестабильной сетью (мобильные компаньоны, IM-боты, достигающие 1000+ чатов) требуют гарантий Stage 1.5+, которых нет в этом релизе. Смотрите [Гарантии выполнения Stage 1.5+](#гарантии-выполнения-stage-15) для полного списка пробелов и #3803 для дорожной карты сходимости.
:::

## Что это даёт

- **Один процесс агента, много клиентов** — при `sessionScope: 'single'` по умолчанию каждый клиент, подключающийся к демону, использует одну сессию ACP. Живое межклиентское взаимодействие в одном разговоре, одних и тех же файловых диффах, одних и тех же запросах разрешений.
- **Безопасное переподключение потока** — SSE с переподключением `Last-Event-ID` позволяет клиенту отключиться и возобновить работу точно с того места, где он остановился (в пределах окна воспроизведения кольца).
- **Разрешения первому ответившему** — когда агент запрашивает разрешение на выполнение инструмента, каждый подключённый клиент видит запрос; побеждает тот, кто ответил первым.
- **Один демон, одно рабочее пространство** — каждый процесс `nessy serve` привязывается ровно к одному рабочему пространству при запуске. Развёртывания с несколькими рабочими пространствами запускают по одному демону на рабочее пространство на отдельных портах (или за оркестратором).
- **Управление удалённой средой выполнения** — изменение режима одобрения сессии (`POST /session/:id/approval-mode`), переключение инструмента для рабочего пространства (`POST /workspace/tools/:name/enable`), создание пустого `NESSY.md` (`POST /workspace/init`, только механически — НЕ вызывает модель; для AI-fill выполните `POST /session/:id/prompt`), или перезапуск одного MCP-сервера с предварительной проверкой бюджета (`POST /workspace/mcp/:server/restart`). Все четыре операции требуют строгой аутентификации — сначала настройте `--token`.

## Известные ограничения v0.16-alpha

Alpha предназначена для одного локального пользователя: один daemon обслуживает
одно workspace и несколько сессий, использует собственный bearer token и не
обеспечивает TLS, federation или сохранение сессий между перезапусками. Для
долгого локального запуска см. [шаблоны развёртывания](./nessy-serve-deploy-local.md).

## Быстрый старт

### 1. Запуск демона (loopback, без аутентификации)

```bash
cd your-project/
nessy serve
# → nessy serve listening on http://127.0.0.1:4170 (mode=http-bridge, workspace=/path/to/your-project)
# → nessy serve: bearer auth disabled (loopback default). Set NESSY_SERVER_TOKEN to enable.
```

Привязка по умолчанию — `127.0.0.1:4170`. Bearer-аутентификация **отключена** на loopback, поэтому локальная разработка работает «из коробки». Демон привязывается к текущей рабочей директории; используйте `--workspace /path/to/dir` для переопределения.

### 2. Проверка работоспособности

```bash
curl http://127.0.0.1:4170/health
# → {"status":"ok"}

curl http://127.0.0.1:4170/capabilities
# → {"v":1,"mode":"http-bridge","features":["health","capabilities","session_create",...],"workspaceCwd":"/path/to/your-project"}
```

Поле `workspaceCwd` предоставляет привязанное рабочее пространство, чтобы клиенты могли выполнить предварительную проверку и опустить `cwd` в `POST /session`.

Демон также предоставляет снимки состояния выполнения только для чтения для клиентских UI:
`GET /workspace/mcp`, `GET /workspace/skills`, `GET /workspace/providers`,
`GET /workspace/env`, `GET /workspace/preflight`,
`GET /session/:id/context` и `GET /session/:id/supported-commands`.

`GET /workspace/mcp`, `GET /workspace/skills` и `GET /workspace/providers`
отражают живое состояние ACP и не запускают дочерний процесс ACP в простое;
простаивающий демон возвращает `initialized: false` с пустым снимком. Как только
сессия активна, они переключаются на `initialized: true` и показывают реальное
состояние.

`GET /workspace/env` и `GET /workspace/preflight` всегда отвечают
`initialized: true` независимо от состояния ACP. `env` никогда не опрашивает ACP
(только информация о процессе демона); `preflight` отвечает на ячейки уровня демона
из `process.*` и выдаёт заполнители `status: 'not_started'` для ячеек уровня ACP,
когда дочерний процесс простаивает.

`GET /workspace/env` сообщает о времени выполнения процесса демона, платформе,
песочнице, прокси и **наличии** (никогда не значении) разрешённых секретных
переменных окружения, таких как `OPENAI_API_KEY`. URL прокси очищаются от учётных
данных и сводятся к `host:port` перед передачей по сети. Маршрут всегда отвечает
напрямую из процесса демона и никогда не порождает дочерний процесс ACP.

`GET /workspace/preflight` возвращает список проверок готовности. **Ячейки уровня
демона** (версия Node, точка входа CLI, рабочая директория, ripgrep, git, npm)
всегда отображаются. **Ячейки уровня ACP** (аутентификация, обнаружение MCP,
скиллы, провайдеры, реестр инструментов, исходящий доступ) требуют живого
дочернего процесса ACP — когда демон простаивает, они выдают заполнители
`status: 'not_started'`, а не запускают ACP только для их заполнения. Ошибки
сопоставляются с закрытым перечислением `errorKind` (`missing_binary`,
`auth_env_error`, `init_timeout`, `protocol_error`, `missing_file`,
`parse_error`, `blocked_egress`), чтобы клиентские UI могли отображать
структурированное исправление.

Демон также предоставляет вспомогательные функции для работы с файлами рабочего пространства:

- `GET /file` читает текстовые файлы и возвращает хэш `sha256:<hex>` сырых байтов.
- `GET /file/bytes` читает ограниченные окна сырых байтов и возвращает содержимое в base64.
- `POST /file/write` создаёт или заменяет текстовые файлы.
- `POST /file/edit` применяет одну точную замену текста.

Write/edit — это **строгие маршруты мутации**: даже на loopback они требуют
настроенного bearer-токена, иначе возвращают `token_required`. Замены и
редактирования требуют последний `expectedHash` из `GET /file` (или
полнооконного `GET /file/bytes`). `create` никогда не перезаписывает. Явные
записи в игнорируемые пути разрешены, но аудируются. Двоичная запись,
удаление/перемещение/mkdir и рекурсивное создание родителей не входят в эту
поверхность.

### 3. Открытие сессии

```bash
curl -X POST http://127.0.0.1:4170/session \
  -H 'Content-Type: application/json' \
  -d '{}'
# → {"sessionId":"<uuid>","workspaceCwd":"…","attached":false}
```

`cwd` можно опустить — маршрут вернётся к привязанному рабочему пространству демона. Отправка `cwd`, который не совпадает с привязанным рабочим пространством, возвращает `400 workspace_mismatch` (демон привязан ровно к одному рабочему пространству; запустите отдельный демон для другого).

Второй клиент, отправляющий запрос в `/session` (любое совпадающее `cwd` или его отсутствие), получает `"attached": true` — теперь они используют общего агента.

### 4. Подписка на поток событий (в другом терминале сначала)

```bash
SESSION_ID="<из шага 3>"
curl -N http://127.0.0.1:4170/session/$SESSION_ID/events
# → id: 1
#   event: session_update
#   data: {"id":1,"v":1,"type":"session_update","data":{"sessionUpdate":"agent_message_chunk","content":{"type":"text","text":"…"}}}
```

Строка `data:` — это **полная обёртка события** — `{id?, v, type, data, originatorClientId?}` — сериализованная в JSON в одной строке. Полезная нагрузка ACP (блок `sessionUpdate` в этом примере) находится под `data` внутри этой обёртки. Строки SSE-уровня `id:` / `event:` удобны для клиентов EventSource; те же значения появляются внутри JSON-обёртки, поэтому потребители raw-fetch тоже получают их.

Откройте это **до** отправки промпта — буфер воспроизведения SSE хранит
последние 4000 событий, поэтому запоздалый подписчик может наверстать через Last-Event-ID,
но для простого случая «наблюдение за одним промптом» проще подписаться
сначала и позволить потоку идти в реальном времени.

Поток испускает `session_update` (фрагменты LLM, вызовы инструментов, использование),
`permission_request` (инструмент требует одобрения), `permission_resolved`
(кто-то проголосовал), `model_switched`, `model_switch_failed`, и терминальные
фреймы `session_died` (дочерний процесс агента упал — SSE затем закрывается) и
`client_evicted` (ваша очередь переполнилась — SSE затем закрывается).

### 5. Отправка промпта (вернитесь в исходный терминал)

```bash
curl -X POST http://127.0.0.1:4170/session/$SESSION_ID/prompt \
  -H 'Content-Type: application/json' \
  -d '{"prompt":[{"type":"text","text":"What does src/main.ts do?"}]}'
# → {"stopReason":"end_turn"}
```

`curl -N` из шага 4 будет печатать фреймы по мере их поступления.

## Аутентификация

Для всего, что выходит за пределы loopback, вы **должны** передать bearer-токен:

```bash
export NESSY_SERVER_TOKEN="$(openssl rand -hex 32)"
nessy serve --hostname 0.0.0.0 --port 4170
# → boot refuses without NESSY_SERVER_TOKEN
```

Затем клиенты отправляют Authorization: Bearer `$NESSY_SERVER_TOKEN` в каждом запросе. `/health` освобождён **только на привязках loopback**, чтобы k8s/Compose `liveness`-пробы внутри пода (где демон слушает `127.0.0.1`) не нуждались в учётных данных. На привязках не-loopback (`--hostname 0.0.0.0` и т.д.) `/health` требует токен, как и любой другой маршрут — в противном случае злоумышленник может зондировать произвольные адреса для подтверждения существования демона. Используйте `/capabilities` для проверки правильности токена сквозным образом (он всегда требует аутентификации):

```bash
curl -H "Authorization: Bearer $NESSY_SERVER_TOKEN" http://your-host:4170/capabilities
# → {"v":1,"mode":"http-bridge","features":[...],"modelServices":[],"workspaceCwd":"/path/to/your-project"}
# Wrong token → 401
```

Сравнение токенов выполняется за постоянное время (SHA-256 + `crypto.timingSafeEqual`); ответы 401 единообразны для «отсутствующий заголовок», «неправильная схема» и «неправильный токен», поэтому боковой канал не может различить их.

**Настройка регуляторов нагрузки.** `--max-sessions` — это ограничение на **новые дочерние процессы**.
Три других уровня также ограничивают нагрузку — при настройке для высококонкурентного
развёртывания настраивайте их вместе:

- **уровень слушателя**: `--max-connections` / `server.maxConnections=256`
  ограничивает сырые TCP-соединения (back-pressure медленных клиентов).
- **подписчики на сессию**: EventBus ограничивает SSE-подписчиков
  64 на сессию по умолчанию; 65-й клиент получает терминальный
  `stream_error` и закрывается.
- **отставание на подписчика**: очередь из 256 фреймов на SSE-клиент;
  клиент сверх вместимости получает терминальный фрейм `client_evicted` и
  закрывается (один медленный потребитель не может заблокировать демон).

Четыре ограничения взаимодействуют: `--max-sessions × 64 подписчика × 256 фреймов`
— это наихудший случай памяти в полёте на уровне EventBus. Настройка по умолчанию
предполагает нагрузку одного пользователя / небольшой команды; увеличивайте постепенно
(и следите за RSS) для мультитенантных развёртываний.
:::

:::tip
**MCP client guardrails.** Рабочее пространство, объявляющее 30 MCP-серверов в `mcpServers`, запустит 30 клиентов без ограничения, если вы не установите его. `--mcp-client-budget=N` ограничивает количество живых MCP-клиентов; `--mcp-budget-mode={enforce,warn,off}` выбирает поведение. По умолчанию `warn`, когда бюджет установлен (снимок показывает предупреждение, но клиент не отклоняется — полезно для измерения реального `fanout` перед включением `enforcement`). Отклонённые серверы в режиме `enforce` получают `disabledReason: 'budget'` на ячейке сервера, а ячейка `budgets[0]` показывает `status: 'error'` + `errorKind: 'budget_exhausted'`. Резервирование слотов по имени сервера и переживает переподключения / таймауты обнаружения — отклонённый сервер не может занять слот у здорового.

⚠️ **v1 scope: на сессию, не на рабочее пространство.** Каждая сессия ACP внутри демона имеет свой `Config`/`McpClientManager` (создаётся через `newSessionConfig` на сессию). Бюджет ограничивает живые MCP-клиенты **на сессию**, не агрегированно по всем сессиям в рабочем пространстве. Снимок на `GET /workspace/mcp` отражает вид `bootstrap`-сессии (ячейка несёт `scope: 'session'` для честности). Если вы запускаете 5 одновременных сессий ACP с `--mcp-client-budget=10`, у вас может быть до 50 живых MCP-клиентов across the daemon — ограничение держится на сессию. **Wave 5 PR 23 (shared MCP pool)** вводит `manager` на уровне рабочего пространства и переводит это на настоящее `enforcement` на рабочее пространство.

```sh
nessy serve --mcp-client-budget=10 --mcp-budget-mode=warn
# позже, после телеметрии, показывающей ваше реальное распределение:
nessy serve --mcp-client-budget=10 --mcp-budget-mode=enforce
```

Это **не** то же самое, что `MCP_SERVER_CONNECTION_BATCH_SIZE` в claude-code (который ограничивает стартовую конкурентность); они ортогональны. PR 23 добавит настоящий общий пул MCP (ячейка `scope: 'workspace'` в `budgets[]` рядом с ячейкой на сессию); PR 14 v1 — это внутрипроцессный счётчик + `soft` `enforcement` на существующем per-session `manager`.

**Push events.** SDK-клиенты, подписанные на `GET /session/:id/events`, получают типизированные фреймы, когда пороги бюджета пересекаются — `mcp_budget_warning` (синтетический, срабатывает один раз на восходящее пересечение 75% с `hysteresis` re-arm на 37.5%, рекламируется через `mcp_guardrail_events`) и `mcp_child_refused_batch` (coalesced один раз на проход обнаружения в режиме `enforce`; length-1 от отказа `readResource` lazy-spawn). Снимок на `GET /workspace/mcp` всё ещё является source-of-truth для состояния-после-переподключения; события — change-edges. Полезно при `dashboarding` в реальном времени без `polling`.
:::

## Модель угроз развёртывания по умолчанию

### Deadlines и idle timeout записи

HTTP-запросы и запись SSE ограничены таймаутами, чтобы зависший или медленный
клиент не удерживал ресурсы daemon бесконечно. Клиент должен переподключаться и
использовать `Last-Event-ID` для доступного replay.

- **Только 127.0.0.1** — привязка loopback, аутентификация не требуется.
- **`--hostname 0.0.0.0` требует токена** — запуск отказывает без него.
- **`LOOPBACK_BINDS` включает IPv6** — `::1` и `[::1]` считаются loopback для правила без токена.
- **Список разрешений заголовка Host** — на привязках **loopback** демон проверяет, что `Host:` совпадает с `localhost:порт` / `127.0.0.1:порт` / `[::1]:порт` / `host.docker.internal:порт` (без учёта регистра согласно RFC 7230 §5.4) для защиты от DNS-rebinding. **Привязки не-loopback (`--hostname 0.0.0.0`) намеренно обходят список разрешений Host** — оператор выбрал поверхность атаки, поэтому gate bearer-токена является единственным уровнем аутентификации; обратные прокси / SNI / привязка клиентских сертификатов — ответственность оператора, а не демона. Если вам нужна изоляция на основе Host на привязке не-loopback, завершайте TLS + проверяйте Host на фронт-прокси.
- **CORS отклоняет любой браузерный Origin** — возвращает JSON `403`. **Следствие для веб-интерфейсов, обслуживаемых браузером** (BUy4e): любой фронтенд в стиле `packages/webui`, живущий на отдельном `origin`, получит 403 на уровне провода. Варианты Stage 1 для браузерного потребления: (a) упакуйте веб-интерфейс как нативную оболочку (Electron/Tauri), чтобы заголовок `Origin` не отправлялся, или (b) разместите перед демоном same-origin обратный прокси, который удаляет/переписывает `Origin` для известного фронтенда. Stage 1.5 добавит `--allow-origin <шаблон>` для opt-in именованных фронтендов.
- **Порождённый дочерний процесс `nessy --acp` наследует окружение демона** с одной явной очисткой: `NESSY_SERVER_TOKEN` удаляется перед запуском дочернего процесса (собственный bearer демона; агенту он не нужен). Всё остальное — `OPENAI_API_KEY` / `ANTHROPIC_API_KEY` / `NESSY_*` / `DASHSCOPE_API_KEY` / ваш пользовательский `modelProviders[].envKey` / и т.д. — передаётся, потому что агенту законно нужны они для аутентификации в LLM. **Это намеренно, а не песочница.** Агент работает под тем же UID с доступом к инструментам оболочки, поэтому всё в `~/.bashrc` / `~/.aws/credentials` / `~/.npmrc` достижимо через prompt-инъекцию независимо. Передача окружения не является границей безопасности; пользователь как корень доверия — является. Не запускайте `nessy serve` под идентификатором, имеющим учётные данные в окружении, которым вы не доверили бы агенту.
- **Ограниченные очереди SSE на подписчика** — медленный клиент, переполняющий свою очередь, получает терминальный фрейм `client_evicted` и закрывается; один застрявший потребитель не может заблокировать демон.
- **Плавное завершение** — SIGINT/SIGTERM осушают дочерние процессы агента перед закрытием слушателя (дедлайн 10 с на дочерний процесс).

:::tip
⚠️ **Известный пробел Stage 1 — разрешения глобальны для демона, а не для сессии (BUy4H).** `pendingPermissions` живёт на уровне демона; любой клиент, держащий bearer-токен, может голосовать по любому `requestId` для любой сессии, которую он видит (и SSE-события `permission_request` несут requestId в своей полезной нагрузке). Это приемлемо в модели доверия одного пользователя / небольшой команды, где каждый аутентифицированный клиент — тот же человек или коллеги, которым они доверяют. Stage 1.5 перейдёт к `POST /session/:id/permission/:requestId` + отображению на уровне сессии + идентичности на клиента (`must-have` #3 из последующего обзора); до тех пор не запускайте `nessy serve` за bearer, разделённым с ненадёжными сторонами.

⚠️ **Известный пробел Stage 1 — тело `POST /session/:id/prompt` ограничено 10 МБ (BUy4L).** Мультимодальные промпты, содержащие изображения / PDF / аудио, превышающие 10 МБ, завершатся ошибкой на этапе разбора тела до запуска логики маршрута (без потоковой передачи, без прерывания в середине загрузки). Обходное решение: уменьшите содержимое на стороне клиента или передайте ссылку на путь и позвольте агенту прочитать файл через `readTextFile`. Stage 1.5 примет `multipart/form-data` или `chunked`-кодирование на `/prompt`, чтобы большие промпты не упирались в потолок.

⚠️ **Известный пробел Stage 1 — фантомные SSE-соединения за NAT.**
Демон обнаруживает мёртвых клиентов через TCP back-pressure на `heartbeat`
(интервал 15 с). Клиент, который исчез БЕЗ TCP RST (например, NAT-бокс,
молча сбрасывающий простые потоки), держит сокет на уровне ядра
«живым», пока зонды `keepalive` Node не истекут — обычно ~2 часа
по умолчанию на Linux. В развёртываниях `--hostname 0.0.0.0` за такими
NAT фантомные SSE-соединения могут накапливаться и в конечном итоге
достичь потолка `server.maxConnections` 256. Stage 2 добавит
дедлайн бездействия на уровне приложения (отслеживание `last-byte-written` +
таймаут на соединение). До тех пор операторам в сетях, которые
поглощают RST, может потребоваться понизить `server.keepAliveTimeout`
через обратный прокси или принять периодические перезапуски демона.
:::

## Развёртывание с несколькими сессиями и рабочими пространствами

Каждый процесс `nessy serve` привязывается к **одному рабочему пространству** при запуске. Внутри этого рабочего пространства он мультиплексирует N сессий на один дочерний процесс `nessy --acp` через собственную карту сессий агента — сессии разделяют процесс дочернего процесса / состояние OAuth / кэш чтения файлов / разбор иерархической памяти.

Для размещения **нескольких рабочих пространств** (один пользователь, несколько репозиториев; или несколько пользователей на одном хосте) запускайте **несколько процессов демона** — по одному на рабочее пространство, каждый на своём порту, под управлением `systemd` / docker-`compose` / k8s / ссылочного оркестратора `nessy-`coordinator`. Компромисс намеренный: одно рабочее пространство на дочерний процесс означает, что `loadSettings`(cwd)` / область OAuth / MCP-серверов остаются выровненными с привязанным каталогом и не дрейфуют между запросами.

> **Подпишитесь ДО отправки `modelServiceId` при подключении.** Когда клиент `POST /session` с `modelServiceId` и в рабочем пространстве уже есть сессия, запускающая другую модель, демон вызывает внутренний вызов `setSessionModel` — сбои НЕ передаются как HTTP-ошибка (сессия остаётся работоспособной на своей текущей модели). Видимый сигнал сбоя — событие `model_switch_failed` в SSE-потоке сессии. Если вы вызываете `POST /session` и только ЗАТЕМ открываете `GET /session/:id/events`, вы пропустите событие сбоя и молча продолжите говорить с неправильной моделью. Сначала откройте SSE-поток или передайте Last-Event-ID: 0` при подписке для воспроизведения самого старого доступного события кольца.

Для обработки нескольких **пользователей** (каждый со своей квотой, журналом аудита, песочницей) или для масштабирования за пределы досягаемости одного процесса (бюджет холодного старта, количество FD, RSS) порождайте по одному демону на рабочее пространство на пользователя за внешним оркестратором. Этот оркестратор (мультитенантность / `OIDC` / квоты / аудит / k8s) **не входит в сферу** проекта nessy-cli — смотрите задачу [#3803](https://gitlab.tcsbank.ru/nestor/nessy-cli/issues/3803) «Внешняя справочная архитектура» для указателей по дизайну.

## Загрузка и возобновление сохранённой сессии

Демон предоставляет ACP `session/load` и `session/unstable_resumeSession` через HTTP через два маршрута:

| Маршрут                    | Когда использовать                                                                                                                                                                                                               |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /session/:id/load`   | У клиента **нет** отображённой истории (холодное переподключение, выбор-затем-открытие). Демон воспроизводит каждый сохранённый поворот через SSE, поэтому подписчики видят полную стенограмму. Тег возможности: `session_load`. |
| `POST /session/:id/resume` | У клиента уже есть повороты на экране и нужна только ручка на стороне демона. Контекст модели восстановлен на стороне агента без повторения UI — поток SSE остаётся чистым. Тег возможности: `unstable_session_resume`.          |

TypeScript SDK предоставляет оба как статические фабрики на `DaemonSessionClient`:

```ts
import { DaemonClient, DaemonSessionClient } from '@nestor/nessy-cli-sdk';

const client = new DaemonClient({ baseUrl: 'http://127.0.0.1:4170' });

// Холодное переподключение — демон воспроизведёт историю через SSE.
const session = await DaemonSessionClient.load(client, 'persisted-id');

// Или, если ваш UI уже имеет историю, пропустите воспроизведение:
// const session = await DaemonSessionClient.resume(client, 'persisted-id');

for await (const event of session.events()) {
  // Сначала воспроизведённые фреймы `session_update` (только load),
  // затем живые события.
}
```

Выполните предварительную проверку `caps.features`.session_load` / ``caps.features``.unstable_session_resume` перед вызовом — старые демоны возвращают `404`. Одновременные запросы одного действия для одного id объединяются; меж-действенные гонки (`load`, гонящаяся с `resume`) получают `409 restore_in_progress` с Retry-After: 5`. Смотрите [справочник по протоколу](../../../developers/nessy-serve-protocol.md) для полной обёртки ошибки.

Примечание: воспроизведение истории ограничено кольцом SSE (по умолчанию 4000 фреймов). Длинные истории с разговорчивыми поворотами могут превысить это — самые ранние фреймы молча отбрасываются. Для очень длинных сессий предпочитайте `resume` и полагайтесь на локальный сохранённый UI клиента.

## Модель долговечности

**Сессии эфемерны в Stage 1.** Планируйте соответственно:

- Сбой дочернего процесса публикует `session_died` и удаляет сессию из карт демона. **Возобновления нет** — клиенты должны снова выполнить `POST /session`.
- Перезапуск демона теряет каждую активную сессию. ACP `loadSession` / `unstable_resumeSession` **не представлены через HTTP** в Stage 1; сессии не переживают демон.
- Долгие отключения клиента (>5 мин на разговорном ходе) могут обогнать кольцо воспроизведения SSE (по умолчанию 4000 фреймов) — переподключение `Last-Event-ID` успешно, но состояние может быть несвязным. Для мобильных / клиентов с нестабильной сетью планируйте воссоздание сессии и повторное открытие SSE при долгих падениях.
- Файловые операции (`writeTextFile`) атомарны при сбоях (запись-затем-переименование); они не атомарны при перезапусках демона в смысле воспроизведения — запись файла либо произошла, либо нет.

Если вашей интеграции требуется долговечность между перезапусками, вам нужен либо Stage 1.5+ (`loadSession` через HTTP, уровень сохранения), либо собственное восстановление состояния на уровне приложения. Не храните долгие, чувствительные к перезапуску состояния внутри сессии демона.

## Гарантии выполнения Stage 1.5+

Контракт Stage 1 рассчитан на прототипирование. Следующее **не** входит в Stage 1 — продакшн-интеграции нуждаются в Stage 1.5+ перед полаганием на них:

**Блокеры для серьёзного `downstream`-использования:**

1. **`loadSession` / `unstable_resumeSession` через HTTP** — без этого ни одна интеграция не переживёт сбой дочернего процесса или перезапуск демона, и любой оркестратор, координирующий демон, не сможет восстановить состояние.
2. **Постоянная идентичность клиента (парные токены + отзыв на клиента)** — Stage 1 использует один общий bearer; утёкший токен отзывает всех, и `originatorClientId` объявляется самим клиентом, а не штампуется демоном из аутентифицированной идентичности.

**Базовый уровень надёжности:**

3. **Путь `heartbeat` по инициативе клиента** — различать «агент думает» от «демон мёртв» без ожидания 15-секундного `heartbeat` сервера.
4. **Событие `permission_already_resolved`**, когда голос проигрывает гонку первому ответившему — в настоящее время UI должны выводить состояние из `404`.
5. **Большее / настраиваемое на сессию кольцо воспроизведения** — по умолчанию 4000 покрывает короткие падения; мобильные / разговорные нагрузки нуждаются в 8000+ или настройке на сессию.
6. **Событие `slow_client_warning` перед `client_evicted`** — мягкое back-pressure, чтобы хорошо ведущие себя медленные клиенты могли самоограничиться (обрезать глубину рендеринга, отбрасывать фрагменты) перед завершением.

**Эргономика интеграции:**

7. **`POST /session/:id/_meta` для IM-стиля контекста** — ключ-значение на сессию, прикреплённое к последующим промптам (id чата, отправитель, id потока) заменяет импровизацию на канал.
8. **Фактическое согласование возможностей `/capabilities`** — `protocol_versions: { acp: '0.14.x', daemon_envelope: 1 }`, чтобы клиенты могли обнаруживать дрейф вместо падения в «неизвестный фрейм, игнорировать».
9. **Первоклассная документация по долговечности** (этот раздел) — уже поставлена выше.

## Границы области Stage 1 — что мы не будем исправлять в Stage 1.5

Два структурных выбора являются явными не-целями для основной дорожной карты Stage 1 / 1.5 / 2. Если ваш вариант использования зависит от любого из них, планируйте вокруг них, а не ждите нас.

### Состояние сессии — только локальная мутация

План Stage 1.5 описывает TUI как внутрипроцессного подписчика EventBus. На практике **UI TUI строго больше, чем проводной протокол**:

- **Только локальный UI** — ~15 компонентов диалогов Ink (`ModelDialog`, `MemoryDialog`, `PermissionsDialog`, `SessionPicker`, `WelcomeBackDialog`, `FolderTrustDialog`, …) и slash-команды ``local`-jsx` (`/ide`, `/auth`, `/init`, `/resume`, `/rename`, `/delete`, `/language`, `/arena`, …) рендерят терминал-специфичный Ink JSX. Удалённые клиенты на HTTP/SSE не могут эквивалентно рендерить Ink, и эти потоки не испускают проводного события.
- **Мутации состояния сессии без проводных событий** — `/approval-mode`, `/memory add`, ``/mcp add-server`, `/agents`, `/tools `enable`/disable`, `/auth`, `/init` (запись `CLAUDE.md`) всё изменяет поведение агента, но только `/model` в настоящее время публикует событие (`model_switched`).

**Выбор Stage 1 — вариант (A) из обзора**: не продвигать эти мутации в проводные события. Два режима развёртывания имеют разные последствия.

#### Режим 1 — headless `nessy serve` (текущее состояние)

Внутри демона не запускается оболочка TUI. Перечисленные выше slash-команды **не существуют** в этом режиме — нет терминального UI для их выдачи. Состояние сессии поэтому:

- **Заморожено во время запуска** для approval-mode / `memory` / `mcp `servers``/`agents`/`tools`allowlist /`auth`— всё загружается из настроек + диска при запуске дочернего процесса`nessy --acp` демона; неизменно в течение жизни сессии.
- **Изменяемо через HTTP** только через маршруты, которые этот MR предоставляет — в первую очередь `POST /session/:id/model` (публикует `model_switched`). Голоса разрешений (`POST /permission/:`requestId``) — на запрос, а не на состояние сессии.

**Следствие:** удалённые клиенты в headless-режиме видят **полное состояние сессии**. Никакой TUI не скрывает дополнительного состояния; дрейф невозможен. Если вы хотите изменить approval-mode или добавить MCP-сервер, перезапустите демон с новыми настройками — демон не предоставляет мутацию выполнения для них сегодня.

#### Режим 2 — Stage 1.5 `nessy --serve совместно размещённый TUI (будет реализовано)

Когда Stage 1.5 приземлит `nessy --serve` (процесс TUI совместно размещает тот же HTTP-сервер), TUI **существует** рядом с удалёнными клиентами. Локальный оператор, вводящий `/approval-mode auto` или ``/mcp add-server`, мутирует состояние сессии, и удалённые клиенты на HTTP не имеют события для наблюдения изменения.

В этом режиме TUI — **«супер-клиент»** — он наблюдает тот же разговор агента, который видят удалённые клиенты, И может мутировать состояние сессии, которое удалённые клиенты не могут. Асимметрия:

- ✅ И TUI, и удалённые клиенты видят одни и те же сообщения агента, вызовы инструментов, файловые диффы, запросы разрешений.
- ❌ Только TUI видит / мутирует approval-mode / память / список MCP-серверов / агенты / allowlist инструментов / состояние аутентификации.

**Следствие в режиме 2:** если UI удалённого клиента пытается отразить настройки сессии, он может дрейфовать после любой slash-команды TUI. Удалённые клиенты должны **повторно получать состояние при подключении / переподключении** (используйте Last-Event-ID: 0`для воспроизведения самого старого события кольца для таких вещей, как`model_switched`); они НЕ должны полагаться на инкрементальные события для мутаций на стороне TUI.

#### Почему (A), а не (B) (продвижение мутаций в семейство событий `session_state_changed`)

(B) — более амбициозный ответ, но запирает Stage 1.5 в существенно большую проводную поверхность, которая также должна чисто пройти через запланированный внутрипроцессный рефакторинг. Мы предпочитаем честно пройти меньший масштаб. Работа по таксономии событий состояния сессии — перечисление, какие потоки TUI являются локальными только по дизайну vs. могли бы правдоподобно выпуститься в провод под будущим opt-in (B)-подобным расширением — перемещается в [#3803](https://gitlab.tcsbank.ru/nestor/nessy-cli/issues/3803), а не в код Stage 1.5.

### N параллельных сессий разделяют один дочерний процесс `nessy --acp`

Несколько сессий на одном рабочем пространстве **разделяют один дочерний процесс `nessy --acp`** через собственную поддержку мультисессий агента (`packages/cli/src/acp-`integration`/acpAgent.ts:194: `private` `sessions`: Map<string, Session>`). Мост вызывает `connection.newSession`(\{cwd, `mcpServers`\})`для каждой сессии — агент хранит их в своей карте сессий и демультиплексирует по`sessionId` вызова.

Конкретная стоимость при N=5 сессий на одном рабочем пространстве:

| Ресурс                                 | На сессию     | При N=5                              |
| -------------------------------------- | ------------- | ------------------------------------ |
| Дочерний процесс демона Node           | 1             | **1** (разделяется)                  |
| Дочерний процесс `nessy --acp`         | разделяется   | **60–100 МБ** (один процесс)         |
| Дочерние процессы MCP-серверов         | на сессию     | 3×N если конфигурации различаются    |
| `FileReadCache` (куча внутри процесса) | разделяется   | распарсено однажды                   |
| Разбор `CLAUDE.md` / памяти иерархии   | разделяется   | распарсено однажды                   |
| Состояние токена обновления OAuth      | разделяется   | **один путь обновления**             |
| Изученные факты авто-памяти            | разделяется   | одна база знаний на дочерний процесс |
| Холодный старт                         | только первый | \<200 мс после первой сессии         |

Мост держит **один канал на демон** (один демон на рабочее пространство, согласно §02). Канал остаётся живым, пока хотя бы одна сессия жива; последний `killSession` (или сбой на уровне канала) убивает дочерний процесс.

**Дочерние процессы MCP-серверов** всё ещё на сессию сегодня — конфигурация каждой сессии может указывать разные серверы, поэтому они порождаются независимо. Последующее действие Stage 1.5: подсчёт ссылок MCP-серверов по `(workspace, config-`hash`)`, чтобы идентичные конфигурации разделялись. Не входит в сферу этого PR.

**Агенты-партнёры (`Cursor` / `Continue` / `Claude Code` / `OpenCode` / `Gemini CLI`) все делают однопроцессные мультисессии.** nessy-cli соответствует им на уровне агента; мост Stage 1 в этом MR делает ту же архитектуру видимой через HTTP.

## Вход в удалённый демон

Когда демон работает на удалённом поде (без общего дисплея с вами), вы всё ещё можете войти в учётную запись Nessy, запустив OAuth `device` `flow` через HTTP. Демон опрашивает IdP сам; ваша задача — просто открыть URL на любом устройстве с браузером.

```bash
# 1. Запустите поток. Демон связывается с IdP, возвращает код + URL.
curl -X POST http://127.0.0.1:4170/workspace/auth/device-flow \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"providerId":"dp-auth"}'
# → 201 {
#     "deviceFlowId": "fa07c61b-…",
#     "userCode": "USER-1",
#     "verificationUri": "https://chat.nessy.ai/api/v1/oauth2/device",
#     "verificationUriComplete": "https://chat.nessy.ai/...?user_code=USER-1",
#     "expiresAt": 1700000600000,
#     "intervalMs": 5000,
#     "attached": false
#   }

# 2. Посетите URL на телефоне / ноутбуке, введите код пользователя.
# 3. Опросите завершение (или подпишитесь на SSE для события auth_device_flow_authorized):
curl http://127.0.0.1:4170/workspace/auth/device-flow/fa07c61b-… \
  -H "Authorization: Bearer $TOKEN"
# → статус переходит: pending → authorized
```

TypeScript SDK обёртывает оба шага в один хелпер:

```ts
import { DaemonClient } from '@nestor/nessy-cli-sdk';

const client = new DaemonClient({ baseUrl, token });
const flow = await client.auth.start({ providerId: 'dp-auth' });
console.log(`Откройте ${flow.verificationUri}\nКод: ${flow.userCode}`);
const result = await flow.awaitCompletion({ signal: abortCtrl.signal });
// result.status === 'authorized'
```

**Демон никогда не открывает браузер от вашего имени.** Даже при локальном запуске демон остаётся пассивным — он возвращает URL и позволяет SDK / пользователю выбрать, где его открыть. Это намеренно: демон на безголовом поде, вызывающий `xdg-open`, молча завершится ошибкой, маскируя фактическую поверхность аутентификации. Отразите UX "Нажмите Enter для открытия браузера" из `gh auth login` в вашем клиенте.

**`--require-auth` и удобство разработки.** Маршруты `device-flow` используют строгий `gate` мутации (PR 15), что означает, что loopback-по умолчанию без токена возвращает `401 token_required`. Локально простейший способ обойти это во время разработки — `nessy serve --token=dev-token`; вам не нужен `--require-auth`, если вы не укрепляете loopback-по умолчанию.

**Ограничение меж-демона.** `oauth_creds.json` общий для демона (`~/.nessy/oauth_creds.json`), поэтому успешный вход в демоне A автоматически подхватывается следующим обновлением токена демона B — но SDK-клиенты демона B не получат событие `auth_device_flow_authorized` (события на демон).

**Перехват меж-клиентом.** Два SDK-клиента на одном демоне, которые оба `POST /workspace/auth/device-flow` для одного и того же провайдера, получают одиночный на провайдер: первый вызов запускает свежий запрос IdP и возвращает `attached: false`; второй вызов возвращает СУЩЕСТВУЮЩУЮ входящую запись с `attached: true`. Перехват записывается в аудиторский след (под `X-Nessy-Client-Id` второго клиента), но НЕ издаёт отдельное событие — оба клиента в конечном итоге наблюдают ОДНО И ТО ЖЕ `auth_device_flow_authorized`, как только пользователь завершает страницу IdP. Если ваш UI различает "Я начал это" и "поток кого-то другого, к которому я присоединился", ветвитесь на поле `attached`, возвращённом `start()`.

## Файл логов daemon

Daemon пишет отдельный диагностический лог, если логирование включено. Он не
заменяет session debug logs и не содержит полной истории диалога.

### Отключение

Лог можно отключить настройкой или флагом запуска, если он не нужен.

### Связь с session debug logs

Daemon log описывает сервер, соединения и runtime; session logs относятся к
конкретным агентским сессиям и настраиваются отдельно.

### Ротация отсутствует

В alpha встроенной ротации нет: используйте systemd/journald, launchd или
внешний logrotate и контролируйте размер файла.

## Управление MCP-серверами во время выполнения

### `POST /workspace/mcp/servers` — добавить сервер

Endpoint добавляет runtime-конфигурацию MCP для текущего workspace без
перезапуска daemon.

### `DELETE /workspace/mcp/servers/:name` — удалить сервер

Удаляет runtime-сервер по имени.

### Shadow semantics

Runtime-запись с тем же именем временно перекрывает статическую конфигурацию; её
удаление снова раскрывает статический сервер.

### События

Добавление, удаление и изменение доступности публикуются в SSE, чтобы клиенты
обновили список инструментов.
