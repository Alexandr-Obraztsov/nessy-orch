# Структурированный вывод (`--json-schema`)

Ограничивает финальный ответ моделью JSON Schema, которую вы предоставляете. Nessy CLI регистрирует синтетический терминальный инструмент, который модель обязана вызвать, разбирает аргументы вызова против вашей схемы и предоставляет проверенную полезную нагрузку в stdout (или в оболочке результата JSON / stream-json). Первый действительный вызов завершает выполнение.

Только режим без интерфейса — работает с `nessy -p`, позиционным промптом или промптом, переданным через stdin.

## Быстрый старт

```bash
nessy --prompt "Summarize the changes in HEAD with risk_level" \
  --json-schema '{
    "type": "object",
    "properties": {
      "summary":    { "type": "string" },
      "risk_level": { "type": "string", "enum": ["low", "medium", "high"] }
    },
    "required": ["summary", "risk_level"],
    "additionalProperties": false
  }'
```

Вывод в stdout (по умолчанию `--output-format text`):

```json
{ "summary": "…", "risk_level": "low" }
```

Строка содержит ровно `JSON`-сериализованную полезную нагрузку + новую строку — без оболочки, без журнала событий. Передавайте её напрямую в `jq` или другой потребитель.

В режиме **text** stdout зарезервирован для JSON-полезной нагрузки при успехе и пуст при ошибке; сообщения об ошибках и строки журнала идут в stderr. Это делает шаблоны захвата вида `$(nessy --json-schema …) || exit 1` безопасными в режиме text — ошибки попадают в stderr, а не смешиваются с захваченной переменной. Случайная проза модели во время планирования **не** дублируется в stderr — режим text отбрасывает её; используйте `--output-format json` или `stream-json`, если нужно её видеть.

В `--output-format json` и `stream-json` сообщение об ошибке результата выдаётся в **stdout** вместе с путём успеха (как финальный элемент массива JSON или завершающая строка `result` в потоке JSONL). Не все режимы ошибок выдают результат в stdout — max-session-`turns` (выход 53) и прерывания сигналом (выход 130) завершаются только выводом в stderr. Сначала проверьте код выхода; `is_error` в объекте результата разбирается в подмножестве ошибок, которые всё же выдают событие результата.

> **Пустая схема:** Передача `{}` производит `{}` (пустой JSON-объект) в stdout. Модель вызывает `structured_output` без аргументов; путь нормализации аргументов на стороне провайдера превращает пустой вызов функции в полезную нагрузку с пустым объектом, которая проходит проверку против пустой схемы и выдаётся дословно.

## Предоставление схемы

Две эквивалентные формы:

```bash
# Встроенный JSON-литерал
nessy -p "…" --json-schema '{"type":"object", "properties":{…}}'

# Чтение из файла
nessy -p "…" --json-schema @./schemas/summary.json
```

Форма `@path` раскрывает `~`, нормализует путь и читает файл с кодировкой `utf8`.

> **Примечание о задержке:** Успешные выполнения требуют задержки завершения **не более ~500 мс**, пока фоновые агенты сбрасывают свои финальные уведомления перед выдачей результата. Завершение происходит досрочно, если нет фоновых задач в ожидании, поэтому простые запуски едва замечают это; конвейеры пакетной обработки, которые разворачивают сотни вызовов `--json-schema` против занятых агентов, должны учитывать эту верхнюю границу.

> **Примечание о безопасности:** Схемы могут содержать пользовательские регулярные выражения в ключевых словах `pattern`. Ajv компилирует их с движком регулярных выражений ECMAScript, который уязвим к катастрофическому бэктрекингу. Поскольку аргументы инструментов всегда являются объектами, ключевое слово `pattern` срабатывает только внутри строковых свойств — злонамеренная схема вида `{"type":"object","properties":{"value":{"type":"string","pattern":"(a+)+b"}}}` может подвесить CLI, когда модель предоставляет умеренно длинное подходящее значение. Запускайте `--json-schema` только со схемами из источников, которым вы доверяете.

Проверка во время разбора:

- Файл должен быть обычным файлом (без FIFO, символьных устройств или каталогов).
- Размер файла ограничен 4 MiB. Реальные JSON-схемы значительно меньше этого; файлы размером в несколько MiB почти всегда указывают на ошибку в пути.
- Схема должна быть допустимым JSON. Для ввода `@path` ошибка разбора общая («содержимое `<path>` не является допустимым JSON»), а не повторяет детали SyntaxError, поэтому оборачивающий процесс, который выводит stderr, не может прочитать префикс содержимого файла из ошибки.
- Схема должна компилироваться под строгой конфигурацией Ajv — опечатки вида `propertees` обнаруживаются, но спецификационно-допустимые паттерны (например, `required` без перечисления каждого ключа в `properties`) принимаются.
- Корень схемы должен принимать значения объектного типа. API вызова функций (Gemini, OpenAI, Anthropic) все требуют, чтобы аргументы инструментов были JSON-объектами, поэтому не-объектный корень зарегистрировал бы непригодный инструмент.

Проверка принятия корнем обходит `type`, `const`, `enum`, `anyOf`, `oneOf`, `allOf`, `not` и `if`/`then`/`else` (`best-effort` для разрешимых случаев). В сомнительных случаях он откладывает решение до Ajv во время выполнения.

:::tip
**Корневой `$ref` отклоняется** проверкой во время разбора. Если ваша схема переиспользует определение через `$ref`, оберните его в `allOf`:

```jsonc
// Отклонено:
{ "$ref": "#/$defs/MyObj", "$defs": { "MyObj": { "type": "object", "properties": { "name": { "type": "string" } } } } }

// Принято (корень принимает объекты через ветвь allOf):
{ "allOf": [{ "$ref": "#/$defs/MyObj" }], "$defs": { "MyObj": { "type": "object", "properties": { "name": { "type": "string" } } } } }
```

`$ref` внутри `anyOf` / `oneOf` / `allOf` откладывается до Ajv во время выполнения, поэтому обёрнутая форма проходит проверку принятия корнем.
:::

## Форма вывода по форматам

| `--output-format`     | Что попадает в stdout                                                                                                                                                                                                   |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `text` (по умолчанию) | `JSON.stringify(payload) + "\n"` — одна строка, проверенный объект.                                                                                                                                                     |
| `json`                | Единый JSON-**массив** объектов сообщений (полный журнал событий). Финальный элемент — сообщение `type: "result"`, которое несёт как `result` (`JSON.stringify(payload)`), так и `structured_result` (исходный объект). |
| `stream-json`         | Каждое событие на отдельной строке как JSONL. Завершающая строка `result` несёт `result` (сериализованный) и `structured_result` (исходный объект).                                                                     |

В обоих форматах JSON предпочитайте чтение `structured_result` вместо `result`, когда вам нужен объект; `result` — это сериализованная форма, предоставленная для потребителей, которые всегда ожидают строку в этом поле. Для `--output-format json` читайте последний элемент массива и извлекайте `structured_result` оттуда (например, `jq '.[-1].structured_result'`); для `stream-json` читайте финальную строку `type: "result"` в потоке.

## Ограничения

| Комбинация                                          | Поведение                                                                                                                                                                                                                                                               |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--json-schema` + `-i` / `--prompt-interactive`     | Отклонено во время разбора. Сообщение синтетического инструмента «сессия завершается сейчас» не имеет терминатора в цикле TUI.                                                                                                                                          |
| `--json-schema` + `--input-format stream-json`      | Отклонено во время разбора. Однократный терминальный контракт несовместим с долгоживущим протоколом ввода stream-json.                                                                                                                                                  |
| `--json-schema` + `--acp` / `--experimental-acp`    | Отклонено во время разбора. ACP запускает свой собственный цикл ходов, который не соблюдает терминальный контракт синтетического инструмента.                                                                                                                           |
| `--json-schema` без промпта и без переданного stdin | Отклонено во время разбора. Режиму без интерфейса нужен промпт — передайте `-p`, позиционный аргумент или передайте его через pipe.                                                                                                                                     |
| `--bare` + `--json-schema`                          | Поддерживается. Синтетический инструмент регистрируется вместе с голой тройкой (`read_file`, `edit`, `run_shell_command`).                                                                                                                                              |
| `--json-schema` внутри subagent                     | Инструмент НЕ регистрируется. Только основные / дренажные ходы выполнения верхнего уровня соблюдают терминальный контракт; subagent, вызывающий инструмент, получит «сессия завершается сейчас» и затем продолжит выполнение, потому что его цикл не имеет терминатора. |

## Повторные попытки и режимы ошибок

:::tip
**Примечание о стоимости.** Две вещи умножают расход токенов в запуске `--json-schema`, обе стоит учитывать при проектировании:

- **Схема встроена в каждый ход.** Схема поставляется как блок `parameters` объявления функции `structured_output` в каждом запросе модели, не только в первом. Большие схемы (до предела разбора 4 MiB) пропорционально увеличивают входные токены на ход для всего запуска.
- **Каждая повторная попытка проверки — полный ход модели.** Схема, которую модель пропускает неоднократно, умножается на каждую ошибку (запрос + вывод + ответ). Держите схемы достаточно ограниченными, чтобы направлять модель, и достаточно простыми, чтобы попасть с первой попытки; повышайте `--max-session-turns`, когда ожидаются повторные попытки.
  :::

Сессия завершается при первом действительном вызове. До тех пор:

- **Аргументы не проходят проверку.** `structured_output` возвращает ошибку tool-result с сообщением Ajv, модель видит его на следующем ходу и может исправить аргументы и вызвать снова.
- **Модель вызывает инструмент с побочными эффектами в том же ходу, что и `structured_output`.** Предварительное сканирование подавляет соседний вызов — он никогда не выполняется, независимо от того, пройдёт ли структурированный вызов проверку в итоге. Два пути расходятся в том, что модель увидит дальше:
  - **Проверка успешна:** запуск завершается немедленно, и модель никогда не получает ещё один ход — подавленный соседний вызов молча отбрасывается.
  - **Проверка не пройдена:** модель получает ещё один ход и видит синтезированный `tool_result` «`Skipped:`» для подавленного вызова, поэтому может переиздать этот вызов в **отдельном ходу** (который не включает `structured_output`).
- **Модель выдаёт plain text вместо вызова `structured_output`.** Код выхода `1`. Сообщение об ошибке включает количество ходов и усечённый предварительный просмотр вывода модели, чтобы вы могли увидеть, что она фактически сказала.
- **Запуск достигает `maxSessionTurns`.** Код выхода `53`. Стандартный выход «Reached max session turns» плюс специфичная для `--json-schema` подсказка, указывающая на три распространённые причины застревания запуска: модель никогда не вызывала инструмент, `structured_output` запрещён правилами разрешений или схема невыполнима.
- **Запуск прерван (SIGINT / Ctrl-C).** Код выхода `130`. Структурированный результат обычно не выдаётся, но цикл shutdown `holdback` не опрашивает сигнал прерывания, поэтому SIGINT, который приходит после захвата успешного вызова, но до того, как результат достигнет stdout, всё ещё может попасть в stdout. Считайте код выхода источником истины.

## Конфиденциальность

Аргументы, которые вы отправляете через `structured_output`, ЯВЛЯЮТСЯ структурированной полезной нагрузкой — уже выданной в stdout. Чтобы избежать сохранения той же полезной нагрузки во второй раз в поверхностях на устройстве, которые могут быть экспортированы за пределы машины, аргументы редактируются с заполнителем `{ __redacted: 'structured_output payload (see stdout result)' }` в:

- Пути телеметрии `ToolCallEvent` (экспорты OTLP, NessyLogger, поток ui-telemetry, зеркало событий UI chat-recording).
- JSONL-записи чата на диске в `~/.nessy/projects/<sanitized-cwd>/chats/<sessionId>.jsonl` (повторно подаётся в контекст модели при `--continue` / `--resume`), включая каждую повторную попытку ошибки проверки.

Метрики вызова инструментов (длительность, успех, решение) и окружающие метаданные событий сохраняются.

:::tip
**Схема отправляется провайдеру модели.** Редактирование охватывает _аргументы вызова_ только на локальных поверхностях. Сама схема передаётся в каждом запросе модели как блок `parameters` объявления функции `structured_output` — поэтому любые литеральные значения, которые вы помещаете внутрь неё (`enum`, `const`, `default`, `examples`, `description`, `$comment` и т.д.), достигают провайдера в открытом тексте так же, как текст промпта. Схемы должны описывать форму и ограничения; относитесь к ним как к публичным по отношению к провайдеру и держите секреты, записи клиентов и другие чувствительные полезные нагрузки вне тела схемы.

**Hooks видят сырые аргументы.** Описанное выше редактирование применяется только к телеметрии и записи чата. Hooks `PreToolUse`, `PostToolUse` и `PostToolUseFailure` (включая HTTP-hooks, которые могут пересылать полезные нагрузки за пределы устройства) получают неотредактированный `tool_input` для `structured_output`, поскольку контракт hook — «видеть то, что видит инструмент». Если вы используете hooks стиля аудита `catch`-all, либо отключите их для `structured_output` (фильтр по `tool_name`), либо добавьте редактирование на стороне hook перед запуском `--json-schema` против чувствительных данных.
:::

## Возобновление сессии (`--continue` / `--resume`)

`--json-schema` — это флаг на запуск, а не свойство сессии. Синтетический инструмент регистрируется, когда CLI разбирает свои аргументы, поэтому:

- Передавайте `--json-schema` при каждом `--continue` / `--resume`, к которому хотите применить терминальный контракт. Та же схема, что и в оригинальном запуске, — безопасное значение по умолчанию — замена схемы в середине сессии разрешена, но меняет контракт, к которому привязана модель.
- Если вы делаете `--continue` без `--json-schema`, возобновлённый запуск — обычная сессия без интерфейса: `structured_output` просто не существует как инструмент, и модель будет отвечать в свободной форме текста.
- Заполнитель `__redacted` в возобновлённой записи чата не влияет на возобновляемость на практике. Успешный вызов `structured_output` завершает сессию немедленно, поэтому единственные отредактированные аргументы, которые может увидеть возобновлённый запуск, — от неудачных попыток. Модель всё ещё имеет ошибку проверки Ajv каждой попытки в записанном `tool_result` и живую схему параметров (перерегистрированную из `--json-schema`), чего достаточно для повторной попытки.

## Управление разрешениями

`structured_output` намеренно обходит `allowlist` `--core-tools`: инструмент существует только когда установлен `--json-schema`, поэтому его исключение оставило бы запуск без терминального контракта.

Явные правила `permissions.deny` и настройки `--exclude-tools` ДЕЙСТВИТЕЛЬНО вступают в силу — оба используют один и тот же механизм запрета и оба предотвращают регистрацию `structured_output`, поэтому модель никогда не видит объявления инструмента. Типичный результат — модель отвечает в `plain text` (выход 1). Если модель зацикливается через другие инструменты без выдачи текста, она в конечном итоге достигнет `maxSessionTurns` (выход 53), и подсказка `--json-schema` в сообщении об ошибке подскажет, куда смотреть.

:::tip
**Предостережение `--bare`.** Режим `bare` игнорирует большинство вводов, полученных из настроек, включая `permissions.deny` и `tools.exclude` на уровне настроек. Синтетический инструмент остаётся зарегистрированным, поэтому запрет только настройками `structured_output` молча станет `no-op` под `--bare`. Флаг `--exclude-tools structured_output` на уровне аргументов всё ещё применяется в режиме `bare` — используйте флаг, а не настройки, если нужно заблокировать `bare`-запуск.
:::

## Конфликт с инструментами MCP

Если MCP-сервер регистрирует инструмент буквально с именем `structured_output`, проверка столкновений в реестре инструментов переименовывает инструмент MCP в `mcp__<server-name>__structured_output`, чтобы синтетический инструмент сохранил голое имя. Предоставленная пользователем схема всегда та, которую видит модель.

## Пример: блокировка многошагового запуска на структурированном выводе

```bash
RESULT=$(nessy --prompt "Audit this diff and rate its risk." \
  --json-schema @./schemas/audit.json) || exit 1

risk=$(jq -r '.risk_level' <<<"$RESULT")
if [ "$risk" = "high" ]; then
  echo "High-risk diff; pausing pipeline." >&2
  exit 2
fi
```
