# Провайдеры моделей

Nessy CLI позволяет настроить несколько провайдеров моделей через параметр `modelProviders` в файле `settings.json`. Это позволяет переключаться между различными AI-моделями и провайдерами с помощью команды `/model`.

## Обзор

Используйте `modelProviders` для объявления курируемых списков моделей по типам аутентификации, которые можно переключать через селектор `/model`. Ключи должны быть валидными типами аутентификации (`openai`, `anthropic`, `gemini` и т.д.). Каждая запись требует `id` и **должна включать `envKey`**, с опциональными `name`, `description`, `baseUrl` и `generationConfig`. Учётные данные никогда не сохраняются в настройках; среда выполнения считывает их из `process.env[envKey]`. Модели DP Auth остаются жёстко закодированными и не могут быть переопределены.

:::note
Только команда `/model` предоставляет доступ к нестандартным типам аутентификации. Anthropic, Gemini и другие должны быть определены через `modelProviders`. Команда `/auth` отображает DP Auth и API Key как встроенные опции аутентификации.
:::

:::note
**Уникальность модели:** Модели в рамках одного `authType` уникально идентифицируются комбинацией `id` + `baseUrl`. Это означает, что вы можете определить один и тот же ID модели (например, `"gpt-4o"`) несколько раз в рамках одного `authType`, если каждая запись имеет разный `baseUrl` — например, один указывает напрямую на OpenAI, а другой на proxy endpoint. Если две записи имеют одинаковый `id` и одинаковый `baseUrl` (или обе опускают `baseUrl`), первое вхождение побеждает, а последующие дубликаты пропускаются с предупреждением.
:::

## Примеры конфигурации по типам аутентификации

Ниже приведены подробные примеры конфигурации для различных типов аутентификации, показывающие доступные параметры и их комбинации.

### Поддерживаемые типы аутентификации

Ключи объекта `modelProviders` должны быть валидными значениями `authType`. В настоящее время поддерживаются следующие типы аутентификации:

| Тип аутентификации | Описание                                                                                  |
| ------------------ | ----------------------------------------------------------------------------------------- |
| `openai`           | OpenAI-совместимые API (OpenAI, Azure OpenAI, локальные серверы вывода вроде vLLM/Ollama) |
| `dp-auth`          | DP Auth (жёстко закодирован, не может быть переопределён в `modelProviders`)              |

:::warning
Если используется невалидный ключ типа аутентификации (например, опечатка вроде `"openai-custom"`), конфигурация будет **молча пропущена**, и модели не появятся в селекторе `/model`. Всегда используйте один из поддерживаемых типов аутентификации, перечисленных выше.
:::

### SDK, используемые для API-запросов

Nessy CLI использует следующие официальные SDK для отправки запросов каждому провайдеру:

| Тип аутентификации | Пакет SDK                                                                         |
| ------------------ | --------------------------------------------------------------------------------- |
| `openai`           | [`openai`](https://www.npmjs.com/package/openai) — официальный OpenAI Node.js SDK |
| `dp-auth`          | [`openai`](https://www.npmjs.com/package/openai) с кастомным провайдером          |

Это означает, что `baseUrl`, который вы настраиваете, должен быть совместим с ожидаемым форматом API соответствующего SDK. Например, при использовании типа аутентификации `openai` endpoint должен принимать запросы в формате OpenAI API.

### OpenAI-совместимые провайдеры (`openai`)

Этот тип аутентификации поддерживает не только официальный API OpenAI, но и любой OpenAI-совместимый endpoint, включая агрегированные провайдеры моделей вроде OpenRouter.

            "temperature": 0.2,
            "top_p": 0.8,

            "presence_penalty": 0.1,

      {
        "id": "gpt-4o-mini",
        "name": "GPT-4o Mini",

### Локальные самодостаточные модели (через OpenAI-совместимый API)

Большинство локальных серверов вывода (vLLM, Ollama, LM Studio и т.д.) предоставляют OpenAI-совместимый API endpoint. Настройте их, используя тип аутентификации `openai` с локальным `baseUrl`:

```json
{
  "env": {
    "OLLAMA_API_KEY": "ollama",
    "VLLM_API_KEY": "not-needed",
    "LMSTUDIO_API_KEY": "lm-studio"
  },
  "modelProviders": {
    "openai": [
      {
        "id": "qwen2.5-7b",
        "name": "Nessy2.5 7B (Ollama)",
        "envKey": "OLLAMA_API_KEY",
        "baseUrl": "http://localhost:11434/v1",
        "generationConfig": {
          "timeout": 300000,
          "maxRetries": 1,
          "contextWindowSize": 32768,
          "samplingParams": {
            "temperature": 0.7,
            "top_p": 0.9,
            "max_tokens": 4096
          }
        }
      },
      {
        "id": "llama-3.1-8b",
        "name": "Llama 3.1 8B (vLLM)",
        "envKey": "VLLM_API_KEY",
        "baseUrl": "http://localhost:8000/v1",
        "generationConfig": {
          "timeout": 120000,
          "maxRetries": 2,
          "contextWindowSize": 128000,
          "samplingParams": {
            "temperature": 0.6,
            "max_tokens": 8192
          }
        }
      },
      {
        "id": "local-model",
        "name": "Local Model (LM Studio)",
        "envKey": "LMSTUDIO_API_KEY",
        "baseUrl": "http://localhost:1234/v1",
        "generationConfig": {
          "timeout": 60000,
          "samplingParams": {
            "temperature": 0.5
          }
        }
      }
    ]
  }
}
```

Для локальных серверов, которые не требуют аутентификации, можно использовать любое placeholder-значение для API ключа:

```bash
# Для Ollama (аутентификация не требуется)
export OLLAMA_API_KEY="ollama"

# Для vLLM (если аутентификация не настроена)
export VLLM_API_KEY="not-needed"
```

:::note
Параметр `extra_body` **поддерживается только для OpenAI-совместимых провайдеров** (`openai`, `dp-auth`). Он игнорируется для провайдеров Anthropic и Gemini.
:::

:::note
**Об `envKey`**: Поле `envKey` указывает **имя переменной окружения**, а не фактическое значение API ключа. Для работы конфигурации необходимо убедиться, что соответствующая переменная окружения установлена с вашим реальным API ключом. Есть два способа сделать это:

- **Вариант 1: Использование файла `.env`** (рекомендуется для безопасности):
  ```bash
  # ~/.nessy/.env (или корень проекта)
  OPENAI_API_KEY=sk-ваш-фактический-ключ-здесь
  ```
  Обязательно добавьте `.env` в `.gitignore`, чтобы предотвратить случайное коммитирование секретов.
- **Вариант 2: Использование поля `env` в `settings.json`** (как показано в примерах выше):
  ```json
  {
    "env": {
      "OPENAI_API_KEY": "sk-ваш-фактический-ключ-здесь"
    }
  }
  ```

Каждый пример провайдера включает поле `env`, чтобы проиллюстрировать, как следует настраивать API ключ.
:::

## Уровни разрешения и атомарность

Эффективные значения auth/model/учётных данных выбираются для каждого поля с использованием следующего приоритета (первое присутствующее побеждает). Вы можете комбинировать `--auth-type` с `--model`, чтобы указать непосредственно на запись провайдера; эти флаги CLI выполняются до других уровней.

| Уровень (сверху вниз)       | authType                     | model                                            | apiKey                                            | baseUrl                                            | apiKeyEnvKey           | proxy                             |
| --------------------------- | ---------------------------- | ------------------------------------------------ | ------------------------------------------------- | -------------------------------------------------- | ---------------------- | --------------------------------- |
| Программные переопределения | `/auth`                      | входные данные `/auth`                           | входные данные `/auth`                            | входные данные `/auth`                             | —                      | —                                 |
| Выбор провайдера модели     | —                            | `modelProvider.id`                               | `env[modelProvider.envKey]`                       | `modelProvider.baseUrl`                            | `modelProvider.envKey` | —                                 |
| Аргументы CLI               | `--auth-type`                | `--model`                                        | `--openaiApiKey` (или специфичные для провайдера) | `--openaiBaseUrl` (или специфичные для провайдера) | —                      | —                                 |
| Переменные окружения        | —                            | Специфичный для провайдера маппинг               | Специфичный для провайдера маппинг                | Специфичный для провайдера маппинг                 | —                      | —                                 |
| Настройки (`settings.json`) | `security.auth.selectedType` | `model.name`                                     | `security.auth.apiKey`                            | `security.auth.baseUrl`                            | —                      | —                                 |
| По умолчанию / вычисляемый  | Возврат к `AuthType.DP_AUTH` | Встроенный default (OpenAI ⇒ `qwen3-coder-plus`) | —                                                 | —                                                  | —                      | `Config.getProxy()` если настроен |

\*При наличии флаги CLI auth переопределяют настройки. В противном случае `security.auth.selectedType` или неявный default определяют тип аутентификации. DP Auth и OpenAI — единственные типы аутентификации, доступные без дополнительной конфигурации.

:::warning
**Устаревание `security.auth.apiKey` и `security.auth.baseUrl`:** Прямая конфигурация учётных данных API через `security.auth.apiKey` и `security.auth.baseUrl` в `settings.json` устарела. Эти настройки использовались в исторических версиях для учётных данных, введённых через UI, но поток ввода учётных данных был удалён в версии 0.10.1. Эти поля будут полностью удалены в будущих версиях. **Настоятельно рекомендуется мигрировать на `modelProviders`** для всей конфигурации моделей и учётных данных. Используйте `envKey` в `modelProviders` для ссылки на переменные окружения для безопасного управления учётными данными вместо хардкодинга учётных данных в файлах настроек.
:::

## Слои конфигурации Generation Config: Непроницаемый слой провайдера

Разрешение конфигурации следует строгой модели слоёв с одним важным правилом: **слой modelProvider непроницаем**.

### Как это работает

1. **Когда модель modelProvider ВЫБРАНА** (например, через команду `/model`, выбирающую модель, настроенную провайдером):
   - Весь `generationConfig` от провайдера применяется **атомарно**
   - **Слой провайдера полностью непроницаем** — нижние уровни (CLI, env, настройки) не участвуют в разрешении generationConfig вообще
   - Все поля, определённые в `modelProviders[].generationConfig`, используют значения провайдера
   - Все поля, **не определённые** провайдером, устанавливаются в `undefined` (не наследуются из настроек)
   - Это гарантирует, что конфигурации провайдеров действуют как полный, самодостаточный «запечатанный пакет»

2. **Когда модель modelProvider НЕ выбрана** (например, использование `--model` с сырым ID модели, или использование CLI/env/настроек напрямую):
   - Разрешение переходит к нижним уровням
   - Поля заполняются из CLI → env → настройки → default
   - Это создаёт **Runtime Model** (см. следующий раздел)

### Приоритет полей для `generationConfig`

| Приоритет | Источник                                      | Поведение                                                                                         |
| --------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 1         | Программные переопределения                   | Runtime `/model`, изменения `/auth`                                                               |
| 2         | `modelProviders[authType][].generationConfig` | **Непроницаемый слой** — полностью заменяет все поля generationConfig; нижние уровни не участвуют |
| 3         | `settings.model.generationConfig`             | Используется только для **Runtime Models** (когда модель провайдера не выбрана)                   |
| 4         | Default контент-генератора                    | Специфичные для провайдера default (например, OpenAI против Gemini) — только для Runtime Models   |

### Атомарная обработка полей

Следующие поля рассматриваются как атомарные объекты — значения провайдера полностью заменяют весь объект, слияния не происходит:

- `samplingParams` — температура, top_p, max_tokens и т.д.
- `customHeaders` — кастомные HTTP заголовки
- `extra_body` — дополнительные параметры тела запроса

### Пример

```json
// Пользовательские настройки (~/.nessy/settings.json)
{
  "model": {
    "generationConfig": {
      "timeout": 30000,
      "samplingParams": { "temperature": 0.5, "max_tokens": 1000 }
    }
  }
}

// Конфигурация modelProviders
{
  "modelProviders": {
    "openai": [{
      "id": "gpt-4o",
      "envKey": "OPENAI_API_KEY",
      "generationConfig": {
        "timeout": 60000,
        "samplingParams": { "temperature": 0.2 }
      }
    }]
  }
}
```

При выборе `gpt-4o` из modelProviders:

- `timeout` = 60000 (от провайдера, переопределяет настройки)
- `samplingParams.temperature` = 0.2 (от провайдера, полностью заменяет объект настроек)
- `samplingParams.max_tokens` = **undefined** (не определено в провайдере, и слой провайдера не наследует из настроек — поля явно устанавливаются в undefined, если не предоставлены)

При использовании сырой модели через `--model gpt-4` (не из modelProviders, создаёт Runtime Model):

- `timeout` = 30000 (из настроек)
- `samplingParams.temperature` = 0.5 (из настроек)
- `samplingParams.max_tokens` = 1000 (из настроек)

Стратегия слияния для самого `modelProviders` — REPLACE: весь `modelProviders` из настроек проекта переопределяет соответствующий раздел в настройках пользователя, а не сливается с ним.

## Конфигурация reasoning / мышления

Опциональное поле `reasoning` в `generationConfig` контролирует, насколько агрессивно модель размышляет перед ответом. Конвертеры Anthropic и Gemini всегда соблюдают его. OpenAI-совместимый конвейер соблюдает его, **если только** не установлен `generationConfig.samplingParams` — см. предостережение "Взаимодействие с `samplingParams`" ниже.

```jsonc
{
  "modelProviders": {
    "openai": [
      {
        "id": "deepseek-v4-pro",
        "name": "DeepSeek V4 Pro",
        "baseUrl": "https://api.deepseek.com/v1",
        "envKey": "DEEPSEEK_API_KEY",
        "generationConfig": {
          // Четырёхуровневая шкала:
          //   'low'    | 'medium' — сервером отображается на 'high' в DeepSeek
          //   'high'   — интенсивность рассуждений по умолчанию
          //   'max'    — экстра-сильный уровень специфичный для DeepSeek
          // Или установите `false`, чтобы полностью отключить reasoning.
          "reasoning": { "effort": "max" },
        },
      },
    ],
  },
}
```

### Поведение для каждого провайдера

| Протокол / провайдер                         | Форма передачи                                                           | Примечания                                                                                                                                                                                                                                                                                                                                                                                           |
| -------------------------------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OpenAI / DeepSeek** (`api.deepseek.com`)   | Плоский параметр тела `reasoning_effort: <effort>`                       | Когда `reasoning.effort` установлен в форме вложенной конфигурации, он переписывается в плоский `reasoning_effort`, и `'low'`/`'medium'` нормализуются в `'high'`, `'xhigh'` в `'max'` — отражая серверную обратную совместимость DeepSeek. Переопределения верхнего уровня `samplingParams.reasoning_effort` или `extra_body.reasoning_effort` пропускают эту нормализацию и отправляются как есть. |
| **OpenAI** (другие совместимые серверы)      | `reasoning: { effort, ... }` передаётся как есть                         | Устанавливается через `samplingParams` (например, `samplingParams.reasoning_effort` для GPT-5/o-series), когда провайдер ожидает другую форму.                                                                                                                                                                                                                                                       |
| **Anthropic** (реальный `api.anthropic.com`) | `output_config: { effort }` плюс хедер `effort-2025-11-24...` [обрезано] |

### `reasoning: false`

Установка `"reasoning": false` в `generationConfig` полностью отключает рассуждения модели. Это полезно для:

- Моделей без поддержки reasoning
- Сценариев, где важна скорость, а не глубина ответа
- Тестирования различий между режимами с reasoning и без

### Взаимодействие с `samplingParams` (только OpenAI-совместимые)

Для OpenAI-совместимых провайдеров существует важное взаимодействие между `reasoning` и `samplingParams`:

- **Если установлен только `reasoning`**: Конвертер применяет нормализацию (например, `'low'` → `'high'` для DeepSeek)
- **Если установлен `samplingParams`**: Поля `reasoning` игнорируются, и `samplingParams.reasoning_effort` (если присутствует) передаётся как есть без нормализации

Это означает, что для получения нормализованного поведения DeepSeek используйте только `reasoning.effort`, а не `samplingParams.reasoning_effort`.

### `budget_tokens`

Параметр `budget_tokens` контролирует максимальное количество токенов, которые модель может использовать для рассуждений. Если не указан, используется значение по умолчанию провайдера.

```json
{
  "generationConfig": {
    "reasoning": {
      "effort": "high",
      "budget_tokens": 4096
    }
  }
}
```

## Модели провайдера против Runtime моделей

Nessy CLI различает два типа конфигураций моделей:

### Модель провайдера

- Определена в конфигурации `modelProviders`
- Имеет полный, атомарный пакет конфигурации
- При выборе её конфигурация применяется как непроницаемый слой
- Отображается в списке команды `/model` с полными метаданными (name, description, capabilities)
- Рекомендуется для multi-model рабочих процессов и командной согласованности

### Runtime модель

- Создаётся динамически при использовании сырых ID моделей через CLI (`--model`), переменные окружения или настройки
- Не определена в `modelProviders`
- Конфигурация строится путём «проецирования» через уровни разрешения (CLI → env → настройки → default)
- Автоматически захватывается как **RuntimeModelSnapshot**, когда обнаружена полная конфигурация
- Позволяет повторное использование без повторного ввода учётных данных

### Жизненный цикл RuntimeModelSnapshot

Когда вы настраиваете модель без использования `modelProviders`, Nessy CLI автоматически создаёт RuntimeModelSnapshot для сохранения вашей конфигурации:

```bash
# Это создаёт RuntimeModelSnapshot с ID: $runtime|openai|my-custom-model
nessy --auth-type openai --model my-custom-model --openaiApiKey $KEY --openaiBaseUrl https://api.example.com/v1
```

Snapshot:

- Захватывает ID модели, API ключ, base URL и generation config
- Сохраняется между сессиями (хранится в памяти во время runtime)
- Отображается в списке команды `/model` как runtime опция
- Может быть переключён через `/model $runtime|openai|my-custom-model`

### Ключевые различия

| Аспект                   | Модель провайдера                 | Runtime модель                                     |
| ------------------------ | --------------------------------- | -------------------------------------------------- |
| Источник конфигурации    | `modelProviders` в настройках     | Уровни CLI, env, настроек                          |
| Атомарность конфигурации | Полный, непроницаемый пакет       | Слоёный, каждое поле разрешается независимо        |
| Повторное использование  | Всегда доступно в списке `/model` | Захватывается как snapshot, появляется если полный |
| Командный доступ         | Да (через коммитимые настройки)   | Нет (локально для пользователя)                    |
| Хранение учётных данных  | Ссылка через `envKey` только      | Может захватывать фактический ключ в snapshot      |

### Когда использовать каждое

- **Используйте модели провайдера** когда: у вас есть стандартные модели, используемые командой, нужны согласованные конфигурации или хотите предотвратить случайные переопределения
- **Используйте Runtime модели** когда: быстро тестируете новую модель, используете временные учётные данные или работаете с ad-hoc endpoints

## Постоянство выбора и рекомендации

:::important
Определяйте `modelProviders` в пользовательской области `~/.nessy/settings.json` whenever possible и избегайте сохранения переопределений учётных данных в любой области. Хранение каталога провайдеров в пользовательских настройках предотвращает конфликты слияния/переопределения между областями проекта и пользователя и гарантирует, что обновления `/auth` и `/model` всегда записываются в согласованную область.
:::

- `/model` и `/auth` сохраняют `model.name` (где применимо) и `security.auth.selectedType` в ближайшую записываемую область, которая уже определяет `modelProviders`; в противном случае возвращаются к пользовательской области. Это держит workspace/пользовательские файлы синхронизированными с активным каталогом провайдеров.
- Без `modelProviders` резолвер смешивает уровни CLI/env/настроек, создавая Runtime модели. Это нормально для setup с одним провайдером, но неудобно при частом переключении. Определяйте каталоги провайдеров, когда multi-model рабочие процессы обычны, чтобы переключения оставались атомарными, с указанием источника и отлаживаемыми.
