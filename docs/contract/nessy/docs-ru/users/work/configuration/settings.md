# Конфигурация Nessy CLI

:::tip
**Аутентификация:** Информация об аутентификации (Nessy DP Authentification) задокументирована в **[Аутентификация](../configuration/auth.md)**.
:::

:::note
**Примечание о новом формате конфигурации:** Формат файла `settings.json` был обновлён до новой, более организованной структуры. Старый формат будет автоматически мигрирован.
Nessy CLI предлагает несколько способов настройки своего поведения, включая переменные окружения, аргументы командной строки и файлы настроек. В этом документе описаны различные методы конфигурации и доступные настройки.
:::

## Уровни конфигурации

Конфигурация применяется в следующем порядке приоритета (значения с меньшими номерами переопределяются значениями с большими номерами):

| Уровень | Источник конфигурации          | Описание                                                                                         |
| ------- | ------------------------------ | ------------------------------------------------------------------------------------------------ |
| 1       | Значения по умолчанию          | Жёстко закодированные значения по умолчанию в приложении                                         |
| 2       | Системный файл по умолчанию    | Общесистемные настройки по умолчанию, которые могут быть переопределены другими файлами настроек |
| 3       | Пользовательский файл настроек | Глобальные настройки для текущего пользователя                                                   |
| 4       | Проектный файл настроек        | Настройки для конкретного проекта                                                                |
| 5       | Системный файл настроек        | Общесистемные настройки, переопределяющие все остальные файлы настроек                           |
| 6       | Переменные окружения           | Общесистемные или сеансовые переменные, потенциально загружаемые из файлов `.env`                |
| 7       | Аргументы командной строки     | Значения, передаваемые при запуске CLI                                                           |

## Файлы настроек

Nessy CLI использует JSON-файлы настроек для постоянной конфигурации. Существует четыре расположения для этих файлов:

| Тип файла                      | Расположение                                                                                                                                                                                                                                                                      | Область применения                                                                                                                                                                                                                                            |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Системный файл по умолчанию    | Linux: `/etc/nessy-cli/system-defaults.json`<br/>Windows: `C:\ProgramData\nessy-cli\system-defaults.json`<br/>macOS: `/Library/Application Support/NessyCLI/system-defaults.json` <br/>Путь можно переопределить с помощью переменной окружения `NESSY_CLI_SYSTEM_DEFAULTS_PATH`. | Обеспечивает базовый слой общесистемных настроек по умолчанию. Эти настройки имеют наименьший приоритет и предназначены для переопределения пользовательскими, проектными или системными настройками.                                                         |
| Пользовательский файл настроек | `~/.nessy/settings.json` (где `~` — ваш домашний каталог).                                                                                                                                                                                                                        | Применяется ко всем сеансам Nessy CLI для текущего пользователя.                                                                                                                                                                                              |
| Проектный файл настроек        | `.nessy/settings.json` в корневом каталоге вашего проекта.                                                                                                                                                                                                                        | Применяется только при запуске Nessy CLI из этого конкретного проекта. Проектные настройки переопределяют пользовательские настройки.                                                                                                                         |
| Системный файл настроек        | Linux: `/etc/nessy-cli/settings.json` <br/>Windows: `C:\ProgramData\nessy-cli\settings.json` <br/>macOS: `/Library/Application Support/NessyCLI/settings.json`<br/>Путь можно переопределить с помощью переменной окружения `NESSY_CLI_SYSTEM_SETTINGS_PATH`.                     | Применяется ко всем сеансам Nessy CLI в системе для всех пользователей. Системные настройки переопределяют пользовательские и проектные настройки. Может быть полезен системным администраторам в организациях для контроля настроек Nessy CLI пользователей. |

:::note
**Примечание о переменных окружения в настройках:** Строковые значения в ваших файлах `settings.json` могут ссылаться на переменные окружения, используя синтаксис `$VAR_NAME` или `${VAR_NAME}`. Эти переменные будут автоматически подставлены при загрузке настроек. Например, если у вас есть переменная окружения `MY_API_TOKEN`, вы можете использовать её в `settings.json` следующим образом: `"apiKey": "$MY_API_TOKEN"`.
:::

### Каталог `.nessy` в вашем проекте

В дополнение к проектному файлу настроек, каталог `.nessy` проекта может содержать другие файлы, связанные с работой Nessy CLI, такие как:

- [Пользовательские профили песочницы](../features/sandbox.md) (например, `.nessy/sandbox-macos-custom.sb`, `.nessy/sandbox.Dockerfile`).
- [Agent Skills](../features/skills.md) в каталоге `.nessy/skills/` (каждый Skill — это каталог, содержащий `SKILL.md`).

### Миграция конфигурации

Nessy CLI автоматически мигрирует устаревшие настройки конфигурации в новый формат. Старые файлы настроек сохраняются в резервную копию перед миграцией. Следующие настройки были переименованы из негативных (`disable*`) в позитивные (`enable*`):

| Старая настройка                         | Новая настройка                             | Примечания                  |
| ---------------------------------------- | ------------------------------------------- | --------------------------- |
| `disableAutoUpdate` + `disableUpdateNag` | `general.enableAutoUpdate`                  | Объединено в одну настройку |
| `disableLoadingPhrases`                  | `ui.accessibility.enableLoadingPhrases`     |                             |
| `disableFuzzySearch`                     | `context.fileFiltering.enableFuzzySearch`   |                             |
| `disableCacheControl`                    | `model.generationConfig.enableCacheControl` |                             |

:::note
**Инверсия булевых значений:** При миграции булевы значения инвертируются (например, `disableAutoUpdate: true` становится `enableAutoUpdate: false`).
:::

#### Политика объединения `disableAutoUpdate` и `disableUpdateNag`

Когда обе устаревшие настройки присутствуют с разными значениями, миграция следует этой политике: если **либо** `disableAutoUpdate`, **либо** `disableUpdateNag` имеет значение `true`, то `enableAutoUpdate` становится `false`:

| `disableAutoUpdate` | `disableUpdateNag` | Мигрированное `enableAutoUpdate` |
| ------------------- | ------------------ | -------------------------------- |
| `false`             | `false`            | `true`                           |
| `false`             | `true`             | `false`                          |
| `true`              | `false`            | `false`                          |
| `true`              | `true`             | `false`                          |

**max_tokens (адаптивные выходные токены):**

Когда `samplingParams.max_tokens` не установлен, Nessy CLI использует стратегию адаптивных выходных токенов для оптимизации использования GPU:

1. Запросы начинаются с лимитом **8K** выходных токенов
2. Если ответ обрезан (модель достигает лимита), Nessy CLI автоматически повторяет попытку с **64K** токенами
3. Частичный вывод отбрасывается и заменяется полным ответом из повторной попытки

Это прозрачно для пользователей — вы можете кратковременно увидеть индикатор повторной попытки, если происходит эскалация. Поскольку 99% ответов меньше 5K токенов, повторная попытка происходит редко (\<1% запросов).

Чтобы переопределить это поведение, установите `samplingParams.max_tokens` в ваших настройках или используйте переменную окружения `NESSY_CLI_MAX_OUTPUT_TOKENS`.

**contextWindowSize:**

Переопределяет размер окна контекста по умолчанию для выбранной модели. Nessy CLI определяет окно контекста, используя встроенные значения по умолчанию на основе сопоставления имён моделей, с постоянным значением fallback. Используйте эту настройку, когда эффективный лимит контекста провайдера отличается от значения по умолчанию Nessy CLI. Это значение определяет предполагаемую максимальную ёмкость контекста модели, а не лимит токенов на запрос.

Когда выбранная модель определена в `modelProviders`, установите `contextWindowSize` в `generationConfig` этой записи провайдера вместо `model.generationConfig` верхнего уровня. Записи моделей провайдера опечатаны, поэтому настройки генерации верхнего уровня не заполняют отсутствующие поля провайдера.

**modalities:**

Переопределяет автоматически определённые модальности ввода для выбранной модели. Nessy CLI автоматически определяет поддерживаемые модальности (изображение, PDF, аудио, видео) на основе сопоставления имён моделей. Используйте эту настройку, когда автоматическое определение неверно — например, чтобы включить `pdf` для модели, которая поддерживает это, но не распознана. Формат: `{ "image": true, "pdf": true, "audio": true, "video": true }`. Опустите ключ или установите его в `false` для неподдерживаемых типов.

**customHeaders:**

Позволяет добавлять пользовательские HTTP-заголовки ко всем API-запросам. Это полезно для трассировки запросов, мониторинга, маршрутизации API-шлюза или когда разным моделям требуются разные заголовки. Для моделей провайдеров определите `customHeaders` в `modelProviders[].generationConfig.customHeaders`. Для моделей времени выполнения без соответствующей записи провайдера определите в `model.generationConfig.customHeaders`. Слияния между двумя уровнями не происходит.

Поле `extra_body` позволяет добавлять пользовательские параметры в тело запроса, отправляемого API. Это полезно для опций, специфичных для провайдера, которые не покрыты стандартными полями конфигурации. **Примечание:** Это поле поддерживается только для OpenAI-совместимых провайдеров (`openai`, `dp-auth`). Оно игнорируется для провайдеров Anthropic и Gemini. Для моделей провайдеров определите `extra_body` в `modelProviders[].generationConfig.extra_body`. Для моделей времени выполнения без соответствующей записи провайдера определите в `model.generationConfig.extra_body`.

**Примеры model.openAILoggingDir:**

- `"~/nessy-logs"` — Логи в каталог `~/nessy-logs`
- `"./custom-logs"` — Логи в `./custom-logs` относительно текущего каталога
- `"/tmp/openai-logs"` — Логи в абсолютный путь `/tmp/openai-logs`

#### Устранение неполадок производительности поиска файлов

Если вы испытываете проблемы с производительностью поиска файлов (например, с автодополнением `@`), особенно в проектах с очень большим количеством файлов, вот несколько вещей, которые можно попробовать в порядке рекомендации:

1. **Использовать `.nessyignore`:** Создайте файл `.nessyignore` в корне вашего проекта для исключения каталогов, содержащих большое количество файлов, которые не нужно использовать (например, артефакты сборки, логи, `node_modules`). Уменьшение общего количества файлов, сканируемых поиском, — самый эффективный способ улучшить производительность.
2. **Отключить нечёткий поиск:** Если игнорирования файлов недостаточно, можно отключить нечёткий поиск, установив `enableFuzzySearch` в `false` в файле `settings.json`. Это использует более простой алгоритм сопоставления без нечёткого поиска, который может быть быстрее.
3. **Отключить рекурсивный поиск файлов:** В крайнем случае можно полностью отключить рекурсивный поиск файлов, установив `enableRecursiveFileSearch` в `false`. Это будет самым быстрым вариантом, так как избегает рекурсивного обхода проекта. Однако это означает, что вам нужно будет вводить полный путь к файлам при использовании автодополнения `@`.

#### permissions

Система разрешений предоставляет детальный контроль над тем, какие инструменты могут выполняться, какие требуют подтверждения, а какие заблокированы.

**Приоритет решений (наивысший первый): `deny` > `ask` > `allow` > _(по умолчанию/интерактивный режим)_**

Первое совпадающее правило побеждает. Правила используют формат `"ToolName"` или `"ToolName(specifier)"`.

**Псевдонимы инструментов (работают в правилах):**

| Псевдоним             | Канонический инструмент | Примечания                |
| --------------------- | ----------------------- | ------------------------- |
| `Bash`, `Shell`       | `run_shell_command`     |                           |
| `Read`, `ReadFile`    | `read_file`             | Мета-категория — см. ниже |
| `Edit`, `EditFile`    | `edit`                  | Мета-категория — см. ниже |
| `Write`, `WriteFile`  | `write_file`            |                           |
| `Grep`, `SearchFiles` | `grep_search`           |                           |
| `Glob`, `FindFiles`   | `glob`                  |                           |
| `ListFiles`           | `list_directory`        |                           |
| `WebFetch`            | `web_fetch`             |                           |

Контролирует разрешения для инструментов на детальном уровне. Позволяет указывать, какие инструменты могут использоваться без подтверждения, какие требуют подтверждения, а какие запрещены.

| Настройка           | Тип              | Описание                                                        | Значение по умолчанию |
| ------------------- | ---------------- | --------------------------------------------------------------- | --------------------- |
| `permissions.allow` | array of strings | Список правил разрешений, которые автоматически подтверждаются. | `[]`                  |
| `permissions.ask`   | array of strings | Список правил разрешений, которые требуют подтверждения.        | `[]`                  |
| `permissions.deny`  | array of strings | Список правил разрешений, которые запрещены.                    | `[]`                  |

**Синтаксис правил:**

| Правило                       | Значение                                                          |
| ----------------------------- | ----------------------------------------------------------------- |
| `"Bash"`                      | Все команды оболочки                                              |
| `"Bash(git *)"`               | Команды оболочки, начинающиеся с `git` (граница слова: НЕ `gitk`) |
| `"Bash(git push *)"`          | Команды оболочки, такие как `git push origin main`                |
| `"Bash(npm run *)"`           | Любые скрипты `npm run`                                           |
| `"Read"`                      | Все операции чтения файлов (read, grep, glob, list)               |
| `"Read(./secrets/**)"`        | Чтение любого файла под `./secrets/` рекурсивно                   |
| `"Edit(/src/**/*.ts)"`        | Редактирование TypeScript файлов под проектом `/src/`             |
| `"WebFetch(api.example.com)"` | Получение из `api.example.com` и всех его поддоменов              |
| `"mcp__puppeteer"`            | Все инструменты из MCP сервера puppeteer                          |

**Префиксы шаблонов путей:**

| Префикс | Значение                                  | Пример              |
| ------- | ----------------------------------------- | ------------------- |
| `//`    | Абсолютный путь от корня файловой системы | `//etc/passwd`      |
| `~/`    | Относительно домашнего каталога           | `~/Documents/*.pdf` |
| `/`     | Относительно корня проекта                | `/src/**/*.ts`      |
| `./`    | Относительно текущего рабочего каталога   | `./secrets/**`      |
| (none)  | То же, что `./`                           | `secrets/**`        |

**Предотвращение обхода команд оболочки:**

Разрешения для `Read`, `Edit` и `WebFetch` также применяются, когда агент запускает эквивалентные команды оболочки. Например, если `Read(./.env)` находится в `deny`, агент не может обойти это через `cat .env` в команде оболочки. Поддерживаемые команды оболочки включают `cat`, `grep`, `curl`, `wget`, `cp`, `mv`, `rm`, `chmod` и многие другие. Неизвестные/безопасные команды (например, `git`) не затрагиваются правилами файлов/сети.

**Миграция из устаревших настроек:**

| Устаревшая настройка | Эквивалентное правило `permissions` | Примечания                                                                           |
| -------------------- | ----------------------------------- | ------------------------------------------------------------------------------------ |
| `tools.allowed`      | `permissions.allow`                 | Автоматически мигрируется при первой загрузке                                        |
| `tools.exclude`      | `permissions.deny`                  | Автоматически мигрируется при первой загрузке                                        |
| `tools.core`         | `permissions.allow` (allowlist)     | Автоматически мигрируется; неперечисленные инструменты отключаются на уровне реестра |

**Пример конфигурации:**

```json
{
  "permissions": {
    "allow": ["Bash(git *)", "Bash(npm run *)", "Read(//Users/alice/code/**)"],
    "ask": ["Bash(git push *)", "Edit"],
    "deny": ["Bash(rm -rf *)", "Read(.env)", "WebFetch(malicious.com)"]
  }
}
```

:::tip
Используйте `/permissions` в интерактивном CLI для просмотра, добавления и удаления правил без прямого редактирования `settings.json`.
:::

#### slashCommands

Контролирует, какие slash-команды доступны в CLI. Полезно для ограничения поверхности команд в многопользовательских или корпоративных развёртываниях.

| Настройка                | Тип              | Описание                                                                                                                                                                                                                                                                                                                                                                                       | Значение по умолчанию |
| ------------------------ | ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| `slashCommands.disabled` | array of strings | Имена slash-команд для скрытия и запрета выполнения. Сопоставляется без учёта регистра с окончательным именем команды (для команд расширений это дизамбигуированная форма, например, `myext.deploy`). **Объединяется как объединение across scopes**, поэтому настройки рабочего пространства могут добавлять, но не удалять записи, определённые в пользовательских или системных настройках. | `undefined`           |

Тот же самый список запрета может быть предоставлен через флаг CLI `--disabled-slash-commands` (разделённый запятыми или повторённый) и переменную окружения `NESSY_DISABLED_SLASH_COMMANDS`; значения из всех трёх источников объединяются.

**Пример — блокировка встроенных команд для развёртывания в песочнице:**

```json
{
  "slashCommands": {
    "disabled": ["auth", "mcp", "extensions", "ide", "quit"]
  }
}
```

С этими значениями в системном `settings.json` (`/etc/nessy-cli/settings.json` или `NESSY_CLI_SYSTEM_SETTINGS_PATH`), пользователи не могут уменьшить список запрета из своей области, и отключённые команды не будут появляться в автодополнении или выполняться при вводе.

:::note
Эта настройка управляет только slash-командами (например, `/auth`, `/mcp`). Она не влияет на разрешения инструментов — см. `permissions.deny` для этого. Она также не перехватывает комбинации клавиш, такие как `Ctrl+C` или `Esc`.
:::

#### mcpServers

Настраивает подключения к одному или нескольким MCP (Model-Context Protocol) серверам для обнаружения и использования пользовательских инструментов. Nessy CLI пытается подключиться к каждому настроенному MCP серверу для обнаружения доступных инструментов. Если несколько MCP серверов предоставляют инструмент с одинаковым именем, имена инструментов будут иметь префикс с псевдонимом сервера, который вы определили в конфигурации (например, `serverAlias__actualToolName`), чтобы избежать конфликтов. Обратите внимание, что система может удалить определённые свойства схемы из определений инструментов MCP для совместимости. Как минимум одно из `command`, `url` или `httpUrl` должно быть предоставлено. Если указано несколько, порядок приоритета: `httpUrl`, затем `url`, затем `command`.

| Свойство                                | Тип              | Описание                                                                                                                                                                                                                                                                                          | Опционально |
| --------------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| `mcpServers.<SERVER_NAME>.command`      | string           | Команда для выполнения для запуска MCP сервера через стандартный ввод/вывод.                                                                                                                                                                                                                      | Да          |
| `mcpServers.<SERVER_NAME>.args`         | array of strings | Аргументы для передачи команде.                                                                                                                                                                                                                                                                   | Да          |
| `mcpServers.<SERVER_NAME>.env`          | object           | Переменные окружения для установки для процесса сервера.                                                                                                                                                                                                                                          | Да          |
| `mcpServers.<SERVER_NAME>.cwd`          | string           | Рабочий каталог, в котором запустить сервер.                                                                                                                                                                                                                                                      | Да          |
| `mcpServers.<SERVER_NAME>.url`          | string           | URL MCP сервера, который использует Server-Sent Events (SSE) для коммуникации.                                                                                                                                                                                                                    | Да          |
| `mcpServers.<SERVER_NAME>.httpUrl`      | string           | URL MCP сервера, который использует потоковый HTTP для коммуникации.                                                                                                                                                                                                                              | Да          |
| `mcpServers.<SERVER_NAME>.headers`      | object           | Карта HTTP заголовков для отправки с запросами к `url` или `httpUrl`.                                                                                                                                                                                                                             | Да          |
| `mcpServers.<SERVER_NAME>.timeout`      | number           | Таймаут в миллисекундах для запросов к этому MCP серверу.                                                                                                                                                                                                                                         | Да          |
| `mcpServers.<SERVER_NAME>.trust`        | boolean          | Доверять этому серверу и обходить все подтверждения вызовов инструментов.                                                                                                                                                                                                                         | Да          |
| `mcpServers.<SERVER_NAME>.description`  | string           | Краткое описание сервера, которое может использоваться для отображения.                                                                                                                                                                                                                           | Да          |
| `mcpServers.<SERVER_NAME>.includeTools` | array of strings | Список имён инструментов для включения из этого MCP сервера. При указании только перечисленные здесь инструменты будут доступны из этого сервера (поведение белого списка). Если не указано, все инструменты из сервера включены по умолчанию.                                                    | Да          |
| `mcpServers.<SERVER_NAME>.excludeTools` | array of strings | Список имён инструментов для исключения из этого MCP сервера. Инструменты, перечисленные здесь, не будут доступны модели, даже если они предоставлены сервером. **Примечание:** `excludeTools` имеет приоритет над `includeTools` — если инструмент находится в обоих списках, он будет исключён. | Да          |

Укажите `${NESSY_DP}` в поле `command`, чтобы запускать бинарь DP, которым
управляет Nessy CLI. Если `NESSY_DP` не задана в окружении процесса, переменная
резолвится в платформо-зависимый абсолютный путь внутри
`<NESSY_HOME>/dp_latest/` (`dp.exe` на Windows и `dp` на macOS/Linux).
По умолчанию `NESSY_HOME` — `~/.nessy`.

```json
{
  "mcpServers": {
    "dpGitlab": {
      "command": "${NESSY_DP}",
      "args": ["ai", "mcp", "gitlab"]
    }
  }
}
```

`${NESSY_HOME}` также доступна в значениях MCP-конфигурации, включая `env`,
`args`, `cwd` и `command`. Она разворачивается в активный глобальный каталог
конфигурации Nessy; если переменная окружения процесса не задана, используется
`~/.nessy`.

```json
{
  "mcpServers": {
    "meetings": {
      "command": "${NESSY_DP}",
      "env": {
        "DP_WORKDIR": "${NESSY_HOME}/dp_latest"
      }
    }
  }
}
```

## История оболочки

Nessy CLI хранит историю выполненных команд оболочки. Чтобы избежать конфликтов между разными проектами, эта история хранится в проектном каталоге внутри домашнего каталога пользователя.

- **Расположение:** `~/.nessy/tmp/<project_hash>/shell_history`
  - `<project_hash>` — уникальный идентификатор, сгенерированный из корневого пути вашего проекта.
  - История хранится в файле с именем `shell_history`.

## Переменные окружения и файлы `.env`

Переменные окружения — распространённый способ настройки приложений, особенно для чувствительной информации (например, токенов) или для настроек, которые могут изменяться между окружениями.

Nessy CLI может автоматически загружать переменные окружения из файлов `.env`.
Для настроек, связанных с аутентификацией (например, `OPENAI_*`), и рекомендуемого подхода с `.nessy/.env`, см. **[Аутентификация](../configuration/auth.md)**.

:::tip
**Исключение переменных окружения:** Некоторые переменные окружения (например, `DEBUG` и `DEBUG_MODE`) автоматически исключаются из проектных файлов `.env` по умолчанию, чтобы предотвратить вмешательство в поведение CLI. Переменные из файлов `.nessy/.env` никогда не исключаются. Вы можете настроить это поведение, используя настройку `advanced.excludedEnvVars` в вашем файле `settings.json`.
:::

## Файлы контекста (иерархический инструктивный контекст)

Хотя файлы контекста не являются строго конфигурацией _поведения_ CLI, они (по умолчанию `NESSY.md`, но настраиваются через настройку `context.fileName`) критически важны для настройки _инструктивного контекста_ (также называемого "памятью"). Эта мощная функция позволяет вам давать специфичные для проекта инструкции, руководства по стилю кода или любую соответствующую справочную информацию AI, делая его ответы более адаптированными и точными для ваших нужд. CLI включает элементы UI, такие как индикатор в нижнем колонтитуле, показывающий количество загруженных файлов контекста, чтобы держать вас в курсе активного контекста.

- **Назначение:** Эти Markdown-файлы содержат инструкции, руководства или контекст, которые вы хотите, чтобы модель Nessy знала во время ваших взаимодействий. Система предназначена для управления этим инструктивным контекстом иерархически.

### Пример содержимого файла контекста (например, `NESSY.md`)

Вот концептуальный пример того, что может содержать файл контекста в корне TypeScript-проекта:

```
# Проект: Моя потрясающая TypeScript-библиотека

## Общие инструкции:
- При генерации нового TypeScript-кода следуйте существующему стилю кода.
- Убедитесь, что все новые функции и классы имеют JSDoc-комментарии.
- Предпочитайте парадигмы функционального программирования, где это уместно.
- Весь код должен быть совместим с TypeScript 5.0 и Node.js 22+.

## Стиль кода:
- Используйте 2 пробела для отступов.
- Имена интерфейсов должны иметь префикс `I` (например, `IUserService`).
- Приватные члены класса должны иметь префикс подчёркивания (`_`).
- Всегда используйте строгое равенство (`===` и `!==`).

## Конкретный компонент: `src/api/client.ts`
- Этот файл обрабатывает все исходящие API-запросы.
- При добавлении новых функций API-вызовов убедитесь, что они включают надёжную обработку ошибок и логирование.
- Используйте существующую утилиту `fetchWithRetry` для всех GET-запросов.

## Относительно зависимостей:
- Избегайте введения новых внешних зависимостей, если это не абсолютно необходимо.
- Если новая зависимость требуется, пожалуйста, укажите причину.
```

Этот пример демонстрирует, как вы можете предоставить общий контекст проекта, конкретные соглашения о кодировании и даже заметки о конкретных файлах или компонентах. Чем более релевантными и точными будут ваши файлы контекста, тем лучше AI сможет помочь вам. Файлы контекста, специфичные для проекта, настоятельно рекомендуются для установления соглашений и контекста.

- **Иерархическая загрузка и приоритет:** CLI реализует иерархическую систему памяти, загружая файлы контекста (например, `NESSY.md`) из нескольких расположений. Содержание из файлов, находящихся ниже в этом списке (более специфичные), обычно переопределяет или дополняет содержание из файлов выше (более общие). Точный порядок конкатенации и окончательный контекст могут быть проверены с помощью команды `/memory show`. Типичный порядок загрузки:
  1. **Глобальный файл контекста:**
  - Расположение: `~/.nessy/<configured-context-filename>` (например, `~/.nessy/NESSY.md` в вашем домашнем каталоге пользователя).
  - Область: Предоставляет инструкции по умолчанию для всех ваших проектов.
  2. **Файлы контекста корня проекта и предков:**
  - Расположение: CLI ищет настроенный файл контекста в текущем рабочем каталоге, а затем в каждом родительском каталоге вплоть до либо корня проекта (определяемого папкой `.git`), либо вашего домашнего каталога.
  - Область: Предоставляет контекст, релевантный для всего проекта или значительной его части.
- **Конкатенация и индикация UI:** Содержание всех найденных файлов контекста конкатенируется (с разделителями, указывающими их происхождение и путь) и предоставляется как часть системного запроса. Нижний колонтитул CLI отображает количество загруженных файлов контекста, давая вам быструю визуальную подсказку об активном инструктивном контексте.
- **Импорт содержимого:** Вы можете модуляризировать ваши файлы контекста, импортируя другие Markdown-файлы, используя синтаксис `@path/to/file.md`. Для получения дополнительной информации см. [документацию процессора импорта памяти](../configuration/memory.md).
- **Команды для управления памятью:**
  - Используйте `/memory refresh` для принудительного повторного сканирования и перезагрузки всех файлов контекста из всех настроенных расположений. Это обновляет инструктивный контекст AI.
  - Используйте `/memory show` для отображения объединённого инструктивного контекста, который в настоящее время загружен, позволяя вам проверить иерархию и содержание, используемое AI.
  - См. [документацию по командам](../features/commands.md) для полной информации о команде `/memory` и её подкомандах (`show` и `refresh`).

Понимая и используя эти уровни конфигурации и иерархическую природу файлов контекста, вы можете эффективно управлять памятью AI и адаптировать ответы Nessy CLI к вашим конкретным потребностям и проектам.

## Песочница

Nessy CLI может выполнять потенциально небезопасные операции (например, команды оболочки и модификации файлов) в среде песочницы для защиты вашей системы.

[Песочница](../features/sandbox.md) отключена по умолчанию, но вы можете включить её несколькими способами:

- Используя флаг `--sandbox` или `-s`.
- Установив переменную окружения `NESSY_SANDBOX`.
- Песочница включается при использовании `--approval-mode=auto` по умолчанию.

По умолчанию используется предварительно собранный Docker-образ `nessy-cli-sandbox`.

Для проектных потребностей песочницы вы можете создать пользовательский Dockerfile в `.nessy/sandbox.Dockerfile` в корневом каталоге вашего проекта. Этот Dockerfile может быть основан на базовом образе песочницы:

```dockerfile
FROM nessy-cli-sandbox
# Добавьте ваши пользовательские зависимости или конфигурации здесь
# Например:
# RUN apt-get update && apt-get install -y some-package
# COPY ./my-config /app/my-config
```

Когда `.nessy/sandbox.Dockerfile` существует, вы можете использовать переменную окружения `BUILD_SANDBOX` при запуске Nessy CLI для автоматической сборки пользовательского образа песочницы:

```bash
BUILD_SANDBOX=1 nessy -s
```
