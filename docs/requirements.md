# Требования

## Цель

Дать главной ноде (Claude Code в песочнице tclaude + человек) удобный и понятный способ **оркестрировать нативную
нейросеть nessy**: запускать множество независимых агентов, писать им, получать ответы, видеть всю переписку и
состояние в одном месте. Агенты могут писать друг другу и главной ноде (произвольный граф общения).

Почему это нужно: nessy имеет доступ к dp-инструментам (GitLab, Jira, Sage, Wiki), которых у Claude в песочнице нет,
и умеет долгую автономную работу в воркспейсе.

## Решения, принятые с заказчиком

| Вопрос | Решение |
|---|---|
| Топология общения | **Произвольный граф** (вариант «В»): `you ↔ агент`, `агент ↔ агент`. Ребро `parent` (кто создал) хранится отдельно |
| Права агентов (permission) | **Автоподтверждение** (`ORCH_AUTO_APPROVE=1` по умолчанию). Решение пишется в события агента (аудит). Ручной режим поддержан кодом и UI |
| Запуск оркестратора | **launchd** (`nessy-orch install`), вне песочницы, `KeepAlive`. Состояние — в `~/.nessy-orch/` |
| Язык | **TypeScript**, строгий; **запрет `any`** линтером (`typescript-eslint` strictTypeChecked) |
| UI | **React** (см. [ui-design.md](ui-design.md)); сначала готовое API |
| Главная нода | Максимально удобный CLI: один бинарь, предсказуемый вывод, `--json`, блокирующие и неблокирующие режимы |

## Функциональные требования

### Ядро

1. **Мультиспейсы.** Space = воркспейс-каталог + один процесс `nessy serve` (managed) либо внешний демон по `url` (external).
   Создаётся явно (`space add`) или лениво по пути при первом `spawn`. Порты выделяются из пула и переиспользуются.
2. **Агент = независимая сессия nessy.** Создаётся через `POST /session {cwd, sessionScope:"thread"}` — это даёт
   изолированные контексты внутри одного serve (проверено живьём). Лимит — `--max-sessions` serve (по умолчанию 20 на space).
3. **Единая шина сообщений.** Любое сообщение `you → агент`, `агент → агент`, `агент → you`, а также системные события
   попадает в общую ленту с отправителем, адресатом, временем и типом. Лента переживает рестарт.
4. **Очередь на агента.** Пока агент работает, новые сообщения ждут; порядок и авторство сохраняются; очередь
   переживает рестарт оркестратора.
5. **Ответы.** Ответ агента на сообщение уходит отправителю автоматически (`reply`). Ответ на `reply` не порождается
   (нет пинг-понга). Дальше агенты общаются явными `send`.
6. **Синхронный режим (`--wait`).** Отправитель может заблокироваться до ответа; ответ возвращается в вывод команды и
   не дублируется ему промптом.
7. **Инициатива агентов.** Агент сам пишет другим через shell: `nessy-orch send --from <id> [--wait] <кому> "текст"`.
   Вводная (preamble) в начале контекста агента объясняет, кто он, кто рядом и как писать (`Orchestrator.preambleFor`).
8. **Автоподтверждение прав.** Агент голосует «разрешить» на `permission_request`. При `ORCH_AUTO_APPROVE=0` запросы
   копятся в `pendingPermissions` и решаются через API/UI.
9. **Устойчивость.** Падение `nessy serve` → текущий ход завершается ошибкой, следующее обращение поднимает serve и пытается
   восстановить сессию (`/session/:id/load`), иначе создаёт новую с пометкой «контекст сброшен». Падение отдельной сессии
   (`session_died`) → агент `error`, отправитель получает ответ с `failed`; следующее сообщение создаёт новую сессию.
   Статусы: `starting | working | idle | error`; успешно закончивший работу агент уходит в архив (`archived`) и просыпается
   от любого сообщения. Сообщение от you прерывает текущий ход (`interrupt`), агент→агент — встаёт в очередь.
   Роли (`roles.json`) — сохранённые инструкции, добавляемые во вводную агента при `spawn --role`.
10. **Защиты:** лимит длины цепочки `hops` (8), лимит сообщений на пару в минуту (30), детектор взаимного ожидания
    (`409 deadlock`), проверка `Host`/`Origin` (защита от DNS-rebinding/CSRF из браузера — API управляет агентами с автоправами).

### API

HTTP + SSE на `127.0.0.1:4337`, JSON, без аутентификации (loopback, см. защиты). Полное описание — [api.md](api.md).
Один поток `/stream` отдаёт снапшот и все изменения графа/ленты; отдельный поток на агента отдаёт его чат.

### CLI

Единый бинарь `nessy-orch` (+ тонкие алиасы `nessy-ask`, `nessy-jobs`, `nessy-watch` для обратной совместимости).
Полезный результат — в stdout, служебное — в stderr, `--json` везде. Описание — в [README](../README.md).

### UI

Граф (you в центре, агенты — точки), справа общий чат как групповой в Telegram, клик по агенту — чат с ним.
Видны **все отправляемые сообщения каждому агенту**. Описание — [ui-design.md](ui-design.md).

## Нефункциональные требования

- **Без рантайм-зависимостей** на сервере (Node ≥ 20, только стандартная библиотека). Dev-зависимости: TypeScript, ESLint.
- **Типобезопасность:** внешний JSON (nessy, HTTP-тела) читается только через хелперы `src/lib/json.ts`
  (`unknown` → проверенные типы). `any` и `@ts-ignore` запрещены линтером.
- **Единственное место, знающее протокол nessy** — `src/infrastructure/nessy/` (`nessy-client.ts`, `event-mapper.ts`). Изменение контракта nessy правится там
  и в `docs/contract/`.
- **Наблюдаемость:** логи serve — `~/.nessy-orch/logs/space-<имя>.log`; лог оркестратора — `orch.{out,err}.log`.
- **Восстановление:** состояние атомарно пишется в `state.json` (tmp + rename), JSONL допускает битую последнюю строку.
- **Безопасность:** слушаем только loopback; `Host` должен быть `127.0.0.1:<порт>`/`localhost:<порт>`; `Origin`, если есть,
  — только свой. Токены nessy оркестратор не читает и не хранит.

## Не-цели (сейчас)

- Аутентификация/многопользовательский режим, доступ не с loopback.
- Подтверждение прав «по запросу» как основной режим (код есть, но по умолчанию автоподтверждение).
- Встраивание nessy in-process (используем `nessy serve` по HTTP).
- Древовидное делегирование внутри nessy (субагенты самого nessy) — не перехватываем; у нас своя модель агентов.
- Редактирование/удаление сообщений ленты; поиск по истории (позже).
