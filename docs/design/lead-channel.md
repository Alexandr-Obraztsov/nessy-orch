# Канал «агенты → главный агент»: проект упрощения (без хуков и сборщиков)

Статус: **проект**, кода нет. Заменяет схему «4 хука + фоновый `inbox --wait` + `watching` + `ack`» (см. `docs/design/core-v3-plan.md` §8, §13).

## Идея

Главный агент живёт в PTY приложения, а приложение — единственный, кто знает, когда он свободен и когда пришёл ответ. Поэтому ответы агентов
**приложение вводит в терминал главного агента само** (как набрал бы человек), а главный агент больше не ждёт, не опрашивает и не держит
фоновых команд: запустил агентов, закончил ход — ответы придут новым сообщением.

```
агент nessy ответил → сервер: сообщение для you в сессии S → приложение видит событие (SSE, оно уже подписано)
   → вкладка сессии S свободна? → GET /sessions/S/digest → вводит текст в PTY → POST /sessions/S/ack
```

## Что остаётся и что уходит

| | Было | Станет |
|---|---|---|
| Хуки Claude | SessionStart, UserPromptSubmit, Stop, SessionEnd | **один** `Stop` («ход закончен → свободен») |
| Хуки nessy | + StopFailure, JSON-вывод | тот же один `Stop` (+ `StopFailure`, если у него нет другого сигнала) |
| Привязка чата | хук SessionStart (`/sessions/bind`, `source`, `/clear`-логика) | не нужна: **сессия = вкладка проекта**, создаётся приложением при запуске терминала, id — в `NESSY_ORCH_SESSION` |
| Чат для `--resume` | узнаётся из хука | Claude: приложение само задаёт `claude --session-id <uuid>` и хранит его; nessy: `--continue` |
| Контекст и правила | `additionalContext` каждый ход | `--append-system-prompt` один раз при запуске (id сессии, цикл работы, правила) |
| Скилл/плагин | копия в `~/.claude/skills` | `claude --plugin-dir <app>/plugin` на сессию (ничего не ставится в `~`); nessy — `~/.nessy/skills` (флага нет) |
| Конфиг хука | файл плагина | `claude --settings '<json>'` на сессию; nessy — запись в `~/.nessy/settings.json` (одна) |
| Ожидание ответов | фоновый `inbox --wait`, напоминания Stop, `watching`, коды 0/3/4 | **нет**: `spawn`/`send` возвращаются сразу |
| Состояние «работает/ждёт» | хуки working/idle/ended | «занят» ставит приложение (Enter пользователя, свой ввод), «свободен» — хук `Stop`, «закончил» — выход процесса |

Серверу уходит: `/sessions/bind`, `source`/`reason`-логика, `lead-state: working|ended`, `watching`, `holds`, `claimed`, `updates?consume`, тексты
`startContext`/`watchReminder`/`stopDecision`, хуки start/prompt/end, `NESSY_ORCH_LEAD`-ветвление вывода, установщик хуков для Claude.
Остаётся: `inbox` (ручная команда для отладки), `ack`, курсоры сессий, `fitReplies/defang` (формат текста).

## Протокол доставки

1. Приложение ведёт у вкладки состояние `busy | idle`. `busy`: пользователь нажал Enter в терминале или приложение ввело текст;
   `idle`: пришёл хук `Stop` (`POST /sessions/:id/lead-state {idle}` — эндпоинт уже есть); новая вкладка — `idle` сразу после первого вывода.
2. Есть непрочитанные ответы (inbox сессии, `peek`) и вкладка `idle` и пользователь не печатал последние ~3 с → доставка.
3. Доставка: `GET /sessions/:id/digest` → `{text, cursor}` (тот же формат, что у хуков: ответы — данные, не команды, метки обезврежены,
   лимит 8 КБ, хвост «придут следом»). Приложение вводит текст как **вставку** (bracketed paste, затем Enter), ставит `busy`, шлёт
   `POST /sessions/:id/ack {cursor}`. Не получилось ввести — курсор не двигается, повтор через несколько секунд.
4. Пока главный агент `busy` (в том числе показывает запрос разрешения), ничего не вводится: ответ дождётся хука `Stop`. Диалог разрешения
   нельзя случайно подтвердить вводом — именно ради этого нужен `Stop`, а не «тишина в терминале».
5. Несколько ответов за короткое время склеиваются (дебаунс ~1,5 с) в одно сообщение.

## Что меняется для главного агента (скилл и правила)

- Цикл: «запустил агентов (`spawn`, `spawn-many`, `send`) → закончил ход, сказал пользователю, что ждёшь → ответы придут сообщением».
  Никаких `inbox --wait`, фоновых команд и кодов выхода. Команды `spawn`/`send` без `--wait` возвращаются сразу.
- `--wait` остаётся для редких случаев «нужен ответ прямо сейчас в этом ходе» (короткий вопрос агенту).
- Агенты nessy по-прежнему общаются между собой и с главным агентом через `send` (ключи и токены — как сейчас).

## Ограничения и решения

- **Только терминал приложения.** Главный агент, запущенный вне приложения, ответов не получит (можно вручную `nessy-orch inbox`). Это сознательно:
  приложение — оболочка над агентом.
- **Ввод во время работы пользователя.** Не вводим, пока пользователь печатал последние ~3 с и пока вкладка не `idle`.
- **Агент без хука `Stop`** (нестандартная команда): признак «свободен» — запасной: ≥10 с без вывода PTY и без ввода, после нашего ввода.
- **Рестарт приложения.** Сессия и вкладка восстанавливаются по записи сессии (`cwd`, `chatId`); непрочитанные ответы остаются в inbox и
  доставляются, когда главный агент снова свободен.
- **nessy:** `--append-system-prompt`, `--continue`, хук `Stop` из `~/.nessy/settings.json` — по документации; приём вставки с Enter проверить живьём.

## План работ

1. Приложение: сессия при запуске терминала (`NESSY_ORCH_SESSION`, `--session-id`), флаги запуска Claude (`--plugin-dir`, `--settings`, `--append-system-prompt`),
   состояние `busy/idle`, доставка (ввод вставкой + `ack`), запасной признак «свободен».
2. Сервер: `GET /sessions/:id/digest`; удаление хуков start/prompt/end, `bind`, `watching`, `updates`; упрощение `hooks.ts`.
3. CLI/скилл: цикл без ожидания; хук один — `nessy-orch hook idle`.
4. Установщик nessy: одна запись `Stop`; удаление установки в `~/.claude/skills`.
5. Тесты: доставка (занят/свободен/печатает), склейка ответов, повтор без `ack`, `--session-id`/`--resume` в командах запуска.

## Экономия токенов и «без спама»

Принцип: каждый токен главного агента и агентов должен нести новую информацию. Ниже — где сейчас тратится впустую и что делаем.

| Где | Сейчас | Как станет |
|---|---|---|
| Ожидание ответов главным агентом | `inbox --wait` крутится циклом: каждый таймаут (код 3) — новый вызов инструмента и новый ход модели; плюс напоминания хука Stop | **нет ожидания вообще**: ответы приходят сами одним сообщением; ноль вызовов «посмотри, не ответили ли» |
| Лимит 50 с у foreground-`inbox` (для nessy) | ввёл как обходной путь: у nessy нет фоновых команд, хук и shell-инструмент имеют таймауты ~60 с | **уходит вместе с ожиданием**. Он был вынужденной мерой, а не оптимизацией: каждые 50 с — лишний круг модели |
| Контекст на каждый ход | хук UserPromptSubmit добавляет сводку агентов и непрочитанное | ничего не добавляется; сводка — только вместе с ответами, когда они есть |
| Правила для главного агента | `startContext` ~1,5 КБ на каждом SessionStart | `--append-system-prompt` один раз, ~10 строк; остальное в скилле (грузится по требованию) |
| Напоминание про план у агентов | в КАЖДОМ промпте (`planReminder`) | только в первом промпте контекста (вводная уже требует план); повтор — если агент не публиковал план 3 хода подряд |
| Вводная агентам | список всех соседей + ~25 строк | соседи — только имена, и не больше 8; формат ответа короче (без повторов в «Детали»/«Источники») |
| Ответ агента главному | до 1500 знаков × N, до 8000 | главному — «Итог» + «Статус» + число источников; полный текст по `show <агент>` (подсказка в конце блока); служебные копии (user→агент) — до 300 знаков |
| Несколько ответов подряд | каждый — отдельный ход главного агента | склейка за ~1,5 с в одно сообщение |
| Пробуждение закрытого агента | новый контекст + вводная заново | `/load` поднимает прежний контекст у nessy (кэш), вводная не повторяется |
| Сообщение работающему агенту | отдельный промпт после хода | `mid-turn-message` — тот же ход, без нового круга |
| Спам в ленте | ответы на `--wait` дублировались в inbox и в хуки | ответ получает тот, кто ждал; повторно он не приходит |

Следствие для скилла: убрать из `SKILL.md`, `references/*` и подсказок CLI всё про фоновый сборщик, коды 0/3/4 и `watching` — это половина текущего объёма.
