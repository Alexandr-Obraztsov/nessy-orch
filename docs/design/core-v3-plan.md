# Ядро v3: план для ревью

Документ — бриф для независимого ревью до реализации. Статус: **план, кода нет**. Всё, что помечено «не проверено», проверяется спайком до реализации.

## 1. Что есть сейчас (сделано)

- **Сервер** (`src/`, TypeScript без рантайм-зависимостей, слои domain → application → infrastructure → interfaces): HTTP/SSE на `127.0.0.1:4337`, `Orchestrator` (`application/orchestrator.ts`), сервисы `AgentsService`, `MessagingService`, `SessionsService`, `SpacesService`, `Feed` (лента, inbox с long-poll, курсоры), `Hub` (события), `SessionPool` (сессии nessy), шлюз `NessyGateway` (`infrastructure/nessy/nessy-client.ts`, процессы `nessy serve` по пространствам: `infrastructure/process/serve-space.ts`).
- **Приложение** `app/` (SwiftUI, macOS 26): одно окно, вкладки-проекты, терминал с Claude справа панель агентов. Терминал сейчас — login-оболочка пользователя, в ней пользователь сам запускает/уже запущен `claude` (автозапуск настраиваемой командой).
- **Плагин `plugins/nessy`**: скилл, CLI-шим `bin/nessy-orch`, хуки `hooks/hooks.json` (`SessionStart`, `UserPromptSubmit`, `Stop`, `SessionEnd`) → `nessy-orch hook <событие>` (`interfaces/cli/commands/hook.commands.ts`, тексты — `domain/hooks.ts`). Хуки действуют только при `NESSY_ORCH_TERMINAL`/`NESSY_ORCH_SESSION`. Вывод хуков — простой текст (контекст) и exit 2 + stderr (Stop), без JSON-схемы.
- **Привязка чата**: `session_id` Claude из хука → сессия оркестратора (`SessionsService.bind`, `cwd` сохраняется), агенты создаются в каталоге чата.
- **inbox**: ждёт, только пока в сессии кто-то работает (`activeAgents`); коды выхода 0 ответы / 3 таймаут / 4 ждать нечего; будится на смену состояния агента; курсор без дублей.
- **send**: `started` / `interrupted` / `queued`. **spawn-many** без heredoc. Агенты удаляются из UI.

## 2. Проблемы, которые решаем

1. **Лимит 20 сессий.** `--max-sessions` у `nessy serve` — 20 на пространство (docs/requirements.md:30). Оркестратор сессии nessy не закрывает; агент, порождающий агентов, упирается в 20 и получает ошибку.
2. **Терминал = оболочка**: пользователь может выйти в обычный терминал. Нужна «обёртка»: агент запускается сразу, выход из агента закрывает проект, нет проектов — стартовый экран.
3. **Всё завязано на Claude** (хуки, формат ответа, переменные). Нужно запускать и другие CLI-агенты (Codex, Gemini CLI, opencode…) и сам nessy.
4. **Субагенты изолированы**: нет навыка оркестратора, нельзя писать друг другу и оркестратору; сообщение пользователя субагенту прерывает его, а оркестратор об этом не знает.
5. Корнер-кейсы остановки главного агента и субагентов (список в п. 7).

## 3. Режим «обёртка»

- Терминал запускает `$SHELL -l -c 'exec <агент>'` вместо интерактивной оболочки; обычного терминала нет.
- Выход из агента закрывает проект; закрыты все — стартовый экран (проект + выбор агента, по умолчанию последний).
- Быстрое падение (< 3 с, ненулевой код) — экран «Агент не запустился» (перезапуск / вывод), а не молчаливое закрытие.
- Переменные окружения терминала: `NESSY_ORCH_TERMINAL` (ключ), `NESSY_ORCH_AGENT_KIND` (`claude|codex|gemini|opencode|nessy`), `NESSY_ORCH_DIR`, `ORCH_PORT` (если не 4337); у субагентов nessy ещё `NESSY_ORCH_AGENT` (id) и `NESSY_ORCH_DEPTH`. `NESSY_ORCH_SESSION` выставляет хук `start` (для Claude — через `CLAUDE_ENV_FILE`).

## 4. Адаптеры агентов

Контракт `AgentAdapter`: `launch` (команда, аргументы, env), `detect` (установлен ли, версия), `install/uninstall` (хуки и инструкции в конфиг этого агента), `events` (нативное событие → нормальное), `reply` (как вернуть контекст/блокировку).

Нормальные события: `start`, `prompt`, `idle` (ход закончен), `permission`, `end`, `tool`. Сервер видит только их. Хук: `nessy-orch hook <событие> --agent <id>` — разбирает stdin агента, шлёт нормальное событие, печатает ответ в формате агента.

Данные об агентах (из документации, **не проверено живьём**; Codex/opencode дочитаны не полностью):

| Агент | Конец хода | Разрешение | Блок остановки | Прочее |
|---|---|---|---|---|
| Claude Code | `Stop` | `PermissionRequest`, `Notification` | exit 2 + stderr | `SubagentStart/Stop`, env `CLAUDE_PROJECT_DIR`, `CLAUDE_PLUGIN_ROOT` |
| Gemini CLI | `AfterAgent` | `Notification` | exit 2 | stdout — один JSON, `GEMINI_SESSION_ID`, `.gemini/settings.json` |
| Codex | `Stop` / `notify` | `PermissionRequest` | не подтверждено | хуки включаются `features.hooks`; `AGENTS.md` |
| opencode | `session.idle` | `permission.asked` | `throw` в `tool.execute.before` | плагин, не хук-команда |
| Cursor / aider | мало или нет | — | — | запасной путь: опрос состояния |

nessy как главный агент: свой адаптер на протоколе `nessy serve` (статус из протокола, не из хуков).

## 5. Жизненный цикл сессий nessy: hot / cold

Агент — запись оркестратора (имя, роль, цель, план, история, `nessyId`), живая сессия nessy — арендуемый ресурс.

| Состояние | Сессия nessy | Примечание |
|---|---|---|
| `working` | открыта | не закрывается никогда |
| `hot` | открыта, агент свободен | можно слать мгновенно |
| `pending` | нет места | ждёт освобождения, сообщения копятся в очереди |
| `cold` | закрыта (`DELETE /session/:id` или `close`) | запись, история, последний ответ, `nessyId` сохранены |

- **Закрытие**: агент свободен, ответ доставлен и подтверждён, очередь пуста, нет ожидающих разрешения, никто не ждёт его (`domain/wait-graph.ts`) → таймер `idleClose` (по умолчанию 2 мин) → запись `cold` в хранилище, затем закрытие сессии.
- **Лимит hot**: 5 на оркестратор (`hotLimit`). Пробуждение шестого вытесняет самого давнего свободного (`lastUsedAt`). Все пять `working` → `pending` (очередь), не ошибка. Аварийная граница nessy (20) не должна достигаться.
- **Пробуждение**: `send`/сообщение от другого агента холодному — `POST /session/:id/resume`, доставка, `working`. В `SendResponse` — `resumed`/`restored: full|partial`.
- **Фолбэк**: resume не вернул контекст → новая сессия с «досье» (цель, план, последний ответ из истории), `restored: partial`, предупреждение оркестратору.
- **Одноразовые**: `spawn --once` — закрыть сразу после доставки ответа.
- **Каскад**: `session done` и закрытие терминала освобождают все hot-сессии этого оркестратора (записи остаются, `/resume` чата возвращает агентов). Сироты (сессия есть у nessy, записи/владельца нет) — GC при старте. Удаление агента делает `DELETE` сессии. Повторные close/delete (404) — успех.
- **Защита от гонок**: закрытие под блокировкой на агента; `send` во время закрытия ждёт и делает resume. Порядок «сначала `cold` в хранилище, потом close».
- **inbox/active**: `pending` считается активным (иначе inbox вернёт код 4 раньше времени).
- **Не проверено**: поддержка `resume` и `loadedFromHistory` в `nessy serve` (строки `/resume`, `/sessions/delete` в docs/contract/README.md:59-60 помечены «из кода»). Спайк №1: закрыть сессию, поднять `resume`, проверить восстановленный контекст, поведение при потере истории, стоимость.

## 6. Лимиты и защита от рекурсии

- Бюджет на сессию оркестратора: одновременных агентов (hot+pending+working) ≤ 8, глубина вложенности ≤ 2 (`NESSY_ORCH_DEPTH`), всего спавнов ≤ 40; превышение — понятная ошибка с подсказкой (какие агенты можно закрыть). Для сравнения: Claude Code — до 20 одновременных, глубина до 3.
- Лимит токенов на сессию с остановкой при превышении (настройка).
- Субагент может вызывать `spawn`, пока глубина < лимита; родитель записывается (`parent`), удаление родителя каскадно освобождает детей (политика: остановить / оставить — решить).

## 7. Общение агентов и доставка без остановок

- У каждого агента nessy: `NESSY_ORCH_AGENT`, урезанный навык оркестратора (`send`, `inbox`, `ls`, `spawn` с глубиной). Адресация: `send <агент|you>`; лента хранит `from/to`.
- Защита от петель: счётчик переходов (hop) в сообщении, лимит частоты на отправителя (`domain/rate-limiter.ts`), граф ожиданий (отказ при цикле). Сообщение от агента — не разрешение пользователя.
- Пользователь пишет субагенту из UI: агента не прерываем, сообщение в очередь (`queued`), доставка между шагами; оркестратору автоматически уходит служебная запись «пользователь написал агенту X: …».
- Сообщения оркестратору (Claude) доставляются хуками без остановки (`PostToolUse`/`UserPromptSubmit` добавляют контекст); когда он idle — будится готовым механизмом inbox/Stop-хука. Режим «разбудить idle-сессию» не проверен.

## 8. Корнер-кейсы остановки (чек-лист)

1. Compaction забыл правило ожидания → переустановка контекста после сжатия.
2. Агент ждёт разрешения часами → флаг «ждёт вас» + уведомление; по таймауту `stalled`.
3. Агент завис (нет событий N минут) → `stalled`, кнопка «Остановить», предупреждение оркестратору.
4. Рестарт оркестратора → reconcile: `working` сверяются с nessy, мёртвые → `lost`, сообщить.
5. `nessy serve` недоступен → ошибка в ленте, inbox код 5, а не вечное ожидание.
6. Закрыт терминал с работающими агентами → подтверждение; результаты сохраняются.
7. Дубли чата (`/resume`, `/clear`) → привязка по `session_id`, тесты.
8. Недоставленный ответ → «прочитано» только после успешного вывода хука.
9. Взаимные ожидания агентов → `wait-graph`, отказ при цикле.
10. Фоновое ожидание Claude (`inbox --wait` в background) умерло/не запущено → напоминание хука Stop (уже есть) + проверка `watching`.
11. Вытеснение агента, которого ждёт другой агент → запрещено (п. 5).
12. Падение оркестратора между `cold` и `close` → сирота, GC.

## 9. Интеграции в UI и API

- Мастер первого запуска и «Настройки → Агенты»: для каждого CLI — найден ли и версия, установлены ли навык/хуки, «Установить / Переустановить / Удалить», перед записью — список файлов и изменений, команда запуска, откат. Ничего в чужие конфиги без явного согласия.
- API (план): `GET /integrations`, `POST /integrations/:agent/install|uninstall`, `GET/PUT /settings/agents` (команда запуска, `hotLimit`, `idleCloseSeconds`, бюджеты). Поля агента: `state: working|hot|pending|cold|stalled|lost`, `depth`, `parent`; `SendResponse`: `resumed`, `restored`.
- UI агента: при клике — только чат и план, шапка с названием и кнопками (описание/цель/статистика убраны). Холодный агент приглушён: «в архиве, проснётся при сообщении»; в панели счётчик `hot 5/5`.

## 10. Порядок реализации

1. Спайк `resume`/`DELETE`/история в `nessy serve`.
2. Hot/cold + вытеснение + `pending` + inbox/active.
3. Бюджеты, глубина, `parent`, каскад, GC сирот, reconcile.
4. Адаптеры и нормальные события; режим «обёртка».
5. Общение агентов, доставка без прерываний.

## 11. Вопросы, на которые ждём ответа ревью

Полнота и корректность модели hot/cold (гонки, потеря данных, стоимость resume); не пропущены ли ломающие кейсы; корректность контракта адаптера; безопасность (агент пишет агенту, установка хуков в чужие конфиги, права); порядок реализации и риски; что упрощать, а что обязательно сделать раньше.

## 12. Итоги ревью (Opus) и пересмотренный порядок

Ревью нашло расхождения с кодом; план выше читать с этими поправками.

- **Шаг 0 (сделан):** двухфазная доставка ответов хуками (`peek` → вывод → `POST /sessions/:id/ack`), экранирование служебных меток в ответах агентов (`defang`).
- **Не сделано, нужно решение:** токены `you`/агентов (любой локальный процесс может выдать себя за оператора; при `ORCH_AUTO_APPROVE=true` это `send/spawn/rm` от его имени). Слабость: все процессы работают под одним пользователем, токен в файле или окружении доступен агенту, если он не изолирован песочницей. Реальная граница возможна, только если `nessy serve` не передаёт агентам окружение терминала — это проверяется спайком.
- **Уточнения модели:** автомат агента `hot|closing|cold|waking`; пробуждение через `/load`, а не `/resume`; учёт сессий по пространству вместе с прогретыми сессиями пула; `pending`, LRU и GC сирот отложены; условие закрытия — не занят, очередь пуста, нет разрешений, простой ≥ T; токены считаются по `nessyId`; отдельный отправитель `user`; закрытие терминала сообщает приложение; `/clear` и fork переносят агентов в новую сессию; обёртка — `-l -i -c` и подключение плагина флагами запуска.
- **Спайки (нужен `nessy serve`):** `DELETE` → `/load`, `replay_complete`, срок `contextId`, цена сессии, код ошибки лимита; для Claude Code — `asyncRewake`, `--plugin-dir`, доступ к `127.0.0.1` из песочницы.
- **Порядок:** шаг 0 → спайки → автомат hot/cold → `parent`/бюджеты → отправитель `user` → обёртка (Claude) → мягкий `hotLimit` → второй CLI → UI интеграций.
