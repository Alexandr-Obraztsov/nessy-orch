# Рецепт: изменение кода (план → исполнение → проверка)

Сначала загрузи скилл `nessy-orch` и иди по его циклу: шаг 0 (`task new "<цель>" --owner claude` → id, ссылка на панель задачи `http://127.0.0.1:4337/?task=<id>`),
`ls --all --task <id>`, `role ls`. Все `spawn` — с `--task <id>`, сборщик — `inbox --task <id>`, в конце — `task done <id> --summary "…"`. Здесь — то, что специфично для изменения кода. Даже если репозиторий открыт у тебя,
код правит агент.

## Когда

- Нужно изменить код: фича, исправление, рефакторинг, тесты.
- Мелкая правка («одна строка») — тот же путь, но можно без `analyst`: сразу `executor`, затем `verifier`.

## Роли

| Шаг | Роль | Когда |
|---|---|---|
| 0. Причина | `debugger` | баг с неясной причиной |
| 0. Разведка | `code-explorer` | код в чужом репозитории, нужно понять, где менять |
| 1. План | `analyst` (или `architect` для крупного дизайна) | всегда, кроме мелочей |
| 2. Реализация | `executor` | всегда |
| 3. Проверка | `verifier` (или `code-reviewer`) | всегда, **отдельным** агентом |
| Тесты | `test-engineer` | тесты — отдельная задача или их нет вовсе |

Шаги последовательные: следующий получает результат предыдущего в своём поручении. После каждого `spawn` или
`send` запускай фоновый `nessy-orch inbox --task <id> --wait 1500` (`run_in_background`) и заканчивай ход — следующий шаг
делай, когда сборщик принесёт ответ.

## Поручения

```bash
# 1) план
nessy-orch spawn --task <id> --space <путь к репозиторию> --role analyst --name <тема>-plan "
Цель: план <изменения> (задача <КЛЮЧ-123>: <суть>).
Контекст: репозиторий <путь>, ветка <ветка>, модуль <путь/>. Известно: <что уже выяснили>.
Границы: ничего не менять, только план.
Результат: шаги с файлами, риски, как проверить (какие тесты и команды).
В конце: строка «Статус: …»."

# 2) исполнение — план передаёшь целиком
nessy-orch spawn --task <id> --space <путь к репозиторию> --role executor --name <тема>-impl "
Цель: реализовать план ниже в <путь>, ветка <ветка>.
План: <вставь план из <тема>-plan>
Границы: не коммитить и не пушить; не трогать файлы вне <область>.
Готово, когда: тесты из плана проходят, вывод команд приложен, дифф описан по файлам.
В конце: строка «Статус: …»."

# 3) независимая проверка — другим агентом
nessy-orch spawn --task <id> --space <путь к репозиторию> --role verifier --name <тема>-verify "
Цель: независимо проверить изменения в рабочем дереве <путь> по задаче <КЛЮЧ-123>.
Требования: <критерии из плана>.
Заявлено исполнителем: <краткий отчёт <тема>-impl>. Не доверяй отчёту — проверь по коду и запуском тестов.
Границы: ничего не менять.
Результат: что подтверждено (с доказательством), что нет, проблемы по важности.
В конце: строка «Статус: …»."
```

Нашёл `verifier` проблемы — отправь их исполнителю (`send <тема>-impl "Исправь: …"`), затем
перепроверь тем же `verifier` (`send <тема>-verify "Перепроверь после правок: …"`). Цикл — пока
`verifier` не вернёт `DONE` или пока не станет ясно, что нужен другой подход (тогда к пользователю).

## Сводка пользователю

1. Что сделано, одной-двумя фразами.
2. Изменённые файлы и суть правок.
3. Доказательства: какие тесты и команды прошли (от `verifier`, а не со слов исполнителя).
4. Риски и что осталось (замечания `DONE_WITH_CONCERNS`, непокрытое тестами).
5. Следующий шаг: коммит, MR — предложи, но делай только по просьбе (поручением `executor` через `send`).

## Красные флаги

| Мысль | Как на самом деле |
|---|---|
| «Правка маленькая, сделаю сам» | Нет: `executor`, затем `verifier` |
| «Исполнитель сказал, что тесты зелёные» | Подтверждает только отдельный `verifier` |
| «Пусть исполнитель сразу закоммитит и откроет MR» | Только по прямой просьбе пользователя |
| «Разделю правку на трёх исполнителей» | Только если части не трогают общие файлы; иначе один `executor` |
| «Verifier нашёл проблему — запущу нового executor» | Пиши прежнему через `send`: у него контекст правки |
